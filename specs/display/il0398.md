# Chip Spec: IL0398

**Manufacturer:** Good Display (the datasheet text is UltraChip-lineage: "UltraChip reserved" pins, UC81xx command family). Also written **IL0389** — the datasheet is titled "IL0389" while its cascade figure says "IL0398"; the issue uses both, so the spec file is `il0398` and treats the two names as the same chip  
**Datasheet:** `datasheets/display/il0389.pdf` (Good Display "E paper IC Specifications" IL0389, issue date 2016-04-07, 51 pages, preliminary: package, bump data and some loading values are TBD). No panel or module datasheet is committed: the module mapping below comes from the issue's Waveshare survey and is **unverified**  
**Category:** `display`  
**Transports:** SPI (4-wire; write-only or half-duplex, via `DisplayConnection`)

## Overview

The IL0398 is an all-in-one driver with timing controller for **black/white** (and, with a red-capable panel, black/white/red) electrophoretic (EPD) panels of up to **400 source × 300 gate** outputs: two bit-planes of display RAM (400 × 300 bits each), an on-chip oscillator/PLL (1.625 MHz RC), DC-DC booster and regulators for the gate, source and VCOM voltages (VGH/VGL ±13…±16 V, VDH/VDL ±2.4…±11 V), an on-chip temperature sensor (−25…+50 °C, 8 bit) with an I²C master for an external LM75, a 4 KB OTP holding up to 15 temperature-dependent waveform sets (LUTs) and a low-power detector. The issue names the Waveshare **4.2inch e-Paper V1** as the module (**unverified**, believed to be a 400 × 300 black/white panel).

**The same silicon is the UltraChip UC8176** (`specs/display/uc8176.md`, datasheet UC8176c_A0.1): the IL0389 document is a rebranded copy of that datasheet with identical technical content, so the two drivers should share one implementation.

The chip is **command-compatible with the UC8276C** (`specs/display/uc8276c.md`) and the UC8179 (`specs/display/uc8179.md`) and in the details that matter it is the **panel-datasheet reading of the UC8276C** — same `PWR` layout (VDH/VDL 2.4 V + 0.2 V/step, VGH ±16…±13 V), same 3-byte `BTST`, the same `PLL` M/N table, 6-bit `VDCS`, the same 4-byte `TRES`/`GSST` — which is why the register layouts need no cross-document reconciliation. It differs from the UC8276C by what it lacks: **no `AUTO` (`0x17`)**, no `LVSEL` (`0xE4`), no second `PSR` byte, no `LUTOPT`, no panel-break-check (`0x44`), no CRC; and **the datasheet does not document the LUT commands `0x20`–`0x24`** (they appear only in the BUSY table). Against the IL0373 (`specs/display/il0373.md`) the register layouts are the same family, but `TRES` is 4 bytes here (3 on the IL0373), `PWR` caps at 11 V (15 V there) and the gate voltage is ±13…±16 V (±17…±20 V there).

The chip differs from an OLED/LCD in ways that shape the driver: a refresh is a long full-panel waveform (**no duration is stated** in the datasheet, see Timing Constraints), the picture is **bistable**, and the display must be explicitly **powered on (PON) → refreshed (DRF) → powered off (POF)** around every update, with BUSY_N waited on after each step. The driver keeps a framebuffer and sends it on `show()`.

The chip has **two pixel modes**: *KW* (black/white with NEW/OLD planes) and *KWR* (black/white/red, **power-on default**, `PSR.BWR = 0`). Because the only named module is a black/white panel, **this spec makes KW the primary mode** (as the IL0373 spec does) and exposes KWR (and the red colour) in Full only — see Implementation Notes.

This spec covers **4-wire SPI**, full-panel updates with the **waveform loaded from OTP**, a user-supplied LUT (escape hatch), a partial-window write and, with a half-duplex wire mode, the read commands. Partial *refresh* waveforms are not in the datasheet and are not specified.

## Transport Configuration

### SPI (4-wire)
- **Mode:** CPOL=0 CPHA=0 (Mode 0), MSB first; the datasheet's write figures show data stable around the rising SCL edge
- **Max clock:** write cycle ≥ 100 ns (SCL high/low ≥ 35 ns each) → **10 MHz**. The feature list's "clock rate up to 20 MHz" contradicts the AC table; the AC table is used. Driver default 4 MHz. **Read** cycle ≥ **150 ns** (high/low ≥ 60 ns) → ≤ 6.6 MHz; reads are short and the driver uses its write clock capped at 4 MHz
- **CS active:** low (CSB). Commands are processed on the stop condition (CSB rising edge: note 3 of the command table). The datasheet figures show one DC level held over each 8-bit group; it does not say that CSB must stay low across a command and its parameters, so the per-call CS framing of `DisplayConnection` is acceptable (**no `hold_cs` extension is needed**; compare the SSD168x specs)
- **Framing:** a byte stream; the **DC pin** is sampled per 8-bit group: low → command, high → parameter/data/read. Bytes are sent verbatim — no register address, no read/write bit
- **Bus selection:** pin **BS** low = 4-wire, high = 3-wire (9-bit frames; **power-on default per the pin table**, so the module's strap decides). The driver requires **4-wire**; the BS strap is board-specific. 3-wire framing is **not supported**
- **Bidirectional SDA:** the chip's SDA pin is an I/O. Read commands (listed under Command Set) clock data out on SDA after the command byte, with DC high and CSB low. Whether the board exposes DOUT depends on the wiring → `DisplayConnection` wire mode (`SIMPLEX` / `HALF_DUPLEX_HW` / `HALF_DUPLEX_PIN`, see `specs/transport_display.md`). `SIMPLEX` is sufficient for everything in Minimal
- **Register addressing:** none — takes a `DisplayConnection`, not a `RegisterConnection`

## Command Set

All commands are one byte sent with DC low; parameters follow with DC high. POR values in brackets. **Defaults can be changed by OTP** ("Command default setting", OTP addresses `0x020`–`0x033`: PSR, PFS, BTST, TSE, CDI, TCON, TRES, GSST, CCSET, PWS, TSSET), so a panel may not power up with exactly these values; the driver writes every setting it depends on. Only commands the driver uses or exposes are listed. There is a single document for this chip, so there are no cross-document layout conflicts.

### BUSY_N flag

All commands except `REV`, `FLG`, `VV` (and the read forms of `DSP`, `TSC`, `LPD`, `TSR`) are **ignored while a refresh (DRF/DSP) is running** (datasheet "BUSY_N Signal" table). Commands that drive BUSY_N low (flag column): `POF`, `PON`, `PMES`, `DSLP`, `DSP`, `DRF`, `TSC`, `LPD`, `AMV`, `APG`. Data/LUT/setting commands raise no BUSY_N. (Unlike the UC8276C there is no `AUTO` and no soft-reset BUSY note.)

### Power-on / reset defaults

PSR `0x0F` (400 × 300, **B/W/Red**, LUT from OTP, scan up, shift right, booster on), PFS 1 frame, BTST `0x17 0x17 0x17`, PLL `0x3C` (50 Hz), CDI `0xD7`, TCON `0x22`, TSE internal with offset 0, PWR `0x03 0x00 0x26 0x26 0x03`. The display RAM contents are **undefined** after power-up.

## Display RAM

Two planes, each **400 × 300 bits** (50 bytes × 300 rows); `DTM1` writes plane 1 and `DTM2` plane 2. A transfer is a plain stream written from the first pixel to the last: the chip has no address counter or window commands for a full frame. Each byte carries 8 horizontal pixels with **D7 = first (leftmost) pixel**; a frame is `width/8 × height` bytes per plane, rows in gate-scan order (`G0` first at PSR UD = 1, `S0` first at SHL = 1).

**B/W mode** (`PSR.BWR = 1`; `DTM1` = OLD, `DTM2` = NEW). With `CDI.DDX = 01` (the default) the `{NEW, OLD}` bit pair selects the waveform:

| NEW | OLD | LUT |
|-----|-----|-----|
| 0 | 0 | LUTBB (stays black) |
| 0 | 1 | LUTWB (white → black) |
| 1 | 0 | LUTBW (black → white) |
| 1 | 1 | LUTWW (stays white) |

so **a NEW bit of 1 is white**. A pixel with equal NEW and OLD bits is not driven, so the driver sends `OLD = NOT NEW` for every pixel: every pixel is driven to its final state, which makes a refresh independent of what the panel showed before (a full "flashing" update) and needs no second framebuffer. The panel does not report its previous image, so a differential update is not offered. (`DDX = 10`/`11` select NEW-only waveforms; not used.) Border (`VBD`, `DDX[0] = 1`): `00`/`11` floating, `01` LUTWB, `10` LUTBW.

**B/W/Red mode** (`PSR.BWR = 0`, power-on default; `DTM1` = B/W plane, `DTM2` = red plane). With `DDX = 01`:

| Red bit | B/W bit | Colour (LUT) |
|---------|---------|--------------|
| 0 | 0 | black (LUTB) |
| 0 | 1 | white (LUTW) |
| 1 | 0 | red (LUTR) |
| 1 | 1 | red (LUTR) |

Red wins. Border (`DDX[0] = 1`): `00` LUTB, `01` LUTW, `10` LUTR, `11` floating.

**The polarity depends on CDI.DDX, and the OTP may change the power-on value** (command default setting, OTP `0x027`). The driver therefore writes CDI explicitly instead of relying on the OTP default.

## Initialization Sequence

Derived from the datasheet's power-management notes and command descriptions and from the UC8276C/UC8179 flow and the IL0373 B/W flow (the UC8276C flow was measured on hardware; the datasheet contains no reference code). **Not verified on an IL0398 panel.**

1. Apply VDD/VDDIO; BS strapped low (4-wire). The power-on figure shows delays of "> 10 ms" and "> 80 ms" around VDD, without saying what they separate; the caller should let the supply settle for ≥ 100 ms before constructing the driver.
2. **Hardware reset:** `RST_N` low ≥ 10 ms, then high; wait ≥ 10 ms, then BUSY_N high (the datasheet gives no reset timing; the UC8276C figures are 50 µs low, > 1 ms recovery, so these are conservative).
3. `PSR` `0x1F` in B/W mode (LUT from OTP, `BWR = 1`, scan up, shift right, booster on) — `0x0F` in B/W/Red mode.
4. `TRES` with `(width, height)` (`0x01 0x90 0x01 0x2C` for 400 × 300; redundant with the PSR RES bits at the default size, but explicit); `GSST` is left at 0.
5. `CDI` `0x97` in B/W mode (VBD = 10, DDX = 01, 10 hsync; the IL0373 value) or `0xD7` in B/W/Red mode: written explicitly so the framebuffer polarity does not depend on the OTP default. Leave `PWR`, `BTST`, `PLL`, `TCON` at their power-on/OTP values (see Implementation Notes).
6. No RAM clear is required: `show()` always writes both planes completely.

An update (`show()`):

1. `DTM1` + `ceil(width/8) × height` bytes (B/W mode: OLD = `NOT fb`; B/W/Red mode: the B/W plane); `DTM2` + the same number of bytes (B/W mode: NEW = `fb`; B/W/Red mode: the red plane, zeros when no red pixel was drawn).
2. `PON`; wait BUSY_N high.
3. `DRF`; wait BUSY_N high (refresh, no stated duration).
4. `POF`; wait BUSY_N high.

Deep sleep: `POF`, then `DSLP` `0xA5`. **Wake = hardware reset + the Initialization Sequence**; the driver's framebuffer is unaffected.

## Implementation Stages

### Minimal

Goal: a 400 × 300 (or smaller) black/white e-paper panel you can draw pixels on out of the box.

| Operation | Parameters | Returns | Notes |
|-----------|------------|---------|-------|
| `init` | `connection` (`DisplayConnection`), `width: int = 400`, `height: int = 300`, `busy_timeout_ms: int \| None = 30000` | — | Allocates the framebuffer, runs the Initialization Sequence in B/W mode (including the BUSY_N wait), leaves the panel unchanged until `show()`. `width` a multiple of 8 and ≤ 400, `height` ≤ 300 |
| `clear` | `color: int = WHITE` | — | Fill the framebuffer (`WHITE` or `BLACK`) |
| `set_pixel` | `x: int`, `y: int`, `color: int = BLACK` | — | Framebuffer only; out-of-range ignored |
| `show` | — | — | Write OLD/NEW, `PON` → `DRF` → `POF`; blocks until BUSY_N is high again |
| `sleep` | — | — | `POF` (if on) then `DSLP`; only `wake()` / a hardware reset restores communication |

**Constants:** `BLACK = 0`, `WHITE = 1`.

**Sensible defaults:** 400 × 300 B/W (KW), waveform from OTP (`PSR.REG = 0`), internal temperature sensor, power setting / soft start / PLL / TCON at power-on values, CDI `0x97`, SPI Mode 0 at 4 MHz, BUSY timeout 30 s (not derived from the datasheet, which states no refresh time; the UC8276C's tri-colour refresh took 16.8 s, a black/white one is expected to be shorter — measure the real refresh and adjust). The framebuffer is `ceil(width / 8) × height` bytes (**15 000** at 400 × 300), initialised to white; the OLD/NEW planes are produced while streaming, no second buffer. In C++ the buffer is caller-supplied (`valid()` instead of exceptions). Works with `SIMPLEX` wiring.

## Data Conversion

```
bytes_per_row = ceil(width / 8)
index         = y * bytes_per_row + (x // 8)
bit           = 7 - (x % 8)                      # D7 = first (left) pixel
set pixel     : fb[index] |= (1 << bit) for WHITE;  &= ~(1 << bit) for BLACK        (RED: see below)

B/W mode      : DTM1 (OLD) = NOT fb      DTM2 (NEW) = fb          # every pixel driven
B/W/Red mode  : DTM1 = fb_bw             DTM2 = fb_red
                BLACK: bw=0 red=0   WHITE: bw=1 red=0   RED: bw=0 red=1    (DDX = 01)
                fb_red[index] |= (1 << bit) for RED;  &= ~(1 << bit) otherwise
```

## Timing Constraints

- **Reset:** the datasheet gives no reset pulse width or recovery time; the driver holds RST_N low ≥ 10 ms and waits ≥ 10 ms (`DisplayConnection.reset()`), then BUSY_N high.
- **Refresh:** after `DRF`, BUSY_N goes low and the panel refreshes. **No duration or maximum is stated.** The reference value for the sibling UC8276C (400 × 300 B/W/R, measured) is 16.8 s; the IL0398 has not been measured, so the driver default timeout is 30 s (a driver choice, not a datasheet value). The update must not be interrupted.
- **Commands that drive BUSY_N low** (datasheet "BUSY_N Signal" table): `POF`, `PON`, `PMES`, `DSLP`, `DSP`, `DRF`, `TSC`, `LPD`, `AMV`, `APG`. Everything else raises no BUSY_N. The driver waits BUSY_N high after each of PON, DRF, POF.
- **SPI (write):** tSCYCW ≥ 100 ns, SCL high/low ≥ 35 ns, CSB setup (tCSS) ≥ 60 ns, CSB hold (tCSH) ≥ 65 ns, CSB-to-clock (tSCC) ≥ 20 ns, CSB high between transfers (tCHW) ≥ 40 ns, data setup/hold ≥ 30 ns.
- **SPI (read):** tSCYCR ≥ 150 ns, SCL high/low ≥ 60 ns, SDA access time ≤ 10 ns, output disable ≥ 15 ns.
- **Deep sleep exit:** hardware reset, then the full Initialization Sequence. Deep sleep current ≈ 0.1 µA typ (digital) + 0.1 µA (I/O) + 0.3 µA (DC-DC) typ; standby ≈ 8 µA + 2.5 µA + 15.5 µA typ.
- **Operating range:** −30 … +85 °C (chip). The OTP picks the waveform by the sensed temperature from up to 14 boundaries (`TB0`–`TB13`, "temperature ≤ TBx" in order, the last used boundary must be `0x7F`); a temperature outside the OTP's ranges selects the last set.
- **Conformance:** no bound exists to compare against (see `specs/display/il0398_timing.conf`).

## Implementation Notes

- **DisplayConnection owns D/C, RES, BUSY and CS.** The driver never touches them; it calls `send_command(cmd, data)`, `send_data`, `read_data`, `reset`, `wait_busy` from `specs/transport_display.md`, exactly as the UC8276C and IL0373 drivers do. `read_data(n)` is `n` one-byte CS windows with DC high. **The transport needs no extension for this chip** (CS# may be released between a command and its parameters — commands are processed on the stop condition).
- **BUSY_N low = busy** (pin table, BUSY_N flag table, FLG bit 0).
- **Streamed data:** a full frame is 15 000 bytes per plane; the driver streams `send_data` blocks under one CS assertion (this worked for the whole plane on the UC8276C). **Confirm on hardware**; the fallback is per-byte `send_data` calls.
- **Pixel mode default:** KW (B/W) is the primary mode because the named module is a black/white panel and the IL0373 B/W design (OLD = NOT NEW, full drive) was verified on a panel; the chip's power-on mode is KWR (`PSR.BWR = 0`). Whether the module's OTP carries waveforms for the selected mode is **not in the datasheet** — if a refresh does not run or looks wrong, try `set_mode`. The `OLD = NOT NEW` choice and the border value (`VBD = 10`, white border) are driver decisions; if the panel ghosts, the alternative is to keep the previous frame as OLD.
- **LUT commands are undocumented:** the command table lists no `0x20`–`0x24` rows and no LUT layout, only the BUSY_N table names them (`LUTC`, `LUTWW/-`, `LUTWB/LUTW`, `LUTBW/LUTR`, `LUTBB/LUTB`). Sibling chips use 44 (VCOM) and 42-byte tables (IL0373 chip datasheet) — **unverified for this chip**. `write_lut` is an untested escape hatch; without register-LUT data the driver uses the OTP waveform only.
- **Defaults and OTP:** OTP can override PSR, PFS, BTST, TSE, CDI, TCON, TRES, GSST, CCSET, PWS and TSSET defaults. The driver writes PSR, TRES and CDI explicitly and leaves `PWR`, `BTST`, `PLL`, `TCON` and `VDCS` alone: a wrong `PWR` can drive the panel outside its rating, and the VCOM value is normally set at the factory. `set_power` / `set_vcom_dc` are for users who know their panel's values.
- **PSR bit name:** the command table calls bit 4 `KW/R`, the command description `BWR` (0 = B/W/Red, 1 = B/W); both mean the same bit, with the polarity used in this spec (and in the UC8276C/IL0373 specs).
- **DSP vs. DRF:** the datasheet says that after DTM1/DSP "when data_flag = 1, the refreshing of panel starts", and `DRF` also refreshes. The driver sends `DRF` explicitly and does not send `DSP`; whether `DSP` alone starts a refresh is unconfirmed — verify on hardware to avoid a double refresh if `DSP` is ever added.
- **Refresh requires power on:** `DRF` must be preceded by `PON`; the driver always wraps `DRF` in `PON`/`POF`. Datasheet: after a refresh VCOM is floated automatically; in LUT mode (`REG_EN = 0`) the OTP LUT is copied to the registers automatically after DSP/DRF.
- **No `AUTO`:** the UC8276C's `AUTO` (`0x17`) does not exist here (and did not start a refresh there); there is no `refresh_auto`.
- **Temperature:** the internal sensor is the POR choice and is read once automatically at `PON`; the driver does not expose forced temperature (`TSSET`, cascade only).
- **No partial *refresh* waveform:** `PTL`/`PTIN` restrict gate scanning to a window (`PT_SCAN = 0`), but the waveform is the OTP full waveform; a fast partial update needs a vendor LUT the datasheet does not provide. `show_region` is therefore a RAM-transfer saving, not a flicker-free update.
- **Orientation:** with the power-on `UD = 1`, `SHL = 1`, row 0 is `G0` and column 0 is `S0`; whether that is the physical top-left depends on the panel's FPC; `set_flip` corrects either case. Confirm on hardware.
- **SKU mapping:** the issue lists the Waveshare 4.2inch e-Paper V1 as an IL0398/IL0389 module (unverified). No panel specification is committed; check it before claiming support. The Waveshare 4.2inch (B) (UC8276C, `specs/display/uc8276c.md`) and a V2 variant (SSD1683, `specs/display/ssd1683.md`) are *different* controllers: do not infer the controller from the "4.2inch" name.
- **Memory:** 15 000 bytes at 400 × 300 (one framebuffer in B/W mode; plus 15 000 for the red plane in KWR). In C++ the buffer is the caller's (no heap): an undersized or null buffer, a width that is not a multiple of 8 or a size over 400 × 300 makes `valid()` false instead of corrupting memory.
- **Blocking update:** `show()` blocks for the whole refresh; on MicroPython/CircuitPython this stalls the interpreter and the examples must say so.
- **Datasheet status:** preliminary (2016-04-07): package, bump pitch/gap/surface and the RC loading figures are TBD, the title says IL0389 while a figure says IL0398, the feature list's "clock rate up to 20 MHz" conflicts with the 100 ns write cycle (the AC table is used), the VDH/VDL feature text says ±2.4…±11 V while `PWR` allows codes up to `0x3F` (all above `0x2B` map to 11 V), and the command table's `TRES` POR column is 0 while the description says the PSR RES bits apply by default.

## Sigrok Decoder

Decoder id `il0398`, input **`display_spi`**: it stacks on the connection decoder `Display-SPI` (`sigrok/display_spi/`, see `specs/transport_display.md`), which frames the SPI (4-wire or 3-wire) and reports CS#, RES# and the raw BUSY level as `BYTE` / `CS` / `BUSY` / `RESET` / `IDLE` packets. The BUSY polarity is chip-level: this decoder treats BUSY_N **low** as busy and emits the `busy_start` / `busy_done` timing markers. It has no channels or options of its own. After a read command the response bytes are taken from the connection decoder's DOUT value when that channel is wired, otherwise from the shared DIN line. A CS# release between a command and its parameters is legal (the command is processed on the stop condition) and not warned. Typical stack: `-P display_spi:clk=0:mosi=1:cs=2:dc=3:busy=4:res=5,il0398`.

Annotation rows: **Data** — one annotation per command with decoded parameters (resolution, power settings in volts, partial window, PSR bit fields, deep-sleep check code, CDI fields, frame rate, …); **Status** — `Busy for <duration>` spans (BUSY_N low) and RES# low spans; **Warnings** — a command from the BUSY list above for which BUSY_N was not already low at the CS# rising edge that completes it (`NOBUSY`; skipped when BUSY is not probed), unknown command, wrong parameter count (`LUT` commands accept any length), command while BUSY_N is low (other than `FLG`, `REV`, `VV`), pixel write larger than the frame, bad deep-sleep check code. Read commands (`FLG`, `TSC`, `REV`, `LPD`, `VV`, `DSP`, `ROTP`) show the decoded response bytes; they are meaningful only when the probe sits on the shared DIN/DOUT line of a half-duplex wiring. A command with parameters, or an open-ended read, is reported when the next command arrives or on the connection decoder's `IDLE` packet.

`OUTPUT_PYTHON` packets: `('COMMAND', (command_byte, parameter_bytes))`.
