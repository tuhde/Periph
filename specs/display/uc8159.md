# Chip Spec: UC8159

**Manufacturer:** UltraChip (module: Waveshare 5.65inch e-Paper (F), "ACeP" 7-colour)  
**Datasheet:** `datasheets/display/UC8159 5.65inch e-Paper (F).pdf` (Waveshare "5.65inch e-Paper" technical specification v0.2, 2019-11-19; it documents the panel with its UC8159-family controller - there is no separate chip datasheet, so the controller name is an inference from the command set and the vendor capture, see Implementation Notes)  
**Category:** `display`  
**Transports:** SPI (4-wire; write-only or half-duplex, via `DisplayConnection`)

## Overview

The controller drives a **600 x 448** seven-colour electrophoretic panel (black, white, green, blue, red, yellow, orange; plus a "clean" code) with on-chip frame RAM, an oscillator/PLL, a DC-DC booster, VCOM control, an on-chip temperature sensor (I2C master for an external LM75) and a **waveform read from an external SPI flash on the module** - there are no LUT commands and the waveform is not host-visible. Pixels are **4 bits** on the wire (3 bits of colour). A refresh takes **about 30 s**.

The command set is the UC8151/UC8276 family's, with these differences: a single image plane (`DTM1`, 4 bits per pixel), no partial window, no LUT upload, `PWR` is 4 bytes, `PSR` is 2 bytes, `TRES` is 4 bytes, a `PWS` (`0xE3`) power-saving write and an `IPC` (`0x13`) image-process command. BUSY is active low and, unlike the 2.13inch (D) module, is a clean busy signal.

This spec covers 4-wire SPI, full-frame updates, and (with a half-duplex wire mode) the read commands.

## Transport Configuration

### SPI (4-wire)
- **Mode:** CPOL=0 CPHA=0 (Mode 0), MSB first
- **Max clock:** see the SPI timing table of the datasheet (write cycle ~100 ns); driver default 4 MHz. The vendor demo ran at about 1 MHz
- **CS active:** low. Every byte of the vendor demo is its own CS window; a whole 134 400-byte frame in one window was **not** verified on this panel
- **Framing:** command byte with D/C# low, parameters/data with D/C# high; no register address
- **Bus selection:** pin **BS1** low = 4-wire (default), high = 3-wire; the driver requires 4-wire
- **Reads:** `TSC`, `LPD`, `FLG`, `VV`, `TSR`, `DSP` return data on the shared SDA line; they need a half-duplex wire mode (`DisplayConnection`, see `specs/transport_display.md`)

## Pin Configuration

| Pin | Active | Notes |
|-----|--------|-------|
| BUSY | **low = busy** | Low while powering on/off, refreshing or reading the temperature sensor; clean signal (measured) |
| RES# | low | Hardware reset; the vendor demo pulses it for 1 ms; the only exit from deep sleep |
| D/C#, CS#, SCL, SDA | - | As in the other display chips |
| FMSDO | - | Flash data out; **do not share with SDA** (datasheet note) |
| TSCL / TSDA | - | I2C master for an external LM75; leave open |

## Command Set

All commands are one byte (D/C# low); parameters follow with D/C# high. Values marked *vendor* are from the capture `sigrok/tests/uc8159/5in65 Init and Clear.sr`.

| Command | Code | Parameters | Description |
|---------|------|-----------|-------------|
| Panel setting (PSR) | `0x00` | 2 bytes | Byte 1: `[3]` UD (1 = scan up), `[2]` SHL (1 = shift right), `[1]` SHD_N (1 = booster on), `[0]` RST_N (0 = soft reset); bits `[7:6]` are `11` in the datasheet's example. *Vendor:* `0xEF 0x08` |
| Power setting (PWR) | `0x01` | 4 bytes | Datasheet shows the first byte (`VSH/VSL`, `VSH_LV/VSL_LV`, `VDG_EN`); *vendor:* `0x37 0x00 0x23 0x23` |
| Power off (POF) | `0x02` | - | BUSY low for the power-off sequence (*vendor:* 60 ms) |
| Power-off sequence (PFS) | `0x03` | 1 byte | `[5:4]` T_VDS_OFF: 1-4 frames. *Vendor:* `0x00` |
| Power on (PON) | `0x04` | - | BUSY low until the power sequence is ready (*vendor:* 96 ms) |
| Booster soft start (BTST) | `0x06` | 3 bytes | *Vendor:* `0xC7 0xC7 0x1D` (datasheet example `0xE7 0xE7 0x1D`-style) |
| Deep sleep (DSLP) | `0x07` | `0xA5` | Check code required; exit by hardware reset |
| Data start transmission 1 (DTM1) | `0x10` | 134 400 bytes | The frame: **two pixels per byte, first pixel in the high nibble**; `KPixel[2:0]` below, bit 3 unused (*vendor:* `0x11` = white, white) |
| Data stop (DSP) | `0x11` | - (read 1 byte) | `data_flag` in bit 7. **Not sent by the vendor demo** |
| Display refresh (DRF) | `0x12` | - | BUSY low for the whole update (*vendor:* 29.86 s) |
| Image process (IPC) | `0x13` | 1 byte | `0x00` in the datasheet; not sent by the vendor demo |
| PLL control (PLL) | `0x30` | 1 byte | Frame-rate code; `0x3C` = 50 Hz (*vendor*), `0x3A` = 100 Hz, `0x39` = 200 Hz, `0x00` = 12.5 Hz ... `0x0F` = 200 Hz |
| Temperature sensor calibration (TSC) | `0x40` | read 2 bytes | `TS[7:0]` signed deg C (internal) |
| Temperature sensor enable (TSE) | `0x41` | 1 byte | `[7]` 0 = internal, 1 = external LM75; `[3:0]` offset -8..+7 deg C (*vendor:* `0x00`) |
| Temperature sensor write / read (TSW / TSR) | `0x42` / `0x43` | 3 bytes / read 2 bytes | I2C pass-through; not exposed |
| VCOM and data interval (CDI) | `0x50` | 1 byte | `[7:5]` VBD (border colour, same colour table as DTM1), `[4]` DDX (1 = default polarity), `[3:0]` CDI (interval, `0111` = 10 hsync). *Vendor:* `0x37` |
| Low power detection (LPD) | `0x51` | read 1 byte | bit 0: 1 = normal, 0 = VDD < 2.5 V |
| TCON setting (TCON) | `0x60` | 1 byte | *Vendor:* `0x22` |
| Resolution setting (TRES) | `0x61` | 4 bytes | `HRES` (2 bytes, big-endian), `VRES` (2 bytes): **600 x 448 = `02 58 01 C0`** (*vendor*) |
| Power saving (PWS) | `0xE3` | 1 byte | *Vendor:* `0xAA`; not in the datasheet's register table |
| Get status (FLG) | `0x71` | read 1 byte | `[5]` I2C_ERR, `[4]` I2C_BUSYN, `[3]` data_flag, `[2]` PON, `[1]` POF, `[0]` BUSY_N |
| VCOM value (VV) | `0x81` | read 1 byte | `VV[6:0]`: `0x02` = -0.10 V, 0.05 V per step, to -4.0 V |
| VCOM_DC setting (VDCS) | `0x82` | 1 byte | `VDCS[6:0]`: `0x02` = -0.10 V ... -4.0 V |

### Colour codes (`DTM1` nibble and `CDI.VBD`, `DDX = 1`)

`0` black, `1` white, `2` green, `3` blue, `4` red, `5` yellow, `6` orange, `7` clean. With `DDX = 0` the table is mirrored (0 blue ... 3 black, 4 clean ... 7 red); the driver always writes `DDX = 1`.

## Display RAM

One plane of 600 x 448 pixels, 4 bits per pixel, written by `DTM1` as a plain stream of `600 / 2 x 448 = 134 400` bytes, rows in gate-scan order (`UD = 1`: first row first), each byte = (pixel 2n << 4) | pixel 2n+1.

## Initialization Sequence

From the vendor capture (`sigrok/tests/uc8159/5in65 Init and Clear.sr`, 4 MHz, 66 s: init + clear to white + one test frame):

1. Hardware reset: RES# low ~1 ms, then high; wait BUSY high (BUSY is low during the reset pulse).
2. `PSR` `EF 08`, `PWR` `37 00 23 23`, `PFS` `00`, `BTST` `C7 C7 1D`, `PLL` `3C`, `TSE` `00`, `CDI` `37`, `TCON` `22`, `TRES` `02 58 01 C0`, `PWS` `AA`.
3. The vendor then waits ~100 ms and repeats `CDI` `37` and `TRES`.
4. `DTM1` + 134 400 bytes (the vendor sends one CS window per byte, about 1.6 s).
5. `PON`; wait BUSY high (96 ms).
6. `DRF`; wait BUSY high (29.9 s).
7. `POF`; wait BUSY high (60 ms).

The vendor demo does this twice (clear to white `0x11`, then a test frame that is mostly white with green, black and blue areas) and never sends `DSP`, `IPC`, partial or LUT commands.

An update (`show()`): `DTM1` + frame, `PON`, wait, `DRF`, wait, `POF`, wait. Deep sleep: `DSLP` `0xA5`; wake = hardware reset + the initialization commands (the frame must be re-sent: the controller keeps no image across a reset that is relied on here).

## Implementation Stages

### Minimal

| Operation | Parameters | Returns | Notes |
|-----------|------------|---------|-------|
| `init` | `connection`, `busy_timeout_ms = 60000` | - | Reset and the initialization commands; panel unchanged until `show()` |
| `clear` | `color: int = WHITE` | - | Fill the framebuffer |
| `set_pixel` | `x, y, color = BLACK` | - | Framebuffer only; out-of-range ignored; `color` 0..7 |
| `show` | - | - | `DTM1`, `PON`, `DRF`, `POF`; blocks about 30 s |
| `sleep` | - | - | `DSLP` |

**Constants:** `BLACK = 0, WHITE = 1, GREEN = 2, BLUE = 3, RED = 4, YELLOW = 5, ORANGE = 6, CLEAN = 7`; `WIDTH = 600`, `HEIGHT = 448`.

**Framebuffer:** 134 400 bytes at 4 bpp. In C++ the caller supplies the buffer; to fit a 128 KB MCU (NUCLEO-F411RE) the C++ driver stores **3 bits per pixel** (`buffer_size() = 100 801` bytes) and expands to nibbles while sending. The other languages keep a nibble-per-pixel buffer (134 400 bytes) or a byte per pixel, as suits them.

## Data Conversion

```
pixels_per_byte = 2
byte index      = (y * 600 + x) // 2
nibble          = high if x even else low        # (p0 << 4) | p1
TRES            = 02 58 01 C0                    # 600, 448
VCOM / VDCS     = -0.10 - 0.05 * (code - 2) V    # code 0x02 .. 0x50 (-4.0 V)
temperature     = int8(TS)                       # -25 .. +60 deg C
```

## Timing Constraints

- **Reset:** RES# low ~1 ms (vendor); BUSY follows RES# (low while RES# is low) and is high ~2 ms after release.
- **PON:** BUSY low 96 ms. **POF:** 60 ms. **DRF:** **29.86 s** (full-frame seven-colour update), measured from the vendor capture. The panel is specified for 15-35 deg C only.
- **Frame transfer:** 134 400 bytes; vendor 1.6 s at about 1 MHz per-byte CS.
- **Conformance:** no vendor bound; see `specs/display/uc8159_timing.conf`.

## Implementation Notes

- **Controller identification:** the only document is Waveshare's panel specification, which never names the controller; the command set (PSR/PWR/PFS/BTST/PLL/TSC/TSE/CDI/TCON/TRES/FLG/VV/VDCS, flash-sourced waveform) matches UltraChip's UC8159. The driver is named `UC8159` after the Waveshare module's page and the family.
- **No chip datasheet:** register fields that the panel specification does not detail (`PWR` bytes 2-4, `PWS`, `TCON`, `BTST`) are written with the vendor demo's values and exposed only via `send_command`.
- **Memory:** a 4 bpp frame is 134 400 bytes and does not fit a NUCLEO-F411RE (128 KB RAM); the C++ driver packs 3 bpp (100 801 bytes), which does fit with a small stack.
- **Update time:** about 30 s per refresh; the panel needs 15-35 deg C and should not be refreshed more often than the vendor's guidance (not stated; E Ink ACeP panels are typically >= 180 s).
- **No partial refresh, no DSP/IPC in the vendor flow:** not implemented beyond raw commands.
- **Hardware status:** the C++ STM32Cube demo (`cpp/examples/stm32cube/display/UC8159/demo`) was run on a NUCLEO-F411RE + Waveshare 5.65inch e-Paper (F) with the Waveshare e-Paper Shield, SPI1 0.78 MHz: `show()` completes in 32.3 s (including the 64-byte-chunk frame transfer, `PON`, `DRF`, `POF`) and the seven colour bars were confirmed visually, without the vendor's 100 ms delay and repeated `CDI`/`TRES`. The other languages, `sleep()`/`wake()` and the reads are not verified on a panel.
