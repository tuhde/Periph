# Chip Spec: SH1107

**Manufacturer:** Sino Wealth  
**Datasheet:** `datasheets/display/sh1107.pdf` (SH1107 V2.1, 62 pages, from `https://microcontroller-course.web.cern.ch/Exercises/OLED_display/resources/SH1107.pdf`). No module datasheet is committed: the module mapping below comes from the issue's Waveshare survey and is **unverified**  
**Category:** `display`  
**Transports:** I²C, SPI (4-wire)

## Overview

The SH1107 is a single-chip CMOS OLED/PLED driver with controller for monochrome dot-matrix graphic panels of up to **128 × 128** pixels: 128 segment (column) outputs, 128 common (row) outputs, 128 × 128 bits of display RAM (16 pages of 128 columns), an on-chip oscillator, an internal DC-DC converter for the OLED supply VPP (with an external NMOS/inductor circuit on the module), 256-step contrast control, row/column remapping, vertical scrolling through the display start line and programmable multiplexing (1–128). It supports 8-bit 6800/8080 parallel, 3-/4-wire SPI and 400 kHz I²C interfaces; this spec covers **I²C and 4-wire SPI**. The issue names the Waveshare **1.5inch OLED Module (B)** (SPI / I²C) as the SH1107 module (**unverified**).

It is the 128 × 128 sibling of the SH1106 (`specs/display/sh1106.md`) and the same page-addressed family as the SH1106/SSD1306/SSD1305 specs, with these differences that shape the driver:
- **16 pages × 128 columns** (page commands `0xB0`–`0xBF`, a 7-bit column address `0x00`–`0x7F`), no 132-column RAM and therefore **no column offset**.
- **Two memory-addressing modes** selectable with `0x20` / `0x21`: *page addressing* (POR, as on the SH1106) and *vertical addressing* (the page pointer auto-increments). There are no `0x21`/`0x22`-style column/page range commands.
- **The display start line is a double-byte command `0xDC`** (not `0x40|line`), the multiplex ratio is 1–128 (`0xA8`, POR `0x7F`), the DC-DC command `0xAD` is followed by a byte `0x80 | F | D` (switching frequency bits + on/off) instead of `0x8A`/`0x8B` only, and there is **no pump-voltage command (`0x30`)** and **no COM-pins command (`0xDA`)**.
- **VCOMH (`0xDB`) is a continuous 8-bit value** (β = 0.430 + code × 0.006415, POR `0x35`).
- **A readable identity:** the status read returns `BUSY`, `ON/OFF` and a 6-bit chip ID `000111` (`0x07`) — but only on I²C and parallel; see Implementation Notes (it does not fit the registry's register-based `id_probe`).

The two transports share one command set. The driver family is therefore a base class holding the command logic and framebuffer with two transport hooks: `Sh1107Minimal` / `Sh1107Full` (I²C) and `Sh1107SpiMinimal` / `Sh1107SpiFull` (SPI) — see Implementation Notes.

## Transport Configuration

### I²C
- **Address:** `0x3C` (SA0 = VSS) — `0x3D` (SA0 = VDD); 7-bit address `0111 10 SA0`, the A0 pad acting as SA0 (the same two addresses as the SH1106, SSD1305, SSD1306, SSD1327 and PCF8578/PCF8579)
- **Max clock:** 400 kHz (fast mode; TLOW ≥ 1.3 µs, THIGH ≥ 0.6 µs)
- **Identity register:** none in the registry's sense (`registry/chips.json` entry has `"id_probe": null`); the status byte carries the chip ID `0x07` in bits 5:0, but it is read without a register address and shares `0x3C`/`0x3D` with the SH1106, SSD1305, SSD1306, SSD1327 and PCF8578/PCF8579, so it cannot be used by the generic discovery probe
- **Probe safety:** `write_sensitive` — every byte after the address and a control byte is a command or display data
- **Interface select pins:** IM0 = 0, IM1 = 1, IM2 = 0; CS tied low, D2–D7 tied to VDD/VSS or left open
- **Protocol:** write = `[addr+W] [control byte] [data byte(s)] …`. The **control byte** is `Co D/C 0 0 0 0 0 0`: `Co = 1` means one data byte follows and then another control byte; `Co = 0` means all remaining bytes in the transaction are data. `D/C = 0` → the data is a command (including a command's data byte), `D/C = 1` → display RAM data. So a command stream is `0x00, cmd, cmd, …` (or `0x80, cmd` per command) and a RAM stream is `0x40, d0, d1, …`. Read = `[addr+R] [data…]`, returning the status byte or RAM data according to the D/C bit of the last write (see Read access)
- **Register addressing:** none — plain `Connection` (`write`, `read`), not `RegisterConnection`

### SPI (4-wire)
- **Mode:** CPOL=0 CPHA=0 (Mode 0) — SI is shifted in on the rising SCL edge; the datasheet does not name the idle level, Mode 0 is the usual choice (confirm on hardware)
- **Max clock:** 4 MHz at VDD1 2.4–3.5 V (tSCYC ≥ 250 ns, SCL high/low ≥ 100 ns), **2 MHz** at VDD1 down to 1.65 V (tSCYC ≥ 500 ns); drivers default to 2 MHz
- **Bit order:** MSB first
- **CS active:** low; "the serial interface is initialized when CS is high", and "the SPI is also able to work properly when CS always keeps low, but it is not recommended"
- **Framing:** a plain byte stream — no opcode or address bytes. The **D/C pad (A0)** is sampled on every eighth clock: `A0 = 0` → the byte is a command **or a command's data byte**, `A0 = 1` → display RAM data. SPI goes through a `DisplayConnection` (`specs/transport_display.md`) with `busy = None`, which owns D/C, RES and CS; the driver sends **every command and parameter byte with `send_command(byte)`** (D/C low) and display RAM data with `send_data()`. The transport's `send_command(cmd, data)` sends its `data` with D/C *high* and must **not** be used for the second byte of a double-byte command (the table lists the data byte of `0x81`, `0xA8`, `0xD3`, … with A0 = 0; same note as `specs/display/ssd1331.md`)
- **CS# across a command and its data byte:** the datasheet does not say whether CS may be released between the two bytes of a double-byte command; the per-call CS framing of `DisplayConnection` is the working assumption (as for the SH1106 SPI driver). **Confirm on hardware**
- **Read:** not possible over SPI ("read is not possible while in serial interface mode")
- **3-wire SPI (9-bit frames, IM = `100`) and the parallel interfaces are not supported** (the byte-oriented SPI connection cannot send 9-bit frames)
- **Interface select pins:** IM0 = 0, IM1 = 0, IM2 = 0; D2–D7 tied to VDD/VSS or left open

## Command Set

All commands are single bytes sent with D/C = 0; "double-byte" commands are a mode byte followed by a data byte sent **also with D/C = 0**, in the same command stream. POR values are in parentheses. Do not send commands not listed here ("Do not use any other command, or the system malfunction may result"). After the contrast mode byte `0x81`, only the contrast data byte is accepted.

| Command | Code | Description |
|---------|------|-------------|
| Set lower column address | `0x00 \| A[3:0]` | Low nibble of the column pointer (POR `0x00`) |
| Set higher column address | `0x10 \| A[6:4]` | High 3 bits of the column pointer, columns 0–127 (`0x10`–`0x17`; POR `0x10`) |
| Set memory addressing mode | `0x20 \| D` | `0x20` page addressing (POR), `0x21` vertical addressing |
| Set contrast | `0x81`, then `00`–`FF` | Segment current ISEG = α/256 × IREF × 32 with IREF = 15.625 µA (POR `0x80`) |
| Segment re-map (ADC) | `0xA0` / `0xA1` | `0xA0`: normal (POR); `0xA1`: reversed (column order and the bit direction of each byte are reversed) |
| Multiplex ratio | `0xA8`, then `00`–`7F` | Ratio = data + 1: 1…128 (POR `0x7F` = 128) |
| Entire display on | `0xA4` / `0xA5` | `0xA4` follows RAM (POR); `0xA5` forces all pixels on (RAM kept; has priority over normal/reverse) |
| Normal / reverse | `0xA6` / `0xA7` | `0xA6` RAM 1 = pixel on (POR); `0xA7` inverted |
| Display offset | `0xD3`, then `00`–`7F` | Maps the display start line to COM0–127 (POR 0) |
| DC-DC control | `0xAD`, then `0x8x` | Data byte `1000 F2 F1 F0 D`: `D = 1` DC-DC on when the display is on (POR; the table prints POR `0x81`), `D = 0` off (external VPP); `F[2:0]` switching frequency 0.6…1.3 × SF (`000` = 0.6 SF POR … `111` = 1.3 SF; SF = 500 kHz −25 % / +35 %). Issue while the display is **off** |
| Display off / on | `0xAE` / `0xAF` | `0xAE` sleep (POR): oscillator and DC-DC stop, segment/common outputs high-impedance, display data kept and **writable**; `0xAF` on |
| Set page address | `0xB0 \| A[3:0]` | Page 0–15 (POR 0) |
| COM scan direction | `0xC0` / `0xC8` | `0xC0` COM0 → COM[N−1] (POR); `0xC8` reversed — takes effect immediately (vertical flip) |
| Clock divide / oscillator | `0xD5`, then `A7:A4 osc, A3:A0 div−1` | Divide ratio = A[3:0] + 1; oscillator −25 % … +50 % in 5 % steps, `0101` = nominal (POR `0x50`; fOSC 720 kHz typ, frame ≈ 104 Hz at 128 COM) |
| Pre-charge / discharge | `0xD9`, then `A7:A4 discharge, A3:A0 precharge` | DCLKs, 1–15 (POR `0x22`); precharge 0 = none (+2 DCLK display period, saves power); discharge 0 invalid |
| VCOM deselect level | `0xDB`, then `00`–`FF` | VCOMH = (0.430 + code × 0.006415) × VREF; codes `0x40`–`0xFF` = 1.0 × VREF (POR `0x35` = 0.770) |
| Set display start line | `0xDC`, then `00`–`7F` | RAM line shown at COM0 (POR 0) — hardware vertical scroll |
| Read-modify-write | `0xE0` | Column (page-mode) or page (vertical-mode) pointer increments only on writes until `0xEE` |
| End | `0xEE` | Leaves read-modify-write; the pointer returns to its pre-`0xE0` value |
| NOP | `0xE3` | No operation |
| Write / read display data | (A0 = 1) | RAM access; reads need a dummy read after the address is set (parallel/I²C only) |
| Read ID / status | (read, A0 = 0) | `D7` BUSY, `D6` ON/OFF (**0 = display on**, the inverse of the on/off command), `D5:D0` chip ID `000111` = `0x07` |

### Power-on / reset defaults

Display off (sleep), 128 × 128 mode, normal segment and scan mapping, start line 0, column pointer 0, page 0, **page addressing mode**, contrast `0x80`, DC-DC selected (on when the display is on), multiplex 128, clock divide 1 at nominal oscillator, pre-charge/discharge 2/2, VCOMH `0x35`, normal (non-inverted) display, entire display follows RAM. The display RAM contents are **undefined** at power-up (the datasheet's init flow ends with "clear internal RAM to 00H").

## Display RAM

128 columns × 16 pages × 8 bits = 128 × 128 bits. One data byte holds 8 vertical pixels of one column of one page; the datasheet's RAM-map figures do not survive text extraction, so **bit 0 = top row of the page** is the assumption (same as the SH1106/SSD1306 family — confirm on hardware); page 0 is at the top at start line 0 with the normal scan direction.

- **Page addressing (POR; used by the driver):** set the page (`0xB0|p`) and the column pointer (`0x00|low`, `0x10|high`), then write data bytes; the column pointer **auto-increments after every data read/write** (to column 127) but the page does **not** change; moving to the next page needs a new page + column command (the column pointer is independent of the page address).
- **Vertical addressing (`0x21`):** after each data byte the **page** pointer increments (wrapping at the page end back to the start page) while the column stays; a new column address must be set to continue with the next column.
- **Segment re-map (ADC = `0xA1`)** reverses both the page/column mapping direction and the bit direction of each byte (a horizontal and vertical mirror of the byte layout, datasheet figures 13-2 / 13-4). The COM scan direction (`0xC8`) flips the picture vertically.
- The display start line (`0xDC`) and offset (`0xD3`) rotate which RAM row appears at which COM; with a multiplex ratio below 128 only that many rows are shown.

A panel with fewer than 128 rows (for example 128 × 64) uses multiplex `rows` and, depending on how it is wired, an offset — **not in the datasheet** (see Implementation Notes).

## Initialization Sequence

Per the datasheet's power-on flow (1.1, built-in DC-DC; 1.2 for external VPP):

1. Apply VDD (and AVDD) with RES low ≥ 10 µs (if RES is wired, `connection.reset()` pulses it low for `reset_pulse_us ≥ 10` and releases it, then waits `reset_settle_ms ≥ 2 µs` for the chip to be ready).
2. Send the setup commands in one command stream with the display off (every byte with D/C low): `0xAE`, `0xD5 0x50` (clock, POR), `0xA8 height−1` (multiplex), `0xD3 0x00` (offset 0), `0xDC 0x00` (start line 0), `0xA0|ADC`, `0xC0|(scan<<3)`, `0x81 0x80` (contrast), `0xD9 0x22`, `0xDB 0x35`, `0x20` (page addressing), `0xA4`, `0xA6`.
3. `0xAD 0x81` (DC-DC on at the lowest switching frequency, the POR value) for the internal DC-DC, or `0xAD 0x80` for an external VPP.
4. Clear the display RAM (16 pages × 128 bytes of `0x00`, one page + column set per page) before `0xAF`.
5. `0xAF` (display on); wait **100 ms** (the datasheet's flow: "Set display on: AFH, wait 100 ms, send display data") before relying on the picture.

Power-off: `0xAE`, switch off VPP/VDD (the datasheet notes that power sequencing mistakes do not damage the module).

## Implementation Stages

### Minimal

Goal: a 128 × 128 monochrome OLED you can draw pixels on out of the box.

## Data Conversion

```
page, bit      = y // 8 , y % 8                     # 16 pages of 8 rows at 128 rows
fb[page][x]    = framebuffer byte for column x of that page            (x = 0..width-1)
set pixel      : fb[page][x] |=  (1 << bit)     clear: &= ~(1 << bit)           (bit 0 = top row, assumed)

show() (page mode):  for p in 0..height/8-1:
            cmd stream: 0xB0|p, 0x00, 0x10                  (column 0; every byte with D/C low)
            data stream: fb[p][0..width-1]
show() (vertical mode):  for c in 0..width-1:
            cmd stream: 0xB0, 0x00|(c & 0x0F), 0x10|(c >> 4)
            data stream: fb[0][c], fb[1][c], ... fb[height/8-1][c]

DC-DC data byte = 0x80 | (freq << 1) | on         freq 0..7 -> 0.6 .. 1.3 x SF      (POR 0x81)
VCOMH           = (0.430 + code * 0.006415) * VREF        code 0x00..0x3F ; 0x35 = 0.770 (POR)
Segment current = contrast / 256 * 15.625 uA * 32          (0xFF -> about 500 uA)
Frame rate      = fOSC / (D * K * MUX)        D = divide ratio, K = 54 DCLK per row (common width), MUX = multiplex ratio ; 720 kHz -> about 104 Hz at 128 MUX

I²C control bytes:  0x00  = last control byte, following bytes are commands (and their data bytes)
                    0x80  = command byte follows, then another control byte
                    0x40  = last control byte, following bytes are display data
SPI:  D/C low for command and command-data bytes, D/C high for display data bytes
```

## Timing Constraints

- **Reset:** RES low ≥ 10 µs (tRW); the chip is ready within 2 µs (tR) after RES goes high.
- **Display-on sequence:** after the setup commands, the RAM clear and `0xAF`, wait **100 ms** before sending display data (datasheet flows 1.1 / 1.2). The DC-DC (`0xAD`) must be configured while the display is off. These are recommended delays, not hard limits; the datasheet gives no separate VPP stabilisation time.
- **I²C:** fSCL ≤ 400 kHz, TLOW ≥ 1.3 µs, THIGH ≥ 0.6 µs, data setup ≥ 100 ns, start setup/hold and stop setup ≥ 0.6 µs, bus free time TBUF ≥ 1.3 µs. A full 128 × 128 frame is 2 048 data bytes (≈ 50 ms at 400 kHz).
- **SPI:** SCL cycle ≥ 250 ns (VDD1 2.4–3.5 V) / ≥ 500 ns (1.65–2.4 V), CS setup/hold 120/60 ns (240/120 ns at low VDD1), address (D/C) setup/hold 150 ns (300 ns at low VDD1), data setup/hold 100 ns (200 ns), pulse widths ≥ 100/200 ns — hence the 2 MHz default.
- **BUSY:** the status register's BUSY bit is high during internal operation or reset; commands sent while busy are rejected. Over SPI there is no status read, so the driver relies on the datasheet timing and does not stream commands faster than the clock limits.
- **Conformance:** none of these has a bus-decodable start/end annotation pair that the host controls (the delays are recommended waits after commands, not measured events), so `specs/display/sh1107_timing.conf` defines no checks.

## Implementation Notes

- **One base class, two transports:** implement an abstract base (`_Sh1107Base`) with the framebuffer, drawing, and command logic and two hooks `write_commands(bytes)` / `write_data(bytes)`. The I²C classes prepend the control byte (`0x00`/`0x40`) to every transaction (one `connection.write` per stream, chunked to the platform's maximum write size; every chunk of data repeats the `0x40` control byte); the SPI classes call `DisplayConnection.send_command(byte)` for every command and command-data byte and `send_data()` for RAM data. SPI RAM data can be sent as a single transaction per page.
- **Plain `Connection`, not `RegisterConnection`:** the control byte is not a register address; the same style as the SH1106 and SSD1305 drivers. The SPI connection must not fold read/burst bits into the first byte.
- **I²C transaction sizes:** some platform I²C layers limit a write to 32 bytes (Arduino `Wire`); chunk RAM data accordingly (each chunk a fresh `0x40` control byte; the column pointer keeps advancing between chunks, up to column 127).
- **SPI double-byte commands:** the data byte of `0x81`, `0xA8`, `0xAD`, `0xD3`, `0xD5`, `0xD9`, `0xDB` and `0xDC` is sent with D/C **low** (the command table shows A0 = 0 for them); the transport's `send_command(cmd, data)` would send it with D/C high. Use per-byte `send_command(byte)` calls (or a command-stream helper).
- **No column offset on 128 × 128 panels:** the RAM has exactly 128 columns, so `column_offset` does not exist (unlike the SH1106/SSD1305). Panels with fewer than 128 columns centred on the 128 segment outputs are not described in the datasheet.
- **Panel with fewer than 128 rows (not in the datasheet):** a 128 × 64 or 128 × 32 panel connected to the SH1107 uses a multiplex ratio below 128 and often a display offset (`0xD3`) and/or a start line to match its COM wiring; if the picture is shifted vertically or wraps, adjust `set_display_offset` / `set_start_line`. The module in the issue is a 128 × 128 panel, so the defaults are those of the full size; its orientation (ADC / COM scan) is **unverified** — `set_flip` corrects either mirror.
- **Rotation:** some SH1107 modules are reported (unverified) to be used with the byte layout rotated by 90° (vertical addressing); the datasheet's `0x21` mode makes that possible, but this spec's driver exposes it only as `set_addressing_mode`; the framebuffer stays page-major.
- **DC-DC:** the data byte after `0xAD` carries both the on/off bit and the switching frequency; the table's POR `0x81` is "on, 0.6 SF". Vendor snippets that send `0xAD 0x8A` (off, F = 101) or `0xAD 0x8B` (on, F = 101) are valid values of the same field; which one a module needs depends on whether its VPP is generated on board (external NMOS/inductor on SW/SENSE/FB) or supplied externally — **not in the datasheet**; configure with `init(internal_dcdc=…)` / `set_dcdc`. With the display on and DC-DC off, VPP must be supplied externally.
- **Page-mode column wrap:** after column 127 the column pointer stops (the datasheet describes the pointer incrementing "until address 127 is accessed"); never write past the last column in one go.
- **Read access (I²C only):** RAM reads need one **dummy read** after the column address is set; the status/ID byte is read with the D/C bit cleared in the last control byte (`D7` BUSY, `D6` ON/OFF inverted, `D5:D0` = `0x07`). The ID read could identify the chip, but it needs the raw (non-register) read of `read_status` and is **write-sensitive on every other device at `0x3C`/`0x3D`**, so the registry keeps `id_probe: null`. Reading over SPI is impossible. Reading is rarely needed because the driver keeps a framebuffer.
- **Read-modify-write:** `0xE0` … `0xEE` is not used by the driver (the framebuffer replaces it); `send_command` exposes it.
- **Do not use undocumented commands:** the datasheet warns that other commands may cause malfunction; many SSD1306-oriented code snippets (`0x21`/`0x22` ranges, charge pump `0x8D`, scroll commands, `0xDA` COM pins, `0x40|line` start line, `0x30` pump voltage) do **not** exist on the SH1107 — a shared SH110x/SSD1306 driver must not send them (note that `0x21` here is the vertical-addressing mode, not a column range).
- **Datasheet quality:** V2.1; the RAM-map and scan-direction figures are bitmaps that do not survive text extraction (so bit order and the segment-remap effect on page order are derived from the SH1106 family and the text), the VCOMH table prints `0.525` for code `0x12` where the formula gives 0.545 (a typo; the formula is used), the DC-DC section's text says `8AH–8BH` while the bit table shows `0x80`–`0x8F`, and the SPI mode is not named.
- **Not covered:** parallel (6800/8080) and 3-wire SPI interfaces, the external-clock mode (CLS low) and the scroll helpers of other controllers.
- **Datasheet:** SH1107 V2.1 (62 pages).

## Sigrok Decoder

Two decoders sharing one command table: `sh1107` (input `['i2c']`, addresses `0x3C`/`0x3D`) and `sh1107_spi` (input `['spi']`; the D/C line is read from an optional logic channel, otherwise every transfer is shown as raw bytes). The I²C decoder splits each write into control bytes (`Co`, `D/C`) and payload; command payloads are decoded into named commands with arguments (column nibbles combined into a column number, page 0–15, addressing mode, start line, contrast, ADC, invert, multiplex, DC-DC (frequency and on/off), display on/off, scan direction, offset, clock divide / oscillator, pre-charge/discharge, VCOMH, read-modify-write / end), double-byte commands consume their data byte, and data payloads are shown with the current page and column (auto-incrementing, clamped at 127) and a count; each data byte can be rendered as an 8-pixel column. Reads are shown as status (BUSY / ON-OFF / ID) or RAM data. Warnings: a command byte not in the table (including SSD1306-only commands such as `0x22`, `0x8D`, `0xDA` and `0x40|line`), a data write that crosses column 127, a status ID other than `0x07`, and a write whose first control byte has `Co = 0`/`D/C = 0` but no command bytes. No timing annotation pair is emitted (the datasheet delays are recommendations, not measured events).
