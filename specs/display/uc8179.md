# Chip Spec: UC8179

**Manufacturer:** UltraChip  
**Datasheet:** `datasheets/display/uc8179c.pdf` (UC8179c_C0.6, IC version c_C, datasheet revision 0.6 "for TFT Module Use Only", 2019-11-26). No panel or module datasheet is committed: module mappings below come from the issue's Waveshare survey and are **unverified**  
**Category:** `display`  
**Transports:** SPI (4-wire; write-only or half-duplex, via `DisplayConnection`)

## Overview

The UC8179 is an all-in-one driver with timing controller for **white/black/red** electrophoretic (EPD) panels of up to **800 source × 600 gate** outputs: two bit-planes of display RAM (800 × 600 bits each), an on-chip oscillator/PLL, DC-DC booster and regulators for the gate, source and VCOM voltages (VGH/VGL ±9…±12 V or ±17…±20 V, VDH/VDL ±2.4…±15 V), an on-chip temperature sensor (−25…+50 °C, 8 bit) with an I²C master for an external LM75, a 6 KB OTP holding the temperature-dependent waveform sets (LUTs), and a low-power detector. It is the larger sibling of the **UC8276C** (`specs/display/uc8276c.md`, 400 × 300) and uses the same command family and the same PON → DRF → POF update cycle.

Candidate modules (from the issue survey, **unverified**): Waveshare 7.5inch e-Paper V2 and (B) V2 (believed 800 × 480) and 5.83inch e-Paper V2 (believed 648 × 480). The issue also notes that the 7.5inch V2 exists in two hardware revisions (before/after September 2023, "V2_old" in the vendor driver); which controller each revision carries is **not established** here — check the panel specification before claiming support for a given module.

The chip differs from an OLED/LCD in ways that shape the driver: a refresh is a long full-panel waveform (**no duration is stated** in the datasheet, see Timing Constraints), the picture is **bistable**, and the display must be explicitly **powered on (PON) → refreshed (DRF) → powered off (POF)** around every update, with BUSY_N waited on after each step. The driver keeps a framebuffer and sends it on `show()`.

The chip has **two pixel modes**: *KWR* (black/white/red, power-on default) and *KW* (black/white with NEW/OLD planes). This spec makes KWR the primary mode; KW is exposed in Full only (see Implementation Notes).

This spec covers **4-wire SPI**, full-panel updates with the **waveform loaded from OTP**, a user-supplied LUT, a partial-window write, and (with a half-duplex wire mode) the read commands. Partial *refresh* waveforms are not in the datasheet and are not specified.

## Transport Configuration

### SPI (4-wire)
- **Mode:** CPOL=0 CPHA=0 (Mode 0) — "data are written in order from MSB at the clock rising edge" (host interfaces section)
- **Max clock:** write cycle ≥ 100 ns (SCL high/low ≥ 35 ns each) → **10 MHz**. The feature list's "clock rate up to 20 MHz" contradicts the AC table; the AC table is used. Driver default 4 MHz. **Read** cycle ≥ **150 ns** (high/low ≥ 60 ns) → ≤ 6.6 MHz; reads are short and the driver uses its write clock capped at 4 MHz
- **Bit order:** MSB first
- **CS active:** low (CSB). The serial counter resets on the CSB rising edge; the datasheet *recommends* CSB high after every 8 bits and its figures show one CSB window per byte. A command is processed on the stop condition
- **Framing:** a byte stream; the **DC pin** is sampled per 8-bit group: low → command, high → parameter/data/read. Bytes are sent verbatim — no register address, no read/write bit
- **Bus selection:** pin **BS** low = 4-wire, high = 3-wire (9-bit frames, DC tied to GND). The driver requires **4-wire**; the BS strap on a module is board-specific. 3-wire framing and the **dual-SPI** modes (`DUSPI` `0x15`, second data line SDA1) are **not supported**
- **Bidirectional SDA:** the chip's SDA pin is an I/O. Read commands (listed under Command Set) clock data out on SDA after the command byte, with DC high and CSB low. Whether the board exposes DOUT depends on the wiring → `DisplayConnection` wire mode (`SIMPLEX` / `HALF_DUPLEX_HW` / `HALF_DUPLEX_PIN`, see `specs/transport_display.md`). `SIMPLEX` is sufficient for everything in Minimal
- **Register addressing:** none — takes a `DisplayConnection`, not a `RegisterConnection`

## Command Set

All commands are one byte sent with DC low; parameters follow with DC high. POR values in brackets. **Defaults can be changed by OTP** ("Command default setting": PSR, BTST, KWOPT, CDI, TCON, HRES), so a panel may not power up with exactly these values; the driver writes every setting it depends on. Only commands the driver uses or exposes are listed. This chip has **one** datasheet (no separate panel datasheet), so there are no cross-document layout conflicts as on the UC8276C.

| Command | Code | Parameters | Description |
|---------|------|-----------|-------------|
| Panel setting (PSR) | `0x00` | `A` | `[5]` REG (0 LUT from OTP, 1 from register), `[4]` KW/R (0 KWR, 1 KW), `[3]` UD (1 scan G0→Gn−1), `[2]` SHL (1 shift S0→Sn−1), `[1]` SHD_N (1 booster on), `[0]` RST_N (0 = soft reset). ### BUSY_N flag

All commands except `REV`, `FLG`, `VV` and read cycles are **ignored while a refresh (DRF/DSP) is running**. Commands that drive BUSY_N low (datasheet "BUSY_N Signal" table): `POF`, `PON`, `PMES`, `DSLP`, `AUTO`, `DSP`, `DRF`, `TSC`, `LPD`, `AMV`, `APG`, and the soft-reset bit (RST_N = 0). Data/LUT/setting commands raise no BUSY_N.

### Power-on / reset defaults

PSR `0x0F` (KWR, LUT from OTP, scan up, shift right, booster on), PWR `0x07 0x17 0x3A 0x3A 0x03`, BTST `0x17` ×4, PLL `0x06` (50 Hz), CDI `0x31 0x07`, TCON `0x22`, TRES `0x03 0x20 0x02 0x58` (800 × 600), TSE internal with offset 0, LVSEL `0x03`. The display RAM contents are **undefined** after power-up.

## Display RAM

Two planes, each **800 × 600 bits** (100 bytes × 600 rows); `DTM1` writes plane 1 (B/W) and `DTM2` plane 2 (red). A transfer is a plain stream written from the first pixel to the last: the chip has no address counter or window commands for a full frame. Each byte carries 8 horizontal pixels with **D7 = first (leftmost) pixel**; a frame is `width/8 × height` bytes per plane, rows in gate-scan order (`G0` first at PSR UD = 1, `S0` first at SHL = 1).

In KWR mode with the default CDI (`DDX = 01`):

| Red bit | B/W bit | Colour (LUT) |
|---------|---------|--------------|
| 0 | 0 | black (LUTK) |
| 0 | 1 | white (LUTW) |
| 1 | 0 | red (LUTR) |
| 1 | 1 | red (LUTR) |

Red wins. In KW mode, `DTM1` = OLD and `DTM2` = NEW, and the LUT is selected by the (NEW, OLD) pair (DDX[1] = 0) or by NEW alone (DDX[1] = 1, "without NEW/OLD").

**The polarity depends on CDI.DDX, and the OTP may change its power-on value** (command default setting, address `0x0013`). `DDX[0]` selects the B/W polarity and `DDX[1]` the red polarity. The driver therefore writes CDI explicitly instead of relying on the OTP default.

## Initialization Sequence

Derived from the datasheet's power-management notes and command descriptions and from the UC8276C flow (`specs/display/uc8276c.md`, which was measured on hardware); the datasheet contains no reference code. Confirm on hardware.

1. Apply VDD/VDDIO; BS strapped low (4-wire).
2. **Hardware reset:** `RST_N` low ≥ 50 µs, then high; wait **> 1 ms** (commands sent earlier are ignored), then BUSY_N high.
3. `PSR` `0x0F` (KWR, LUT from OTP, scan up, shift right, booster on).
4. `TRES` with `(width, height)` (`0x03 0x20 0x02 0x58` for 800 × 600); `GSST` is left at 0.
5. `CDI` `0x31 0x07` (BDV = 11, DDX = 01, interval 10 hsync): written explicitly so the framebuffer polarity (B/W 1 = white, red 1 = red) does not depend on the OTP default. Leave `PWR`, `BTST`, `PLL`, `TCON` at their power-on/OTP values (see Implementation Notes).
6. No RAM clear is required: `show()` always writes both planes completely.

An update (`show()`):

1. `DTM1` + `ceil(width/8) × height` B/W bytes; `DTM2` + the same number of red bytes (zeros when no red pixel was drawn).
2. `PON`; wait BUSY_N high.
3. `DRF`; wait BUSY_N high (refresh, no stated duration).
4. `POF`; wait BUSY_N high.

(The UC8276C's measured vendor flow sends `PON` *before* `PSR` and the data; the UC8276C spec records that and its driver uses the order above successfully. The same order is used here.)

Deep sleep: `POF`, then `DSLP` `0xA5`. **Wake = hardware reset + the Initialization Sequence**; the driver's framebuffer is unaffected. In deep sleep tie control signals to 0 V and keep light off the bare die.

## Implementation Stages

### Minimal

Goal: an 800 × 600 (or smaller) black/white/red e-paper panel you can draw pixels on out of the box.

| Operation | Parameters | Returns | Notes |
|-----------|------------|---------|-------|
| `init` | `connection` (`DisplayConnection`), `width: int = 800`, `height: int = 600`, `busy_timeout_ms: int \| None = 60000` | — | Allocates the B/W framebuffer, runs the Initialization Sequence (including the BUSY_N wait), leaves the panel unchanged until `show()`. `width` a multiple of 8 and ≤ 800, `height` ≤ 600 |
| `clear` | `color: int = WHITE` | — | Fill the framebuffer (`WHITE`, `BLACK` or `RED`) |
| `set_pixel` | `x: int`, `y: int`, `color: int = BLACK` | — | Framebuffer only; out-of-range ignored. `RED` allocates the red plane on first use |
| `show` | — | — | Write both planes, `PON` → `DRF` → `POF`; blocks until BUSY_N is high again |
| `sleep` | — | — | `POF` (if on) then `DSLP`; only `wake()` / a hardware reset restores communication |

**Constants:** `BLACK = 0`, `WHITE = 1`, `RED = 2`.

**Sensible defaults:** 800 × 600 KWR, waveform from OTP (`PSR.REG = 0`), internal temperature sensor, power setting / soft start / PLL / TCON at power-on values, CDI `0x31 0x07`, SPI Mode 0 at 4 MHz, BUSY timeout 60 s (not derived from the datasheet; measure the real refresh and adjust). The framebuffer is `width / 8 × height` bytes (**60 000** at 800 × 600), initialised to white; the red plane (same size, initialised to 0) is optional. **Buffer ownership:** languages with a no-heap driver rule (C++) take caller-supplied buffers (`bw`, optional `red`) and the red plane is simply absent when none is given (RED is then drawn as BLACK and the plane is sent as zeros); the other languages allocate the red plane lazily on the first red pixel or `clear(RED)`. Works with `SIMPLEX` wiring.

## Data Conversion

```
bytes_per_row = width // 8
index         = y * bytes_per_row + (x // 8)
bit           = 7 - (x % 8)                      # D7 = first (left) pixel

colour -> planes (DDX = 01, KWR):  BLACK: bw=0 red=0   WHITE: bw=1 red=0   RED: bw=0 red=1
set pixel (BW) :  fb_bw[index]  |=  (1 << bit) for WHITE;  &= ~(1 << bit) for BLACK / RED
set pixel (red):  fb_red[index] |=  (1 << bit) for RED;    &= ~(1 << bit) otherwise

TRES/GSST:  b0 = (value >> 8) & 3 ; b1 = value & 0xF8      # horizontal (multiple of 8)
            b2 = (value >> 8) & 3 ; b3 = value & 0xFF      # vertical
            800 x 600 -> 03 20 02 58

VDH / VDL / VDHR (PWR):   code = round((volts_abs - 2.4) / 0.2)    2.4 .. 15.0 V (0x00..0x3F; VDL negative)
VG_LVL (PWR byte 2):      volts_abs 9..12  -> code = volts_abs - 9        (000..011)
                          volts_abs 17..20 -> code = volts_abs - 17 + 4   (100..111);  VGL = -VGH
                          byte 2 = 0x10 | code        (VCOM_SLEW = bit 4, fixed 1; POR 0x17)
VCOM_DC (VDCS, VV):       code = round((-0.10 - volts) / 0.05)             -0.10 .. -3.30 V (0x00..0x40)
                          read: volts = -0.10 - 0.05 * VV
frame rate (PLL FRS):     5,10,15,20,30,40,50,60,70,80,90,100,110,130,150,200 Hz = code 0..15
temperature (TSC):        celsius = int8(ts)                  -25 .. +50 degC range, two's complement
temperature offset (TSE): TO[3:0] two's complement, -8 .. +7 degC
```

All mappings are regular fits of the datasheet tables (VDH/VDL/VDHR 0.2 V per code from 2.4 V; VG_LVL as listed; VCOM 0.05 V per code with code 0 = −0.10 V; the datasheet's `VDCS` table runs to code `0x40` = −3.30 V). In the second `PWR` byte VCOM_SLEW is bit 4 and `VG_LVL` bits 2:0 (the command-table row for POR `0x17`); bit 3 is unused (write 0).

## Timing Constraints

- **Reset:** RST_N low ≥ **50 µs**; after RST_N rises wait **> 1 ms** before the first command (any command in that window is ignored). Soft reset (PSR RST_N = 0): BUSY_N low meanwhile.
- **Refresh:** after `DRF`, BUSY_N goes low and the panel refreshes. **No duration or maximum is stated in the datasheet.** The reference measurement for the sibling UC8276C (400 × 300 B/W/R) was 16.8 s; an 800 × 600 panel has not been measured, so the driver default timeout is a generous 60 s (a driver choice, not a datasheet value). The update must not be interrupted. A measurement from the first hardware run is still missing.
- **Commands that drive BUSY_N low** (datasheet "BUSY_N Signal" table): `POF`, `PON`, `PMES`, `DSLP`, `AUTO`, `DSP`, `DRF`, `TSC`, `LPD`, `AMV`, `APG`, and the PSR soft-reset bit. Everything else raises no BUSY_N. The driver waits BUSY_N high after each of PON, DRF, POF.
- **SPI (write):** tSCYCW ≥ 100 ns, SCL high/low ≥ 35 ns, CSB setup ≥ 60 ns, CSB hold ≥ 65 ns, CSB high between transfers ≥ 40 ns, CSB-to-clock ≥ 20 ns, DC setup/hold ≥ 30 ns, data setup/hold ≥ 30 ns.
- **SPI (read):** tSCYCR ≥ 150 ns, SCL high/low ≥ 60 ns, SDA access time ≤ 50 ns, output disable ≥ 15 ns.
- **Deep sleep exit:** hardware reset, then the full Initialization Sequence. Deep sleep current ≈ 0.5 µA (digital) + 0.3 µA (I/O) + 0.3 µA (DC-DC) maxima; standby ≈ 35 µA total maxima.
- **Operating range:** −30 … +85 °C (chip). Panel makers advise refreshing at least every 24 hours and storing with a white image (UC8276C panel advice, unverified for these panels).
- **Conformance:** no bound exists to compare against (see `specs/display/uc8179_timing.conf`).

## Implementation Notes

- **DisplayConnection owns D/C, RES, BUSY and CS.** The driver never touches them; it calls `send_command(cmd, data)`, `send_data`, `read_data`, `reset`, `wait_busy` from `specs/transport_display.md`, exactly as the UC8276C driver does.
- **BUSY_N low = busy** (pin description, BUSY_N flag table, FLG bit 0).
- **CS per byte vs. streamed data:** the datasheet only *recommends* CSB high every 8 bits. A full frame is 60 000 bytes per plane; the driver streams `send_data` blocks under one CS assertion (this worked on the UC8276C: the whole 15 000-byte plane in one CS# window). **Confirm on hardware**; the fallback is per-byte `send_data` calls.
- **Defaults and OTP:** OTP can override PSR, BTST, KWOPT, CDI, TCON and HRES defaults ("Command default setting"). The driver writes PSR, TRES and CDI explicitly and leaves `PWR`, `BTST`, `PLL`, `TCON` and `VDCS` alone: a wrong `PWR` can drive the panel outside its rating, and the VCOM value is normally set at the factory. `set_power` / `set_vcom_dc` are for users who know their panel's values.
- **Black/white-only modules:** a plain B/W panel (e.g. the 7.5inch V2, as opposed to the (B) tri-colour one) may ship an OTP with only KW waveform sets, in which case a KWR refresh would not run or would look wrong; the vendor drivers for such modules use the KW mode (`PSR.KW/R = 1`) with OLD/NEW planes. That is **not documented in the chip datasheet** and is unverified here — try `set_mode(MODE_KW)` first on such a module. In KW mode with `DDX[1] = 0` the planes are OLD (`DTM1`) and NEW (`DTM2`); with `DDX[1] = 1` NEW alone drives the LUT. `set_mode` only switches the PSR bit; how the driver fills the OLD/NEW planes in KW mode (framebuffer as NEW and the previously shown frame, or white, as OLD) and their polarity are **not specified by the datasheet** and must be settled on hardware.
- **DSP vs. DRF:** the datasheet says that after DTM1/DSP "when data_flag = 1, the refreshing of panel starts", and `DRF` also refreshes. The driver sends `DRF` explicitly and does not send `DSP`; whether `DSP` alone starts a refresh is unconfirmed — verify on hardware to avoid a double refresh if `DSP` is ever added.
- **Refresh requires power on:** `DRF` must be preceded by `PON`; the driver always wraps `DRF` in `PON`/`POF`.
- **AUTO:** `0x17` (`0xA5` / `0xA7`) is in the datasheet, but measurements on the UC8276C panel showed it starts no refresh; treat `refresh_auto` as unverified here.
- **Temperature:** the internal sensor is the POR choice and is read once automatically at `PON`; the OTP picks the waveform set from it (temperature ranges and LUT format are in the datasheet's OTP sections). The driver does not expose forced temperature (`TSSET`, cascade only).
- **No partial *refresh* waveform:** `PTL`/`PTIN` restrict gate scanning to a window (`PT_SCAN = 0`), but the waveform is the OTP full waveform; a fast partial update needs a vendor LUT the datasheet does not provide. `show_region` is therefore a RAM-transfer saving, not a flicker-free update.
- **Orientation:** with the power-on `UD = 1`, `SHL = 1`, row 0 is `G0` and column 0 is `S0`; whether that is the physical top-left depends on the panel's FPC; `set_flip` corrects either case. Confirm on hardware.
- **Panel sizes:** the chip's active area is set by `TRES` (and `GSST` for an offset). Waveshare 800 × 480 and 648 × 480 modules (believed, unverified) pass `height = 480` / `width = 648`; an offset panel needs `GSST`, reachable through `send_command`.
- **Memory:** **60 000 bytes per plane at 800 × 600** (120 000 for both); 48 000 per plane at 800 × 480. Boards with less RAM than the buffers cannot run the full size — use a smaller window (`TRES`), drop the red plane, or use a board with enough RAM (ESP32-S3 with PSRAM, Raspberry Pi, Pico 2). In C++ the buffers are the caller's (no heap): an undersized or null buffer, a width that is not a multiple of 8, or a size over 800 × 600 makes `valid()` false instead of corrupting memory.
- **Blocking update:** `show()` blocks for the whole refresh; on MicroPython/CircuitPython this stalls the interpreter and the examples must say so. A full frame also takes a noticeable time to transfer (120 000 bytes).
- **Datasheet status:** UC8179c_C0.6 is an engineering specification "for TFT module use only"; the feature list's "clock rate up to 20 MHz" conflicts with the 100 ns write cycle (the AC table is used).

## Sigrok Decoder

Decoder id `uc8179`, input **`display_spi`**: it stacks on the connection decoder `Display-SPI` (`sigrok/display_spi/`, see `specs/transport_display.md`), which frames the SPI (4-wire or 3-wire) and reports CS#, RES# and the raw BUSY level as `BYTE` / `CS` / `BUSY` / `RESET` / `IDLE` packets. The BUSY polarity is chip-level: this decoder treats BUSY_N **low** as busy and emits the `busy_start` / `busy_done` timing markers. It has no channels or options of its own. After a read command the response bytes are taken from the connection decoder's DOUT value when that channel is wired, otherwise from the shared DIN line. A CS# release between a command and its parameters is legal (the command is processed on the stop condition) and not warned. Typical stack: `-P display_spi:clk=0:mosi=1:cs=2:dc=3:busy=4:res=5,uc8179`.

Annotation rows: **Data** — one annotation per command with decoded parameters (resolution, power settings in volts, partial window, PSR bit fields, deep-sleep check code, CDI fields, frame rate, …); **Status** — `Busy for <duration>` spans (BUSY_N low) and RES# low spans; **Warnings** — a command from the BUSY list above for which BUSY_N was not already low at the CS# rising edge that completes it (`NOBUSY`; skipped when BUSY is not probed), unknown command, wrong parameter count, command while BUSY_N is low (other than `FLG`, `REV`, `VV`), pixel write larger than the frame, bad deep-sleep check code. Read commands (`FLG`, `TSC`, `REV`, `LPD`, `VV`, `DSP`, `PBC`, `ROTP`) show the decoded response bytes; they are meaningful only when the probe sits on the shared DIN/DOUT line of a half-duplex wiring. A command with parameters, or an open-ended read, is reported when the next command arrives or on the connection decoder's `IDLE` packet.

`OUTPUT_PYTHON` packets: `('COMMAND', (command_byte, parameter_bytes))`.
