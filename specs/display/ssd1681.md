# Chip Spec: SSD1681

**Manufacturer:** Solomon Systech  
**Datasheet:** `datasheets/display/ssd1681.pdf` (SSD1681 Rev 0.13, Jun 2019, "Product Preview"). No panel or module datasheet is committed: the module mappings below come from the issue's Waveshare survey and are **unverified**  
**Category:** `display`  
**Transports:** SPI (4-wire, write-only; via `DisplayConnection`)

## Overview

The SSD1681 is an active-matrix electrophoretic display (EPD) driver with controller for **red/black/white** panels of up to **200 source × 200 gate** outputs: two on-chip bit-planes of display RAM (B/W and red, 200 × 200 bits each), an on-chip oscillator, booster and regulators for the gate, source and VCOM voltages, an internal temperature sensor, OTP storage for 36 temperature-dependent waveform sets, and a programmable waveform (LUT). It is the controller of the Waveshare **1.54inch e-Paper V2** (black/white) and **1.54inch e-Paper (B/C) V2** (black/white/red) modules (200 × 200); both mappings come from the issue survey and are unverified. Black/white-only panels work too (the red plane is simply never set).

This chip is the sibling of the SSD1680 (`specs/display/ssd1680.md`, 176 × 296) and, further out, of the SSD1683 (`specs/display/ssd1683.md`, 400 × 300): the same commands, RAM model, voltage tables and 153-byte LUT as the SSD1680, with a 200 × 200 RAM and **three SSD1680 features removed** (gate scan start position `0x0F`, the source-output-mode bit of `0x21`, and cascade mode). Drivers for the chips should share structure; this spec stands alone and lists only the SSD1681 values.

An e-paper panel differs from an OLED/LCD in ways that shape the driver: a refresh is a multi-second full-panel waveform, the picture is **bistable** (it stays with the power off), the update must not be interrupted, and BUSY is a level output that must be waited on. The driver therefore keeps a framebuffer, sends it on `show()`, and blocks until BUSY goes low again. The datasheet gives **no refresh duration**; vendor material suggests a few seconds for black/white panels and on the order of 15 s for three-colour panels (unverified), so the default BUSY timeout is generous.

This spec covers **4-wire SPI**, **full-panel updates in 3-colour or black/white mode with the waveform loaded from OTP**, a user-supplied waveform, and a RAM-window write. Partial *refresh* waveforms are **not** in the datasheet and are not specified (see Implementation Notes).

## Transport Configuration

### SPI (4-wire)
- **Mode:** CPOL=0 CPHA=0 (Mode 0) — SDA is shifted in on the rising SCL edge (datasheet table 6-2); the idle level is not named, Mode 0 is the usual choice (confirm on hardware)
- **Max clock:** **20 MHz** in write mode (tSCL high/low ≥ 25 ns); the driver default is 4 MHz. Read mode is limited to 2.5 MHz and is not used
- **Bit order:** MSB first
- **CS active:** low; hold CS low for the whole command + parameter/data sequence of one transfer
- **Framing:** a plain byte stream. The **D/C# pin** is sampled on every eighth clock: low → the byte is a **command**, high → **parameter / RAM data**. `DisplayConnection` drives D/C# (low for the command byte of `send_command`, high for its parameter bytes and for `send_data`); bytes are sent verbatim, no register or read bits are folded into them (no register addressing)
- **Read:** the chip supports reads (commands `0x0A`, `0x1B`, `0x27`, `0x2D`, `0x2E`, `0x2F`, `0x35`), but breakout modules wire **no MISO**; the driver is **write-only** (`SIMPLEX` wire mode) and exposes no read
- **3-wire SPI (BS1 high, 9-bit frames with an embedded D/C bit):** **not supported** (byte-oriented SPI connection). On the modules BS1 is strapped low (4-wire)
- **Register addressing:** none — takes a `DisplayConnection`, not a `RegisterConnection` or a plain `Connection`

### DisplayConnection fit and required extension

The driver is written against `DisplayConnection` (`specs/transport_display.md`) in `SIMPLEX` wire mode, not a bare `Connection` plus loose pins. It owns D/C#, RES#, BUSY and CS#; the driver calls `send_command`, `send_data`, `reset` and `wait_busy` only.

- **Fits as-is:** mode 0 / MSB first, D/C# framing, hardware reset (`reset_pulse_us`, `reset_settle_ms` from the constructor), BUSY level read with `wait_busy(True, timeout_ms)` (active high is passed by the driver), `clock_hz` (default 4 MHz, chip maximum 20 MHz), SoftSPI fallback, the mocks, and the `display_spi` Sigrok decoder.
- **Gap — CS# across a command and its parameters.** `specs/transport_display.md` makes every `send_command` / `send_data` call a separate SPI transfer, so CS# is released between the command byte and its parameters (right for the UC8276C, whose datasheet allows it) and states that a chip needing CS# held "must say so explicitly, and the interface will then need a combined-transfer operation". **This chip needs it:** the datasheet's write procedure (figure 6-1) keeps CS# low across the command byte and the parameter / RAM bytes that follow, and the Sigrok decoder warns `CS-SPLIT` when CS# is released in between. The implementation must therefore **extend `DisplayConnection`** (and `specs/transport_display.md`, all platform classes and the mocks) with a `hold_cs` option: `send_command(cmd, data = [], hold_cs = False)`. With `hold_cs = True` one CS# window covers the command byte, the D/C# change to high and every byte of `data`; the default `False` keeps today's behaviour for the existing chips. The driver sends **every** command with `hold_cs = True` (a RAM write is one `send_command(0x24, plane_bytes, hold_cs = True)`).
- **Platform limit of the extension:** holding CS# while D/C# toggles needs CS# under software control (an `OutputPin` CS#, or SoftSPI). Where the kernel or SPI driver frames CS# itself (Linux spidev hardware CS, ESP-IDF `spics_io_num`, Zephyr `config.cs`), D/C# cannot change inside one framed message; there `hold_cs` must either be refused at construction with a clear error or degrade to per-call CS# (documented in the platform class), and the caller should pass a GPIO CS# for full conformance. Whether the chip tolerates CS# release between command and data is **not stated** in the datasheet (vendor reference code is reported to release CS# around every byte — unverified), so the degraded mode is acceptable pending a hardware test.
- **Large writes:** with ESP-IDF the class splits at `maxTransferBytes`; with driver-owned CS# the hold must span the chunks, otherwise each chunk becomes its own CS# window.

## Command Set

All commands are one byte sent with D/C# = 0; parameter bytes follow with D/C# = 1. POR values in brackets. Only the commands the driver uses or exposes are listed; OTP programming, CRC, VCOM sensing and cascade commands are not covered.

| Command | Code | Parameters | Description |
|---------|------|-----------|-------------|
| Driver output control | `0x01` | `A[7:0]`, `A[8]`, `B[2:0]` | Gate lines = `A[8:0] + 1` (POR `0x0C7` = 200). `B`: GD, SM, TB scan order/direction (POR 0) |
| Gate driving voltage | `0x03` | `A[4:0]` | VGH 10–20 V in 0.5 V steps (POR `0x00` = 20 V) |
| Source driving voltage | `0x04` | `A`, `B`, `C` | `A` VSH1 (POR `0x41` = 15 V), `B` VSH2 (POR `0xA8` = 5 V), `C` VSL (POR `0x32` = −15 V); VSH1 ≥ VSH2 |
| Booster soft start | `0x0C` | `A`, `B`, `C`, `D` | Phase 1/2/3 strength + min-off time, phase durations (POR `0x8B 0x9C 0x96 0x0F`) |
| Deep sleep | `0x10` | `A[1:0]` | `00` normal (POR), `01` deep sleep 1 (RAM retained, not accessible), `11` deep sleep 2 (RAM lost). BUSY stays high; exit needs a hardware reset |
| Data entry mode | `0x11` | `A[2:0]` | `ID[1:0]`: `00` X−/Y−, `01` X+/Y−, `10` X−/Y+, `11` X+/Y+ (POR `011`); `AM`: 0 = X direction first, 1 = Y first (POR 0) |
| Software reset | `0x12` | — | Registers to defaults (not deep sleep), RAM kept. BUSY high meanwhile |
| Temperature sensor control | `0x18` | `A[7:0]` | `0x80` internal sensor; `0x48` external I²C sensor (POR) |
| Write temperature register | `0x1A` | `A[11:4]`, `A[3:0]<<4` | 12-bit two's complement, 1/16 °C per LSB (POR `0x7FF`) |
| Master activation | `0x20` | — | Run the display update sequence selected by `0x22`. BUSY high until done; must not be interrupted |
| Display update control 1 | `0x21` | `A` | `A[7:4]` red-RAM option, `A[3:0]` B/W-RAM option: `0` normal, `4` bypass (RAM content as 0), `8` inverse (POR 0). Unlike the SSD1680 there is **no** second parameter byte (no source output mode) |
| Display update control 2 | `0x22` | `A[7:0]` | Sequence for `0x20` (see below). POR `0xFF` |
| Write RAM (B/W) | `0x24` | data… | B/W plane. **1 = white, 0 = black** |
| Write RAM (red) | `0x26` | data… | Red plane. **1 = red**, 0 = not red |
| Write VCOM | `0x2C` | `A[7:0]` | VCOM −0.2 … −3.0 V (POR `0x00`) |
| Write LUT | `0x32` | 153 bytes | Waveform LUT, WS bytes 0–152 (datasheet §6.7) |
| Border waveform | `0x3C` | `A[7:0]` | VBD select/level/transition (POR `0xC0` = HiZ) |
| End option | `0x3F` | `A` | LUT end option (POR `0x02`; `0x22` normal, `0x07` keep source level) |
| RAM X window | `0x44` | `XSA[4:0]`, `XEA[4:0]` | In **8-pixel units** (POR `0x00`; the datasheet prints `0x15`, a leftover from the SSD1680 — the 200-pixel value is `0x18`) |
| RAM Y window | `0x45` | `YSA[7:0]`, `YSA[8]`, `YEA[7:0]`, `YEA[8]` | In rows (POR `0x000`, `0x0C7`; the datasheet prints `0x127`, a leftover from the SSD1680) |
| Auto write red RAM | `0x46` | `A[7:0]` | Fill red RAM with a regular pattern; `A[7]` first-step value, `A[6:4]` height, `A[2:0]` width. BUSY high meanwhile |
| Auto write B/W RAM | `0x47` | `A[7:0]` | Same for B/W RAM |
| RAM X counter | `0x4E` | `A[4:0]` | Address counter X (POR 0) |
| RAM Y counter | `0x4F` | `A[7:0]`, `A[8]` | Address counter Y (POR 0) |
| NOP | `0x7F` | — | Terminates a RAM write |

**`0x22` sequences** (the datasheet names the two waveform kinds *Display Mode 1* and *Display Mode 2*; the mapping Mode 1 = three-colour, Mode 2 = black/white follows the RAM/LUT tables 6-4 and 6-5 and is inferred — confirm on hardware): `0xF7` = load temperature + display with Mode 1; `0xFF` = same with Mode 2 (POR); `0xC7` / `0xCF` = display only (Mode 1 / Mode 2); `0x91` / `0x99` load LUT only; `0xB1` / `0xB9` load temperature + LUT; `0x80` / `0x01` clock on/off; `0xC0` / `0x03` clock + analog on/off.

### Power-on / reset defaults

POR values as in the table: 200 gate lines, VGH 20 V, VSH1 15 V / VSH2 5 V / VSL −15 V, X+/Y+ data entry, X window `0x00`–`0x18`, Y window `0x000`–`0x0C7` (the datasheet's window POR values are the SSD1680 ones; the driver always sets both windows), counters 0, **update sequence `0xFF`**, **external** temperature sensor selected (`0x18` = `0x48`), border HiZ. The display RAM contents are **undefined** after power-up. The status register (`0x2F`, not exposed) reads `0x01` after reset (chip ID 01).

## Display RAM

Two planes, each **200 × 200 bits** (25 bytes × 200 rows). The X address counts **bytes** (8 horizontal pixels, `0x00`–`0x18`), the Y address counts rows (`0x000`–`0x0C7`). Data are written as a byte stream; after each byte the counter advances according to `0x11` within the window set by `0x44`/`0x45`, so one `0x24`/`0x26` command followed by `width/8 × height` bytes fills the whole window.

| Red RAM | B/W RAM | Colour (3-colour mode, LUT) |
|---------|---------|-----------------------------|
| 0 | 0 | black (LUT0) |
| 0 | 1 | white (LUT1) |
| 1 | 0 | red (LUT2) |
| 1 | 1 | red (LUT3 = LUT2) |

In **black/white mode** (Display Mode 2, table 6-5) the red plane is not a colour: red = 1 selects the duplicate LUT (LUT2 = LUT0 black, LUT3 = LUT1 white), so the B/W plane alone decides the colour.

**Bit order inside a byte is not stated in the datasheet.** The driver uses **bit 7 = leftmost pixel** of each 8-pixel group (common module practice); confirm on hardware.

## Initialization Sequence

Per the chip's operation flow (§8.1), for a panel of `width × height` (default 200 × 200). The datasheet gives no register values for the flow beyond the command names; the values below are POR / datasheet-table values except where marked *vendor*:

1. Wait ≥ 10 ms after VCI is applied.
2. **Hardware reset:** `connection.reset()` (the caller builds the `DisplayConnection` with `reset_pulse_us` ≥ 10 000 and `reset_settle_ms` ≥ 10) (the datasheet gives no numeric reset pulse; these are conservative values — *vendor* code uses 10–20 ms); then **wait BUSY low**.
3. **Software reset** `0x12`; wait BUSY low (flow §8.1: then wait 10 ms).
4. `0x01` with `(height − 1) & 0xFF`, `(height − 1) >> 8`, `0x00` — gate lines.
5. `0x11` `0x03` — data entry X increment / Y increment (the POR value; *vendor* code also uses it).
6. `0x44` with `0x00`, `(width / 8) − 1`; `0x45` with `0x00 0x00`, `(height − 1)` low/high — window covering the full panel, row 0 at RAM Y 0.
7. `0x3C` `0x05` — border follows LUT1 (white) (`A[7:6] = 00` GS transition, `A[2] = 1` follow LUT, `A[1:0] = 01` LUT1; the *vendor* value, decoded from the `0x3C` table).
8. `0x18` `0x80` — **select the internal temperature sensor** (the POR selects the external I²C sensor; without one the sensed temperature is invalid and no waveform set may match).
9. `0x0C` `0x8B 0x9C 0x96 0x0F` — booster soft start (POR values, flow §8.1 step 5).
10. Set the RAM counters (`0x4E` `0x00`, `0x4F` `0x00 0x00`), then wait BUSY low.

The RAM contents are undefined after power-up, so the first `show()` always writes **both** planes in full; `init` does not clear them.

An update (`show()` / `refresh()`):

1. Set the RAM counters: `0x4E` `0x00`, `0x4F` `0x00 0x00`.
2. `0x24` + B/W plane bytes; then `0x4E`/`0x4F` again and `0x26` + red plane bytes (zeros streamed when no red pixel was ever drawn).
3. `0x22` with the update mode (`0xF7` 3-colour, `0xFF` B/W), then `0x20`; **wait BUSY low**.

Deep sleep: `0x10` `0x01` (RAM retained) or `0x03` (RAM lost). **Wake = hardware reset + the Initialization Sequence** (the framebuffer in the driver is unaffected, so the next `show()` redraws it).

## Implementation Stages

### Minimal

Goal: a 200 × 200 (or smaller) black/white/red e-paper panel you can draw pixels on out of the box.

| Operation | Parameters | Returns | Notes |
|-----------|------------|---------|-------|
| `init` | `connection` (`DisplayConnection`, `SIMPLEX`, RES and BUSY wired), `width: int = 200`, `height: int = 200`, `busy_timeout_ms: int \| None = 30000` | — | Allocates the B/W framebuffer, runs the Initialization Sequence (including the BUSY waits), leaves the display unchanged until `show()`. `width` a multiple of 8 and ≤ 200, `height` ≤ 200 |
| `clear` | `color: int = WHITE` | — | Fill the framebuffer (`WHITE`, `BLACK` or `RED`); call `show` to update the panel |
| `set_pixel` | `x: int`, `y: int`, `color: int = BLACK` | — | Framebuffer only (0 ≤ x < width, 0 ≤ y < height); out-of-range ignored. `RED` allocates the red plane on first use |
| `show` | — | — | Write the framebuffer to RAM and run a full display update; blocks until BUSY is low |
| `sleep` | — | — | Deep sleep 1 (`0x10 0x01`); only a hardware reset (`wake`) restores communication |

**Constants:** `BLACK = 0`, `WHITE = 1`, `RED = 2`.

**Sensible defaults:** 200 × 200, 3-colour update (`0x22` = `0xF7`), internal temperature sensor, X+/Y+ data entry with the full-panel window, border `0x05`, soft start POR, SPI Mode 0 at 4 MHz, BUSY timeout 30 s. The B/W framebuffer is `width / 8 × height` bytes (5 000 bytes at 200 × 200), initialised to white; the red plane (same size, initialised to 0) is allocated only when the first red pixel or `clear(RED)` is requested. On the black/white-only 1.54inch V2 module the red plane stays unused; if its OTP lacks three-colour waveform sets use `MODE_BW` (confirm on hardware).

## Data Conversion

```
bytes_per_row = width // 8
index         = y * bytes_per_row + (x // 8)
bit           = 7 - (x % 8)                                  # bit 7 = leftmost pixel (assumed)

colour -> planes:  BLACK : bw=0 red=0     WHITE : bw=1 red=0     RED : bw=0 red=1
set pixel (BW) :  fb_bw[index] |=  (1 << bit)  for WHITE;   &= ~(1 << bit)  for BLACK / RED
set pixel (red):  fb_red[index] |= (1 << bit)  for RED;     &= ~(1 << bit)  otherwise

RAM Y of framebuffer row y (X+ / Y+ data entry, window YStart = 0):
    first row written (y = 0) -> RAM Y = 0; last row -> RAM Y = height - 1
window        : X = 0 .. width/8 - 1 ;  Y = 0 .. height-1

VGH  (0x03)   : code = 3 + round((volts - 10.0) / 0.5)      10.0 .. 20.0 V   (0x03 = 10 V, 0x17 = 20 V; POR 0x00 = 20 V)
VSH1 / VSH2 (0x04 A / B):
                volts 2.4 ..  8.8 : code = 0x8E + round((volts - 2.4) / 0.1)   (bit 7 set, 0x8E .. 0xCE)
                volts 9.0 .. 17.0 : code = 0x23 + round((volts - 9.0) / 0.2)   (0x23 = 9.0 V, 0x4B = 17.0 V)
                (8.8 < volts < 9.0 is not representable; round to the nearer end)
VSL  (0x04 C) : code = 0x0A + 2 * round((-5.0 - volts) / 0.5)    -5.0 .. -17.0 V  (0x0A = -5 V, 0x3A = -17 V)
VCOM (0x2C)   : code = 0x08 + 4 * round((-0.2 - volts) / 0.1)    -0.2 .. -3.0 V   (0x08 = -0.2 V, 0x78 = -3.0 V)
temperature   : v = round(celsius * 16) & 0xFFF                  (12-bit two's complement, 1/16 degC)
                bytes = (v >> 4) & 0xFF, (v & 0x0F) << 4
```

The voltage-to-code mappings are regular fits of the datasheet tables (0x03 command table: 0.5 V/step; VSH1/VSH2 0.1 V/step with bit 7 set up to 8.8 V, 0.2 V/step from 9.0 V; VSL 0.5 V per 2 codes; VCOM 0.1 V per 4 codes). The VGH table in the datasheet repeats two rows (`07h`/`08h`) in the 12–12.5 V range; the regular fit above is used. These differ from the SSD1683 tables (VSH1 low end `0x21 = 8.6 V` there), so the two drivers must not share them.

### Demo flow

An inject node every 10 minutes drives a function node that builds a status card (red header bar, black border, bar chart from a counter) and sends `{ clear: "white" }`, the draw messages and `{ show: true }`, followed by `{ sleep: true }` after the `{ updated: true }` reply; a second inject sends `{ wake: true }` ahead of each redraw.

## Timing Constraints

- **Power-up:** wait ≥ 10 ms after VCI before the first reset (datasheet flow §8.1).
- **Reset:** the datasheet gives no numeric reset pulse width or recovery time; the driver holds RES# low ≥ 10 ms and waits ≥ 10 ms before the first command. BUSY is high during reset; wait for it to go low.
- **Software reset:** after `0x12`, BUSY high until done; wait low, then ≥ 10 ms (flow §8.1).
- **Display update:** BUSY high for the whole `0x20` sequence; **the datasheet states neither a typical nor a maximum duration** (panel-dependent, see Overview) — the driver's default timeout is 30 s. The update must not be interrupted.
- **Commands that drive BUSY high** (datasheet command table, "BUSY pad will output high during operation"): `0x08` program initial code (OTP), `0x10` deep sleep (BUSY then **stays high** until a hardware reset), `0x12` software reset, `0x14` HV-ready detection, `0x15` VCI detection, `0x1C` write command to external temperature sensor, `0x20` master activation, `0x28` VCOM sense, `0x2A` program VCOM OTP, `0x30` program WS OTP, `0x31` load WS OTP, `0x34` CRC calculation, `0x36` program OTP selection, `0x46`/`0x47` auto-write RAM. No BUSY is stated for the other commands (including `0x18`, `0x1A`, `0x22`, `0x24`, `0x26`, `0x32`); the driver waits after each of the listed ones it uses.
- **SPI (write):** the datasheet states fSCL ≤ 20 MHz but gives every other SPI timing value (and the read-mode ones) as **TBD**; the driver assumes the SSD1680 values — fSCL ≤ 20 MHz, CS# setup ≥ 60 ns, CS# hold ≥ 65 ns, CS# high between transfers ≥ 100 ns, SCL high/low ≥ 25 ns, data setup ≥ 10 ns / hold ≥ 40 ns (VDDIO 2.2–3.7 V). Read mode is limited to 2.5 MHz (unused).
- **Deep sleep exit:** hardware reset, then the full Initialization Sequence. Deep sleep current: 1 µA typ (mode 1) / 0.7 µA typ (mode 2), maxima TBD.
- **Operating range:** chip −40 … +85 °C; the OTP waveform sets cover a panel-specific temperature range (waveform lookup is by the sensed temperature). Panel makers advise refreshing at least every 24 hours and storing with a white image (module datasheet advice, unverified for these panels).
- **Conformance:** the datasheet defines no maximum for BUSY, so no timing check has a bound to compare against; `specs/display/ssd1681_timing.conf` defines no checks (see its header).

## Implementation Notes

- **`DisplayConnection` owns D/C#, RES#, BUSY and CS#:** the driver never touches a pin; it uses `send_command(cmd, data, hold_cs=True)`, `send_data`, `reset` and `wait_busy` from `specs/transport_display.md`. The `hold_cs` option does not exist yet — implementing it is part of this chip's work (see "DisplayConnection fit and required extension").
- **BUSY is a level read:** `wait_busy` reads BUSY through the `InputPin` level read of `specs/feature_inputpin_level_read.md`; the driver passes `busy_active_high = True`.
- **Temperature sensor:** `0x18` POR selects the **external** I²C sensor. On a module with nothing on TSCL/TSDA the driver selects the **internal** sensor in the Initialization Sequence; omitting this is a likely cause of "no update" on bare-controller bring-up.
- **3-colour vs B/W update (`0x22`):** the chip's POR is `0xFF`. The driver defaults to **`0xF7`**, the mode that uses the red plane and matches an OTP holding three-colour waveform sets; with an all-zero red plane the result is a pure black/white picture. On a black/white-only panel (OTP without three-colour sets) use `MODE_BW`. Which of the two OTP sets a given module carries is not in the datasheet — **confirm on hardware**, and note that the Mode 1 = three-colour mapping is inferred.
- **Orientation:** the driver writes with X increment / **Y increment** (the POR `0x11 = 0x03`), framebuffer row 0 at RAM Y 0. Whether row 0 is the physical top edge depends on how the panel is wired; `set_flip` corrects either case. This differs from `specs/display/ssd1683.md`, whose reference flow decrements Y. Confirm on hardware.
- **Panel sizes:** 200 is a multiple of 8, so the 1.54inch panels need no padding; the first source line is assumed to be column 0 (unconfirmed — the SSD1680's `0x21` source-output-mode bit does not exist here).
- **Auto-fill (`0x46`/`0x47`):** not used by the driver (a full `show()` writes both planes anyway). For reference, the step table gives height and width codes `101`, `110` and `111` all as 200 (SSD1680: 256/296 and 176): a solid 200 × 200 fill is `A[6:4] = 101`, `A[2:0] = 101`, i.e. `0x47 0xD5` (B/W all 1 = white) and `0x46 0x55` (red all 0). Inferred from the table, not a datasheet example; reachable through `send_command`.
- **LUT size:** 153 bytes (`0x32`), same as the SSD1680 (the SSD1683 takes 227). The 159-byte waveform setting also carries EOPT, VGH, VSH1/VSH2/VSL and VCOM (datasheet §6.7); `write_lut` accepts either length.
- **No partial *refresh* waveform:** the datasheet advertises "support display partial update" but gives no partial LUT — it is waveform data supplied by the panel maker. `write_lut` takes a caller-supplied waveform; `show_region` limits only which RAM is rewritten. A partial-refresh helper would need a vendor LUT and is **not** specified. RAM ping-pong (`0x37` byte F bit 6, Display Mode 2 only) is likewise not exposed.
- **Window byte units:** the X window and counter are in bytes (8 pixels). `show_region` widens x and w to multiples of 8 and must not exceed the panel width.
- **Red RAM must be defined:** after power-up the red RAM is undefined; in 3-colour mode stale red data would show as red pixels. `show` always writes the red plane.
- **Memory:** the B/W framebuffer is 5 000 bytes at 200 × 200 and the red plane another 5 000, heap-allocated at runtime (the red one lazily), so the code builds everywhere; boards with ≤ 8 KB RAM (Arduino AVR Mega) can run the full size only with the red plane unused — otherwise use a smaller `width`/`height`. Drivers must fail with a clear error (not corrupt memory) when allocation fails.
- **Blocking update:** `show()` blocks for the full refresh. On MicroPython and CircuitPython this stalls the interpreter for seconds; examples must say so. A non-blocking variant is not specified.
- **SKU mapping:** the issue lists Waveshare 1.54inch e-Paper V2 and 1.54inch e-Paper (B/C) V2 as SSD1681 modules; both are unverified (no panel specification committed). Check each against its panel specification before claiming support. The plain 1.54inch V2 is a black/white panel.
- **Sibling chips:** the SSD1680 (176 × 296, issue #697) is the reference sibling; it adds `0x0F`, the `0x21` source-output-mode bit and cascade mode. A shared implementation helper is allowed, but each chip keeps its own class and spec.
- **Not covered:** 3-wire SPI, OTP programming (`0x08`, `0x09`, `0x2A`, `0x30`, `0x36`–`0x39`), VCOM sensing (`0x28`, `0x29`), CRC (`0x34`, `0x35`), VCI/HV-ready detection (`0x14`, `0x15`; these need the status read, which the write-only wiring cannot provide), read-RAM (`0x27`, `0x41`) and the external-sensor I²C pass-through (`0x1C`).
- **Datasheet status:** "Product Preview", Rev 0.13. Several values are **TBD** (SPI timing, sleep currents) and the window POR values were not updated from the SSD1680 datasheet; the VGH table has duplicate rows; there is no reset timing or refresh duration.

## Sigrok Decoder

Decoder id `ssd1681`, input **`display_spi`**: it stacks on the connection decoder `Display-SPI` (`sigrok/display_spi/`, see `specs/transport_display.md`), which frames the SPI (4-wire or 3-wire) and reports CS#, RES# and the raw BUSY level as `BYTE` / `CS` / `BUSY` / `RESET` / `IDLE` packets. The BUSY polarity is chip-level: this decoder treats BUSY **high** as busy and emits the `busy_start` / `busy_done` timing markers. Its only option is `warn_cs_split` (default `yes`). After a read command (`0x0A`, `0x1B`, `0x27`, `0x2D`, `0x2E`, `0x2F`, `0x35`) the response bytes are taken from the connection decoder's DOUT value when that channel is wired, otherwise from the shared DIN line, and are meaningful only with half-duplex wiring. Typical stack: `-P display_spi:clk=0:mosi=1:cs=2:dc=3:busy=4:res=5,ssd1681`.

Annotation rows (taxonomy order): **Data** — one annotation per command spanning the command byte and its parameter/data bytes, with decoded arguments (gate lines and GD/SM/TB, VGH/VSH1/VSH2/VSL/VCOM in volts, soft-start bytes, deep-sleep mode, data-entry mode, temperature-sensor select, temperature in °C, update-control-1 options, update sequence name for `0x22`, RAM plane with byte count and the window size, LUT byte count, X/Y window and counters, auto-fill step size); **Status** — `Busy for <duration>` spans (BUSY high) and RES# low spans; **Warnings** — unknown command, wrong parameter count (`0x32` expects 153 bytes), a command sent while BUSY is high, a RAM write larger than the window set by `0x44`/`0x45`, a data byte without a preceding command, a CS# release after a non-multiple of 8 (9) bits, and a **CS# release between a command and its parameters**.

Warning strings carry a short tag (`NOBUSY` — a command from the list under Timing Constraints for which BUSY was not already high at the CS# rising edge that completes it, skipped when BUSY is not probed; `BUSY-DROP` — BUSY went low in deep sleep, where the datasheet keeps it high; `CS-SPLIT`, `BUSY!`, `PARAM?`, `CMD?`, `WIN?`, `NOCMD`, `BITS?`). `OUTPUT_PYTHON` packets: `('COMMAND', (command_byte, parameter_bytes))`.
