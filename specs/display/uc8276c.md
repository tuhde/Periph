# Chip Spec: UC8276C

**Manufacturer:** UltraChip  
**Datasheet:** `datasheets/display/UC8276.pdf` (UC8276c_A0.6, "for TFT Module Use only", ES specification, 2019-11-19). Panel datasheet: `datasheets/display/uc8276c_4.2inch-e-paper-b.pdf` (Waveshare 4.2inch e-Paper (B), product specification rev 1.0, 2020-11-01)  
**Category:** `display`  
**Transports:** SPI (4-wire; write-only or half-duplex, via `DisplayConnection`)

## Overview

The UC8276C is an all-in-one driver with timing controller for **white/black/red** electrophoretic (EPD) panels of up to **400 source × 300 gate** outputs: two bit-planes of display RAM (400 × 300 bits each), an on-chip oscillator/PLL, DC-DC booster and regulators for the gate, source and VCOM voltages (VGH/VGL ±10…±20 V, VSH/VSL ±2.4…±15 V), an on-chip temperature sensor (−25…+50 °C, 8 bit) with an I²C master for an external LM75, a 6 KB OTP holding twelve temperature-dependent waveform sets (LUTs), and a low-power detector. It drives the 400 × 300 B/W/R panel of the Waveshare **4.2inch e-Paper (B)**, the reference hardware for this spec.

The chip differs from an OLED/LCD in ways that shape the driver: a refresh is a long full-panel waveform (no duration is stated in either document, see Timing Constraints), the picture is **bistable**, and the display must be explicitly **powered on (PON) → refreshed (DRF) → powered off (POF)** around every update, with BUSY_N waited on after each step. The driver keeps a framebuffer and sends it on `show()`.

The chip has **two pixel modes**: *KWR* (black/white/red, power-on default) and *KW* (black/white with NEW/OLD planes). This spec makes KWR the primary mode; KW is exposed in Full only (see Implementation Notes).

This spec covers **4-wire SPI**, full-panel updates with the **waveform loaded from OTP**, a user-supplied LUT, a partial-window write, and (with a half-duplex wire mode) the read commands. Partial *refresh* waveforms are not in the datasheets and are not specified.

## Transport Configuration

### SPI (4-wire)
- **Mode:** CPOL=0 CPHA=0 (Mode 0) — "data are written in order from MSB at the clock rising edge" (host interfaces section); the read figure shows SDA changing after the falling edge
- **Max clock:** write cycle ≥ 100 ns (SCL high/low ≥ 35 ns each) → **10 MHz**. The feature list's "clock rate up to 20 MHz" contradicts the AC table; the AC table is used. Driver default 4 MHz. **Read** cycle ≥ **350 ns** (high/low ≥ 175 ns) per the chip datasheet → **≤ 2.5 MHz**; the panel datasheet states 150 ns, the stricter chip value is used
- **Bit order:** MSB first
- **CS active:** low (CSB). The serial counter resets on the CSB rising edge; the datasheet *recommends* CSB high after every 8 bits and its figures show **one CSB window per byte** (command, each parameter, each read byte). A command is processed on the stop condition
- **Framing:** a byte stream; the **DC pin** is sampled per 8-bit group: low → command, high → parameter/data/read. Bytes are sent verbatim — no register address, no read/write bit
- **Bus selection:** pin **BS** high = 3-wire (9-bit frames, **power-on default** per the pin description), low = 4-wire. The driver requires **4-wire**; the BS strap is board-specific and not covered by the provided documents. 3-wire framing is **not supported**
- **Bidirectional SDA:** the chip's SDA pin is an I/O. Read commands (listed under Command Set) clock data out on SDA after the command byte, with DC high and CSB low. Whether the board exposes DOUT depends on the wiring → `DisplayConnection` wire mode (`SIMPLEX` / `HALF_DUPLEX_HW` / `HALF_DUPLEX_PIN`, see `specs/transport_display.md`). `SIMPLEX` is sufficient for everything in Minimal
- **Register addressing:** none — takes an `DisplayConnection`, not a `RegisterConnection`

## Command Set

All commands are one byte sent with DC low; parameters follow with DC high. POR values in brackets. **Defaults can be changed by OTP** (see "Command default setting" in the datasheet), so a panel may not power up with exactly these values; the driver writes every setting it depends on. **Two documents describe this chip and they disagree in several register layouts** (PWR, PLL, VV/VDCS, LPSEL, REV, and which commands exist). The table gives the **panel datasheet** layout where they differ — it describes the product that ships and its power-on values — and notes the chip datasheet's reading; confirm each on hardware before relying on it. Only commands the driver uses or exposes are listed.

### BUSY_N flag

All commands except `REV`, `FLG`, `VV` and read cycles are **ignored while a refresh (DRF/DSP) is running**. Commands that drive BUSY_N low: `POF`, `PON`, `PMES`, `DSLP`, `AUTO`, `DSP`, `DRF`, `TSC`, `LPD`, `AMV`, `APG`, and the soft-reset bit (≥ 50 µs). Data/LUT/setting commands raise no BUSY_N.

### Power-on / reset defaults

PSR `0x0F` (+ `0x0D` in the chip datasheet; 400 × 300, KWR, LUT from OTP, scan up, shift right, booster on), PLL `0x3C` (50 Hz), CDI `0xD7`, TCON `0x22`, TSE internal with offset 0, soft-start `0x17 0x17 0x17`, LPSEL `0x03`. The display RAM contents are **undefined** after power-up.

## Display RAM

Two planes, each **400 × 300 bits** (50 bytes × 300 rows); `DTM1` writes plane 1 (B/W) and `DTM2` plane 2 (red). A transfer is a plain stream written from the first pixel to the last: the chip has no address counter or window commands for a full frame. Each byte carries 8 horizontal pixels with **D7 = first (leftmost) pixel**; a frame is `width/8 × height` bytes per plane, rows in gate-scan order (`G0` first at PSR UD = 1, `S0` first at SHL = 1).

In KWR mode with the default CDI (`DDX = 01`):

| Red bit | B/W bit | Colour (LUT) |
|---------|---------|--------------|
| 0 | 0 | black (LUTK) |
| 0 | 1 | white (LUTW) |
| 1 | 0 | red (LUTR) |
| 1 | 1 | red (LUTR) |

Red wins. In KW mode, `DTM1` = OLD and `DTM2` = NEW, and the LUT is selected by the (NEW, OLD) pair.

**The polarity depends on CDI.DDX, and the OTP may change its power-on value.** `DDX[0]` selects the B/W polarity and `DDX[1]` the red polarity: with `DDX[1] = 1` the red plane is inverted (0 = red, 1 = not red). The captured init sequence (below) never writes CDI yet clears the panel by sending `0xFF` in **both** planes. That is a white screen only if the panel's OTP default has `DDX[1] = 1`; with the datasheet's `DDX = 01` it would be an all-red screen. The driver therefore writes CDI (`0x50`) explicitly instead of relying on the OTP default, and treats "both planes 0xFF = white" as an observation to confirm on the panel, not a guarantee.

## Initialization Sequence

Derived from the datasheet's power-management notes and command descriptions; neither provided document contains reference code. Confirm on hardware.

1. Apply VDD/VDDIO; BS strapped low (4-wire).
2. **Hardware reset:** `RST_N` low ≥ 50 µs, then high; wait **> 1 ms** (commands sent earlier are ignored), then BUSY_N high.
3. `PSR` `0x0F` (KWR, LUT from OTP, UD/SHL default, booster on). Add the 2nd byte `0x0D` only if the OTP defaults are suspected to differ.
4. `TRES` with `(width, height)` when not 400 × 300 (`0x01 0x90 0x01 0x2C` for 400 × 300; redundant with the PSR RES bits but explicit).
5. `CDI` `0xD7` (VBD = 11, DDX = 01, CDI = 10 hsync): written explicitly so the framebuffer polarity (B/W 1 = white, red 1 = red) does not depend on the OTP default. Leave `PWR`, `BTST`, `PLL`, `TCON` at their power-on/OTP values (see Implementation Notes).
6. No RAM clear is required: `show()` always writes both planes completely.

An update (`show()`):

1. `DTM1` + `ceil(width/8) × height` B/W bytes; `DTM2` + the same number of red bytes (zeros when no red pixel was drawn).
2. `PON`; wait BUSY_N high.
3. `DRF`; wait ≥ 200 µs, then wait BUSY_N high (refresh, no stated duration).
4. `POF`; wait BUSY_N high.

`AUTO` `0xA5` performs steps 2–4 in one command; `AUTO` `0xA7` also enters deep sleep.

### Observed vendor sequence (logic-analyser capture)

`sigrok/tests/uc8276c/Init sequence.sr` (init + clear screen of a UC8276C panel, 3 MHz sampling) shows this exact order, decoded with `display_spi` + `uc8276c` and cross-checked against an independent decode of the raw samples:

| Step | Bus | BUSY_N |
|------|-----|--------|
| Power-up / hardware reset | RES# low 5.00 ms | low from the start of the capture until 0.26 ms after RES# is released (33.69 ms from capture start) |
| ~200 ms idle | — | high |
| `BTST` `0x06` `17 17 17` | 4 bytes | high |
| `PON` `0x04` | 1 byte | falls on the last SCK rising edge of the command, rises **36.18 ms** later |
| `PSR` `0x00` `0F` | 2 bytes | high |
| `DTM1` `0x10` + 15 000 × `0xFF` | 15 001 bytes | high |
| `DTM2` `0x13` + 15 000 × `0xFF` | 15 001 bytes | high |
| `DRF` `0x12` | 1 byte | falls on the last SCK rising edge, rises **16.83 s** later |

Observations: `PON` comes **before** `PSR` and the data (the "write planes, then PON" order above is not the vendor's); no `PWR`, `TRES`, `PLL` or `CDI` is sent, so the OTP/power-on defaults (including the DDX polarity) are in force; no `POF` or `DSLP` follows within the capture; SCK runs at about 1 MHz and **every byte is its own CS# window** (30 010 windows, CS# high about 0.7 µs between bytes), including the 30 000 pixel bytes; BUSY_N falls on the same sample as the final SCK rising edge, three samples (1 µs) before CS# rises. The 3 MHz sample rate gives only 3–4 samples per SCK period, so the decode relies on every rising edge being sampled; use ≥ 10 MHz for new captures.

Deep sleep: `POF`, then `DSLP` `0xA5` (or `AUTO 0xA7`). **Wake = hardware reset + the Initialization Sequence**; the driver's framebuffer is unaffected. In deep sleep tie control signals to 0 V and keep light off the bare die.

## Implementation Stages

### Minimal

Goal: a 400 × 300 black/white/red e-paper panel you can draw pixels on out of the box.

| Operation | Parameters | Returns | Notes |
|-----------|------------|---------|-------|
| `init` | `connection` (`DisplayConnection`), `width: int = 400`, `height: int = 300`, `busy_timeout_ms: int \| None = 30000` | — | Allocates the B/W framebuffer, runs the Initialization Sequence (including the BUSY_N wait), leaves the panel unchanged until `show()`. `width` a multiple of 8 and ≤ 400, `height` ≤ 300 |
| `clear` | `color: int = WHITE` | — | Fill the framebuffer (`WHITE`, `BLACK` or `RED`) |
| `set_pixel` | `x: int`, `y: int`, `color: int = BLACK` | — | Framebuffer only; out-of-range ignored. `RED` allocates the red plane on first use |
| `show` | — | — | Write both planes, `PON` → `DRF` → `POF`; blocks until BUSY_N is high again |
| `sleep` | — | — | `POF` (if on) then `DSLP`; only `wake()` / a hardware reset restores communication |

**Constants:** `BLACK = 0`, `WHITE = 1`, `RED = 2`.

**Sensible defaults:** 400 × 300 KWR, waveform from OTP (`PSR.REG = 0`), internal temperature sensor, power setting / soft start / PLL / CDI at power-on values, SPI Mode 0 at 4 MHz, BUSY timeout 30 s (not derived from the datasheet; measure the real refresh and adjust). The framebuffer is `width / 8 × height` bytes (15 000 at 400 × 300), initialised to white; the red plane (same size, initialised to 0) is optional. **Buffer ownership:** languages with a no-heap driver rule (C++) take caller-supplied buffers (`bw`, optional `red`) and the red plane is simply absent when none is given (RED is then drawn as BLACK and the plane is sent as zeros); the other languages allocate the red plane lazily on the first red pixel or `clear(RED)`. Works with `SIMPLEX` wiring.

## Data Conversion

```
bytes_per_row = width // 8
index         = y * bytes_per_row + (x // 8)
bit           = 7 - (x % 8)                      # D7 = first (left) pixel

colour -> planes (DDX = 01, KWR):  BLACK: bw=0 red=0   WHITE: bw=1 red=0   RED: bw=0 red=1
set pixel (BW) :  fb_bw[index]  |=  (1 << bit) for WHITE;  &= ~(1 << bit) for BLACK / RED
set pixel (red):  fb_red[index] |=  (1 << bit) for RED;    &= ~(1 << bit) otherwise

TRES/GSST:  b0 = (value >> 8) & 1 ; b1 = value & 0xF8      # horizontal (multiple of 8)

VCOM_DC (VDCS, panel layout):          code = round((-0.10 - volts) / 0.05)  -0.10 V (0) .. -3.25 V (0x3F)
VV (read, panel layout):               volts = -0.10 - 0.05 * VV
```

The voltage-to-code mappings are regular fits of the **panel** datasheet tables (0.2 V per code from 2.4 V; VGH/VGL 1 V per level; VCOM 0.05 V per code with code 0 = −0.10 V). The chip datasheet's mappings differ (VSH/VSL up to ±15 V in 0x3F steps, VGH/VGL 20…10 V, VCOM 7 bits at 0.1 V, `FRS[4:0]` frame rates) and are not used.

## Timing Constraints

- **Reset:** RST_N low ≥ **50 µs**; after RST_N rises wait **> 1 ms** before the first command (any command in that window is ignored). Soft reset (PSR RST_N = 0): ≥ 50 µs, BUSY_N low meanwhile.
- **Refresh:** after `DRF`, BUSY_N goes low and the panel refreshes. **No duration or maximum is stated in either document.** Measured on the reference panel (full 400 × 300 B/W/R refresh after the vendor init, see the captured sequence): **16.83 s**. The driver's 30 s default timeout is about 1.8× that; it is a driver choice, not a datasheet value. The update must not be interrupted. Other measured BUSY_N times from the same capture: `PON` 36.18 ms, power-up/reset busy 33.69 ms from capture start (0.26 ms after RES# is released).
- **First FLG read:** BUSY_N falling → first `FLG` read must be **> 200 µs** (chip and panel datasheets).
- **Commands that drive BUSY_N low** (chip datasheet "BUSY_N Signal" table, flag column): `POF`, `PON`, `PMES`, `DSLP`, `AUTO`, `DSP` (only when a whole frame was received), `DRF`, `TSC`, `LPD`, `AMV` (when AMVE = 1), `APG`, and the PSR soft-reset bit (RST_N = 0, ≥ 50 µs). Everything else (PSR, PWR, PFS, BTST, DTM1/2, LUTs, PLL, TSE/TSW/TSR, CDI, TCON, TRES, GSST, REV, FLG, VV, VDCS, PTL/PTIN/PTOUT, CCSET, PWS, LVSEL, TSSET) raises no BUSY_N. The panel datasheet confirms only `PON`, `DSP`, `DRF`, `APG` and temperature-sensor communication; the others are chip-datasheet-only. The driver waits BUSY_N high after each of PON, DRF, POF.
- **SPI (write):** tSCYCW ≥ 100 ns, SCL high/low ≥ 35 ns, CSB setup ≥ 60 ns, CSB hold ≥ 65 ns, DC setup/hold ≥ 30 ns, data setup/hold ≥ 30 ns.
- **SPI (read):** tSCYCR ≥ 350 ns (chip) / 150 ns (panel), SCL high/low ≥ 175 / 60 ns, SDA access time ≤ 250 ns (chip) / 10 ns (panel), output disable ≥ 15 ns.
- **Deep sleep exit:** hardware reset, then the full Initialization Sequence.
- **Refresh interval:** the panel datasheet advises refreshing at least every 24 hours (ghosting / image sticking) and storing/shipping with a white image. Operating temperature 0–40 °C (panel), −30–85 °C (chip).
- **Conformance:** no bound exists to compare against (see `specs/display/uc8276c_timing.conf`).

## Implementation Notes

- **DisplayConnection owns D/C, RES, BUSY and CS.** The driver never touches them; it calls `send_command(cmd, data)`, `send_data`, `read_data`, `reset`, `wait_busy` from `specs/transport_display.md`. `read_data(n)` is `n` one-byte CS windows with DC high, matching the 4-wire read figure.
- **BUSY_N low = busy** in both the chip datasheet and the panel datasheet; unlike the SSD1683 module note there is no inversion to work around. The existing decoder and this spec agree.
- **CS per byte vs. streamed data:** the datasheet only *recommends* CSB high every 8 bits and shows per-byte windows. A full frame is 30 000 bytes; the driver streams `send_data` blocks under one CS assertion. **Confirm on hardware** that streaming works; the fallback is per-byte `send_data` calls (slow, but within the documented timing).
- **Register layouts and defaults differ between the two documents and OTP may change them:** `PWR` (panel: VDH/VDL `0x26` = ±10 V, VGH/VGL ±16 V, VCOM_HV; chip: VSH/VSL `0x3F` = ±15 V, VGH/VGL ±20 V, VCOM_SLEW), `PLL` (M/N `0x3C` vs. `FRS` `0x09`), `VV`/`VDCS` (6 bit × 0.05 V vs. 7 bit × 0.1 V), `LPSEL` vs. `LVSEL`, `REV` (1 vs. 5 bytes), and `AUTO`, the LUT commands, `GSST`, `PBC` and `CRC` exist only in the chip datasheet. The spec follows the panel datasheet; verify on hardware. The panel documents that "Vcom value will be OTP before in factory or present on the label sticker". The driver therefore does **not** write `PWR`, `VDCS` or `BTST` by default; a wrong `PWR` can drive the panel outside its rating. `set_power` / `set_vcom_dc` are for users who know their panel's values.
- **DSP vs. DRF:** the datasheet says that after DTM1/DSP "when data_flag = 1, the refreshing of panel starts", and `DRF` also refreshes. The driver sends `DRF` explicitly and does not send `DSP`; whether `DSP` alone starts a refresh is unconfirmed — verify on hardware to avoid a double refresh if `DSP` is ever added.
- **Refresh requires power on:** `DRF` must be preceded by `PON` (the AUTO sequence is `PON → DRF → POF`); the driver always wraps `DRF` in `PON`/`POF`.
- **Temperature:** the internal sensor is the POR choice and is read once automatically at `PON`; the OTP picks the waveform set from it (12 ranges, boundaries in OTP). "If less than 10 ranges are used the last TBx must be 0x7F". The driver does not expose forced temperature (`TSSET`, cascade only).
- **Pixel polarity** is from the DDX table at the datasheet's default CDI `0xD7`; the OTP may override that default (see Display RAM and the captured sequence), `set_interval(polarity=...)` changes it, and the framebuffer-to-plane mapping above assumes `DDX = 01` *as written by the driver*. Changing `DDX` is the caller's responsibility.
- **KW mode** needs the panel's OTP to contain the KW LUT set (five LUTs per temperature range); unconfirmed for the reference panel, so `MODE_KW` and `write_lut` are untested paths.
- **No partial *refresh* waveform:** `PTL`/`PTIN` restrict gate scanning to a window (`PT_SCAN = 0`), but the waveform is the OTP full waveform; a fast partial update needs a vendor LUT that neither document provides. `show_region` is therefore a RAM-transfer saving, not a flicker-free update.
- **Orientation:** with the power-on `UD = 1`, `SHL = 1`, row 0 is `G0` and column 0 is `S0`; whether that is the physical top-left depends on the panel's FPC; `set_flip` corrects either case. Confirm on hardware.
- **Hardware identification:** the provided panel PDF is the Waveshare "4.2inch e-Paper (B)" product specification (rev 1.0, 2020-11-01) with a UC8276C controller. The existing decoder text names the module "V2 (SKU 13379)", which `specs/display/ssd1683.md` assigns to an **SSD1683** module — the SKU/revision mapping is unresolved; do not infer the controller from the SKU.
- **Memory:** 15 000 bytes per plane at 400 × 300; boards with ≤ 8 KB RAM cannot run the full case. In C++ the buffers are the caller's (no heap): the AVR test runs a 64 × 64 window (`TRES`), the full size elsewhere. An undersized or null buffer, a width that is not a multiple of 8, or a size over 400 × 300 makes `valid()` false instead of corrupting memory.
- **Blocking update:** `show()` blocks for the whole refresh; on MicroPython/CircuitPython this stalls the interpreter and the examples must say so.
- **Verified on hardware** (NUCLEO-F411RE + Waveshare 4.2inch e-Paper (B) on the Waveshare e-Paper Shield, SPI1 0.78 MHz, 2026-10-15): the captured vendor sequence and the driver both refresh the panel; BUSY_N asserts on the rising CS# edge of the command and `PON` takes about 37 ms, `DRF` 17.1 s (a full `show()` is about 17.5 s including the 0.35 s plane transfer); the whole 15 000-byte plane in one CS# window works (no per-byte CS# needed); the red plane, `show_region` and the drawing helpers produce the expected picture; `AUTO` does not (see `refresh_auto`). A frame drawn exactly on the panel edge can be hidden by the bezel: examples inset it.
- **Datasheet status:** UC8276c_A0.6 is an engineering-sample specification "for TFT module use only" marked confidential; the panel datasheet is rev 1.0. Several statements conflict (20 MHz vs. 100 ns cycle, read access time 250 ns vs. 10 ns, PWR layout) — the more conservative value is used.

## Sigrok Decoder

Decoder id `uc8276c`, input **`display_spi`**: it stacks on the connection decoder `Display-SPI` (`sigrok/display_spi/`, see `specs/transport_display.md`), which frames the SPI (4-wire or 3-wire) and reports CS#, RES# and the raw BUSY level as `BYTE` / `CS` / `BUSY` / `RESET` / `IDLE` packets. The BUSY polarity is chip-level: this decoder treats BUSY_N **low** as busy and emits the `busy_start` / `busy_done` timing markers. It has no channels or options of its own. After a read command the response byte is taken from the connection decoder's DOUT value when that channel is wired, otherwise from the shared DIN line. A CS# release between a command and its parameters is legal (the command is processed on the stop condition) and not warned. Typical stack: `-P display_spi:clk=0:mosi=1:cs=2:dc=3:busy=4:res=5,uc8276c`.

Annotation rows: **Data** — one annotation per command with decoded parameters (resolution, power settings in volts, partial window, PSR bit fields, deep-sleep check code, …); **Status** — `Busy for <duration>` spans (BUSY_N low) and RES# low spans; **Warnings** — a command from the BUSY list above for which BUSY_N was not already low at the CS# rising edge that completes it (the edge that ends the command byte, or its last parameter byte; `NOBUSY` for the panel-confirmed ones, hedged `NOBUSY?` for the chip-datasheet-only ones; skipped when BUSY is not probed), unknown command, wrong parameter count, command while BUSY_N is low (other than `FLG`), `FLG` within 200 µs of BUSY_N falling, pixel write larger than the frame, bad deep-sleep check code. Read commands (`FLG`, `TSC`, `REV`, `LPD`, `VV`, `DSP`, `PBC`, `CRC`, `ROTP`) show the decoded response bytes; SDA is driven by the chip there, so they are meaningful only when the probe sits on the shared DIN/DOUT line of a half-duplex wiring. Register layouts follow the panel datasheet (a `PWR` write that does not fit it is also shown in the chip-datasheet reading). A command with parameters, or an open-ended read, is reported when the next command arrives or on the connection decoder's `IDLE` packet (10 ms of bus idle), because libsigrokdecode has no end-of-capture hook.

`OUTPUT_PYTHON` packets: `('COMMAND', (command_byte, parameter_bytes))`.
