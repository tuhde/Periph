# Chip Spec: UC1611s

**Manufacturer:** UltraChip (module: Electronic Assembly / Display Visions **EA DOGXL240-7**, "DOG XL series", 240 × 128, 3.3 V)  
**Datasheet:** `datasheets/display/uc1611s.pdf` (UC1611s Revision A1.0, MP specifications), module `datasheets/display/DOGXL240-7.pdf` (EA DOGXL240-7, 03.2014)  
**Category:** `display`  
**Transports:** I²C and 4-wire SPI (S8) through `DisplayConnection` (phase 2). The chip also has 3-wire SPI (S9, 9-bit frames the byte-oriented `DisplayConnection` cannot send) and 4-/8-/16-bit parallel interfaces, which are not covered

## Overview

The UC1611s is a single-chip, ultra-low-power **160 COM × 256 SEG STN LCD controller-driver** with 160 × 256 × 4-bit display RAM, an on-chip 11x charge pump (the LCD supply `VLCD` is generated from a single 2.7–3.3 V rail), a software **potentiometer** (8 bit contrast), four temperature-compensation curves, programmable bias ratio, mux rate and line rate, hardware vertical scroll with a fixed-lines (soft icon) area, partial display, and four display-shade modes (16 / 8 / 4 shades and On/Off). In **On/Off mode with 1 bit per pixel** the RAM holds four complete black/white screens, which is the mode the DOG module uses.

The reference module is the **EA DOGXL240-7** (240 × 128 dots, STN/FSTN, 94 × 67 mm, 15 µm dot gap; variants `W` white/FSTN positive transflective, `B` blue/STN negative, `S` black/FSTN negative, `N` white reflective). It strobes **1/128 mux** (`CEN = 127`), uses SEG1–SEG240 (the module ties the controller's ID1 pin so only 240 columns are active), needs **no external LCD voltage** (only five small capacitors, see Pin Configuration) and a separate LED backlight (EA LED94x67-W/-A/-GR, **not driven by the chip**; external current source or series resistor required). Supply is **2.7–3.3 V only; never 5 V**.

This spec describes **1 bit per pixel B/W mode on the 240 × 128 module over I²C**. Grayscale modes (4 bit per pixel) are not exposed: the DOGXL240-7 is a 1-bit panel and the framebuffer is monochrome; the escape hatch `send_command` reaches them.

## Transport Configuration

### I²C
- **Interface select:** `BM1/BM0 = L/H` on the bare chip; on the module `BM0 = H` (pin 33) **and** `D13 = H` (pin 40) = 2-wire I²C. `CD` (pin 34) is unused in I²C mode and tied to VSS; `WR0/WR1` are tied low internally on the module
- **Address:** the 7-bit address is `0 1 1 1 A3 A2 CD` — the chip occupies **two** consecutive 7-bit addresses, the **command** address (`CD = 0`) and the **data** address (`CD = 1`). `A2` = module pin 36 (CS0), `A3` = module pin 35 (CS1); the pins must be wired to VDD/VSS, they cannot float:

  | A3 | A2 | Command (7-bit) | Data (7-bit) | 8-bit write cmd / read status / write data / read data |
  |----|----|-----------------|--------------|-----------------------------------------------|
  | VSS | VSS | `0x38` | `0x39` | `0x70` / `0x71` / `0x72` / `0x73` (application example) |
  | VSS | VDD | `0x3A` | `0x3B` | `0x74` / `0x75` / `0x76` / `0x77` |
  | VDD | VSS | `0x3C` | `0x3D` | `0x78` / `0x79` / `0x7A` / `0x7B` |
  | VDD | VDD | `0x3E` | `0x3F` | `0x7C` / `0x7D` / `0x7E` / `0x7F` |

  The driver therefore takes **two `I2CConnection`s on the same bus**: `command_connection` (`addr = 0x38 + 2 * n`) and `data_connection` (`addr = command address + 1`). This is the same two-connection pattern as chips with a bypass secondary device
- **Max clock:** the module datasheet allows 1.7 MHz; the chip's write cycle is ≥ 276 ns at 2.5–3.6 V (≈ 3.6 MHz) and reads are ≥ 580 ns. Driver default **400 kHz** (standard fast mode, the common bus rate). The pins SDA/SCK have 600–1000 Ω internal resistance, so the pull-ups must not be too strong (4.7 kΩ to 3.3 V recommended; the datasheet's application circuit shows 2–10 kΩ). **Do not pull up to 5 V**
- **NACKs:** the master NACKs the last byte of every read (end of read, per the datasheet). The chip itself was also seen to NACK a write or read **occasionally** (a few percent of the long data writes with the display on, and nearly every transfer for ~6 ms after leaving sleep or reset while the charge pump restarts); the cause is not documented (cable length and the weak internal pull-ups of the host make it worse). The driver must detect and retry (see Error handling)
- **Sequence:** `S` — header byte (address + `RW`) — `A` — payload bytes — `P`. The content type (command / data) and direction are fixed by the header for the whole transaction; changing either needs a new START with a new header (= another `write()` / `read()` on the other connection). **Every byte written to the command address is a command byte** (double-byte commands: the argument byte follows in the same transaction as a plain byte); **every byte written to the data address is display RAM data**
- **Write-chunking:** a platform that limits a transaction to 32 bytes (Arduino `Wire`) splits RAM data into 32-byte chunks; the RAM column pointer advances across transactions, so no address commands are needed between chunks
- **System Reset:** the transaction carrying the System Reset command (`0xE2`) **must be ended with STOP** before any further transaction (the driver sends it as its own `write`)
- **Read:** supported (unlike SPI). `read` on the command address returns the status bytes cyclically (`Status1, Status2, Status3, Status1, …`); `read` on the data address returns RAM data with the **first byte a dummy** that must be discarded, directly after every column/page address change. **Measured on an EA DOGXL240-7:** the status cycle position advances by *n + 1* per read transaction (the byte after the one the master NACKs is consumed too), so two consecutive 3-byte reads return `Status1 Status2 Status3` and then `Status2 Status3 Status1`; any other transaction in between (a command write, a data read) restarts the cycle at `Status1`. The driver therefore sends a NOP (`0xE3`) before every status read
- **Identity register:** none addressable by register; a plain read on the command address returns `Status3` with product code `0x1` in bits 7–4 (`0x10`/`0x11`), which the discovery registry cannot express (`id_probe: null`, `probe_safety: write_sensitive`)
- **Register addressing:** none — plain `Connection` (`write`, `read`), not `RegisterConnection`

### 4-wire SPI (S8) through DisplayConnection
- **Interface select:** on the module `BM0 = L` (pin 33) **and** `D13 = L` (pin 40) = 4-wire SPI (S8). `CD` (pin 34) is the data/command select (**L = command, H = data**), `CS0` (pin 36) the active-low chip select, `SCK`/`SI` clock and data in; `A2/CS1` are unused. `RST` (pin 37) is optional: without it the System Reset command is enough, and a driver given no reset line skips the hardware reset. The module's SPI is **write-only** (no `SO`, no acknowledge)
- **Connection:** a `DisplayConnection` (see `specs/transport_display.md`) in simplex wire mode with `dc` = CD, `res` = RST (or none), `busy` none, hardware CS. Mode 0 (the chip latches on the rising SCK edge; the module datasheet allows up to 8 MHz, the C++ bench ran SPI1 at about 6 MHz), MSB first
- **Framing:** every command byte **including the arguments** of two- and three-byte commands (`0x81 PM`, `0xF1 CEN`, `0xC0 map`, …) is sent with CD low as **its own CS window** (`send_command(byte)` with no parameter bytes, because the connection sends parameters with CD high); RAM data goes out with CD high, one CS window per ≤ 240-byte chunk (a page per transfer). A falling CS edge restarts the bit counter, the chip keeps the pending command state across windows. Verified on an EA DOGXL240-7 with a NUCLEO-F411RE
- **Class names:** `UC1611sSpiMinimal` / `UC1611sSpiFull` (Python, C++, Node.js), `Uc1611sSpiMinimal` / `Uc1611sSpiFull` (Rust, JVM), `NewUC1611sSpiMinimal` / `NewUC1611sSpiFull` (Go). Constructor: `(connection, width = 240, height = 128)` for Minimal and `(connection, width, height, top_view, contrast)` for Full; Rust `new_spi(connection, width, height[, top_view, contrast])` on `Uc1611sMinimal` / `Uc1611sFull`. C++ is `template <typename CONN>`
- **Behaviour differences from I²C:** no NACK, so no retry (`retry_count()` stays 0, `error_count()` counts only a failing connection); `init` runs the hardware reset first (if a reset line is wired), then the same sequence; the `DE` poll is replaced by a **fixed 10 ms wait** after enabling the display (after `init`, `wake`, `reset`; the I²C bench saw ≈ 6 ms); `read_status` / `read_ram` are **unsupported**: C++ returns `false` (buffers zeroed), Python raises `NotImplementedError`, Node.js rejects, Rust returns `Error::Unsupported`, Go returns `ErrUC1611sUnsupported`, JVM throws `UnsupportedOperationException`. The framebuffer, drawing, configuration commands, `show` and all other `Full` operations are identical
- **Sigrok:** the same decoder `uc1611s` also stacks on `display_spi` (see Sigrok Decoder)

Power-supply sequencing: either VDD or VDD2/3 first; no delay needed between them. After power-up the host must wait ≥ 150 ms before the first command (power-on-reset plus MTP read). **Power-down:** send System Reset (`0xE2`) and wait ~1 ms before removing power so the charge-drain circuit discharges `CL` (otherwise a residual horizontal line can remain).

### Status bytes (read from the command address)

`Status1`: bit 7 `Ver` (1), bit 6 `MX`, bit 5 `MY`, bit 4 `WA`, bit 3 `DE` (display enabled), bit 2 `WS` (MTP command succeeded), bit 1 `MD` (MTP version flag), bit 0 `MS` (MTP operation in progress).  
`Status2`: bits 7–6 `ID[1:0]` (state of the ID pins), bits 5–0 `PMO` (PM offset, from the MTP).  
`Status3`: bits 7–4 product code `0x1`, bits 3–1 = 0, bit 0 `EF` (ESD flag).  
Consecutive status reads within one transaction return `Status1, Status2, Status3, Status1, …`.

### Power-up defaults

After Power-On-Reset or System Reset (control registers; RAM content is not stated and must be assumed **undefined**): `CA = 0`, `PA = 0`, `SL = 0`, `FL = 0`, `BR = 11`, `TC = −0.05 %/°C`, `PM = 0xEA`, `PC = 0xF` (internal pump, 33–55 nF), `AC = 001`, `DC = 0x18` (**16-shade mode, display off**, i.e. `DC[4:2] = 110b`), `LC = 0x020` (line rate 28 klps in 16-shade mode, no mirror), `CEN = 159`, `DST = 0`, `DEN = 159`, partial display off, window = whole RAM, `ISOF = 1`, `ISOB = 0`.

## Display RAM

In On/Off mode with `DC5 = 1` (1 bit per pixel) the RAM is organised as **pages of 8 vertical pixels × 256 columns** (20 pages for 160 rows; the DOG module uses 16 pages × 240 columns). One data byte holds the 8 pixels of one column of one page: with `MSF = 0` **bit 0 is the top pixel of the page** (`D0` = line 8·page, `D7` = line 8·page + 7) — the same layout as SSD1306 / SH1106. The address registers are `PA` (page) and `CA` (column). After every data write/read the column pointer increments; with wrap-around on (`AC0 = 1`, reset) the pointer returns to column 0 at the end of the page and the page advances by `PID` (+1/−1). The driver does **not rely on the wrap**: it sets page and column explicitly for each page.

Four complete B/W screens ("patterns") fit in RAM: `PA[6:5]` selects the pattern that data is written to and `DC[7:6]` (Set Display Pattern) selects the one that is displayed. Pattern 0 is the default for both.

Orientation: `MX = 1` stores column `n` at SEG(240 − n) and is what the datasheet's **bottom-view (6:00) initialization** uses (`0xC0, 0x02`); top view (12:00, module mounted rotated 180°) is `MY = 1, MX = 0` (`0xC0, 0x04`). `MY` takes effect immediately and does not change RAM; `MX` is applied when the RAM data is written, so after changing it the framebuffer must be re-sent (`show`). The visible vertical start line is `SL`; `FL` splits the screen into a fixed and a scrolling part.

RAM rows 128–159 (pages 16–19) are outside the module's 128 rows; a scroll by `SL` rows moves the image up and brings in rows from there (wrap-around at 160 rows, not 128): the driver clears them during `init`, so the hardware scroll shows a blank band.

## Initialization Sequence

Derived from the DOG module's "Initialisation example (bottom view)" (page 7 of `DOGXL240-7.pdf`) and the UC1611s power-up sample. Command stream = one `write` on the **command connection**:

1. Wait **150 ms** after power-on (datasheet: wait for the power-on reset and MTP read; skippable only when the display has been powered for longer — the driver always waits).
2. `0xE2` System Reset (its own transaction), then wait **150 ms** (conservative: the datasheet states only ≥ 10 µs; the MTP version re-reads its memory).
3. Command stream: `0x25` (temp. compensation −0.10 %/°C), `0xC0 0x02` (mapping: `MX = 1`, bottom view; `0xC0 0x04` for top view), `0xA3` (line rate 9.4 klps), `0xF1 0x7F` (COM end = 127), `0xF2 0x00` (partial start 0), `0xF3 0x7F` (partial end 127), `0x81 0x8F` (potentiometer = 143), `0x89` (RAM address control: wrap on, column first, +1 — the reset default stated explicitly), `0xD1` (1 bit per pixel, pattern 0). Bias ratio, pump and panel loading stay at the reset values (1/11, internal 11x pump, 33–55 nF), as in the datasheet example.
4. Clear RAM pattern 0, pages 0–19 (the module shows 16; pages 16–19 are the rows a scroll brings in): for each page send the page and column commands, then 240 `0x00` bytes on the **data connection** (chunked), so the display is blank when switched on. Patterns 1–3 are not cleared (unused by default).
5. `0xA9` — display enable in On/Off mode. The charge pump starts; the chip itself waits for `VLCD` before releasing the drivers. The driver polls Status1.`DE` (bit 3) every 2 ms (a NACK while the pump restarts is expected and not counted as an error) for at most 200 ms; `DE` was measured to return about 6 ms after `0xA9`.

(The DOG example enables the display before writing RAM; the driver clears first because the RAM content is undefined after power-up.)

## Implementation Stages

### Minimal

Primary use: a 240 × 128 black/white graphic display you can draw pixels on out of the box.

| Operation | Parameters | Returns | Notes |
|-----------|------------|---------|-------|
| `init` | `command_connection` (`I2CConnection`, `0x38 + 2n`), `data_connection` (`I2CConnection`, command address + 1), `width: int = 240`, `height: int = 128` | — | Runs the Initialization Sequence (with the waits), clears RAM and framebuffer, switches the display on. `width` ≤ 240, `height` a multiple of 8, ≤ 128 (`CEN = height − 1`) |
| `clear` | — | — | Zero the framebuffer (call `show` to update the panel) |
| `set_pixel` | `x: int`, `y: int`, `on: bool = True` | — | Framebuffer only (0 ≤ x < width, 0 ≤ y < height); out-of-range ignored |
| `show` | — | — | Write the whole framebuffer: per page one address command stream (page, column 0) followed by `width` data bytes in ≤ 32-byte chunks |

**Sensible defaults:** 240 × 128, B/W 1 bit per pixel, bottom view (`MX = 1`), contrast `PM = 0x8F`, temperature compensation −0.10 %/°C, bias 1/11, internal pump, line rate 9.4 klps, normal (non-inverted) display. The framebuffer is `width × height / 8` bytes, page-major (`fb[page * width + x]`), bit 0 = top row; **it needs 3840 bytes of RAM at 240 × 128**.

| `set_display_pattern` | `pattern: int` (0–3) | — | `0xD0 \| (pattern << 1) \| 1` (`DC[7:6]` = pattern, `DC5` = 1): select which of the four RAM screens is displayed |
| `set_write_pattern` | `pattern: int` (0–3) | — | Subsequent `show` / `show_page` / data writes go to this RAM screen (`PA[6:5]`); the framebuffer is shared |
| `read_status` | — | `bytes` (3) | Send NOP (`0xE3`) on the command connection to restart the status cycle, then read 3 bytes: `Status1, Status2, Status3` (C++: returns `bool`, bytes via out parameter) |
| `read_ram` | `page: int`, `column: int`, `n: int` | `bytes` | Set page and column, read `n + 1` bytes from the data connection, discard the first (dummy). C++ (no heap) clips `n` to 32 |
| `reset` | — | — | System Reset (`0xE2`, own transaction) and the post-reset wait; the driver re-runs the configuration part of `init`, enables the display and polls `DE` |
| `ok` / `retry_count` / `error_count` / `clear_errors` | — | `bool` / `int` / `int` / — | Error bookkeeping (see Error handling); in languages with exceptions or error returns the counters are optional |
| `send_command` | `*bytes` | — | Raw command stream on the command connection (escape hatch) |
| `send_data` | `bytes` | — | Raw data on the data connection (chunked) |

**Additional configuration options:** contrast, bias ratio, temperature compensation, line rate, pump / external VLCD, panel loading, flip / top view, scroll, fixed lines, partial display, N-line inversion, isolation clock, patterns, sleep, invert, all-on.

`set_*` methods that change controller state do not touch the framebuffer. The driver caches nothing that the chip can report: configuration is one-way except `read_status`.

## Data Conversion

```
page, bit       = y // 8 , y % 8
fb[page*W + x]  = framebuffer byte for column x of that page          (W = width)
set pixel       : fb |=  (1 << bit)     clear: &= ~(1 << bit)

command address = 0x38 + 2*n            (n = A3<<1 | A2 → 0x38, 0x3A, 0x3C, 0x3E)
data address    = command address + 1
address bits    : 0 1 1 1 A3 A2 CD  (7-bit),  CD = 0 command, 1 data

show():  for p in 0..H/8-1:
           command write: [0x60 | (p & 0x0F), 0x70 | (p >> 4), 0x00, 0x10]      # page, column 0 (pattern 0)
           data    write: fb[p*W .. p*W+W-1]   (chunks of ≤ 32 bytes)

page address    : 0x60 | (PA & 0x0F),  0x70 | ((PA >> 4) & 0x07)      PA = pattern << 5 | page
column address  : 0x00 | (CA & 0x0F),  0x10 | (CA >> 4)
contrast        : [0x81, PM]                       PM 0–255
VLCD (BR = 11)  = (9.925 V + PM × 30.48 mV) × (1 + (T − 25) × CT)       # CT: curve coefficient; keep VLCD < 17.5 V
VLCD (BR = 10)  = 9.048 V + PM × 27.68 mV;  BR = 12: 10.791 V + PM × 33.25 mV;  BR = 5: 4.518 V + PM × 14.19 mV
mapping         : [0xC0, (MY << 2) | (MX << 1)]
display on/off  : 0xA9 / 0xA8
```

## Timing Constraints

- **Power-up:** ≥ 150 ms after VDD / VDD2/3 are stable (power-on reset + MTP read) before the first command; `RST` (if wired) low ≥ 1 ms then high and another 150 ms. VDD2/3 − VDD ≤ 2.0 V, `VDD ≥ 1.8 V`, `VDD2/3 ≥ 2.5 V`; the two supplies may be switched in either order within 10 µs … 10 ms of each other.
- **After System Reset / Set Display Enable:** ≥ 10 µs (datasheet); driver waits 150 ms after the initial System Reset and, after `wake` / `reset` / `init`, polls Status1.`DE` (≈ 6 ms measured, limit 50 ms; 200 ms at init). The chip NACKs while the pump restarts.
- **Power-down:** System Reset, then ~1 ms before removing VDD.
- **I²C:** SCK cycle ≥ 276 ns write / 580 ns read (≥ 2.5 V; 330 / 750 ns below 2.5 V), start setup 28 ns / hold 50 ns, stop setup 28 ns, bus free time (STOP → START) ≥ 165 ns; DOG module ≤ 1.7 MHz; driver default 400 kHz.
- **Frame rate of the LCD:** `line rate / mux`: 9.4 klps / 128 ≈ 73 Hz in On/Off mode.
- **Conformance:** every stated bound is a minimum wait that the driver satisfies by construction; none can be checked as a start/end annotation delta. See `specs/display/uc1611s_timing.conf`.

## Error handling

The chip NACKs transfers now and then (see Transport Configuration), so every driver checks each transfer and retries:

- **Detection:** C++ `Connection` gained `bool ok()` (the last write/read was acknowledged); each platform I²C connection sets it from its bus status (Arduino `endTransmission`/`requestFrom`, Linux `write`/`read`/`ioctl`, Zephyr/ESP-IDF return codes, Pico SDK byte counts, STM32 HAL status) and the I²C mock can inject failures (`failNextWrites(n, after)`, `failNextReads(n)`). Connections that cannot detect failures always report true. Python (OSError), Rust (`Err`), Go (`error`), JVM (IOException) and Node.js (rejected promise) detect failures natively.
- **Policy:** up to **8 attempts**, **2 ms** apart (covers the ~6 ms wake window). A command stream is simply repeated; a RAM page is rewritten **from its page/column address command** (a partial write cannot be continued); a read repeats its address commands and the read together; a status read repeats the NOP and the read.
- **Counters:** `retry_count` (repeated attempts), `error_count` (transfers that failed after all attempts), `ok()` (no unrecovered failure since the last `clear_errors()`). `send_data` (raw) cannot restart a page, so it makes a single attempt per chunk and only counts a failure.
- **After the last attempt:** C++ (no exceptions) counts the failure and goes on; every transfer's OSError / `Err` / `error` / exception is otherwise raised to the caller after the counters were updated. **Dead chip:** if the System Reset at the start of `init` is not acknowledged after all attempts, the C++ driver reports `valid() == false` and sends nothing else; the other languages raise from the constructor.
- **Poll instead of sleeping:** `init`, `wake` and `reset` poll Status1.`DE` so they return as soon as the pump is up; NACKed polls are not counted as errors.

## Implementation Notes

- **Two I²C addresses per device.** The command/data selection is the lowest address bit, so the driver owns two `I2CConnection`s (same bus, addresses `n` and `n + 1`). Constructors of both Minimal and Full take them in that order. Examples/tests open the bus once and create both connections. The I²C scan lists both addresses.
- **Plain `Connection`, not `RegisterConnection`:** there is no register-address byte; a command write is `[cmd, (arg)…]`.
- **One base class, two transports.** The framebuffer, drawing, configuration commands and `show` sit in a transport-agnostic base with two hooks `write_commands(bytes)` and `write_data(bytes)`; the I²C classes map them to `command_connection.write` / chunked `data_connection.write`. The SPI classes of Phase 2 will call `DisplayConnection.send_command()` / `send_data()` (D/C low / high, one CS window per call) with the same command bytes; `read_status` / `read_ram` then raise (SPI is write-only on the module). Class names in this phase: `UC1611sMinimal` / `UC1611sFull` (Python, C++, Node.js), `Uc1611sMinimal` / `Uc1611sFull` (Rust, JVM), `NewUC1611sMinimal` / `NewUC1611sFull` (Go) — all I²C; Phase 2 adds the `Spi` variants (`UC1611sSpiMinimal` …), as for the SH1106 spec.
- **Phase 2 (SPI via DisplayConnection):** implemented for all host languages, see the section *4-wire SPI (S8) through DisplayConnection*; each language has a transport object (C++ `UC1611sBus`, Python `_I2CBus` / `_SpiBus`, Node.js `I2CBus` / `SpiBus`, Rust `Transport`, Go `uc1611sBus`, JVM `Uc1611sBus`) under the shared framebuffer / command code, and the SPI classes only pick the transport.
- **I²C transaction size:** chunk RAM data to the platform's maximum write size (32 bytes on Arduino `Wire`), **a fresh header per chunk**, no address commands in between.
- **Dummy read:** after every column/page address command the first byte read from the data address is a dummy; `read_ram` discards it ("Achtung: Nach den Befehlen zum Setzen der Page- bzw. Column-Adresse muss immer zuerst ein Dummy-Byte gelesen werden", DOG datasheet).
- **System Reset framing:** the command carrying `0xE2` must be its own transaction, ended with STOP; never concatenate further bytes after it.
- **Contrast is mandatory to tune.** `PM = 0x8F` is the datasheet's example value; the right value depends on the panel variant (W/B/S), supply and temperature. The chip compensates temperature drift; the one-time contrast adjustment is the application's job. A blank or fully dark display after init means `PM` is off, not a hardware fault.
- **`CEN` must match the row count.** The reset value (159) drives 160 rows; the DOG module needs `0xF1 0x7F` (127). A wrong `CEN` shifts the contrast and shows a dark band.
- **`MX` and re-show.** `MX` is applied to the RAM write address, not to the displayed image: after `set_flip` with a changed `mirror_x`, call `show`. `MY` is immediate.
- **No other shade modes.** The driver always works with `DC[4:2] = 001` (On/Off, display on) and `DC5 = 1`. Sending `0xA8 \| DC[4:2]` with other values via `send_command` selects 4/8/16 shades and a 4-bit RAM format, which the framebuffer layout does not describe.
- **Registry:** `registry/chips.json` entry `uc1611s` with addresses `0x38..0x3F`, `id_probe: null`, `probe_safety: write_sensitive` (every write is a command or data; the chip would execute the probe byte), `driver: null` until implemented. Shares addresses with the PCF8574A, PCF8576, SH1106, PCF8578 and AHT21 families.
- **RAM size:** the framebuffer needs 3840 bytes at 240 × 128; AVR-class Arduino boards below the Mega do not have enough RAM (the Mega with 8 KB works).
- **Backlight:** separate LED module (EA LED94x67): white = 3 paths of 3 LEDs in series (9.6 V typ., 15 mA per path, a constant-current source such as CAT4238TD is recommended), amber = 3 paths of 5 parallel LEDs (2.1 V, 100 mA per path, 12 Ω / path at 3.3 V). **Never connect directly to 3.3 V / 5 V.** Not controlled by the driver.
- **Touch panel:** the optional EA TOUCH240-3 is an analog 4-wire panel, unrelated to the controller; not covered.
- **Hardware verification (C++):** the C++ driver is verified on an EA DOGXL240-7 with a NUCLEO-F411RE (I2C1, external pull-ups, 400 kHz; A3 high, A2 = PB6 low, CD = PC7 low, RST = PA9): status, mirror, sleep/wake, RAM read-back and reset checks pass (15/15) with 0 retries and 0 HAL errors. The STM32Cube connection now resets the I²C peripheral after a timeout / bus error and has a settable HAL timeout (the examples use 50 ms). With only the internal pull-ups 400 kHz was unreliable and the bench ran at 100 kHz; with external pull-ups on SDA/SCL 400 kHz runs cleanly (smoke test 15/15 with 0 retries, demo 0–1 retries), so external pull-ups (2–4.7 kΩ to 3.3 V) are recommended.

## Sigrok Decoder

Decoder id `uc1611s` (`sigrok/uc1611s/`), inputs `['i2c', 'display_spi']`. Stacked on `display_spi` (4-wire SPI) every CD-low byte is a command byte and every CD-high byte display data (each byte its own CS window, command arguments are command bytes too; reset pulses on RST are shown in the status row); there are no reads. Stacked on `i2c`: the header byte is split into address and `CD`/`RW` (annotated `0x38 cmd` / `0x39 data`, addresses `0x38`–`0x3F`); command-address writes are decoded into named commands with fields (column nibbles combined into a column number, page and pattern, temperature compensation, panel loading, pump, scroll line, potentiometer, partial display, RAM address control, fixed lines, line rate, all-on, invert, display enable with mode, mapping control with MX/MY/MSF, N-line inversion, display pattern, System Reset, NOP, bias ratio, COM end, partial start/end, window registers, window mode), double- and triple-byte commands consume their argument bytes; data-address writes are shown with the tracked page and column (incrementing, wrapping at the end of the page) and a count, each byte renderable as an 8-pixel column; reads are shown as status fields (`Ver`, `MX`, `MY`, `WA`, `DE`, `ID`, `PMO`, product code, `EF`) or RAM data (first byte marked dummy). Warnings: a command byte not in the table (including MTP, test-control and APC commands), an argument byte missing at STOP, bytes sent after `0xE2` in the same transaction, a data write while the column pointer exceeds 239.
