# Chip Spec: IL0373

**Manufacturer:** Good Display / Dalian Good Display Co., Ltd. (IL0373 is the Ilitek-lineage controller, command-compatible with the UltraChip UC8151/UC8276 family)  
**Datasheet:** `datasheets/display/IL0373.pdf` (IL0373 driver IC specification, Good Display). Panel datasheet: `datasheets/display/WS14986 2.13inch e-Paper (D).pdf` (Waveshare 2.13inch e-Paper (D), specification rev 1.0, 2018-01-05)  
**Category:** `display`  
**Transports:** SPI (4-wire; write-only or half-duplex, via `DisplayConnection`)

## Overview

The IL0373 is an all-in-one driver with timing controller for **black/white** (and, with a red-capable panel, black/white/red) electrophoretic panels of up to **160 source x 296 gate** outputs: display RAM for NEW and OLD data, an on-chip oscillator and PLL (1.625 MHz RC), DC-DC booster and regulators, an on-chip temperature sensor with an I2C master for an external LM75, a waveform (LUT) OTP and a low-power detector. The reference hardware is the Waveshare **2.13inch e-Paper (D)**: a **104 x 212** pixel (source x gate) **black/white** panel (the specification calls it 212(H) x 104(V), landscape) that the module drives in **KW mode** (`PSR.KW/R = 1`).

The chip is a close relative of the UC8276C (`specs/display/uc8276c.md`): same one-byte command set, same `PON -> DRF -> POF` update cycle with an active-low BUSY_N, same `DisplayConnection` wiring. The differences that matter to the driver: the panel is **black/white only** (the second RAM plane is the NEW image, not red), data polarity is `NEW/OLD`-based, the register value layouts of `PWR`, `VDCS` and the LUT commands differ, and the vendor reference flow powers the booster **before** the panel setting.

This spec covers **4-wire SPI**, full-panel updates with the **waveform loaded from OTP**, a partial-window write, a user-supplied LUT and (with a half-duplex wire mode) the read commands. Partial *refresh* waveforms are not specified. `AUTO` (`0x17`) is listed in the panel datasheet only and is not used (it does not start a refresh on the sibling UC8276C panel).

## Transport Configuration

### SPI (4-wire)
- **Mode:** CPOL=0 CPHA=0 (Mode 0), MSB first; data clocked on the rising edge
- **Max clock:** write cycle >= 100 ns (SCL high/low >= 35 ns) -> **10 MHz**; read cycle >= **150 ns** (SCL high/low >= 60 ns) -> **<= 6.6 MHz**. The IL0373 feature list's "clock rate up to 20 MHz" contradicts its AC table; the AC table is used. Driver default 4 MHz
- **CS active:** low (CS#). Commands are processed on the stop condition (CS# rising edge)
- **Framing:** a byte stream; the D/C# pin is sampled per 8-bit group: low = command, high = parameter/data/read. No register address, no read/write bit
- **Bus selection:** pin **BS1** low = 4-wire SPI (used), high = 3-wire 9-bit SPI (not supported). On the Waveshare module BS1 is strapped by the board
- **Bidirectional SDA:** read commands clock data out on the data line after the command byte. Whether the board exposes DOUT depends on the wiring -> `DisplayConnection` wire mode (`SIMPLEX` / `HALF_DUPLEX_HW` / `HALF_DUPLEX_PIN`, see `specs/transport_display.md`). `SIMPLEX` is sufficient for everything in Minimal
- **Register addressing:** none - takes a `DisplayConnection`, not a `RegisterConnection`

## Command Set

All commands are one byte sent with D/C# low; parameters follow with D/C# high. POR values in brackets. The table follows the **panel datasheet** where it differs from the chip datasheet; differences are noted.

**LUT lengths.** The chip datasheet defines 7 states per table: VCOM `0x20` = 44 bytes (7 x 6 + `ST_XON`, `ST_CHV`), `0x21`-`0x24` = 42 bytes each. The panel datasheet describes the same commands with 10 / 6 states (60 / 36 / 60 / 36 / 36 bytes). The two disagree; the driver passes the caller's bytes through unchanged and the Full API documents both lengths.

**Not covered:** OTP programming (`0xA0`, `0xA1`), cascade (`0xE0`, `0xE5`), the glass check `0x44`, `AUTO` (`0x17`), the external-sensor pass-through (`0x42`, `0x43`).

### BUSY flag

All commands except `REV`, `FLG`, `VV` and read cycles are ignored while a refresh is running. BUSY goes low for `PON`, `POF`, `DRF`, `DSP`, `DSLP`, `TSC`, `LPD`, `AMV`, `APG`. Data/LUT/setting commands raise no BUSY.

## Display RAM

Two RAM planes of up to 160 x 296 bits; `DTM1` writes the OLD image and `DTM2` the NEW image in KW mode. A transfer is a plain stream written from the first pixel to the last. Each byte carries 8 horizontal pixels with **D7 = first (leftmost) pixel**; a frame is `ceil(width/8) x height` bytes per plane (13 x 212 = **2756 bytes** on the 2.13inch (D)), rows in gate-scan order (`G0` first with `UD = 1`, `S0` first with `SHL = 1`).

In KW mode with `CDI.DDX[0] = 1` (default) the `{NEW, OLD}` bit pair selects the waveform:

| NEW | OLD | LUT |
|-----|-----|-----|
| 0 | 0 | LUTBB (stays black) |
| 0 | 1 | LUTWB (white -> black) |
| 1 | 0 | LUTBW (black -> white) |
| 1 | 1 | LUTWW (stays white) |

so **a NEW bit of 1 is white**. The pixels of a frame that the controller changes are decided by NEW *and* OLD: a pixel with equal bits is not driven. The driver therefore sends `OLD = NOT NEW` for every pixel: every pixel is driven to its final state, which makes a refresh independent of what the panel showed before (a full "flashing" update) and needs no second framebuffer. The panel does not report its previous image, so a differential update is not offered.

## Initialization Sequence

Follows the panel datasheet's "BW mode & LUT from OTP" reference flow (page 36). Hardware behaviour is **not verified on a panel** - see Implementation Notes.

1. Apply VCI/VDDIO; BS1 low (4-wire).
2. **Hardware reset:** RES# low (>= 10 ms is used), then high; wait BUSY high.
3. `PWR` `0x03 0x00 0x2B 0x2B 0x03` (the vendor demo's values; without them `PON` does not complete on the reference module).
4. `BTST` `0x17 0x17 0x17`.
5. `PON`; **settle: wait up to 200 ms for BUSY high and ignore a timeout** (see Implementation Notes).
6. `PSR` `0x1F` (OTP LUT, KW, scan up, shift right, booster on).
7. `TRES` `0x68 0x00 0xD4` for 104 x 212 (`HRES = width`, `VRES = height`).
8. `CDI` `0x97` (VBD = 10, DDX = 01, CDI = 10 hsync).

An update (`show()`), the reference "Load image data / Display refresh / Border floating / Power off" part, preceded by the power-on from step 4 if the booster is off:

1. (if the panel is powered off: `PON`, settle 200 ms, `CDI` `0x97`)
2. `DTM1` + OLD bytes; `DTM2` + NEW bytes.
3. `DRF`; wait >= 200 us, then BUSY high.
4. `CDI` `0xF7` (border floating).
5. `POF`; wait BUSY high.

Deep sleep: (if powered on: `CDI` `0xF7`, `POF`, wait) then `DSLP` `0xA5`. **Wake = hardware reset + the Initialization Sequence**; the framebuffer is unaffected.

## Implementation Stages

### Minimal

Goal: a 104 x 212 black/white e-paper panel you can draw pixels on out of the box.

| Operation | Parameters | Returns | Notes |
|-----------|------------|---------|-------|
| `init` | `connection` (`DisplayConnection`), `width: int = 104`, `height: int = 212`, `busy_timeout_ms: int \| None = 30000` | - | Allocates the framebuffer, runs the Initialization Sequence (including the BUSY wait), leaves the panel unchanged until `show()`. `width` a multiple of 8 and <= 160, `height` <= 296 |
| `clear` | `color: int = WHITE` | - | Fill the framebuffer (`WHITE` or `BLACK`) |
| `set_pixel` | `x: int`, `y: int`, `color: int = BLACK` | - | Framebuffer only; out-of-range ignored |
| `show` | - | - | Write OLD/NEW, `DRF`, power off; blocks until BUSY is high again |
| `sleep` | - | - | `POF` (if on) then `DSLP`; only `wake()` / a hardware reset restores communication |

**Constants:** `BLACK = 0`, `WHITE = 1`.

**Sensible defaults:** 104 x 212 KW, OTP waveform (`PSR.REG = 0`), internal temperature sensor, power setting / PLL at power-on values, SPI Mode 0 at 4 MHz, BUSY timeout 30 s (not derived from the datasheet; the panel datasheet states the update time as TBD). The framebuffer is `ceil(width / 8) x height` bytes (2756 at 104 x 212), initialised to white. In C++ the buffer is caller-supplied (`valid()` instead of exceptions). Works with `SIMPLEX` wiring.

## Data Conversion

```
bytes_per_row = ceil(width / 8)
index         = y * bytes_per_row + (x // 8)
bit           = 7 - (x % 8)                  # D7 = first (left) pixel
set pixel     : fb[index] |= (1 << bit) for WHITE;  &= ~(1 << bit) for BLACK
OLD plane     : ~fb  (every pixel driven)      NEW plane : fb

TRES:   b0 = width & 0xF8 ; b1 = (height >> 8) & 1 ; b2 = height & 0xFF      # 104 x 212 -> 68 00 D4
PTL:    HRST = x0 & 0xF8, HRED = (x1 & 0xF8) | 0x07, VRST (2 bytes), VRED (2 bytes), PT_SCAN

VDH / VDL (PWR):   code = round((volts - 6.4) / 0.2)       6.4 .. 15.0 V (0x00..0x2B)
VGHL_LV (PWR):     20 - volts_abs                           20 V (00) .. 17 V (11), VGL = -VGH
VCOM_DC (VDCS):    code = round((-0.10 - volts) / 0.05)     -0.10 V (0) .. -3.00 V (0x3A)
VV (read):         volts = -0.10 - 0.05 * VV
frame rate (PLL):  byte = (M << 3) | N       (M/N table as in specs/display/uc8276c.md)
temperature (TSC): celsius = int8(ts)         two's complement
```

## Timing Constraints

- **Reset:** RES# low >= 10 ms is used by `DisplayConnection.reset()`; the documents give no minimum. After RES# rises wait for BUSY high.
- **Refresh:** after `DRF`, BUSY goes low and the panel refreshes. The panel datasheet states the image update time at 25 deg C as **TBD**. Measured on the reference module (NUCLEO-F411RE): **3.3 s** for a full OTP-waveform `show()` including the data transfer (2.0 s for the vendor demo's register waveform, from its capture). The driver's 30 s default timeout is a driver choice. The update must not be interrupted. Do not refresh more often than every 180 s (panel datasheet, optical characteristics note).
- **First FLG read:** BUSY falling -> first `FLG` read must be **> 200 us**.
- **Commands that drive BUSY low:** `PON`, `POF`, `DRF`, `DSP`, `DSLP`, `TSC`, `LPD`, `AMV`, `APG`. The driver waits BUSY high after DRF and POF; after PON it only settles (see Implementation Notes).
- **SPI (write):** tSCYCW >= 100 ns, SCL high/low >= 35 ns. **(read):** tSCYCR >= 150 ns, SCL high/low >= 60 ns.
- **Deep sleep exit:** hardware reset, then the full Initialization Sequence.
- **Operating temperature:** 0-50 deg C (panel); storage -25..70 deg C.
- **Conformance:** no vendor bound exists to compare against (see `specs/display/il0373_timing.conf`).

## Implementation Notes

- **DisplayConnection owns D/C, RES, BUSY and CS.** The driver never touches them; it calls `send_command(cmd, data)`, `send_data`, `read_data`, `reset`, `wait_busy` from `specs/transport_display.md`.
- **Hardware status:** the C++ STM32Cube demo (`cpp/examples/stm32cube/display/IL0373/demo`) was run on a NUCLEO-F411RE + Waveshare 2.13inch e-Paper (D) with the Waveshare e-Paper Shield, SPI1 0.78 MHz: a full `show()` completes in 3.3 s and a raw top-black / bottom-white frame was confirmed visually. `sleep()`, `show_region`, reads and all other languages are **not verified on a panel**.
- **BUSY after `PON` is not a clean ready on the reference module.** Measured (NUCLEO-F411RE + Waveshare 2.13inch (D)): BUSY is high after reset, goes low at `PON` and stays low until the first `DRF` completes; `POF` returns it high within ~40 ms; `DRF` holds it low for the refresh (3.3-3.7 s). The vendor demo (`sigrok/tests/il0373/2in13 Full Demo.sr`, decoded in this work) issues `PWR`, `BTST`, `PON`, three `0x71` status reads and then a fixed 200 ms delay before `PSR`; its BUSY trace toggles at about 2 MHz from `PWR` until the LUT upload, so the vendor's readiness check is effectively that delay. The driver does the same: `PON`, then wait at most 200 ms and ignore the result. Waiting for BUSY high after `PON` times out.
- **The vendor demo uses register LUTs** (`PSR 0xBF 0x0E`, `PLL 0x3A`, `VDCS 0x28`, `CDI 0xB7`, 44/42/42/42/42-byte LUTs, about 2 s refresh, partial refresh with `PTIN`/`PTL` and its own LUT set); this driver uses the OTP waveform (`PSR 0x1F`), which refreshes in about 3.3 s. The captured LUT bytes are the 44/42-byte lengths of the chip datasheet.
- **Power flow follows the vendor reference**, not the UC8276C driver: `PON` is sent before `PSR` and the picture data, and `POF` follows each refresh with the border set floating via `CDI 0xF7`.
- **`OLD = NOT NEW`** (see Display RAM) is a driver design choice for a memory-free full refresh; the vendor reference sends a separate OLD plane. If the panel shows ghosting, the alternative is to keep the previous frame as OLD; `set_interval(polarity=...)` changes DDX.
- **TRES is 3 bytes here** (chip and panel datasheets), unlike the UC8276C's 4. The driver always writes it, since the panel's 104 x 212 is not a PSR RES preset.
- **LUT byte counts differ between the two documents** (44/42/42/42/42 vs 60/36/60/36/36). `write_lut` is an untested escape hatch; the reference LUT bytes are not in either document.
- **Register layouts follow the panel datasheet** (PWR 6.4 V base and VGH 17-20 V, VDCS up to -3.00 V). The IL0373 chip datasheet shows the same fields; the panel's OTP may override defaults, so the driver writes everything it depends on (PSR, TRES, CDI).
- **Orientation:** with `UD = 1`, `SHL = 1` row 0 is `G0` and column 0 is `S0`; whether that is the physical top-left depends on the FPC; `set_flip` corrects either case. Confirm on hardware.
- **Memory:** 2756 bytes at 104 x 212. In C++ the buffer is the caller's (no heap); a null/undersized buffer, a width that is not a multiple of 8 or a size over 160 x 296 makes `valid()` false.
- **Blocking update:** `show()` blocks for the whole refresh; on MicroPython/CircuitPython this stalls the interpreter and the examples say so.
- **Hardware identification:** the provided panel PDF is the Waveshare "2.13inch e-Paper (D)" specification (rev 1.0, 2018-01-05); its command table includes `AUTO` and `GSST`, which the IL0373 chip datasheet does not list - the panel's silicon may be a UC8151-family part. The driver uses only commands common to both documents.
- **Datasheet status:** both documents are preliminary; several values conflict (20 MHz vs. 100 ns cycle, LUT lengths). The more conservative value is used.

## Sigrok Decoder

Decoder id `il0373`, input **`display_spi`**: it stacks on the `Display-SPI` connection decoder (`sigrok/display_spi/`, see `specs/transport_display.md`). Typical stack: `-P display_spi:clk=<SCK>:mosi=<DIN>:cs=<CS#>:dc=<D/C#>:busy=<BUSY>:res=<RES#>,il0373`. BUSY is treated as active low.

Annotation rows: **Data** - one annotation per command with decoded parameters (PSR bit fields, PWR voltages in volts, PLL frame rate, 3-byte TRES, 7-byte PTL, CDI fields, LUT lengths, deep-sleep check code); **Status** - `Busy for <duration>` spans (BUSY low for at least 20 us, shorter spans are the module's BUSY noise) and RES# low spans; **Warnings** - DRF / POF / TSC / APG that did not see BUSY go low within 20 us of the CS# rising edge, unknown command, wrong parameter count, a command sent while a refresh is running (other than FLG, REV, VV), the first FLG of a polling run within 200 us of BUSY falling, a pixel write larger than the frame, a bad check code. `PON` is deliberately not checked for BUSY (module quirk, see Implementation Notes). Register layouts follow the panel datasheet; LUTs are accepted with 44/42 or 60/36 bytes.

`OUTPUT_PYTHON` packets: `('COMMAND', (command_byte, parameter_bytes))`.

Test captures in `sigrok/tests/il0373/`: `2in13 Full Demo.sr` (Waveshare's vendor demo, 4 MHz, register-LUT flow, no decoder warnings except two "sent while BUSY low" where its BUSY noise reaches 20 us) and `Driver Demo.sr` (this driver's C++ STM32Cube demo on the NUCLEO-F411RE, 8 MHz: PWR, BTST, PON, PSR 0x1F, TRES, CDI 0x97, DTM1/2, DRF with `Busy for 3.91 s`, CDI 0xF7, POF, DSLP). The first byte of the driver capture is mis-framed by a CS#/SCK glitch while the MCU configures its pins (the PWR command shows as `0x80` with 5 parameters).
