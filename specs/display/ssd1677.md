# Chip Spec: SSD1677

**Manufacturer:** Solomon Systech  
**Datasheet:** `datasheets/display/ssd1677.pdf` (SSD1677 Rev 1.0, Nov 2018, "Advance Information"). No panel or module datasheet is committed: the module mappings below come from the issue's Waveshare survey and are **unverified**  
**Category:** `display`  
**Transports:** SPI (4-wire, write-only)

## Overview

The SSD1677 is an active-matrix electrophoretic display (EPD) driver with controller for **red/black/white** panels of up to **960 source × 680 gate** outputs: two on-chip bit-planes of display RAM (B/W and red, 960 × 680 bits each), an on-chip oscillator, booster and regulators for the gate, source and VCOM voltages, an internal temperature sensor, OTP storage for 34 temperature-dependent waveform sets, a programmable waveform (LUT) and a built-in dithering engine. The issue lists the Waveshare **3.7inch e-Paper** and **7.5inch e-Paper HD** modules as SSD1677 users (both unverified) and notes that the controller is confirmed on a **3.97inch 800 × 480** panel in ESPHome; the driver default is therefore 800 × 480. Black/white-only panels work too (the red plane is simply never set).

This chip is the large-panel sibling of the SSD1680 (`specs/display/ssd1680.md`, 176 × 296) and SSD1681 (`specs/display/ssd1681.md`, 200 × 200): the same command families, RAM model and display-update sequences, but with **10-bit RAM addresses**, a **105-byte LUT**, a **5-byte soft-start**, a single deep-sleep mode and an extra dithering path. Drivers for the chips should share structure; this spec stands alone and lists only the SSD1677 values.

An e-paper panel differs from an OLED/LCD in ways that shape the driver: a refresh is a multi-second full-panel waveform, the picture is **bistable** (it stays with the power off), the update must not be interrupted, and BUSY is a level output that must be waited on. The driver therefore keeps a framebuffer, sends it on `show()`, and blocks until BUSY goes low again. The datasheet gives **no refresh duration**; panels of this size usually take a few seconds (black/white) and longer for three colours (unverified), so the default BUSY timeout is generous.

This spec covers **4-wire SPI**, **full-panel updates in 3-colour or black/white mode with the waveform loaded from OTP**, a user-supplied waveform, and a RAM-window write. Partial *refresh* waveforms and the dithering engine's data path are **not** in the datasheet in usable detail and are not specified (see Implementation Notes).

## Transport Configuration

### SPI (4-wire)
- **Mode:** CPOL=0 CPHA=0 (Mode 0) — SDA is shifted in on the rising SCL edge (datasheet table 6-2); the idle level is not named, Mode 0 is the usual choice (confirm on hardware)
- **Max clock:** **20 MHz** in write mode (SCL cycle ≥ 50 ns, high/low ≥ 25 ns); the driver default is 4 MHz. Read mode is limited to 2.5 MHz and is not used
- **Bit order:** MSB first
- **CS active:** low; hold CS low for the whole command + parameter/data sequence of one transfer
- **Framing:** a plain byte stream. The **D/C# pin** is sampled on every eighth clock: low → the byte is a **command**, high → **parameter / RAM data**. The driver drives `dc_pin` (an `OutputPin`) low before each command byte and high before its parameter and data bytes. All writes are plain `connection.write(bytes)`; the connection must **not** fold register/read bits into the first byte (no register addressing — same convention as `specs/display/ssd1681.md` and `specs/display/ssd1683.md`)
- **Read:** the chip supports reads (commands `0x0A`, `0x1B`, `0x27`, `0x2D`, `0x2E`, `0x2F`, `0x35`), but breakout modules wire **no MISO**; the driver is **write-only** and exposes no read
- **3-wire SPI (BS1 high, 9-bit frames with an embedded D/C bit):** **not supported** (byte-oriented SPI connection). On the modules BS1 is strapped low (4-wire)
- **Register addressing:** none — plain `Connection`, not `RegisterConnection`

The issue notes say "Uses DisplayConnection". The sibling SSD168x specs use a plain SPI `Connection` plus `dc_pin`/`res_pin`/`busy_pin` (as `specs/display/ssd1683.md` does) and only the Sigrok decoder stacks on `display_spi`; this spec follows the siblings so the family shares one wiring convention. If `DisplayConnection` (`specs/transport_display.md`) is preferred for the driver, the command set, framing and timing below are unchanged.

## Command Set

All commands are one byte sent with D/C# = 0; parameter bytes follow with D/C# = 1. POR values in brackets. Only the commands the driver uses or exposes are listed; OTP programming, CRC, VCOM sensing, detection and the dithering engine are not covered.

| Command | Code | Parameters | Description |
|---------|------|-----------|-------------|
| Driver output control | `0x01` | `A[7:0]`, `A[9:8]`, `B[2:0]` | Gate lines = `A[9:0] + 1` (POR `0x2A7` = 680; the chip supports 300–680). `B`: GD, SM, TB scan order/direction (POR 0; `TB = 1` is reserved) |
| Gate driving voltage | `0x03` | `A[4:0]` | VGH 12–20 V in 0.5 V steps (POR `0x00` = 20 V) |
| Source driving voltage | `0x04` | `A`, `B`, `C` | `A` VSH1 (POR `0x41` = 15 V), `B` VSH2 (POR `0xA8` = 5 V), `C` VSL (POR `0x32` = −15 V); VSH1 > VSH2 |
| Booster soft start | `0x0C` | `A`, `B`, `C`, `D`, `E` | **Five** bytes. Level 1 = `0xAE 0xC7 0xC3 0xC0 0x40`, level 2 = `0xAE 0xC7 0xC3 0xC0 0x80` (the datasheet states no POR) |
| Deep sleep | `0x10` | `A[1:0]` | `00` normal (POR), `11` deep sleep (**RAM not retained**). BUSY stays high; exit needs a hardware reset. There is no RAM-retaining mode |
| Data entry mode | `0x11` | `A[2:0]` | `ID[1:0]`: `00` X−/Y−, `01` X+/Y−, `10` X−/Y+, `11` X+/Y+ (POR `011`); `AM`: 0 = X direction first, 1 = Y first (POR 0) |
| Software reset | `0x12` | — | Registers to defaults (not deep sleep), RAM kept. BUSY high meanwhile |
| Temperature sensor control | `0x18` | `A[7:0]` | `0x80` internal sensor; `0x48` external I²C sensor (POR) |
| Write temperature register | `0x1A` | `A[11:4]`, `A[3:0]<<4` | 12-bit two's complement, 1/16 °C per LSB (POR `0x7FF`) |
| Master activation | `0x20` | — | Run the display update sequence selected by `0x22`. BUSY high until done; must not be interrupted |
| Display update control 1 | `0x21` | `A` | `A[7:4]` red-RAM option, `A[3:0]` B/W-RAM option: `0` normal, `4` bypass (RAM content as 0), `8` inverse (POR 0). One parameter byte |
| Display update control 2 | `0x22` | `A[7:0]` | Sequence for `0x20` (see below). POR `0xFF` |
| Write RAM (B/W) | `0x24` | data… | B/W plane. **1 = white, 0 = black** |
| Write RAM (dithering) | `0x25` | data… | Feeds the dithering engine (`0x4D`); not covered |
| Write RAM (red) | `0x26` | data… | Red plane. **1 = red**, 0 = not red |
| Write VCOM | `0x2C` | `A[7:0]` | VCOM −0.2 … −4.0 V (POR `0x00`) |
| Write LUT | `0x32` | 105 bytes | Waveform LUT, WS bytes 0–104 (datasheet §6.7) |
| Border waveform | `0x3C` | `A[7:0]` | VBD select/level/transition (POR `0xC0` = HiZ) |
| RAM X window | `0x44` | `XSA[7:0]`, `XSA[9:8]`, `XEA[7:0]`, `XEA[9:8]` | Four bytes; POR `0x000`, `0x3BF` (= 959) |
| RAM Y window | `0x45` | `YSA[7:0]`, `YSA[9:8]`, `YEA[7:0]`, `YEA[9:8]` | Four bytes; POR `0x000`, `0x2A7` (= 679) |
| Auto write red RAM | `0x46` | `A[7:0]` | Fill red RAM with a regular pattern; `A[7]` first-step value, `A[6:4]` height, `A[2:0]` width. BUSY high meanwhile |
| Auto write B/W RAM | `0x47` | `A[7:0]` | Same for B/W RAM |
| RAM X counter | `0x4E` | `A[7:0]`, `A[9:8]` | Address counter X (POR 0) |
| RAM Y counter | `0x4F` | `A[7:0]`, `A[9:8]` | Address counter Y (POR 0) |
| NOP | `0x7F` | — | Terminates a RAM write |

There is **no** `0x0F` (gate scan start), `0x3F` (end option), cascade mode or RAM-retaining sleep mode on this chip.

**`0x22` sequences** (the datasheet names the two waveform kinds *Display Mode 1* and *Display Mode 2*; the mapping Mode 1 = three-colour, Mode 2 = black/white follows the RAM/LUT tables 6-4 and 6-5 and is inferred — confirm on hardware): `0xF7` = load temperature + display with Mode 1; `0xFF` = same with Mode 2 (POR); `0xC7` / `0xCF` = display only (Mode 1 / Mode 2); `0x91` / `0x99` load LUT only; `0xB1` / `0xB9` load temperature + LUT; `0x80` / `0x01` clock on/off; `0xC0` / `0x03` clock + analog on/off.

### Power-on / reset defaults

POR values as in the table: 680 gate lines, VGH 20 V, VSH1 15 V / VSH2 5 V / VSL −15 V, X+/Y+ data entry, X window `0x000`–`0x3BF`, Y window `0x000`–`0x2A7`, counters 0, **update sequence `0xFF`**, **external** temperature sensor selected (`0x18` = `0x48`), border HiZ, VCOM register `0x00`. The display RAM contents are **undefined** after power-up. The status register (`0x2F`, not exposed) reads `0x01` after reset (chip ID 01; bit 2 = BUSY).

## Display RAM

Two planes, each **960 × 680 bits** (120 bytes × 680 rows = **81 600 bytes** per plane). The X and Y addresses are 10 bits wide. **The X address unit is not stated in the datasheet.** The window and counter registers hold a 10-bit value whose POR end value is `0x3BF` = 959, which matches **pixel** addressing (not bytes as on the SSD1680/SSD1681); the driver therefore writes X start/end/counter in **pixels** (x = 0 and `width − 1`), with X start a multiple of 8 and X end ≡ 7 (mod 8) so that whole bytes are written, and streams the RAM bytes. Whether the counter then advances by 8 per byte is **unconfirmed — verify on hardware** (see Implementation Notes). The Y address counts rows (`0x000`–`0x2A7`). After each byte the counter advances according to `0x11` within the window set by `0x44`/`0x45`, so one `0x24`/`0x26` command followed by `width/8 × height` bytes fills the whole window.

| Red RAM | B/W RAM | Colour (3-colour mode, LUT) |
|---------|---------|-----------------------------|
| 0 | 0 | black (LUT0) |
| 0 | 1 | white (LUT1) |
| 1 | 0 | red (LUT2) |
| 1 | 1 | red (LUT3 = LUT2) |

In **black/white mode** (Display Mode 2, table 6-5) the red plane is not a colour: red = 1 selects the duplicate LUT (LUT2 = LUT0 black, LUT3 = LUT1 white), so the B/W plane alone decides the colour.

**Bit order inside a byte is not stated in the datasheet.** The driver uses **bit 7 = leftmost pixel** of each 8-pixel group (common module practice); confirm on hardware.

## Initialization Sequence

Per the chip's operation flow (§9.1), for a panel of `width × height` (default 800 × 480). The datasheet gives no register values for the flow beyond the command names; the values below are POR / datasheet-table values except where marked *vendor*:

1. Wait ≥ 10 ms after VCI is applied.
2. **Hardware reset:** `res_pin` low, wait ≥ 10 ms, high, wait ≥ 10 ms (the datasheet gives no numeric reset pulse; these are conservative values); then **wait BUSY low**.
3. **Software reset** `0x12`; wait BUSY low (flow §9.1: then wait 10 ms).
4. `0x01` with `(height − 1) & 0xFF`, `(height − 1) >> 8`, `0x00` — gate lines.
5. `0x11` `0x03` — data entry X increment / Y increment (the POR value).
6. `0x44` with `0x00 0x00`, `(width − 1)` low/high; `0x45` with `0x00 0x00`, `(height − 1)` low/high — window covering the full panel, row 0 at RAM Y 0.
7. `0x3C` `0x05` — border follows LUT1 (white) (`A[7:6] = 00` GS transition, `A[1:0] = 01` LUT1; **assumed**, decoded from the `0x3C` table — the flow only says "set panel border").
8. `0x18` `0x80` — **select the internal temperature sensor** (the POR selects the external I²C sensor; without one the sensed temperature is invalid and no waveform set may match).
9. `0x0C` `0xAE 0xC7 0xC3 0xC0 0x40` — booster soft start, level 1 (datasheet table; the flow places it just before the display drive).
10. Set the RAM counters (`0x4E` `0x00 0x00`, `0x4F` `0x00 0x00`), then wait BUSY low.

The RAM contents are undefined after power-up, so the first `show()` always writes **both** planes in full; `init` does not clear them (the flow's auto-fill clear, see Implementation Notes, is not needed).

An update (`show()` / `refresh()`):

1. Set the RAM counters: `0x4E` `0x00 0x00`, `0x4F` `0x00 0x00`.
2. `0x24` + B/W plane bytes; then `0x4E`/`0x4F` again and `0x26` + red plane bytes (zeros streamed when no red pixel was ever drawn).
3. `0x22` with the update mode (`0xF7` 3-colour, `0xFF` B/W), then `0x20`; **wait BUSY low**.

Deep sleep: `0x10` `0x03` (`A[1:0] = 11`; the chip's RAM is lost). **Wake = hardware reset + the Initialization Sequence** (the framebuffer in the driver is unaffected, so the next `show()` redraws it).

## Implementation Stages

### Minimal

Goal: an 800 × 480 (or smaller) black/white/red e-paper panel you can draw pixels on out of the box.

| Operation | Parameters | Returns | Notes |
|-----------|------------|---------|-------|
| `init` | `connection` (SPI), `dc_pin: OutputPin`, `res_pin: OutputPin`, `busy_pin: InputPin`, `width: int = 800`, `height: int = 480`, `busy_timeout_ms: int \| None = 60000` | — | Allocates the B/W framebuffer, runs the Initialization Sequence (including the BUSY waits), leaves the display unchanged until `show()`. `width` a multiple of 8 and ≤ 960, `height` ≤ 680 |
| `clear` | `color: int = WHITE` | — | Fill the framebuffer (`WHITE`, `BLACK` or `RED`); call `show` to update the panel |
| `set_pixel` | `x: int`, `y: int`, `color: int = BLACK` | — | Framebuffer only (0 ≤ x < width, 0 ≤ y < height); out-of-range ignored. `RED` allocates the red plane on first use |
| `show` | — | — | Write the framebuffer to RAM and run a full display update; blocks until BUSY is low |
| `sleep` | — | — | Deep sleep (`0x10 0x03`); only a hardware reset (`wake`) restores communication; the chip RAM is lost |

**Constants:** `BLACK = 0`, `WHITE = 1`, `RED = 2`.

**Sensible defaults:** 800 × 480, 3-colour update (`0x22` = `0xF7`), internal temperature sensor, X+/Y+ data entry with the full-panel window, border `0x05`, soft start level 1, SPI Mode 0 at 4 MHz, BUSY timeout 60 s. The B/W framebuffer is `width / 8 × height` bytes (48 000 bytes at 800 × 480, 81 600 at 960 × 680), initialised to white; the red plane (same size, initialised to 0) is allocated only when the first red pixel or `clear(RED)` is requested. On a black/white-only panel the red plane stays unused; if its OTP lacks three-colour waveform sets use `MODE_BW` (confirm on hardware).

## Data Conversion

```
bytes_per_row = width // 8
index         = y * bytes_per_row + (x // 8)
bit           = 7 - (x % 8)                                  # bit 7 = leftmost pixel (assumed)

colour -> planes:  BLACK : bw=0 red=0     WHITE : bw=1 red=0     RED : bw=0 red=1
set pixel (BW) :  fb_bw[index] |=  (1 << bit)  for WHITE;   &= ~(1 << bit)  for BLACK / RED
set pixel (red):  fb_red[index] |= (1 << bit)  for RED;     &= ~(1 << bit)  otherwise

RAM Y of framebuffer row y (X+ / Y+ data entry, window YStart = 0):
    first row written (y = 0) -> RAM Y = 0; last row -> RAM Y = height - 1
window        : X = 0 .. width - 1 (pixel units, assumed) ;  Y = 0 .. height - 1
10-bit value  : bytes = v & 0xFF, (v >> 8) & 0x03             (X/Y window, counters, 0x01)

VGH  (0x03)   : code = 0x07 + round((volts - 12.0) / 0.5)    12.0 .. 20.0 V   (0x07 = 12 V, 0x17 = 20 V; POR 0x00 = 20 V)
VSH1 (0x04 A) : code = 0x23 + round((volts - 9.0) / 0.2)     9.0 .. 17.0 V    (0x23 = 9.0 V, 0x4B = 17.0 V)
VSH2 (0x04 B) : volts 2.4 ..  8.8 : code = 0x8E + round((volts - 2.4) / 0.1)   (bit 7 set, 0x8E .. 0xCE)
                volts 9.0 .. 17.0 : code = 0x23 + round((volts - 9.0) / 0.2)   (0x23 = 9.0 V, 0x4B = 17.0 V)
                (8.8 < volts < 9.0 is not representable; round to the nearer end)
VSL  (0x04 C) : code = 0x1A + 2 * round((-9.0 - volts) / 0.5)    -9.0 .. -17.0 V  (0x1A = -9 V, 0x3A = -17 V)
VCOM (0x2C)   : code = 0x08 + 4 * round((-0.2 - volts) / 0.1)    -0.2 .. -4.0 V   (0x08 = -0.2 V, 0xA0 = -4.0 V)
temperature   : v = round(celsius * 16) & 0xFFF                  (12-bit two's complement, 1/16 degC)
                bytes = (v >> 4) & 0xFF, (v & 0x0F) << 4
```

The voltage-to-code mappings are regular fits of the datasheet tables (0x03 command table: 0.5 V/step; VSH1 0.2 V/step; VSH2 0.1 V/step with bit 7 set up to 8.8 V, 0.2 V/step from 9.0 V; VSL 0.5 V per 2 codes; VCOM 0.1 V per 4 codes). The VCOM table prints `84h` as −3.2 V (a duplicate of `80h`); the regular fit (−3.3 V) is used. The lower limits differ from the SSD1680/SSD1681 (VGH ≥ 12 V, VSH1 ≥ 9 V, VSL ≥ −9 V, VCOM down to −4 V), so the drivers must not share these tables. The feature list states VGH 15 V to 20 V while the command table covers 12–20 V; the command table is used.

### Demo flow

An inject node every 10 minutes drives a function node that builds a status card (red header bar, black border, bar chart from a counter) and sends `{ clear: "white" }`, the draw messages and `{ show: true }`, followed by `{ sleep: true }` after the `{ updated: true }` reply; a second inject sends `{ wake: true }` ahead of each redraw.

## Timing Constraints

- **Power-up:** wait ≥ 10 ms after VCI before the first reset (datasheet flow §9.1).
- **Reset:** the datasheet gives no numeric reset pulse width or recovery time; the driver holds RES# low ≥ 10 ms and waits ≥ 10 ms before the first command. BUSY is high during reset; wait for it to go low.
- **Software reset:** after `0x12`, BUSY high until done; wait low, then ≥ 10 ms (flow §9.1).
- **Display update:** BUSY high for the whole `0x20` sequence; **the datasheet states neither a typical nor a maximum duration** (panel-dependent, see Overview) — the driver's default timeout is 60 s. The update must not be interrupted.
- **Commands that drive BUSY high** (datasheet command table, "BUSY pad will output high during operation"): `0x08` program initial code (OTP), `0x10` deep sleep (BUSY then **stays high** until a hardware reset), `0x12` software reset, `0x14` HV-ready detection, `0x15` VCI detection, `0x1C` write command to external temperature sensor, `0x20` master activation, `0x28` VCOM sense, `0x2A` program VCOM OTP, `0x30` program WS OTP, `0x31` load WS OTP, `0x34` CRC calculation, `0x36` program OTP selection, `0x46`/`0x47` auto-write RAM. No BUSY is stated for the other commands (including `0x18`, `0x1A`, `0x22`, `0x24`, `0x26`, `0x32`); the driver waits after each of the listed ones it uses.
- **SPI (write):** fSCL ≤ 20 MHz, SCL cycle ≥ 50 ns, SCL high/low ≥ 25 ns, CS# setup ≥ 20 ns, CS# hold ≥ 20 ns, CS# high between transfers ≥ 100 ns, data setup ≥ 10 ns / hold ≥ 40 ns (VDDIO 2.2–3.7 V, 30 pF). Read mode: fSCL ≤ 2.5 MHz, CS# setup ≥ 100 ns / hold ≥ 50 ns, CS# high ≥ 250 ns, SCL high/low ≥ 180 ns (unused).
- **Deep sleep exit:** hardware reset, then the full Initialization Sequence. Deep sleep current: 1 µA typ / 5 µA max (RAM not retained); sleep-mode current 25 µA typ / 40 µA max; operating current 2.0 mA typ.
- **Operating range:** chip −25 … +85 °C (internal temperature sensor ±2 °C accuracy from −25 to +50 °C); the OTP waveform sets cover a panel-specific temperature range (waveform lookup is by the sensed temperature, last matching range wins, no update when none matches). Panel makers advise refreshing at least every 24 hours and storing with a white image (module datasheet advice, unverified for these panels).
- **Conformance:** the datasheet defines no maximum for BUSY, so no timing check has a bound to compare against; `specs/display/ssd1677_timing.conf` defines no checks (see its header).

## Implementation Notes

- **Plain `Connection` plus three pins:** one `Connection` for SPI (CS handled by the connection, bytes sent verbatim), `OutputPin` for D/C and RES, and `InputPin` for BUSY. The driver never drives CS itself. No new `Connection` type is needed (see the DisplayConnection note under Transport Configuration).
- **BUSY is a level read:** the driver polls `busy_pin.is_high()`; this needs the `InputPin` level read of `specs/feature_inputpin_level_read.md`, which must be implemented first. Active level is **high**.
- **X address unit (key uncertainty):** unlike the SSD1680/SSD1681, whose X window is in bytes, the SSD1677 datasheet gives a 10-bit X window with a POR end value of `0x3BF` (959) and a range limit of `3BFh`, which only fits **pixel** addressing; it never states how the counter advances per data byte. The spec assumes pixel units with 8-aligned start/end. If hardware shows the counter advancing by 1 per byte, the window must be given in byte units instead (end = `width / 8 − 1`) — **verify on hardware before release** and update this note; this is the single most likely cause of a skewed or wrapped picture.
- **Temperature sensor:** `0x18` POR selects the **external** I²C sensor. On a module with nothing on TSCL/TSDA the driver selects the **internal** sensor in the Initialization Sequence; omitting this is a likely cause of "no update" on bare-controller bring-up. The `0x22` sequences `0xF7`/`0xFF` are described as loading the temperature "from I²C single master interface"; whether that also covers the internal sensor is not stated (same wording in the SSD1680/SSD1681 datasheets) — **confirm on hardware**.
- **3-colour vs B/W update (`0x22`):** the chip's POR is `0xFF`. The driver defaults to **`0xF7`**, the mode that uses the red plane and matches an OTP holding three-colour waveform sets; with an all-zero red plane the result is a pure black/white picture. On a black/white-only panel (OTP without three-colour sets) use `MODE_BW`. Which of the two OTP sets a given module carries is not in the datasheet — **confirm on hardware**, and note that the Mode 1 = three-colour mapping is inferred. The `0x37` display-option register (which WS belongs to which mode, WS 0–35) is OTP-time configuration and not exposed.
- **Orientation:** the driver writes with X increment / **Y increment** (the POR `0x11 = 0x03`), framebuffer row 0 at RAM Y 0. Whether row 0 is the physical top edge depends on how the panel is wired; `set_flip` corrects either case. Confirm on hardware.
- **Panel sizes:** the chip supports 960 sources × 680 gates (MUX 300–680 gates); smaller panels (800 × 480, 880 × 528, 480 × 280) use a subset of the outputs. Which source line is column 0 and which gate line is row 0 on a given panel is panel-dependent and not in the chip datasheet — confirm against the panel specification. `width` must be a multiple of 8.
- **Auto-fill (`0x46`/`0x47`):** not used by the driver (a full `show()` writes both planes anyway). The step height codes are 8, 16, 32, 64, 128, 256, 512 and `111` = **680**; the width codes are 8, 16, 32, 64, 128, 256, 512 and `111` = **960**. A solid full-panel fill is therefore `A[6:4] = 111`, `A[2:0] = 111` with `A[7]` the value: `0x47 0xF7` (B/W all 1 = white) and `0x46 0x77` (red all 0). Inferred from the table. The datasheet's operation flow (§9.1) reads "Command 0x46, Data 0xF7 for RAM 0x24 and Command 0x47, Data 0xF7 for RAM 0x26" — which pairs the commands with the wrong RAM (0x46 is the red-RAM fill, 0x47 the B/W fill) and would fill the red plane with 1 (= red); treat it as a typo. Reachable through `send_command`.
- **LUT size:** **105 bytes** (`0x32`) — the SSD1680/SSD1681 take 153 and the SSD1683 227. The datasheet's WS is 112 bytes: bytes 0–104 are VS/TP/RP and the five frame-rate bytes (the 5 LUTs LUT0–LUT4, LUT4 for VCOM), 105 = VGH, 106–108 = VSH1/VSH2/VSL, 109 = VCOM, 110–111 reserved. `write_lut` accepts 105 or 110 bytes.
- **No partial *refresh* waveform:** the datasheet advertises "support display partial update" but gives no partial LUT — it is waveform data supplied by the panel maker. `write_lut` takes a caller-supplied waveform; `show_region` limits only which RAM is rewritten. A partial-refresh helper would need a vendor LUT and is **not** specified. RAM ping-pong (`0x37` byte F bit 6, Display Mode 2 only) is likewise not exposed.
- **Dithering engine (`0x25`, `0x4D`):** the chip can dither on the fly (Sierra Lite `0x4D 0x80 0x00 0x78 0x00`, Floyd–Steinberg `0x4D 0x83 0x00 0x78 0x00`, stop `0x4D 0x00 0x00 0x78 0x00`; `0x4D` before the `0x25` data, stop after it), but the datasheet does not define the `0x25` data format or what the `0x78` byte (= 120 = 960 / 8) means. Not part of the API; reachable through `send_command` for experimentation.
- **Window byte units:** `show_region` widens x and w to multiples of 8 and must not exceed the panel width.
- **Red RAM must be defined:** after power-up the red RAM is undefined; in 3-colour mode stale red data would show as red pixels. `show` always writes the red plane.
- **Memory:** the B/W framebuffer is 48 000 bytes at 800 × 480 (81 600 at 960 × 680) and the red plane the same again, heap-allocated at runtime (the red one lazily), so the code builds everywhere; boards with ≤ 64 KB of RAM (Arduino AVR Mega, small Cortex-M) cannot hold the full-size framebuffer — use a smaller `width`/`height` there. Drivers must fail with a clear error (not corrupt memory) when allocation fails.
- **Blocking update:** `show()` blocks for the full refresh. On MicroPython and CircuitPython this stalls the interpreter for seconds; examples must say so. A non-blocking variant is not specified.
- **SKU mapping:** the issue lists the Waveshare 3.7inch e-Paper and 7.5inch e-Paper HD as SSD1677 modules (both unverified) and a 3.97inch 800 × 480 panel as confirmed in ESPHome. No panel specification is committed: check each module against its panel specification before claiming support, in particular its resolution (480 × 280 and 880 × 528 are *believed*, not verified), whether it is black/white only and which waveform sets its OTP carries.
- **Sibling chips:** the SSD1680 (176 × 296, issue #697) and SSD1681 (200 × 200, issue #698) are the references; the SSD1683 (400 × 300) takes a 227-byte LUT. A shared implementation helper is allowed, but each chip keeps its own class and spec.
- **Not covered:** 3-wire SPI, OTP programming (`0x08`, `0x09`, `0x2A`, `0x30`, `0x36`–`0x39`), VCOM sensing (`0x28`, `0x29`), CRC (`0x34`, `0x35`), VCI/HV-ready detection (`0x14`, `0x15`; these need the status read, which the write-only wiring cannot provide), read-RAM (`0x27`, `0x41`), the external-sensor I²C pass-through (`0x1C`), the VCOM glitch register (`0x2B`, fixed values `0x04 0x63`) and the dithering engine.
- **Datasheet status:** "Advance Information", Rev 1.0 (47 pages stated, the PDF has 46). The VGH feature range (15–20 V) disagrees with the command table (12–20 V); the VCOM table has a duplicate `84h`/`80h` entry; the operation flow's auto-fill RAM association looks swapped; there is no reset timing or refresh duration. The VCI range is 2.2–3.3 V in the DC table while the AC table conditions state VDDIO up to 3.7 V.

## Sigrok Decoder

Decoder id `ssd1677`, input **`display_spi`**: it stacks on the connection decoder `Display-SPI` (`sigrok/display_spi/`, see `specs/transport_display.md`), which frames the SPI (4-wire or 3-wire) and reports CS#, RES# and the raw BUSY level as `BYTE` / `CS` / `BUSY` / `RESET` / `IDLE` packets. The BUSY polarity is chip-level: this decoder treats BUSY **high** as busy and emits the `busy_start` / `busy_done` timing markers. Its only option is `warn_cs_split` (default `yes`). After a read command (`0x0A`, `0x1B`, `0x27`, `0x2D`, `0x2E`, `0x2F`, `0x35`) the response bytes are taken from the connection decoder's DOUT value when that channel is wired, otherwise from the shared DIN line, and are meaningful only with half-duplex wiring. Typical stack: `-P display_spi:clk=0:mosi=1:cs=2:dc=3:busy=4:res=5,ssd1677`.

Annotation rows (taxonomy order): **Data** — one annotation per command spanning the command byte and its parameter/data bytes, with decoded arguments (gate lines and GD/SM/TB, VGH/VSH1/VSH2/VSL/VCOM in volts, soft-start bytes, deep-sleep mode, data-entry mode, temperature-sensor select, temperature in °C, update-control-1 options, update sequence name for `0x22`, RAM plane with byte count and the window size, LUT byte count, X/Y window and counters, auto-fill step size); **Status** — `Busy for <duration>` spans (BUSY high) and RES# low spans; **Warnings** — unknown command, wrong parameter count (`0x32` expects 105 bytes), a command sent while BUSY is high, a RAM write larger than the window set by `0x44`/`0x45`, a data byte without a preceding command, a CS# release after a non-multiple of 8 (9) bits, and a **CS# release between a command and its parameters**.

Warning strings carry a short tag (`NOBUSY` — a command from the list under Timing Constraints for which BUSY was not already high at the CS# rising edge that completes it, skipped when BUSY is not probed; `BUSY-DROP` — BUSY went low in deep sleep, where the datasheet keeps it high; `CS-SPLIT`, `BUSY!`, `PARAM?`, `CMD?`, `WIN?`, `NOCMD`, `BITS?`). `OUTPUT_PYTHON` packets: `('COMMAND', (command_byte, parameter_bytes))`.
