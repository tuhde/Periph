# Chip Spec: SSD1683

**Manufacturer:** Solomon Systech  
**Datasheet:** `datasheets/display/ssd1683.pdf` (SSD1683 Rev 1.0, Jan 2021, "Advance Information"). Module datasheet: `datasheets/display/ssd1683_module_4.2inch_display_b_v2.pdf` (Waveshare 4.2inch e-Paper (B) V2, SKU 13379, user manual 1.0, 2025-02-21)  
**Category:** `display`  
**Transports:** SPI (4-wire, write-only)

## Overview

The SSD1683 is an active-matrix electrophoretic display (EPD) driver with controller for **red/black/white** panels of up to **400 source × 300 gate** outputs: two on-chip bit-planes of display RAM (B/W and red, 400 × 300 bits each), an on-chip oscillator, booster and regulators for the gate, source and VCOM voltages, an internal temperature sensor, OTP storage for 24 temperature-dependent waveform sets, and a programmable waveform (LUT). It is the controller of the Waveshare **4.2inch e-Paper (B) V2** module (400 × 300, black/white/red), the reference hardware for this spec.

An e-paper panel differs from an OLED/LCD in ways that shape the driver: a refresh is a **~14 s** full-panel waveform (datasheet typical at 25 °C), the picture is **bistable** (it stays with the power off), the update must not be interrupted, and BUSY is a level output that must be waited on. The driver therefore keeps a framebuffer, sends it on `show()`, and blocks until BUSY goes low again.

This spec covers **4-wire SPI**, **full-panel updates in 3-colour or black/white mode with the waveform loaded from OTP**, a user-supplied LUT, and a RAM-window write. Partial *refresh* waveforms are **not** in the datasheet and are not specified (see Implementation Notes).

## Transport Configuration

### SPI (4-wire)
- **Mode:** CPOL=0 CPHA=0 (Mode 0) — SDA is shifted in on the rising SCL edge (datasheet table 6-2); the idle level is not named, Mode 0 is the usual choice (confirm on hardware)
- **Max clock:** **20 MHz** in write mode (tSCL high/low ≥ 25 ns); the driver default is 4 MHz. Read mode is limited to 2.5 MHz and is not used
- **Bit order:** MSB first
- **CS active:** low; hold CS low for the whole command + parameter/data sequence of one transfer
- **Framing:** a plain byte stream. The **D/C# pin** is sampled on every eighth clock: low → the byte is a **command**, high → **parameter / RAM data**. The driver drives `dc_pin` (an `OutputPin`) low before each command byte and high before its parameter and data bytes. All writes are plain `connection.write(bytes)`; the connection must **not** fold register/read bits into the first byte (no register addressing — same convention as `specs/display/sh1106.md`)
- **Read:** the chip supports reads (commands `0x1B`, `0x27`, `0x2D`, `0x2E`, `0x2F`, `0x35`), but breakout modules wire **no MISO**; the driver is **write-only** and exposes no read
- **3-wire SPI (BS1 high, 9-bit frames with an embedded D/C bit):** **not supported** (byte-oriented SPI connection). On the module, BS1 is strapped low (4-wire)
- **Register addressing:** none — plain `Connection`, not `RegisterConnection`

### Power-on / reset defaults

POR values as in the table: 300 gate lines, VGH 20 V, VSH1 15 V / VSH2 5 V / VSL −15 V, X+/Y+ data entry, X window `0x00`–`0x31`, Y window `0x000`–`0x12B`, counters 0, **update sequence `0xFF`**, **external** temperature sensor selected (`0x18` = `0x48`), border HiZ. The display RAM contents are **undefined** after power-up. The status register (`0x2F`, not exposed) reads `0x01` after reset (chip ID 01).

## Display RAM

Two planes, each **400 × 300 bits** (50 bytes × 300 rows). The X address counts **bytes** (8 horizontal pixels, `0x00`–`0x31`), the Y address counts rows (`0x000`–`0x12B`). Data are written as a byte stream; after each byte the counter advances according to `0x11` within the window set by `0x44`/`0x45`, so one `0x24`/`0x26` command followed by `width/8 × height` bytes fills the whole window.

| Red RAM | B/W RAM | Colour (3-colour mode, LUT) |
|---------|---------|-----------------------------|
| 0 | 0 | black (LUTB) |
| 0 | 1 | white (LUTW) |
| 1 | 0 | red (LUTR) |

In **black/white mode** (`0x22` = `0xFF`/`0xCF`) the red plane is not a colour: red = 1 selects the other transition LUT of the same colour (the previous-image plane of the ping-pong waveform), so a B/W-mode update ignores a "red" pixel as colour. The combination red = 1, B/W = 1 is not defined by the datasheet.

**Bit order inside a byte is not stated in the datasheet.** The driver uses **bit 7 = leftmost pixel** of each 8-pixel group (common module practice); confirm on hardware.

## Initialization Sequence

Per the module datasheet's reference code (§13.2) and the chip's operation flow (§9.1), for a panel of `width × height` (default 400 × 300):

1. Wait ≥ 10 ms after VCI is applied.
2. **Hardware reset:** `res_pin` low, wait ≥ 200 µs, high, wait ≥ 200 µs; then **wait BUSY low**.
3. **Software reset** `0x12`; wait BUSY low (then ≥ 10 ms per the flow).
4. `0x18` `0x80` — **select the internal temperature sensor** (the POR selects the external I²C sensor; without one connected the sensed temperature is invalid and a waveform set may not match — "display will not be updated if no suitable temperature range matches"). The module's reference code omits this command; the chip's flow (§9.1 step 4) includes it.
5. `0x01` with `(height − 1) & 0xFF`, `(height − 1) >> 8`, `0x00` — gate lines (reference: `2B 01 00`).
6. `0x11` `0x01` — data entry X increment / Y decrement (reference code).
7. `0x44` with `0x00`, `(width / 8) − 1` (reference: `00 31`); `0x45` with `(height − 1)` low/high then `0x00 0x00` — Y window from the bottom row down to 0 (reference: `2B 01 00 00`).
8. `0x3C` `0x01` — border waveform (reference).
9. `0x0C` `0x8B 0x9C 0x96 0x0F` — booster soft start (POR values, flow §9.1 step 5).
10. Clear both RAM planes: `0x47` `0xE6` (B/W all **1** = white) and `0x46` `0x66` (red all **0**) — a single step spanning 400 × 300 is a solid fill (inferred from the step table, "300" high × "400" wide); wait BUSY low after each. If the pattern fill is not accepted on hardware the fallback is streaming `0xFF` / `0x00` bytes through `0x24` / `0x26`.

An update (`show()` / `refresh()`):

1. Set the RAM counters: `0x4E` `0x00`, `0x4F` `(height − 1)` low/high.
2. `0x24` + B/W plane bytes; then `0x4E`/`0x4F` again and `0x26` + red plane bytes (or the `0x46` fill of zeros when no red pixel was ever drawn).
3. `0x22` with the update mode (`0xF7` 3-colour, `0xFF` B/W), then `0x20`; **wait BUSY low** (typically ~14 s).

Deep sleep: `0x10` `0x01` (RAM retained, reference code) or `0x03` (RAM lost, flow §9.2). **Wake = hardware reset + the Initialization Sequence** (the framebuffer in the driver is unaffected, so the next `show()` redraws it).

## Implementation Stages

### Minimal

Goal: a 400 × 300 black/white/red e-paper panel you can draw pixels on out of the box.

| Operation | Parameters | Returns | Notes |
|-----------|------------|---------|-------|
| `init` | `connection` (SPI), `dc_pin: OutputPin`, `res_pin: OutputPin`, `busy_pin: InputPin`, `width: int = 400`, `height: int = 300`, `busy_timeout_ms: int \| None = 30000` | — | Allocates the B/W framebuffer, runs the Initialization Sequence (including the BUSY waits), leaves the display unchanged until `show()`. `width` a multiple of 8 and ≤ 400, `height` ≤ 300 |
| `clear` | `color: int = WHITE` | — | Fill the framebuffer (`WHITE`, `BLACK` or `RED`); call `show` to update the panel |
| `set_pixel` | `x: int`, `y: int`, `color: int = BLACK` | — | Framebuffer only (0 ≤ x < width, 0 ≤ y < height); out-of-range ignored. `RED` allocates the red plane on first use |
| `show` | — | — | Write the framebuffer to RAM and run a full display update; blocks until BUSY is low |
| `sleep` | — | — | Deep sleep 1 (`0x10 0x01`); only a hardware reset (`wake`) restores communication |

**Constants:** `BLACK = 0`, `WHITE = 1`, `RED = 2`.

**Sensible defaults:** 400 × 300, 3-colour update (`0x22` = `0xF7`), internal temperature sensor, X increment / Y decrement data entry with the window from the bottom row (reference flow), border `0x01`, soft start POR, SPI Mode 0 at 4 MHz, BUSY timeout 30 s (about twice the datasheet's typical refresh). The B/W framebuffer is `width / 8 × height` bytes (15 000 bytes at 400 × 300), initialised to white; the red plane (same size, initialised to 0) is allocated only when the first red pixel or `clear(RED)` is requested.

## Data Conversion

```
bytes_per_row = width // 8
index         = y * bytes_per_row + (x // 8)
bit           = 7 - (x % 8)                                  # bit 7 = leftmost pixel (assumed)

colour -> planes:  BLACK : bw=0 red=0     WHITE : bw=1 red=0     RED : bw=0 red=1
set pixel (BW) :  fb_bw[index] |=  (1 << bit)  for WHITE;   &= ~(1 << bit)  for BLACK / RED
set pixel (red):  fb_red[index] |= (1 << bit)  for RED;     &= ~(1 << bit)  otherwise

RAM Y of framebuffer row y (X+ / Y- data entry, window YStart = height-1):
    first row written (y = 0) -> RAM Y = height - 1; last row -> RAM Y = 0
window        : X = 0 .. width/8 - 1 ;  Y = height-1 downto 0

VGH  (0x03)   : code = 3 + round((volts - 10.0) / 0.5)      10.0 .. 20.0 V   (POR 0x00 = 20 V)
VSH1 (0x04 A) : code = 0x21 + round((volts - 8.6) / 0.2)    8.6 .. 17.0 V
VSH2 (0x04 B) : volts 2.4 ..  8.6 : code = 0x8E + round((volts - 2.4) / 0.1)   (bit 7 set, 0x8E .. 0xCC)
                volts 8.8 .. 17.0 : code = 0x21 + round((volts - 8.6) / 0.2)   (same as VSH1)
VSL  (0x04 C) : code = 0x0A + 2 * round((-5.0 - volts) / 0.5)    -5.0 .. -17.0 V  (0x0A = -5 V, 0x3A = -17 V)
VCOM (0x2C)   : code = 0x08 + 4 * round((-0.2 - volts) / 0.1)    -0.2 .. -3.0 V   (0x08 = -0.2 V, 0x78 = -3.0 V)
temperature   : byte = celsius & 0xFF (two's complement)
```

The voltage-to-code mappings are regular fits of the datasheet tables (0x03 command table: 0.5 V/step; VSH1/VSH2 0.2 V/step, VSH2 low range 0.1 V/step with bit 7 set; VSL 0.5 V per 2 codes; VCOM 0.1 V per 4 codes). The VGH table in the datasheet repeats two rows (`07h`/`08h`) in the 12–12.5 V range; the regular fit above is used.

## Timing Constraints

- **Power-up:** wait ≥ 10 ms after VCI before the first reset (datasheet flow §9.1 / reference code).
- **Reset:** RES# low ≥ 200 µs, then ≥ 200 µs before the first command (module reference code; the chip datasheet gives no numeric reset pulse). BUSY is high during reset; wait for it to go low.
- **Software reset:** after `0x12`, BUSY high until done; wait low, then ≥ 10 ms (flow §9.1).
- **Display update:** BUSY high for the whole `0x20` sequence; **typical 14 s at 25 °C** (module datasheet), no maximum is stated — the driver's default timeout is 30 s. The update must not be interrupted.
- **Commands that drive BUSY high** (datasheet command table, "BUSY pad will output high during operation"): `0x08` program initial code (OTP), `0x10` deep sleep (BUSY then **stays high** until a hardware reset), `0x12` software reset, `0x14` HV-ready detection, `0x15` VCI detection, `0x16` program WS password (OTP), `0x17` program OTP (auto), `0x1C` write command to external temperature sensor, `0x20` master activation, `0x28` VCOM sense, `0x2A` program VCOM OTP, `0x30` program WS OTP, `0x31` load WS OTP, `0x34` CRC calculation, `0x36` program OTP selection, `0x46`/`0x47` auto-write RAM. No BUSY is stated for the other commands (including `0x18`, `0x1A`, `0x1B`, `0x22`, `0x24`, `0x26`, `0x32`); the driver waits after each of the listed ones it uses.
- **SPI (write):** fSCL ≤ 20 MHz, CS# setup ≥ 60 ns, CS# hold ≥ 60 ns, CS# high between transfers ≥ 100 ns, SCL high/low ≥ 25 ns, data setup ≥ 10 ns / hold ≥ 40 ns (VDDIO 2.3–3.7 V). Read mode is limited to 2.5 MHz (unused).
- **Deep sleep exit:** hardware reset, then the full Initialization Sequence.
- **Refresh interval:** the module datasheet advises refreshing at least every 24 hours (ghosting / image sticking) and storing/shipping with a white image. Operating temperature 0–40 °C.
- **Conformance:** the datasheet defines no maximum for BUSY, so no timing check has a bound to compare against; `specs/display/ssd1683_timing.conf` defines no checks (see its header).

## Implementation Notes

- **Plain `Connection` plus three pins:** one `Connection` for SPI (CS handled by the connection, bytes sent verbatim), `OutputPin` for D/C and RES, and `InputPin` for BUSY. The driver never drives CS itself. No new `Connection` type is needed.
- **BUSY is a level read:** the driver polls `busy_pin.is_high()`; this needs the `InputPin` level read of `specs/feature_inputpin_level_read.md`, which must be implemented first. Active level is **high**.
- **Module datasheet BUSY note is inverted:** the Waveshare user manual's note 5-4 says "When Busy is Low, the operation of the chip should not be interrupted". The chip datasheet (BUSY pin table, "When Busy is High …"), the module's own §13.2 reference code ("Read busy pin — wait for busy low") and the status-register definition all show **BUSY high = busy**. The driver follows the chip datasheet.
- **Temperature sensor:** `0x18` POR selects the **external** I²C sensor. On a module with nothing on TSCL/TSDA the driver selects the **internal** sensor in the Initialization Sequence; omitting this is a likely cause of "no update" on bare-controller bring-up. The module's reference code does not send `0x18`, so verify on hardware that an update works either way.
- **3-colour vs B/W update (`0x22`):** the chip's POR is `0xFF` (B/W display). The module's reference code only sends `0x20` and so relies on that POR; the driver defaults to **`0xF7` (3-colour)**, which is the mode that actually uses the red plane and matches an OTP holding 3-colour waveform sets. With an all-zero red plane the result is a pure black/white picture. B/W mode (`0xFF`) needs OTP waveform sets with display mode 2 (black/white); if the panel's OTP lacks them, a B/W-mode update will not run. **Confirm on hardware** which sets the module's OTP carries before relying on `MODE_BW`.
- **Orientation:** the datasheet reference flow writes with X increment / **Y decrement** starting at the bottom row (`0x11 = 0x01`, Y from `0x12B` to `0`), while the chip's POR is `0x03` (Y increment). The driver follows the reference flow and writes framebuffer row 0 first (RAM Y = `height − 1`). Whether row 0 is the physical top edge depends on how the panel is wired; `set_flip` corrects either case. Confirm on hardware.
- **Auto-fill (`0x46`/`0x47`):** a step height of 300 and width of 400 (`A[6:4] = 110`, `A[2:0] = 110`) is intended to make a solid fill: `0x47 0xE6` (B/W = 1 = white) and `0x46 0x66` (red = 0). This is inferred from the table, not an example in the datasheet; keep the streamed-bytes fallback.
- **No partial *refresh* waveform:** the chip datasheet advertises "partial update" but the LUT (233 bytes: 227 via `0x32`, plus `0x3F`, `0x03`, `0x04`, `0x2C`) is **not** given for any panel — it is waveform data supplied by the panel maker. `write_lut` takes a caller-supplied LUT; `show_region` limits only which RAM is rewritten. A partial-refresh helper would need a vendor LUT and is **not** specified. RAM ping-pong (`0x37` byte F bit 6, B/W only, not in 3-colour mode) is likewise not exposed.
- **Window byte units:** the X window and counter are in bytes (8 pixels). `show_region` widens x and w to multiples of 8 and must not exceed the panel width.
- **Red RAM must be defined:** after power-up the red RAM is undefined; in 3-colour mode stale red data would show as red pixels. `init` clears both planes and `show` always writes (or auto-fills) the red plane.
- **Memory:** the B/W framebuffer is 15 000 bytes at 400 × 300 and the red plane another 15 000. Both are heap-allocated at runtime (the red one lazily), so the code builds everywhere, but boards with ≤ 8 KB RAM (Arduino AVR Mega) cannot run the 400 × 300 case — use a smaller `width`/`height` or a bigger board. Drivers must fail with a clear error (not corrupt memory) when allocation fails.
- **Blocking update:** `show()` blocks for the full refresh. On MicroPython and CircuitPython this stalls the interpreter for ~14 s; examples must say so. A non-blocking variant is not specified.
- **SKU mapping:** the reference module is Waveshare SKU 13379 ("4.2inch e-Paper (B) V2"), whose controller the module datasheet states as **SSD1683** (mechanical drawing note 4-6). The panel code `WFT0420CZ15` seen on some listings is not confirmed to be the same panel revision.
- **Other panels:** the chip supports up to 400 × 300; a smaller panel needs `width`/`height` set to match, and only works if its source/gate wiring suits the default scan settings (`set_gate_scan`, `set_flip`). Panel-specific RAM offsets are not covered.
- **Not covered:** 3-wire SPI, cascade mode (M/S#, CL, `0x21` bit 4), OTP programming (`0x08`, `0x16`, `0x17`, `0x30`, `0x36`–`0x39`), VCOM sensing, CRC, VCI/HV-ready detection (these need the status read, which the write-only module wiring cannot provide), and the external-sensor I²C pass-through commands (`0x1C`).
- **Datasheet status:** "Advance Information", Rev 1.0; the module manual leaves several AC values TBD and the SSD1683 datasheet's VGH table has duplicate rows.

## Sigrok Decoder

Decoder id `ssd1683`, input **`display_spi`**: it stacks on the connection decoder `Display-SPI` (`sigrok/display_spi/`, see `specs/transport_display.md`), which frames the SPI (4-wire or 3-wire) and reports CS#, RES# and the raw BUSY level as `BYTE` / `CS` / `BUSY` / `RESET` / `IDLE` packets. The BUSY polarity is chip-level: this decoder treats BUSY **high** as busy and emits the `busy_start` / `busy_done` timing markers. Its only option is `warn_cs_split` (default `yes`). After a read command (`0x1B`, `0x27`, `0x2D`, `0x2E`, `0x2F`, `0x35`) the response bytes are taken from the connection decoder's DOUT value when that channel is wired, otherwise from the shared DIN line, and are meaningful only with half-duplex wiring. Typical stack: `-P display_spi:clk=0:mosi=1:cs=2:dc=3:busy=4:res=5,ssd1683`.

Annotation rows (taxonomy order): **Data** — one annotation per command spanning the command byte and its parameter/data bytes, with decoded arguments (gate lines and GD/SM/TB, VGH/VSH1/VSH2/VSL/VCOM in volts, soft-start bytes, deep-sleep mode, data-entry mode, temperature-sensor select, temperature in °C, update-control-1 options, update sequence name for `0x22`, RAM plane with byte count and the window size, LUT byte count, X/Y window and counters, auto-fill step size); **Status** — `Busy for <duration>` spans (BUSY high) and RES# low spans; **Warnings** — unknown command, wrong parameter count (`0x32` expects 227 bytes), a command sent while BUSY is high, a RAM write larger than the window set by `0x44`/`0x45`, a data byte without a preceding command, a CS# release after a non-multiple of 8 (9) bits, and a **CS# release between a command and its parameters** (datasheet Fig. 6-1 keeps CS# low across both).

Warning strings carry a short tag (`NOBUSY` — a command from the list under Timing Constraints for which BUSY was not already high at the CS# rising edge that completes it, skipped when BUSY is not probed; `BUSY-DROP` — BUSY went low in deep sleep, where the datasheet keeps it high; `CS-SPLIT`, `BUSY!`, `PARAM?`, `CMD?`, `WIN?`, `NOCMD`, `BITS?`). `OUTPUT_PYTHON` packets: `('COMMAND', (command_byte, parameter_bytes))`.
