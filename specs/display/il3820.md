# Chip Spec: IL3820

**Manufacturer:** Good Display (Ilitek lineage; the same family as the Solomon SSD1608/SSD1673 — not verified from the documents)  
**Datasheet:** `datasheets/display/il3820.pdf` (Good Display "E paper IC Specifications" IL3820, issue date 2016-04-07, 53 pages). No panel or module datasheet is committed: the module mapping below comes from the issue's Waveshare survey and is **unverified**  
**Category:** `display`  
**Transports:** SPI (4-wire, write-only; via `DisplayConnection`)

## Overview

The IL3820 is a CMOS active-matrix bistable (EPD) display driver with controller for **black/white** panels of up to **240 source × 320 gate** outputs: **one write RAM plane** of 240 × 320 bits (9 600 bytes) with an internal second buffer for the history (previous) image, an on-chip oscillator, booster and regulators for the gate, source and VCOM voltages, OTP storage for 7 waveform sets and 6 temperature ranges, a programmable waveform (LUT, 30 bytes) and an I²C master for an external temperature sensor. There is **no red plane**. The issue names the Waveshare **2.9inch e-Paper V1** as the module (**unverified**; the issue's note says "176 × 296 panel", the Waveshare 2.9inch V1 is generally listed as 128 × 296 — either fits the controller's 240 × 320 maximum). Legacy hardware, lower priority.

This is the oldest chip of the single-plane family; it differs from the SSD1675A/SSD1680 specs in ways that shape the driver:
- **Black/white only, one write command (`0x24`).** No `0x26` red RAM, no `0x21` red/BW options. The chip holds a *current* and a *historical* buffer (datasheet §6.2); how the history buffer is filled is not specified (see Implementation Notes).
- **Two-stage update:** `0x22` selects stages *load temperature*, *load LUT*, **initial display**, **pattern display**, with disable-CP/oscillator; the initial display drives all pixels to a fixed state selected by `0x21` A[1:0].
- **Serial mode is write-only** ("under serial mode, only write operations are allowed"): no status or RAM read over SPI; BUSY is only on the BUSY pin.
- **SPI is slow:** clock cycle ≥ 250 ns → **≤ 4 MHz**; D/C# set-up and hold are 150 ns.
- **LUT is 30 bytes** (`0x32`: 20 VS bytes + 10 TP bytes); the source voltage and dummy bit travel in a 31st/32nd WS byte that `0x32` excludes.
- Small command set: VGH and VGL share one byte (`0x03`), one VSH/VSL magnitude (`0x04`), three-byte soft start, 5-bit X window, `0x1D` loads the temperature register from the sensor, no `0x74`/`0x7E`, no `0x18`, no auto-fill, no `0x2F`.

An e-paper panel differs from an OLED/LCD in ways that shape the driver: a refresh is a multi-second full-panel waveform, the picture is **bistable** (it stays with the power off), the update must not be interrupted, and BUSY is a level output that must be waited on. The driver therefore keeps a framebuffer, sends it on `show()`, and blocks until BUSY goes low again. The datasheet gives **no refresh duration**, so the default BUSY timeout is generous.

This spec covers **4-wire SPI**, full-panel updates with the **waveform loaded from OTP** or a **user-supplied waveform**, and a RAM-window write. Partial *refresh* waveforms are **not** in the datasheet and are not specified (see Implementation Notes).

## Transport Configuration

### SPI (4-wire)
- **Mode:** CPOL=0 CPHA=0 (Mode 0) — SDIN is sampled on the SCLK rising edge (datasheet table 6-6); the idle level is not named, Mode 0 is the usual choice (confirm on hardware)
- **Max clock:** clock cycle time ≥ 250 ns, SCLK low and high ≥ 100 ns each → **≤ 4 MHz**; set `clock_hz` ≤ 4 000 000 (the transport default of 4 MHz sits exactly on the limit: 2 MHz gives margin)
- **Bit order:** MSB first
- **CS active:** low; the write figure (6-5) shows CS# low across the stream of data bytes DB1…DBn; hold CS low for the whole command + parameter/data sequence of one transfer
- **Framing:** a plain byte stream. The **D/C# pin** is sampled with each byte: low → the byte is a **command**, high → **parameter / RAM data** (D/C# set-up and hold ≥ 150 ns around CS#). `DisplayConnection` drives D/C# (low for the command byte of `send_command`, high for its parameter bytes and for `send_data`); bytes are sent verbatim, no register or read bits are folded into them (no register addressing)
- **Read:** **none over SPI** ("under serial mode, only write operations are allowed"); the status read (command-less `A2` BUSY flag, chip ID 01) exists only on the parallel interfaces. The driver is **write-only** (`SIMPLEX` wire mode) and exposes no read
- **Bus selection:** `BS[2:0]`: BS2 low; **BS1 = L, BS0 = L → 4-wire SPI** (used), BS1 = L, BS0 = H → 8-bit 8080 parallel; the 6800/8080 parallel buses and the 3-wire 9-bit SPI are **not supported**. In SPI mode D0 is SCLK and D1 is SDIN (D2 open; D3–D7, E and R/W# tied to a fixed level)
- **Register addressing:** none — takes a `DisplayConnection`, not a `RegisterConnection` or a plain `Connection`

### DisplayConnection fit and required extension

The driver is written against `DisplayConnection` (`specs/transport_display.md`) in `SIMPLEX` wire mode, not a bare `Connection` plus loose pins. It owns D/C#, RES#, BUSY and CS#; the driver calls `send_command`, `send_data`, `reset` and `wait_busy` only. **The gap below is the same as for the SSD1675A, SSD1677, SSD1680 and SSD1681 specs; implement the `hold_cs` extension once for all of them.**

- **Fits as-is:** mode 0 / MSB first, D/C# framing, hardware reset (`reset_pulse_us`, `reset_settle_ms` from the constructor), BUSY level read with `wait_busy(True, timeout_ms)` (active high is passed by the driver), `clock_hz` (≤ 4 MHz), SoftSPI fallback, the mocks, and the `display_spi` Sigrok decoder.
- **Gap — CS# across a command and its parameters.** `specs/transport_display.md` makes every `send_command` / `send_data` call a separate SPI transfer, so CS# is released between the command byte and its parameters (right for the UC8276C, whose datasheet allows it) and states that a chip needing CS# held "must say so explicitly, and the interface will then need a combined-transfer operation". **This chip's figure 6-5 shows CS# held low over the data stream,** and the Sigrok decoder warns `CS-SPLIT` when CS# is released in between. The implementation must therefore **extend `DisplayConnection`** (and `specs/transport_display.md`, all platform classes and the mocks) with a `hold_cs` option: `send_command(cmd, data = [], hold_cs = False)`. With `hold_cs = True` one CS# window covers the command byte, the D/C# change to high and every byte of `data`; the default `False` keeps today's behaviour for the existing chips. The driver sends **every** command with `hold_cs = True` (a RAM write is one `send_command(0x24, frame_bytes, hold_cs = True)`).
- **Platform limit of the extension:** holding CS# while D/C# toggles needs CS# under software control (an `OutputPin` CS#, or SoftSPI). Where the kernel or SPI driver frames CS# itself (Linux spidev hardware CS, ESP-IDF `spics_io_num`, Zephyr `config.cs`), D/C# cannot change inside one framed message; there `hold_cs` must either be refused at construction with a clear error or degrade to per-call CS# (documented in the platform class), and the caller should pass a GPIO CS# for full conformance. Whether the chip tolerates CS# release between command and data is **not stated** in the datasheet (vendor reference code is reported to release CS# around every byte — unverified), so the degraded mode is acceptable pending a hardware test.
- **Large writes:** with ESP-IDF the class splits at `maxTransferBytes`; with driver-owned CS# the hold must span the chunks, otherwise each chunk becomes its own CS# window.

There is **no** red RAM (`0x26`), `0x18`, `0x3F`, auto-fill (`0x46`/`0x47`), `0x74`/`0x7E` block control or `0x2F` status read on this chip.

**`0x22` stage mask.** The datasheet lists only example values; they are consistent with one bit mask (inferred, not stated): `0x80` = clock on (CLKEN), `0x40` = charge pump on (CPEN), `0x20` = load temperature, `0x10` = load LUT, `0x08` = **initial display**, `0x04` = **pattern display**, `0x02` = charge pump off, `0x01` = clock off. Listed values: `0xFF` (POR) = clock, CP, **load temperature, load LUT, initial display, pattern display**, CP off, oscillator off; `0xF7` = the same **without the initial display**; `0xC0` = clock + CP on; `0x80` = clock on; `0x0C` = initial display + pattern display; `0x08` = initial display; `0x04` = pattern display; `0x03` = CP off + clock off; `0x01` = clock off.

### Power-on / reset defaults

POR values as in the table: 320 gate lines, VGH 22 V / VGL −20 V, VSH/VSL ±15 V, X+/Y+ data entry, X window `0x00`–`0x1D`, Y window `0x000`–`0x13F`, counters 0, dummy line 2, gate width 62 µs, soft start `0xCF 0xCE 0x8D`, initial update option `01`, update sequence `0xFF`, **temperature register `0x7FF0`** (+127.9 °C), border `0x71` (HiZ). The display RAM contents are **undefined** after power-up, and the VCOM register is loaded from OTP at reset.

## Display RAM

One write plane of **240 × 320 bits** (30 bytes × 320 rows), with an internal history buffer of the same size. The X address counts **bytes** (8 horizontal pixels, `0x00`–`0x1D`), the Y address counts rows (`0x000`–`0x13F`). Data are written as a byte stream; after each byte the counter advances according to `0x11` within the window set by `0x44`/`0x45`, so one `0x24` command followed by `width/8 × height` bytes fills the whole window. The datasheet's example (X+/Y+, AM = 0, `0x0F` = 0) shows data byte 0 at S0…S7 of G0, **bit 7 = leftmost pixel (S0)**, byte 30 at G1.

**The pixel polarity (which RAM bit is black) is not stated in this datasheet** — it depends on the LUT (GS0/GS1 are the two grey states; the waveform maps GS0 → GS1 transitions to black or white). The driver assumes the common arrangement **1 = white, 0 = black** (confirm on hardware with the module's waveform).

## Initialization Sequence

Per the chip's typical operating sequence (§9.1), for a panel of `width × height` (default 240 × 320). The datasheet gives no register values for the flow beyond the command names; the values below are POR / datasheet-table values except where marked *assumed*:

1. **Hardware reset:** `connection.reset()` (the caller builds the `DisplayConnection` with `reset_pulse_us` ≥ 10 000 and `reset_settle_ms` ≥ 10; the datasheet gives no reset timing, these are conservative values); then wait BUSY low. The flow has no software reset (`0x12` is not needed).
2. `0x01` with `(height − 1) & 0xFF`, `(height − 1) >> 8`, `0x00` — gate lines.
3. `0x03` `0xEA` (VGH 22 V, VGL −20 V) and `0x04` `0x0A` (VSH/VSL ±15 V) — the POR values, written because the flow lists them; a user waveform may change them (`set_gate_voltage`, `set_source_voltage`).
4. `0x3A` `0x02`, `0x3B` `0x08` — dummy line period and gate line width at POR (the `0x3B` remark says the default gives 50 Hz with **22** dummy lines, while the `0x3A` POR is 2; the frame rate at the POR pair is not stated).
5. `0x3C` `0x33` — border at a fixed GS level (*assumed*: `A[6] = 0` GS transition `A[1:0] = 11` GS1→GS1, i.e. the border stays in the white state; decoded from the `0x3C` table — the flow only says "select border waveform").
6. `0x11` `0x03` — data entry X increment / Y increment (the POR value).
7. `0x44` with `0x00`, `ceil(width / 8) − 1`; `0x45` with `0x00 0x00`, `(height − 1)` low/high — window covering the full panel, row 0 at RAM Y 0.
8. Set the RAM counters (`0x4E` `0x00`, `0x4F` `0x00 0x00`).

`0x0C` (soft start) and `0x2C` (VCOM) are **not** written by default: the POR soft-start values apply and the VCOM register is loaded from OTP at reset. The RAM contents are undefined after power-up, so the first `show()` always writes the full frame; `init` does not clear it.

An update (`show()` / `refresh()`):

1. Set the RAM counters: `0x4E` `0x00`, `0x4F` `0x00 0x00`.
2. `0x24` + the frame bytes.
3. `0x1A` with the temperature (default 25.0 °C → `0x19 0x00`); then **OTP waveform (default):** `0x22` `0xFF`, `0x20`; **wait BUSY low** (temperature, LUT from OTP, initial display, pattern display, power down). **User waveform** (`write_lut` was called): `0x22` `0xC0`, `0x20`, wait; `0x22` `0x0C` (initial + pattern; `0x04` when the initial display is disabled), `0x20`, wait; `0x22` `0x03`, `0x20`, wait.
4. **History-buffer sync (assumed, see Implementation Notes):** `0x4E`/`0x4F` again and `0x24` + the same frame bytes, so that the history buffer matches the panel for the next update.

Deep sleep: `0x10` `0x01` (RAM **not** retained). **Wake = hardware reset + the Initialization Sequence** (the framebuffer in the driver is unaffected, so the next `show()` rewrites it; a user waveform is re-sent by the driver after the reset).

## Implementation Stages

### Minimal

Goal: a 240 × 320 (or smaller) black/white e-paper panel you can draw pixels on out of the box.

| Operation | Parameters | Returns | Notes |
|-----------|------------|---------|-------|
| `init` | `connection` (`DisplayConnection`, `SIMPLEX`, RES and BUSY wired, `clock_hz` ≤ 4 MHz), `width: int = 240`, `height: int = 320`, `busy_timeout_ms: int \| None = 30000` | — | Allocates the framebuffer, runs the Initialization Sequence (including the BUSY wait), leaves the display unchanged until `show()`. `width` ≤ 240 (need not be a multiple of 8: the row stride is `ceil(width / 8)`), `height` ≤ 320 |
| `clear` | `color: int = WHITE` | — | Fill the framebuffer (`WHITE` or `BLACK`); call `show` to update the panel |

| `show` | — | — | Write the framebuffer to RAM, load the OTP waveform for an assumed 25 °C and run a full display update; blocks until BUSY is low |
| `sleep` | — | — | Deep sleep (`0x10 0x01`); only a hardware reset (`wake`) restores communication |

**Constants:** `BLACK = 0`, `WHITE = 1`.

**Sensible defaults:** 240 × 320, OTP waveform with an assumed **25.0 °C**, X+/Y+ data entry with the full-panel window, border `0x33`, VGH/VGL/VSH at POR, SPI Mode 0 (clock ≤ 4 MHz), BUSY timeout 30 s. The framebuffer is `ceil(width / 8) × height` bytes (9 600 at 240 × 320; 4 736 at the believed 128 × 296 panel), initialised to white. If the module's OTP holds no usable waveform, `show()` is not expected to work: use `write_lut` (Full) with the vendor waveform.

## Data Conversion

```
bytes_per_row = ceil(width / 8)
index         = y * bytes_per_row + (x // 8)
bit           = 7 - (x % 8)                                  # bit 7 = leftmost pixel
set pixel     : fb[index] |= (1 << bit)  for WHITE;   &= ~(1 << bit)  for BLACK     (assumed polarity)

RAM Y of framebuffer row y (X+ / Y+ data entry, window YStart = 0):
    first row written (y = 0) -> RAM Y = 0; last row -> RAM Y = height - 1
window        : X = 0 .. ceil(width/8) - 1 (bytes) ;  Y = 0 .. height-1   (Y as 9-bit: lo, hi)

VGH / VGL (0x03) : byte = (round((vgh - 15.0) / 0.5) << 4) | round((-vgl - 15.0) / 0.5)
                   VGH 15.0 .. 22.0 V (0x0 .. 0xE), VGL -15.0 .. -20.0 V (0x0 .. 0xA); POR 0xEA
VSH = -VSL (0x04): code = round((volts - 10.0) / 0.5)        10.0 .. 17.0 V (0x0 .. 0xE); POR 0x0A = 15 V
non-overlap (0x0B): code = clocks / 2                         4 .. 28 clocks (0x2 .. 0xE); POR 0x5 = 10
gate line width (0x3B) code -> TGate us: 30 34 38 40 44 46 52 56 62 68 78 88 104 125 156 208
temperature   : v = round(celsius * 16) & 0xFFF                  (12-bit two's complement, 1/16 degC)
                bytes = (v >> 4) & 0xFF, (v & 0x0F) << 4          25 degC -> 0x19 0x00
```

The voltage mappings are regular fits of the datasheet tables. They differ from every other SSD16xx-family spec here (VGH/VGL share one byte; VSH and VSL are one symmetric value), so the drivers must not share them. The datasheet's feature list states "VGH: 15 V to 22 V; VGL: −20 V to −15 V" and the table agrees; VCOM is deliberately not converted (no table).

## Timing Constraints

- **Power-up / reset:** the datasheet's operation flow gives **no numeric delay** (power on, HW reset, send initial code). The driver holds RES# low ≥ 10 ms and waits ≥ 10 ms before the first command.
- **Display update:** BUSY high for the whole `0x20` sequence; **the datasheet states neither a typical nor a maximum duration** (panel-dependent) — the driver's default timeout is 30 s. The update must not be interrupted.
- **BUSY high:** during `0x20` master activation, `0x1D` temperature load, `0x28` VCOM sense, `0x30`/`0x36`/`0x2A` OTP programming (pin description and flow). No BUSY is stated for `0x12`, `0x1A`, `0x24`, `0x32`; the driver waits after each `0x20` and `0x1D` it issues.
- **SPI (write):** clock cycle ≥ 250 ns, SCLK high/low ≥ 100 ns, D/C# set-up/hold ≥ 150 ns, CS# set-up ≥ 120 ns, CS# hold ≥ 60 ns, data set-up ≥ 50 ns / hold ≥ 15 ns, rise/fall ≤ 15 ns (VDDIO 2.4–3.7 V, 20 pF). There is no read mode over SPI.
- **Deep sleep exit:** hardware reset assumed (not stated), then the full Initialization Sequence; the RAM, including the history buffer, is lost. Deep sleep current 2 µA typ / 5 µA max; sleep (RAM retained) 35 µA typ / 50 µA max; operating current 2 mA typ.
- **Operating range:** chip −40 … +85 °C; the OTP holds 7 waveform sets and 6 temperature ranges (waveform 0 is the default; ranges are searched in order, the last match wins, and none matching selects WS0).
- **Conformance:** the datasheet defines no maximum for BUSY, so no timing check has a bound to compare against; `specs/display/il3820_timing.conf` defines no checks (see its header).

## Implementation Notes

- **`DisplayConnection` owns D/C#, RES#, BUSY and CS#:** the driver never touches a pin; it uses `send_command(cmd, data, hold_cs=True)`, `send_data`, `reset` and `wait_busy` from `specs/transport_display.md`. The `hold_cs` option does not exist yet — implementing it is part of this chip's work, shared with the other single-plane SSD16xx-style specs (see "DisplayConnection fit and required extension").
- **BUSY is a level read:** `wait_busy` reads BUSY through the `InputPin` level read of `specs/feature_inputpin_level_read.md`; the driver passes `busy_active_high = True`.
- **Temperature handling is uncertain:** the chip has I²C for an external sensor and a 12-bit temperature register (POR +127.9 °C, which would select the *last* matching OTP range or, if none matches, WS0). The `0x22` stage "load temperature value" is not defined as to its source (the SSD1675A document says "from I²C"; this one only says "load temperature value"). The driver writes `0x1A` before every update; whether the `0xFF`/`0xF7` loading stage then overwrites it with a sensor reading that does not exist is **unverified** — if the waveform is wrong on a module without a sensor, use a user waveform (`write_lut`) with the `0xC0`/`0x0C`/`0x03` sequence, which loads neither temperature nor LUT.
- **Module OTP and vendor flow (unverified):** the module's OTP may be blank or hold only a waveform for another temperature range; vendor example code for this chip family (not in the datasheet) is reported to send its own 30-byte LUT with `0x32` and update with a single `0x22 0xC4` + `0x20` (the bits `0xC0` clock/CP on plus `0x04` pattern display, without the disable stage and without loading temperature/LUT). **`0xC4` is not a listed value** (the listed ones are in the Command Set note); the driver uses the documented three-step equivalent. The module's waveform is **not** in the datasheet and is not transcribed here; obtain it from the vendor and pass it to `write_lut`.
- **History buffer and the second write:** the datasheet says one RAM holds the historical image and the other the current one but defines no command to write the history RAM and no swap rule. A differential waveform (GS transitions between old and new) needs the history to equal what the panel shows; the *initial display* stage (all pixels to a fixed GS state per `0x21` A[1:0], POR GS0 → GS1) is the datasheet's way to establish a known state, and the OLD-RAM bypass (`0x21` A[7] with the value in A[4]) replaces the history with a constant. The driver's step 4 (write the frame a second time after the refresh) is a **precaution from vendor practice**, harmless if the chip does not need it; whether the buffers swap on update is **unconfirmed — verify on hardware**, and drop step 4 if it proves unnecessary. After deep sleep or a power cycle both buffers are undefined, so the first update must include the initial display stage (the default does).
- **Initial display stage:** it drives every pixel from GSC to GSD (`0x21` A[1:0], POR `01` = GS0 → GS1), which on most panels is a full-screen flash; `set_initial_display(False)` skips it for a faster, differential update (only with a correct history buffer).
- **LUT size:** **30 bytes** (`0x32`) — WS bytes 0–19 are `VS[n]` for the four transitions (GS0→GS0, GS0→GS1, GS1→GS0, GS1→GS1), 2 bits each, 20 phases (bytes `n`: `VS[n-11]`, `VS[n-10]`, `VS[n-01]`, `VS[n-00]` in bits 7:6, 5:4, 3:2, 1:0), bytes 20–29 are the 20 phase lengths `TP[n]` (4 bits each, 0–15 frames, 0 = skipped; byte 20 = `TP[1]`:`TP[0]`, …), and WS byte 30/31 carry VSH/VSL and a dummy bit that `0x32` **excludes** (the source voltage comes from `0x04`). `VS` codes: 00 VSS, 01 VSH, 10 VSL, 11 not allowed.
- **Panel sizes:** the chip supports 240 sources × 16–320 gates. The believed 128 × 296 module uses a subset (`width = 128`: 16-byte stride, window `0x00`–`0x0F`; `height = 296`); the issue's "176 × 296" would be an 22-byte stride (`0x00`–`0x15`). Which source line is column 0 is panel-dependent and not in the chip datasheet (some panels are offset or mirrored: `set_flip`; the gate start position `0x0F` can offset rows).
- **Orientation:** the driver writes with X increment / **Y increment** (the POR `0x11 = 0x03`), framebuffer row 0 at RAM Y 0. Whether row 0 is the physical top edge depends on how the panel is wired; `set_flip` corrects either case. Confirm on hardware.
- **Frame rate:** set by TGate (`0x3B`), the dummy-line period (`0x3A`) and the LUT's phase lengths; the datasheet's remark ("default gives 50 Hz with 22 dummy lines") does not match the `0x3A` POR of 2, so the frame rate at the POR pair is not stated. `set_frame_timing` is the escape hatch.
- **No partial *refresh* waveform:** the datasheet describes none; it is waveform data supplied by the panel maker. `write_lut` takes a caller-supplied waveform; `show_region` limits only which RAM is rewritten. A partial-refresh helper would need a vendor LUT and is **not** specified.
- **Window byte units:** the X window and counter are in bytes (8 pixels). `show_region` widens x and w to multiples of 8 and must not exceed the panel width.
- **Memory:** 9 600 bytes at 240 × 320 (one plane), so the code builds everywhere; boards with ≤ 8 KB RAM (Arduino AVR Mega) must use a smaller `width`/`height`. Drivers must fail with a clear error (not corrupt memory) when allocation fails.
- **Blocking update:** `show()` blocks for the full refresh. On MicroPython and CircuitPython this stalls the interpreter for seconds; examples must say so. A non-blocking variant is not specified.
- **SKU mapping:** the issue lists the Waveshare 2.9inch e-Paper V1 as an IL3820 module (unverified); no panel specification is committed. Check the module's controller marking and panel specification before claiming support (the later 2.9inch V2 uses a different controller). The panel's resolution (the issue says 176 × 296, the Waveshare listing 128 × 296) must be checked too.
- **Sibling chips:** the SSD1675A (`specs/display/ssd1675a.md`) is the closest relative with a similar command set but a different LUT (70 bytes), update sequences and temperature handling, and red RAM; a shared implementation helper for RAM windowing and drawing is allowed, but each chip keeps its own class and spec.
- **Not covered:** 3-wire SPI, the 6800/8080 parallel interfaces, cascade mode (`M/S#`, `CL`, `CLS`), OTP programming (`0x2A`, `0x30`, `0x36`, `0x37`), VCOM sensing (`0x28`, `0x29`), read-RAM and read-LUT (`0x25`, `0x33`), OTP read (`0x2D`), the status read (parallel only), the display control override (`0x07`) and the external-sensor I²C pass-through (`0x1C`).
- **Datasheet status:** issue date 2016-04-07, no revision number; the `0x2C` row prints the same code as the reserved `0x2B` and has no code table; the `0x3A` POR (2) conflicts with the `0x3B` remark (22 dummy lines); the NOP is `0xFF` (command table) while sibling chips use `0x7F`; the `0x22` stage mask is described only by examples; there is no reset timing, refresh duration or LUT example; the general description says "Active Matrix EPD" in the title but "CMOS active matrix bistable display driver" in the body and does not mention colours.

## Sigrok Decoder

Decoder id `il3820`, input **`display_spi`**: it stacks on the connection decoder `Display-SPI` (`sigrok/display_spi/`, see `specs/transport_display.md`), which frames the SPI (4-wire or 3-wire) and reports CS#, RES# and the raw BUSY level as `BYTE` / `CS` / `BUSY` / `RESET` / `IDLE` packets. The BUSY polarity is chip-level: this decoder treats BUSY **high** as busy and emits the `busy_start` / `busy_done` timing markers. Its only option is `warn_cs_split` (default `yes`). The chip has no SPI read commands (serial mode is write-only), so no response bytes are decoded. Typical stack: `-P display_spi:clk=0:mosi=1:cs=2:dc=3:busy=4:res=5,il3820`.

Annotation rows (taxonomy order): **Data** — one annotation per command spanning the command byte and its parameter/data bytes, with decoded arguments (gate lines and GD/SM/TB, VGH/VGL/VSH in volts, VCOM as a raw code, soft-start bytes, deep-sleep mode, data-entry mode, temperature in °C, update-control-1 options, stage list for `0x22`, RAM write with byte count and the window size, LUT byte count, X/Y window and counters); **Status** — `Busy for <duration>` spans (BUSY high) and RES# low spans; **Warnings** — unknown command, wrong parameter count (`0x32` expects 30 bytes), a command sent while BUSY is high, a RAM write larger than the window set by `0x44`/`0x45`, a data byte without a preceding command, a CS# release after a non-multiple of 8 (9) bits, and a **CS# release between a command and its parameters**.

Warning strings carry a short tag (`NOBUSY` — a command from the list under Timing Constraints for which BUSY was not already high at the CS# rising edge that completes it, skipped when BUSY is not probed; `CS-SPLIT`, `BUSY!`, `PARAM?`, `CMD?`, `WIN?`, `NOCMD`, `BITS?`). `OUTPUT_PYTHON` packets: `('COMMAND', (command_byte, parameter_bytes))`.
