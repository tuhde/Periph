# Chip Spec: SSD1675A

**Manufacturer:** Solomon Systech (the SSD1675A) / Good Display (the same silicon sold as **IL3897**)  
**Datasheet:** `datasheets/display/il3897.pdf` (Good Display "IL3897" IC specification, version 1.1, 2016-08-03 — the SSD1675A-family datasheet; its die-tray figure is labelled "SSD1675Z"). Supplement: `datasheets/display/ssd1675a_vs_ssd1675b_gdem0154e97lt.pdf` (Good Display "Product Program Upgrade Instructions", 3 pages: waveform and LUT-write differences between the 1675A and 1675B, GDEM0154E97LT). No panel or module datasheet is committed: the module mapping below comes from the issue's Waveshare survey and is **unverified**  
**Category:** `display`  
**Transports:** SPI (4-wire, write-only; via `DisplayConnection`)

## Overview

The SSD1675A / IL3897 is an active-matrix electrophoretic display (EPD) driver with controller for **red/black/white** panels of up to **160 source × 296 gate** outputs: two on-chip bit-planes of display RAM (B/W and red, 160 × 296 bits each = 5 920 bytes per plane), an on-chip oscillator, booster and regulators for the gate, source and VCOM voltages, OTP storage for 25 temperature-dependent waveform sets, a programmable waveform (LUT) and a cascade mode (not covered). It is the older sibling of the SSD1680 (`specs/display/ssd1680.md`) and shares its command families, RAM model and BUSY handling. The issue names the Waveshare **2.13inch e-Paper V2** as the module (IL3897, SSD1675A-compatible per third-party sources; **unverified**, believed to be a 122 × 250 black/white panel driven from a 160 × 296 controller). Legacy hardware, lower priority.

**Differences that matter to the driver (against the SSD1680):**
- **No internal temperature sensor and no `0x18` command.** The temperature that selects the OTP waveform is a 12-bit register (`0x1A`, POR `0x7FF` = +127.9 °C, i.e. the *last* range) written by the host, or loaded from an external I²C sensor by a `0x22` sequence. A driver that does not write it selects the wrong (hottest) waveform set.
- **`0x22` sequences are different and there is no "load temperature + display" combo:** `0xC7` is *display only* (no LUT load), `0x90` loads the LUT, `0xB0` loads temperature from I²C + LUT, `0x47` is display without enabling the clock. The POR value `0xFF` is not in the sequence table.
- **LUT is 70 bytes** (`0x32`), the full waveform setting 76 bytes (plus `0x03`, `0x04`, `0x3A`, `0x3B`); the frame rate is set by the dummy-line period (`0x3A`) and gate line width (`0x3B`).
- **Init needs `0x74 0x54` and `0x7E 0x3B`** (analog / digital block control).
- `0x0C` soft start has four bytes, VGH goes to 21 V (POR 21 V), VSH1/VSH2 to 18 V and VSL to −18 V, VCOM is −0.2…−3.0 V with an irregular code table, deep sleep has two modes, and `0x0F` (gate scan start), `TB` (`0x01` B[0]) and cascade exist.

**The SSD1675B is explicitly excluded.** The SSD1675B (separate datasheet, `SSD1675B.pdf` in the same upstream repository, not committed) uses a different waveform: a **100-byte** LUT (versus 70) with the gate/source/dummy-line values at LUT bytes 100–106 instead of 70–75, and a different waveform output form (Good Display's upgrade note, which shows both code listings, is committed as the supplement above). A 70-byte A-format LUT sent to a B part, or the reverse, gives a wrong waveform. This spec describes the **A** only; a B driver needs its own spec and issue. There is no read-only way to tell the two apart on a write-only module: identify the part from the module/panel documentation.

An e-paper panel differs from an OLED/LCD in ways that shape the driver: a refresh is a multi-second full-panel waveform, the picture is **bistable** (it stays with the power off), the update must not be interrupted, and BUSY is a level output that must be waited on. The driver therefore keeps a framebuffer, sends it on `show()`, and blocks until BUSY goes low again. The datasheet gives **no refresh duration**, so the default BUSY timeout is generous.

This spec covers **4-wire SPI**, full-panel updates with the **waveform loaded from OTP** (using a host-supplied temperature) or a **user-supplied waveform**, and a RAM-window write. Partial *refresh* waveforms are **not** in the datasheet and are not specified (see Implementation Notes).

## Transport Configuration

### SPI (4-wire)
- **Mode:** CPOL=0 CPHA=0 (Mode 0) — SDA is shifted in on the rising SCL edge (datasheet table 6-2); the idle level is not named, Mode 0 is the usual choice (confirm on hardware)
- **Max clock:** **20 MHz** in write mode (SCL high/low ≥ 25 ns); the driver default is 4 MHz. Read mode is limited to 2.5 MHz and is not used
- **Bit order:** MSB first
- **CS active:** low; hold CS low for the whole command + parameter/data sequence of one transfer
- **Framing:** a plain byte stream. The **D/C# pin** is sampled on every eighth clock: low → the byte is a **command**, high → **parameter / RAM data**. `DisplayConnection` drives D/C# (low for the command byte of `send_command`, high for its parameter bytes and for `send_data`); bytes are sent verbatim, no register or read bits are folded into them (no register addressing)
- **Read:** the chip supports reads (commands `0x1B`, `0x27`, `0x2D`, `0x2F`), but breakout modules wire **no MISO**; the driver is **write-only** (`SIMPLEX` wire mode) and exposes no read
- **3-wire SPI (BS1 high, 9-bit frames with an embedded D/C bit):** **not supported** (byte-oriented SPI connection). On the modules BS1 is strapped low (4-wire)
- **Register addressing:** none — takes a `DisplayConnection`, not a `RegisterConnection` or a plain `Connection`

### DisplayConnection fit and required extension

The driver is written against `DisplayConnection` (`specs/transport_display.md`) in `SIMPLEX` wire mode, not a bare `Connection` plus loose pins. It owns D/C#, RES#, BUSY and CS#; the driver calls `send_command`, `send_data`, `reset` and `wait_busy` only. **The gap below is the same as for the SSD1677, SSD1680 and SSD1681 specs; implement the `hold_cs` extension once for all of them.**

- **Fits as-is:** mode 0 / MSB first, D/C# framing, hardware reset (`reset_pulse_us`, `reset_settle_ms` from the constructor), BUSY level read with `wait_busy(True, timeout_ms)` (active high is passed by the driver), `clock_hz` (default 4 MHz, chip maximum 20 MHz), SoftSPI fallback, the mocks, and the `display_spi` Sigrok decoder.
- **Gap — CS# across a command and its parameters.** `specs/transport_display.md` makes every `send_command` / `send_data` call a separate SPI transfer, so CS# is released between the command byte and its parameters (right for the UC8276C, whose datasheet allows it) and states that a chip needing CS# held "must say so explicitly, and the interface will then need a combined-transfer operation". **This chip needs it:** the datasheet's write procedure (figure 6-1) keeps CS# low across the command byte and the parameter / RAM bytes that follow, and the Sigrok decoder warns `CS-SPLIT` when CS# is released in between. The implementation must therefore **extend `DisplayConnection`** (and `specs/transport_display.md`, all platform classes and the mocks) with a `hold_cs` option: `send_command(cmd, data = [], hold_cs = False)`. With `hold_cs = True` one CS# window covers the command byte, the D/C# change to high and every byte of `data`; the default `False` keeps today's behaviour for the existing chips. The driver sends **every** command with `hold_cs = True` (a RAM write is one `send_command(0x24, plane_bytes, hold_cs = True)`).
- **Platform limit of the extension:** holding CS# while D/C# toggles needs CS# under software control (an `OutputPin` CS#, or SoftSPI). Where the kernel or SPI driver frames CS# itself (Linux spidev hardware CS, ESP-IDF `spics_io_num`, Zephyr `config.cs`), D/C# cannot change inside one framed message; there `hold_cs` must either be refused at construction with a clear error or degrade to per-call CS# (documented in the platform class), and the caller should pass a GPIO CS# for full conformance. Whether the chip tolerates CS# release between command and data is **not stated** in the datasheet (vendor reference code is reported to release CS# around every byte — unverified), so the degraded mode is acceptable pending a hardware test.
- **Large writes:** with ESP-IDF the class splits at `maxTransferBytes`; with driver-owned CS# the hold must span the chunks, otherwise each chunk becomes its own CS# window.

## Command Set

All commands are one byte sent with D/C# = 0; parameter bytes follow with D/C# = 1. POR values in brackets. Only the commands the driver uses or exposes are listed; OTP programming, VCOM sensing, detection and cascade are not covered.

| Command | Code | Parameters | Description |
|---------|------|-----------|-------------|
| Driver output control | `0x01` | `A[7:0]`, `A[8]`, `B[2:0]` | Gate lines = `A[8:0] + 1` (POR `0x127` = 296; the chip supports 16–296). `B`: GD, SM, TB (POR 0; `TB = 1` scans G295 → G0) |
| Gate driving voltage | `0x03` | `A[4:0]` | VGH 10–21 V in 0.5 V steps (POR `0x19` = 21 V) |
| Source driving voltage | `0x04` | `A`, `B`, `C` | `A` VSH1 (POR `0x41` = 15 V), `B` VSH2 (POR `0xA8` = 5 V), `C` VSL (POR `0x32` = −15 V) |
| Booster soft start | `0x0C` | `A`, `B`, `C`, `D` | Phase 1/2/3 strength + minimum GDR off time (`A`/`B`/`C` have bit 7 = 1), phase durations in `D[5:0]` (POR `0x8B 0x9C 0x96 0x0F`) |

| Write RAM (red) | `0x26` | data… | Red plane. **1 = red**, 0 = not red |
| Write VCOM | `0x2C` | `A[7:0]` | VCOM −0.2 … −3.0 V (POR `0x00`; reloaded from OTP at reset) |

| Gate line width | `0x3B` | `A[3:0]` | TGate (POR `0x0A`; with 48 dummy lines gives 50 Hz at 296 MUX) |
| Border waveform | `0x3C` | `A[7:0]` | VBD select/level/transition (POR `0xC0` = HiZ) |

| Auto write B/W RAM | `0x47` | `A[7:0]` | Same for B/W RAM |
| RAM X counter | `0x4E` | `A[4:0]` | Address counter X (POR 0) |
| RAM Y counter | `0x4F` | `A[7:0]`, `A[8]` | Address counter Y (POR 0) |
| Analog block control | `0x74` | `0x54` | Required init value (no POR given) |
| Digital block control | `0x7E` | `0x3B` | Required init value (no POR given) |

There is **no** `0x18` temperature-sensor select, `0x3F` end option, `0x25`/`0x4D` dithering or display-mode (1/2) selection on this chip.

**`0x22` sequences** (datasheet table): `0xC7` = clock on, analog on, **display**, analog off, oscillator off (**no LUT load**); `0x90` = clock on, **load LUT** (from OTP, using the temperature register); `0xB0` = clock on, load temperature from the I²C sensor, load LUT; `0x47` = analog on, display, analog off, oscillator off (clock already on); `0x80` / `0x01` = clock on / off; `0xC0` / `0x03` = clock + analog on / off; `0x04` = display. The register's POR `0xFF` is **not** a listed sequence.

### Power-on / reset defaults

POR values as in the table: 296 gate lines, VGH 21 V, VSH1 15 V / VSH2 5 V / VSL −15 V, X+/Y+ data entry, X window `0x00`–`0x13`, Y window `0x000`–`0x127`, counters 0, dummy line 48 / gate width `0x0A`, **temperature register `0x7FF`**, border HiZ, VCOM register loaded from OTP at reset. The display RAM contents are **undefined** after power-up. The status register (`0x2F`, not exposed) reads `0x21` after reset (HV-ready flag set, chip ID 01).

## Display RAM

Two planes, each **160 × 296 bits** (20 bytes × 296 rows). The X address counts **bytes** (8 horizontal pixels, `0x00`–`0x13`), the Y address counts rows (`0x000`–`0x127`). Data are written as a byte stream; after each byte the counter advances according to `0x11` within the window set by `0x44`/`0x45`, so one `0x24`/`0x26` command followed by `width/8 × height` bytes fills the whole window. The datasheet's example (X+/Y+, AM = 0, `0x0F` = 0) shows data byte 0 at S0…S7 of G0, **bit 7 = leftmost pixel (S0)**, byte 20 at G1.

| Red RAM | B/W RAM | Colour (LUT) |
|---------|---------|--------------|
| 0 | 0 | black (LUT0) |
| 0 | 1 | white (LUT1) |
| 1 | 0 | red (LUT2) |
| 1 | 1 | red (LUT3 = LUT2) |

A black/white-only panel (the believed 2.13inch V2) uses LUT0/LUT1 only: leave the red plane at 0.

## Initialization Sequence

Per the chip's typical operating sequence (§9.1), for a panel of `width × height` (default 160 × 296). The datasheet gives no register values for the flow beyond the command names and the two block-control values; the values below are POR / datasheet-table values except where marked:

1. **Hardware reset:** `connection.reset()` (the caller builds the `DisplayConnection` with `reset_pulse_us` ≥ 10 000 and `reset_settle_ms` ≥ 10; the datasheet gives no reset timing, these are conservative values); then **wait BUSY low**.
2. **Software reset** `0x12`; wait BUSY low (BUSY high during the reset).
3. `0x74` `0x54`; `0x7E` `0x3B` (analog / digital block control).
4. `0x01` with `(height − 1) & 0xFF`, `(height − 1) >> 8`, `0x00` — gate lines.
5. `0x3A` `0x30`, `0x3B` `0x0A` — dummy line period and gate line width at their POR values (50 Hz at 296 lines; **the frame rate changes with fewer lines**, see Implementation Notes).
6. `0x3C` `0x05` — border follows LUT1 (white) (`A[7:6] = 00` GS transition, `A[1:0] = 01` LUT1; **assumed**, decoded from the `0x3C` table — the flow only says "border waveform control").
7. `0x11` `0x03` — data entry X increment / Y increment (the POR value).
8. `0x44` with `0x00`, `ceil(width / 8) − 1`; `0x45` with `0x00 0x00`, `(height − 1)` low/high — window covering the full panel, row 0 at RAM Y 0.
9. Set the RAM counters (`0x4E` `0x00`, `0x4F` `0x00 0x00`).

`0x03` (VGH), `0x04` (VSH/VSL) and `0x2C` (VCOM) are **not** written by default: the voltages come with the waveform setting (OTP or the full 76-byte user waveform) and the VCOM register is reloaded from OTP at software reset. The RAM contents are undefined after power-up, so the first `show()` always writes **both** planes in full; `init` does not clear them.

An update (`show()` / `refresh()`):

1. Set the RAM counters: `0x4E` `0x00`, `0x4F` `0x00 0x00`.
2. `0x24` + B/W plane bytes; then `0x4E`/`0x4F` again and `0x26` + red plane bytes (zeros streamed when no red pixel was ever drawn).
3. **OTP waveform (default):** `0x1A` with the temperature (default 25.0 °C → `0x19 0x00`); `0x22` `0x90`, `0x20`; **wait BUSY low** (the chip searches the temperature ranges, the last match wins, and loads the waveform). With an **external I²C sensor** selected instead: `0x22` `0xB0`, `0x20`; wait. **User waveform:** skip this step (the LUT was written with `write_lut`).
4. `0x22` `0xC7`, `0x20`; **wait BUSY low** (display).

Deep sleep: `0x10` `0x01` (mode 1, RAM retained) or `0x03` (mode 2, RAM lost). **Wake = hardware reset + the Initialization Sequence** (the framebuffer in the driver is unaffected, so the next `show()` redraws it; a user waveform is re-sent by the driver after the reset).

## Implementation Stages

### Minimal

Goal: a 160 × 296 (or smaller) black/white(/red) e-paper panel you can draw pixels on out of the box.

| Operation | Parameters | Returns | Notes |
|-----------|------------|---------|-------|
| `init` | `connection` (`DisplayConnection`, `SIMPLEX`, RES and BUSY wired), `width: int = 160`, `height: int = 296`, `busy_timeout_ms: int \| None = 30000` | — | Allocates the B/W framebuffer, runs the Initialization Sequence (including the BUSY waits), leaves the display unchanged until `show()`. `width` ≤ 160 (need not be a multiple of 8: the row stride is `ceil(width / 8)`), `height` ≤ 296 |
| `clear` | `color: int = WHITE` | — | Fill the framebuffer (`WHITE`, `BLACK` or `RED`); call `show` to update the panel |
| `set_pixel` | `x: int`, `y: int`, `color: int = BLACK` | — | Framebuffer only (0 ≤ x < width, 0 ≤ y < height); out-of-range ignored. `RED` allocates the red plane on first use |
| `show` | — | — | Write the framebuffer to RAM, load the OTP waveform for 25 °C and run a full display update; blocks until BUSY is low |
| `sleep` | — | — | Deep sleep mode 1 (`0x10 0x01`); only a hardware reset (`wake`) restores communication |

**Constants:** `BLACK = 0`, `WHITE = 1`, `RED = 2`.

**Sensible defaults:** 160 × 296, OTP waveform selected for an assumed **25.0 °C** (`0x1A`), X+/Y+ data entry with the full-panel window, border `0x05`, dummy line / gate width at POR, soft start at POR, SPI Mode 0 at 4 MHz, BUSY timeout 30 s. The B/W framebuffer is `ceil(width / 8) × height` bytes (5 920 at 160 × 296; 4 000 at the believed 122 × 250 panel), initialised to white; the red plane (same size, initialised to 0) is allocated only when the first red pixel or `clear(RED)` is requested. On a black/white-only panel never draw `RED`.

## Data Conversion

```
bytes_per_row = ceil(width / 8)
index         = y * bytes_per_row + (x // 8)
bit           = 7 - (x % 8)                                  # bit 7 = leftmost pixel
colour -> planes:  BLACK : bw=0 red=0     WHITE : bw=1 red=0     RED : bw=0 red=1
set pixel (BW) :  fb_bw[index] |=  (1 << bit)  for WHITE;   &= ~(1 << bit)  for BLACK / RED
set pixel (red):  fb_red[index] |= (1 << bit)  for RED;     &= ~(1 << bit)  otherwise

RAM Y of framebuffer row y (X+ / Y+ data entry, window YStart = 0):
    first row written (y = 0) -> RAM Y = 0; last row -> RAM Y = height - 1
window        : X = 0 .. ceil(width/8) - 1 (bytes) ;  Y = 0 .. height-1   (Y as 9-bit: lo, hi)

VGH  (0x03)   : code = 0x03 + round((volts - 10.0) / 0.5)    10.0 .. 21.0 V   (0x03 = 10 V, 0x19 = 21 V; POR 0x19)
VSH1 / VSH2 (0x04 A / B):
                volts 2.4 ..  8.8 : code = 0x8E + round((volts - 2.4) / 0.1)   (bit 7 set, 0x8E .. 0xCE)
                volts 9.0 .. 18.0 : code = 0x23 + round((volts - 9.0) / 0.2)   (0x23 = 9.0 V, 0x50 = 18.0 V)
                (8.8 < volts < 9.0 is not representable; round to the nearer end)
VSL  (0x04 C) : code = 0x1A + 2 * round((-9.0 - volts) / 0.5)    -9.0 .. -18.0 V  (0x1A = -9 V, 0x3E = -18 V)
VCOM (0x2C)   : nearest entry of this table (the datasheet table is irregular):
                -0.2:08 -0.3:0B -0.4:10 -0.5:14 -0.6:17 -0.7:1B -0.8:20 -0.9:24 -1.0:28 -1.1:2C
                -1.2:2F -1.3:34 -1.4:37 -1.5:3C -1.6:40 -1.7:44 -1.8:48 -1.9:4B -2.0:50 -2.1:54
                -2.2:58 -2.3:5B -2.4:5F -2.5:64 -2.6:68 -2.7:6C -2.8:6F -2.9:73 -3.0:78
temperature   : v = round(celsius * 16) & 0xFFF                  (12-bit two's complement, 1/16 degC)
                bytes = (v >> 4) & 0xFF, (v & 0x0F) << 4          25 degC -> 0x19 0x00
```

The VGH/VSH/VSL mappings are regular fits of the datasheet tables (0x03 command table: 0.5 V/step; VSH1/VSH2 0.1 V/step with bit 7 set up to 8.8 V, 0.2 V/step from 9.0 V; VSL 0.5 V per 2 codes); unlike the SSD1680/SSD1681 the VSH1 range starts at 2.4 V, VSL at −9 V and VGH goes to 21 V, so the drivers must not share these tables. The feature list states "VGH: 10 V to 21 V" and the table agrees.

## Timing Constraints

- **Power-up / reset:** the datasheet's operation flow gives **no numeric delay** (power on, HW reset, SW reset, wait BUSY low). The driver holds RES# low ≥ 10 ms and waits ≥ 10 ms before the first command; BUSY is high during software reset — wait for it to go low.
- **Display update:** BUSY high for the whole `0x20` sequence; **the datasheet states neither a typical nor a maximum duration** (panel-dependent) — the driver's default timeout is 30 s. The update must not be interrupted.
- **Commands that drive BUSY high** (datasheet command table, "BUSY pad will output high during operation"): `0x10` deep sleep (BUSY then **stays high** until a hardware reset), `0x12` software reset, `0x14` HV-ready detection, `0x15` VCI detection, `0x1C` write command to external temperature sensor, `0x20` master activation, `0x28` VCOM sense, `0x2A` program VCOM OTP, `0x30` program WS OTP, `0x31` load WS OTP, `0x36` program OTP selection, `0x46`/`0x47` auto-write RAM. No BUSY is stated for the other commands (including `0x1A`, `0x22`, `0x24`, `0x26`, `0x32`); the driver waits after each of the listed ones it uses.
- **SPI (write):** fSCL ≤ 20 MHz, CS# setup ≥ 20 ns, CS# hold ≥ 20 ns, CS# high between transfers ≥ 100 ns, SCL high/low ≥ 25 ns, data setup ≥ 10 ns / hold ≥ 40 ns (VDDIO 2.2–3.7 V, 20 pF). Read mode: fSCL ≤ 2.5 MHz, CS# setup ≥ 100 ns / hold ≥ 50 ns, CS# high ≥ 250 ns, SCL high/low ≥ 180 ns (unused).
- **Deep sleep exit:** hardware reset, then the full Initialization Sequence. Deep sleep current: 1 µA typ (mode 1, RAM retained) / 0.7 µA typ (mode 2), maxima TBD; sleep-mode current 20 µA typ / 35 µA max; operating current 1 mA typ.
- **Operating range:** chip −40 … +85 °C; the OTP waveform sets cover a panel-specific temperature range (lookup by the temperature register, last matching range wins; the datasheet does not say what happens when no range matches). Panel makers advise refreshing at least every 24 hours and storing with a white image (module datasheet advice, unverified for these panels).
- **Conformance:** the datasheet defines no maximum for BUSY, so no timing check has a bound to compare against; `specs/display/ssd1675a_timing.conf` defines no checks (see its header).

## Implementation Notes

- **`DisplayConnection` owns D/C#, RES#, BUSY and CS#:** the driver never touches a pin; it uses `send_command(cmd, data, hold_cs=True)`, `send_data`, `reset` and `wait_busy` from `specs/transport_display.md`. The `hold_cs` option does not exist yet — implementing it is part of this chip's work, shared with the SSD168x specs (see "DisplayConnection fit and required extension").
- **BUSY is a level read:** `wait_busy` reads BUSY through the `InputPin` level read of `specs/feature_inputpin_level_read.md`; the driver passes `busy_active_high = True`.
- **Temperature drives the waveform (key difference):** the chip has **no internal sensor** (feature list, command table). With the temperature register at its POR `0x7FF` (+127.9 °C) the OTP search picks the highest-temperature set; a driver that never writes `0x1A` (or loads from an I²C sensor) shows a wrong waveform. Minimal assumes 25.0 °C; `set_temperature` takes the host's reading. Use the OTP waveform only if the panel's OTP actually holds a waveform set — the module's OTP content is **not in the datasheet**.
- **The module likely needs a user waveform:** vendor example code for the 1675A (the Good Display upgrade note) sends the waveform from the MCU (`0x32` with 70 bytes, then `0x03`, `0x04`×3, `0x3A`, `0x3B`) followed by `0x22 0xC7` — i.e. a user LUT and a display-only update, not the OTP. The note's 1675A example LUT is a 76-byte table for a 200 × 200 panel with VGH `0x17` (20 V), VSH1 `0x41` (15 V), VSH2 `0xAC` (5.4 V), VSL `0x32` (−15 V), dummy line `0x1B`, gate width `0x07`; it is only an image in the PDF and **not transcribed** here. A module's real waveform must come from its vendor; `write_lut` accepts it (70 or 76 bytes).
- **`0xC7` is display-only:** per the datasheet table `0xC7` enables the clock and analog, displays and switches off, without loading a LUT; the typical-sequence text ("IC loads the LUT register with the waveform stored in OTP") describes the OTP case generally. The driver therefore loads the LUT explicitly (`0x90` / `0xB0`, or `write_lut`) before `0xC7`. **Confirm on hardware** that `0x90` then `0xC7` (two activations) works and that a single `0xB0` + `0x47` pair is not needed; the POR `0xFF` of `0x22` is not a documented sequence.
- **LUT size:** **70 bytes** (`0x32`) — WS byte 0–34 are the VS bytes of LUT0–LUT4 (7 groups × 5), 35–69 the TP/RP bytes (7 × 5). The datasheet text maps WS byte 70 to `0x03`, 71–73 to `0x04`, 74 to `0x3A` (dummy line) and 75 to `0x3B` (gate line width) — its own Figure 6-6 labels bytes 74–75 "Frame 1/2", which contradicts the text (the Good Display note's code agrees with the text). `write_lut` accepts 70 or 76 bytes. The SSD1675B uses 100 bytes with different positions and is **not** supported.
- **Frame rate / panel size:** `0x3A`/`0x3B` set the frame rate; the datasheet's reference values (`0x30`, `0x0A`) give 50 Hz for 296 lines. Panels with fewer gate lines have a different frame time at the same values (the vendor example uses `0x1B`/`0x07` for 200 lines); `set_frame_timing` is the escape hatch and the default is not retuned per height.
- **Orientation:** the driver writes with X increment / **Y increment** (the POR `0x11 = 0x03`), framebuffer row 0 at RAM Y 0. Whether row 0 is the physical top edge depends on how the panel is wired; `set_flip` corrects either case. Confirm on hardware.
- **Panel sizes:** the chip supports 160 sources × 16–296 gates. The believed 122 × 250 module uses a subset: `width = 122` gives a 16-byte stride (window `0x00`–`0x0F`) with the last 6 pixels of the last byte unused; which source line is column 0 is panel-dependent and not in the chip datasheet (some panels are offset or mirrored: `set_flip`).
- **Auto-fill (`0x46`/`0x47`):** not used by the driver. The step height codes are 8, 16, 32, 64, 128, 256 and `110` = **296**; the width codes are 8, 16, 32, 64, 128 and `101` = **160**. A solid full-panel fill is `A[6:4] = 110`, `A[2:0] = 101`, i.e. `0x47 0xE5` (B/W all 1 = white) and `0x46 0x65` (red all 0) — inferred from the table (the `0x46` table prints `101` = 256 for the height, like `0x47`). Reachable through `send_command`.
- **Display update control 1 (`0x21`):** one parameter byte, no source-output-mode bit.
- **No partial *refresh* waveform:** the datasheet describes none; it is waveform data supplied by the panel maker. `write_lut` takes a caller-supplied waveform; `show_region` limits only which RAM is rewritten. A partial-refresh helper would need a vendor LUT and is **not** specified.
- **Window byte units:** the X window and counter are in bytes (8 pixels). `show_region` widens x and w to multiples of 8 and must not exceed the panel width.
- **Red RAM must be defined:** after power-up the red RAM is undefined; stale red data would show as red pixels on a three-colour LUT. `show` always writes the red plane.
- **Memory:** 5 920 bytes at 160 × 296 per plane (red allocated lazily), so the code builds everywhere; boards with ≤ 8 KB RAM (Arduino AVR Mega) can run the full size only with the red plane unused — otherwise use a smaller `width`/`height`. Drivers must fail with a clear error (not corrupt memory) when allocation fails.
- **Blocking update:** `show()` blocks for the full refresh. On MicroPython and CircuitPython this stalls the interpreter for seconds; examples must say so. A non-blocking variant is not specified.
- **SKU mapping:** the issue lists the Waveshare 2.13inch e-Paper V2 as an IL3897 / SSD1675A-compatible module on third-party sources only; no panel specification is committed. Check the module's controller marking and panel specification before claiming support (the later 2.13inch V3/V4 modules use SSD1680-family parts, covered by `specs/display/ssd1680.md`). Whether a given IL3897 module is an **A** or **B** part must also be checked.
- **Sibling chips:** the SSD1680 (176 × 296) is the reference sibling; a shared implementation helper is allowed, but each chip keeps its own class and spec.
- **Not covered:** 3-wire SPI, cascade mode (`M/S#`, `CL`), OTP programming (`0x2A`, `0x30`, `0x36`, `0x37`), VCOM sensing (`0x28`, `0x29`), VCI/HV-ready detection (`0x14`, `0x15`; these need the status read, which the write-only wiring cannot provide), read-RAM (`0x27`, `0x41`) and the external-sensor I²C pass-through (`0x1C`).
- **Datasheet status:** version 1.1 of the Good Display copy; the title page says IL3897 while the die tray figure says SSD1675Z; the `0x22` POR `0xFF` is not a listed sequence; the Figure 6-6 labels for WS bytes 74–75 conflict with the register mapping; the command table prints the `0x74`/`0x7E` rows with a stray D/C# = 1 on the command byte; deep-sleep maxima are TBD; there is no reset timing, refresh duration or LUT example.

## Sigrok Decoder

Decoder id `ssd1675a`, input **`display_spi`**: it stacks on the connection decoder `Display-SPI` (`sigrok/display_spi/`, see `specs/transport_display.md`), which frames the SPI (4-wire or 3-wire) and reports CS#, RES# and the raw BUSY level as `BYTE` / `CS` / `BUSY` / `RESET` / `IDLE` packets. The BUSY polarity is chip-level: this decoder treats BUSY **high** as busy and emits the `busy_start` / `busy_done` timing markers. Its only option is `warn_cs_split` (default `yes`). After a read command (`0x1B`, `0x27`, `0x2D`, `0x2F`) the response bytes are taken from the connection decoder's DOUT value when that channel is wired, otherwise from the shared DIN line, and are meaningful only with half-duplex wiring. Typical stack: `-P display_spi:clk=0:mosi=1:cs=2:dc=3:busy=4:res=5,ssd1675a`.

Annotation rows (taxonomy order): **Data** — one annotation per command spanning the command byte and its parameter/data bytes, with decoded arguments (gate lines and GD/SM/TB, VGH/VSH1/VSH2/VSL/VCOM in volts, soft-start bytes, deep-sleep mode, data-entry mode, temperature in °C, update-control-1 options, update sequence name for `0x22`, RAM plane with byte count and the window size, LUT byte count, X/Y window and counters, auto-fill step size); **Status** — `Busy for <duration>` spans (BUSY high) and RES# low spans; **Warnings** — unknown command, wrong parameter count (`0x32` expects 70 bytes), a command sent while BUSY is high, a RAM write larger than the window set by `0x44`/`0x45`, a data byte without a preceding command, a CS# release after a non-multiple of 8 (9) bits, and a **CS# release between a command and its parameters**.

Warning strings carry a short tag (`NOBUSY` — a command from the list under Timing Constraints for which BUSY was not already high at the CS# rising edge that completes it, skipped when BUSY is not probed; `BUSY-DROP` — BUSY went low in deep sleep, where the datasheet keeps it high; `CS-SPLIT`, `BUSY!`, `PARAM?`, `CMD?`, `WIN?`, `NOCMD`, `BITS?`). `OUTPUT_PYTHON` packets: `('COMMAND', (command_byte, parameter_bytes))`.
