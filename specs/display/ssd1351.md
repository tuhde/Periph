# Chip Spec: SSD1351

**Manufacturer:** Solomon Systech  
**Datasheet:** `datasheets/display/ssd1351.pdf` (SSD1351 Rev 0.10, May 2008, "Product Preview", 57 pages — an early revision: some values are TBD and a few statements contradict each other, see Implementation Notes). No module datasheet is committed: the module mappings below come from the issue's Waveshare survey and are **unverified**  
**Category:** `display`  
**Transports:** SPI (4-wire, write-only; no BUSY output, RES# optional); the chip also has 3-wire SPI and 8/16/18-bit 6800/8080 parallel interfaces, not covered

## Overview

The SSD1351 is a driver/controller for a **128 × 128 RGB passive-matrix OLED/PLED**: 128 × 128 × 18-bit display RAM (262k colours; the driver uses the **65k RGB 5-6-5** mode), 256-step contrast current control per colour plus a 16-step master current, a programmable 63-entry gray-scale (gamma) table, row/column/colour remapping, a display start line and offset, programmable multiplexing (16–128) and a continuous **horizontal scroll**. The OLED supply **VCC (10–20 V) is external** (the module's boost). The issue names the Waveshare **1.5inch RGB OLED Module (128 × 128)** and the **1.27inch RGB OLED Module (128 × 96)** as SSD1351 modules (**unverified**).

It is the larger sibling of the SSD1331 (`specs/display/ssd1331.md`, 96 × 64); the differences that shape the driver:
- **Command parameters are sent with D/C# high.** The datasheet's command table: "Multiple byte command (D/C# = 0 for the first byte, **D/C# = 1 for the other bytes**)". The SSD1331 sends parameters with D/C# low, so its drivers send every byte as a command; **here `DisplayConnection.send_command(cmd, params)` is the right call** (the connection sends `data` with D/C# high).
- **Pixel RAM is written with an explicit command `0x5C` (Write RAM)** after the column/row window; the SSD1331 streams pixels straight after `0x15`/`0x75`.
- **No hardware drawing engine** (no line / rectangle / copy / dim / clear window); only the scroll commands (`0x96`, `0x9E`, `0x9F`) exist, so all drawing is software into the framebuffer.
- **Three-byte contrast (`0xC1`) and a separate master contrast (`0xC7`)**, a 63-entry gray table (`0xB8`, GS1–GS63), a mux-ratio command at `0xCA`, and the **command-lock quirk**: after reset the commands `0xA2`, `0xB1`, `0xB3`, `0xBB` and `0xBE` are **inaccessible** until `0xFD 0xB1` is sent.
- **The display-mode codes differ from the SSD1306 family:** `0xA4` = **all pixels OFF**, `0xA5` = all ON, **`0xA6` = normal**, `0xA7` = inverse.
- A fast SPI: **50 ns cycle (20 MHz)**; a full 65k frame is 32 768 bytes.

In serial mode the chip is **write-only**.

## Transport Configuration

### SPI (4-wire)
- **Mode:** CPOL=0 CPHA=0 (Mode 0), MSB first — SDIN is shifted in on the rising SCLK edge (datasheet 8.1.3); the idle level is not named, Mode 0 is the usual choice (confirm on hardware)
- **Clock:** the AC table gives a cycle time ≥ 50 ns (SCLK high/low ≥ 20 ns) → **20 MHz** (VDD 2.4–2.6 V, VDDIO ≥ 1.65 V). Driver default 8 MHz (a frame then takes about 33 ms); the vendor-style 4 MHz works too
- **CS#:** the write figure (8-5) shows CS# low across DB1…DBn; one CS# window per command-plus-parameters or per frame is used. The datasheet does not say whether CS# may be released between a command byte and its parameters; the per-call framing of `DisplayConnection` is the working assumption (as for the SSD1331 and SSD1327 SPI drivers) — **confirm on hardware**
- **Framing:** a plain byte stream. The **D/C# pin** is sampled on every eighth clock: low → command byte, high → command **parameter** or display data. SPI goes through a `DisplayConnection` (`specs/transport_display.md`) with `busy = None`, which owns D/C, RES and CS; the driver sends `send_command(cmd, params)` (parameters with D/C# high) and RAM data as `send_command(0x5C, pixels)` — the `data` of `send_command` is exactly the data phase
- **Interface select:** BS[1:0] = `00` selects 4-wire SPI (`0x01` 3-wire, the rest parallel); D1 left open, D2–D17 and E tied to ground, R/W# is SCLK, D0 is SDIN
- **Read:** not possible in serial mode ("only write operations are allowed"); the driver exposes no `read_*`
- **Reset:** RES# low ≥ 2 µs (tRES), registers are reset after the pulse; see Initialization Sequence for the power-up waits
- **BUSY:** none. `DisplayConnection` is used with `busy = None`; the driver never waits
- **Delay:** the display-on delays use the connection's `delay_ms()`

After a scroll command ("graphic command") the datasheet asks for a waiting time to update the GDDRAM (500 ns per pixel at VCI 2.4–3.5 V).

### Power-on / reset defaults

Display off (sleep), 128 MUX, normal segment/column and row/COM mapping (SEG0 ↔ address 0, COM0 ↔ address 0), horizontal address increment, **65k colour mode**, start line 0, column pointer 0, normal COM scan, normal display (`0xA6`), linear gray table, contrast `0x8A / 0x51 / 0x8A`, master contrast 16/16, phase length `0x82`, clock `0xD1`, pre-charge voltage `0x17`, VCOMH `0x05`, second pre-charge 8, external VSL, GPIO output low, unlocked, **commands `0xA2`/`0xB1`/`0xB3`/`0xBB`/`0xBE` locked**. The display RAM contents are **undefined** at power-up; clear it before the display is switched on.

## Display RAM

128 × 128 pixels. In 65k mode a pixel is **two bytes, high byte first**: byte 1 = `C4 C3 C2 C1 C0 B5 B4 B3`, byte 2 = `B2 B1 B0 A4 A3 A2 A1 A0` (datasheet table 8-8, 8-bit serial, 65k): the **5-bit channel C in the most significant bits, the 6-bit channel B in the middle, the 5-bit channel A in the least significant bits**. With the default colour sequence `A → B → C` (`0xA0` `A[2] = 0`) the physical sub-pixel order along the segments is A, B, C (table 8-7: `SA0 SB0 SC0 SA1 …`), so the **most significant 5 bits drive the *last* sub-pixel of each pixel**. For a standard **RGB 5-6-5** word (red in the high bits) on an RGB-ordered panel the driver therefore sets **`A[2] = 1` (colour sequence swapped: C → B → A)** so that C (high bits) is the first, red, sub-pixel — see Implementation Notes. After `0x15`/`0x75` and `0x5C`, the pointer starts at (start column, start row) and increments inside the window (column first in horizontal mode, then the next row; it wraps to the window start after the last pixel). A whole frame is `128 × 128 × 2 = 32 768` bytes.

- The segment/column remap (`A[1]`) mirrors the picture horizontally; the COM scan reverse (`A[4]`) mirrors it vertically; COM split odd/even (`A[5]`) matches panels whose COM pins are wired alternately (figure 10-4) — **which settings a panel needs is not in the chip datasheet**.
- The display start line (`0xA1`) and offset (`0xA2`) rotate which RAM row appears at which COM; with a MUX ratio below 128 only the first `MUX` rows are displayed, starting at the offset.

A 128 × 96 module (the 1.27inch) uses multiplex 96 (`0xCA 0x5F`) and, depending on its wiring, an offset and/or start line — **not in the datasheet** (figure 10-6 shows `0xA2 = 0x20` with MUX 96 as an example of mapping rows 0–95 to COM32–COM127).

## Initialization Sequence

Per the datasheet's power-on sequence (internal VDD, external VCC), with the datasheet's reset values for everything except the unlock and the colour sequence. **Not verified on a panel.**

1. Apply VCI and VDDIO. After they are stable wait ≥ 1 ms (t0, for the internal VDD), then pulse RES# low for ≥ 2 µs (t1; `connection.reset()` with `reset_pulse_us ≥ 2`) and release it. All registers are reset after the pulse.
2. After RES# goes low wait ≥ 2 µs (t2), then power on VCC (board-level; the driver cannot switch it). The vendor-style practice (as for the SSD1331) of holding RES# low for 100 ms and waiting 100 ms after it is a harmless superset: the driver waits ≥ 100 ms after the reset.
3. Send the setup commands with the display off: `0xFD 0x12` (unlock), `0xFD 0xB1` (**make `0xA2`/`0xB1`/`0xB3`/`0xBB`/`0xBE` accessible**), `0xAE`, `0xCA 0x7F` (multiplex 128; `height − 1`), `0xA1 0x00`, `0xA2 0x00`, `0xA0 remap` (default `0x44`: 65k, colour sequence swapped), `0xB9` (linear gray table), `0xC1 0x8A 0x51 0x8A` and `0xC7 0x0F` (reset values), `0xA6` (normal display).
4. Clear the display RAM: `0x15 0x00 0x7F`, `0x75 0x00 0x7F`, `0x5C`, then 32 768 bytes of `0x00`.
5. `0xAF` (display on); SEG/COM are on after tAF = 200 ms — wait 200 ms before relying on the picture.

`0xB1`, `0xB3`, `0xBB`, `0xBE`, `0xAB` and `0xB4` are left at their reset values; vendor example code (reported, unverified) sets non-reset values for the oscillator, phase length, pre-charge and contrast and a display-enhancement command (`0xB2`) that **is not in this datasheet revision**.

Sleep: `0xAE` (RAM kept); optionally disable the internal VDD regulator (`0xAB` `A[0] = 0`) to save power, and before `0xAF` re-enable it and wait ≥ 1 ms. Power-off: `0xAE`, switch VCC off, wait tOFF (typ. 100 ms, min 0), then VCI/VDDIO off. VCI must not be removed before VCC, and VDD/VCC must never be pulled to ground.

## Implementation Stages

### Minimal

Goal: a 128 × 128 colour OLED you can draw pixels on out of the box.

| Operation | Parameters | Returns | Notes |
|-----------|------------|---------|-------|
| `init` | `connection` (`DisplayConnection`, `busy=None`), `width: int = 128`, `height: int = 128`, `remap: int = 0x44` | — | Runs the Initialization Sequence (with the waits; VCC must already be applied), clears the RAM and framebuffer to black, switches the display on; `width` ≤ 128, `height` 16 … 128 |
| `clear` | `color: int = 0` | — | Fill the framebuffer (RGB565) |
| `set_pixel` | `x: int`, `y: int`, `color: int` | — | Framebuffer only; out-of-range ignored |
| `show` | — | — | `0x15 0x00 (width − 1)`, `0x75 0x00 (height − 1)`, `send_command(0x5C, framebuffer)` (the whole `width × height × 2` bytes) |
| `display_on` / `display_off` | — | — | `0xAF` / `0xAE` (the picture is kept) |

**Constants:** `WIDTH = 128`, `HEIGHT = 128` (defaults); `rgb(r, g, b)` → RGB565.

**Sensible defaults:** 128 × 128, 65k colour, remap `0x44` (colour sequence swapped so that RGB565 shows correctly on an RGB-ordered panel — see Implementation Notes), linear gray table, reset values for contrast, clocks and voltages, multiplex `height`, normal display. The framebuffer is `width × height × 2` bytes (RGB565, high byte first): **32 768 bytes** at 128 × 128, 24 576 at 128 × 96; in C++ caller-supplied.

## Data Conversion

```
rgb565(r, g, b) = ((r & 0xF8) << 8) | ((g & 0xFC) << 3) | (b >> 3)
byte order      = high byte first
index           = (y * width + x) * 2

show()          : cmd 0x15, [0, width - 1]            (parameters with D/C# high)
                  cmd 0x75, [0, height - 1]
                  cmd 0x5C, data = framebuffer         (width * height * 2 bytes, one call)
show_region()   : cmd 0x15, [x, x + w - 1]; cmd 0x75, [y, y + h - 1]; cmd 0x5C, rows y .. y+h-1 of the framebuffer, columns x .. x+w-1

Pixel word (65k): C4..C0 B5..B0 A4..A0 (high byte first) ; with remap A[2] = 1 the segment order is C, B, A -> RGB565 on an RGB panel
Master contrast : factor = (n + 1) / 16 ; segment current  = contrast / 256 * IREF * scale, scaled by the master factor
Frame rate      = fOSC / (D * K * MUX)   D = divide ratio (2 ** code), K = phase 1 + phase 2 + X DCLKs per row, MUX = multiplex ratio
                  (fOSC is TBD in this datasheet revision)
Gray scale      : default linear table GS1 = 0, GSn = 2 * (n - 1) for n >= 2, GS63 = 124 (the table is shared by the three colours)
```

## Node-RED

Node name: `periph-ssd1351` (package `node-red-contrib-periph-display`): `{ clear: color }`, `{ pixel: { x, y, color } }`, `{ line }`, `{ rect }`, `{ bitmap }`, `{ show: true }`, `{ on: true|false }`, `{ contrast: [a, b, c] }`, `{ master: n }`, `{ scroll: { direction, columns, startRow, rows, interval } }` / `{ scroll: false }`. Colours are `[r, g, b]` triplets or `"#rrggbb"` strings converted to RGB565. Config panel fields: SPI bus / chip select, D/C and RES GPIO numbers, width, height, remap, auto-show.

### Demo flow

An inject node every 100 ms drives a function node that draws a moving colour gradient bar on the 128 × 128 display and sends `{ clear: 0 }`, `{ rect … }` messages with changing colours, then `{ show: true }`; a second inject toggles `{ master: 4 }` / `{ master: 16 }`, a third starts/stops `{ scroll: … }`.

## Timing Constraints

- **Reset:** RES# low ≥ 2 µs (tRES); the register values are reset after the pulse.
- **Power sequence:** VCI/VDDIO first, wait ≥ 1 ms (t0), RES# low ≥ 2 µs (t1), wait ≥ 2 µs (t2) after RES# low, then VCC; after VCC is stable send `0xAF` — SEG/COM turn on after tAF = 200 ms. Power-off: `0xAE`, VCC off, tOFF typ. 100 ms (min 0), then VCI/VDDIO off. VCI must not be removed before VCC. These are recommended waits, not hard limits; the driver waits ≥ 100 ms after reset and 200 ms after `0xAF`.
- **Sleep exit:** with the VDD regulator disabled during sleep, enable it and wait ≥ 1 ms before `0xAF`.
- **SPI:** cycle ≥ 50 ns (SCLK high/low ≥ 20 ns), D/C# set-up/hold 15 ns, CS# set-up 20 ns / hold 10 ns, data set-up/hold 15 ns, rise/fall ≤ 15 ns — 20 MHz maximum.
- **Frame transfer:** 32 768 bytes; about 13 ms at 20 MHz, 33 ms at 8 MHz, 66 ms at 4 MHz (plus per-call overhead).
- **Scroll:** after `0x9E` the RAM must be rewritten; after a graphic command a waiting time of 500 ns per pixel is required.
- **Conformance:** none of these has a bus-decodable start/end annotation pair that the host controls (the delays are recommended waits after commands, not measured events), so `specs/display/ssd1351_timing.conf` defines no checks.

## Implementation Notes

- **Parameters with D/C# high:** unlike the SSD1331 (whose parameters are sent with D/C# low, so its driver calls `send_command(byte)` per byte), the SSD1351 command table specifies D/C# = 1 for parameter bytes: `DisplayConnection.send_command(cmd, params)` is the correct call and a RAM write is `send_command(0x5C, pixels)`. This is the opposite of `specs/display/ssd1331.md` and `specs/display/ssd1327.md` — do not copy the per-byte call pattern.
- **Command lock after reset:** `0xA2`, `0xB1`, `0xB3`, `0xBB` and `0xBE` are inaccessible after reset ("`FDh` `0xB0` … inaccessible in both lock and unlock state [reset]"); the driver must send `0xFD 0x12` and **`0xFD 0xB1`** before them, or those commands are silently ignored (a classic "contrast works but the picture is dim/offset" bring-up trap).
- **Colour order (derived, unverified):** the 65k word carries channel **C in its five most significant bits** and channel **A in the least significant five**; with the reset colour sequence `A → B → C` the first (leftmost) physical sub-pixel is A, so a standard RGB565 word (red in the high bits) would show **red and blue swapped** on an RGB-ordered panel. The driver therefore defaults to `0xA0 = 0x44` (`A[2] = 1`, C → B → A). If a module's panel is BGR-ordered, `set_color_order` flips it. Vendor code for 128 × 128 modules is reported (unverified) to use `0xA0 0x74` (adds COM scan reversal) or `0x60` (COM split without the swap); the module's real remap bits — mirroring, COM scan, COM split, colour — are **not in the chip datasheet**: if the picture is mirrored, interleaved (try `A[5]`), or has swapped colours, adjust `remap` / `set_flip` / `set_color_order`.
- **128 × 96 module (1.27inch):** use `height = 96` (multiplex `0x5F`). Which COM rows the panel is wired to is not in the datasheet: if the picture is shifted vertically or wraps, adjust `set_display_offset` / `set_start_line` (a 96-row panel on the 128-row chip typically sits at an offset of 32 rows, matching the datasheet's figure 10-6 case).
- **VSL source:** the reset state is *external VSL*, which needs an external circuit between VSL and VSS (figure 14-1). Modules built without it show distorted patterns until `set_vsl(internal=True)` is used; the module's design is not in the datasheet. The driver leaves `0xB4` alone by default.
- **`0xAB` polarity conflict:** the command table says `A[0] = 1` enables the internal VDD regulator (reset) and `A[0] = 0` selects external VDD; the command description (10.1.9) states the opposite. The table agrees with section 8.10 and the SSD1327 datasheet, so it is used; the driver never writes `0xAB` unless asked. With VCI < 2.6 V the regulator cannot be used and VDD must be supplied externally.
- **Display-mode codes:** `0xA4` blanks the display (all OFF) and `0xA6` is normal — the opposite of the SSD1306 family's `0xA4`; `set_display_mode` uses named constants. The driver's `init` sends `0xA6`.
- **No hardware drawing:** the SSD1331's graphic acceleration (line, rectangle, copy, dim window, clear window) does not exist on this chip (only horizontal scrolling). `draw_line`/`draw_rect` are software into the framebuffer.
- **Framebuffer size:** 32 768 bytes at 128 × 128 — boards with ≤ 32 KB of RAM (Arduino AVR Mega and many small Cortex-M parts) cannot hold it; use a smaller `width`/`height` (the window commands let a smaller area be shown) or `show_region` with a caller-supplied partial buffer; in C++ the buffer is the caller's and an undersized or null buffer makes `valid()` false.
- **I²C is not supported by this chip** (SPI/parallel only); there is no registry entry.
- **Scrolling:** the scroll engine runs in hardware; after `0x9E` the datasheet requires the RAM to be rewritten, so `scroll_stop` re-sends the framebuffer. The interval code `00` is a test mode; use 1–3.
- **Power:** the module's boost generates VCC; OLEDs age — keep contrast moderate and use `display_off()` when idle.
- **Product Preview datasheet:** Rev 0.10 (May 2008) lists the internal oscillator frequency and several supply currents as TBD, prints the `0xA2` reset as `0x60` while the description says 0, has the `0xAB` polarity conflict, truncates the VCOMH table at a page break and describes `A[4]` of `0xA0` as `A[1]` in places; later revisions of the SSD1351 are reported (unverified) to add commands such as `0xB2` (display enhancement) that are **not** covered by this document — a module may need them.
- **Not covered:** 3-wire SPI (BS = `01`), the 8/16/18-bit parallel interfaces, the 262k/256-colour modes, RAM read-back, the external-clock mode (CLS low) and the GPIO pins as inputs.

## Sigrok Decoder

Decoder id `ssd1351` (`sigrok/ssd1351/`), stacks on `display_spi` (D/C# and the SPI lines come from the connection decoder; BUSY is not used). Commands are decoded into named commands with arguments (column and row windows, `0x5C` RAM writes with the byte count and the window pixel count, remap bit fields, colour depth, display mode, start line, offset, multiplex, phase length, clock, VSL, GPIO, second pre-charge, gray table (63 values) and linear table, pre-charge voltage, VCOMH, per-colour contrast, master contrast, command lock, scroll setup/start/stop). Warnings: a command byte not in the table, a wrong parameter count, a locked command (`0xA2`, `0xB1`, `0xB3`, `0xBB`, `0xBE`) sent before `0xFD 0xB1` (the chip ignores it), a data write larger than the window or outside a `0x5C`, a gray table that violates the increasing rule, and `0x9E` followed by no RAM rewrite before the next `0x9F`. No timing annotation pair is emitted (the datasheet delays are recommendations, not measured events).
