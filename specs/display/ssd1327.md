# Chip Spec: SSD1327

**Manufacturer:** Solomon Systech  
**Datasheet:** `datasheets/display/ssd1327.pdf` (SSD1327 Rev 1.8, Mar 2013, "Advance Information", 66 pages). No module datasheet is committed: the module mappings below come from the issue's Waveshare survey and are **unverified**  
**Category:** `display`  
**Transports:** I²C, SPI (4-wire, write-only)

## Overview

The SSD1327 is a single-chip CMOS OLED/PLED driver with controller for common-cathode **16-level gray-scale** dot-matrix panels of up to **128 × 128** pixels: 128 segment (column) outputs, 128 common (row) outputs, **128 × 128 × 4 bits of display RAM (GDDRAM, 8 192 bytes)**, an on-chip oscillator, 256-step contrast (segment current 0–300 µA), a programmable 15-entry gray-scale (gamma) table, row/column/nibble remapping, a display start line and offset, programmable multiplexing (16–128) and a hardware horizontal scroll. The panel supply **VCC (8–18 V) is external** — the datasheet describes no charge pump. It supports 8-bit 6800/8080 parallel, 3-/4-wire SPI and I²C (400 kHz); this spec covers **I²C and 4-wire SPI**. The issue names the Waveshare **1.5inch OLED Module (16 gray scale, 128 × 128)** and the **1.32inch OLED Module (128 × 96)** as SSD1327 modules (**unverified**).

It differs from the SSD1305/SSD1306 specs (`specs/display/ssd1305.md`, `specs/display/ssd1306.md`) in ways that shape the driver:
- **4 bits per pixel, not 1.** One RAM byte holds **two horizontally adjacent pixels** (low nibble = the left pixel of the pair by default); there are **no pages**. The RAM is addressed by *column* (0–63, two pixels each) and *row* (0–127) windows.
- **16 gray levels:** a pixel value 0–15 selects the gray-scale table entry GS0–GS15 (pulse width of the current-drive phase); the driver's `set_pixel` takes a gray level.
- A different command set (`0x15`/`0x75` windows, `0xA0` remap with nibble and COM-split bits, `0xAB` VDD-regulator selection, `0xB1` phase length, `0xB8`/`0xB9` gray table, `0xFD` command lock, a column-based horizontal scroll) and **no read access** in I²C or SPI mode.
- A longer power-up (the datasheet asks for ≥ 300 ms after VCI and a 200 ms display-on delay).

The two transports share one command set. The driver family is a base class holding the command logic and framebuffer with two transport hooks, as for the SSD1305: `Ssd1327Minimal` / `Ssd1327Full` (I²C) and `Ssd1327SpiMinimal` / `Ssd1327SpiFull` (SPI) — see Implementation Notes.

## Transport Configuration

### I²C
- **Address:** `0x3C` (SA0 = VSS) — `0x3D` (SA0 = VCI); 7-bit address `0111 10 SA0`, the D/C# pin acting as SA0 (the same two addresses as the SSD1305, SSD1306, SH1106 and PCF8578/PCF8579)
- **Max clock:** 400 kHz (tcycle ≥ 2.5 µs)
- **Identity register:** none (`registry/chips.json` entry has `"id_probe": null`; it shares `0x3C`/`0x3D` with the SH1106, SSD1305, SSD1306 and PCF8578/PCF8579, which cannot be told apart)
- **Probe safety:** `write_sensitive` — every byte after the address and a control byte is a command or display data
- **Interface select pins:** BS[2:0] = `010` (I²C); CS# tied low. SDAIN (D1) and SDAOUT (D2) are shorted together as SDA (if SDAOUT is left open the chip never ACKs — tie them together; the datasheet notes the acknowledge is ignored when SDAOUT is disconnected)
- **Protocol:** write = `[addr+W] [control byte] [data byte(s)] …`. The **control byte** is `Co D/C# 0 0 0 0 0 0`: `Co = 1` means one data byte follows and then another control byte; `Co = 0` means all remaining bytes in the transaction are data. `D/C# = 0` → the data is a command (**including a command's parameter bytes**), `D/C# = 1` → display RAM data. So a command stream is `0x00, cmd, param, cmd, …` (or `0x80, cmd` per command) and a RAM stream is `0x40, d0, d1, …`. The GDDRAM column pointer increments automatically after each data write
- **Read:** the datasheet describes only the write mode for I²C (no status or RAM read); the driver is **write-only** on both transports
- **Register addressing:** none — plain `Connection` (`write`), not `RegisterConnection`

### SPI (4-wire)
- **Mode:** CPOL=0 CPHA=0 (Mode 0) — SDIN is sampled on the rising SCLK edge (D/C# "sampled on every eighth clock"); the idle level is not named in the datasheet, Mode 0 is the usual choice (confirm on hardware)
- **Max clock:** tcycle ≥ 220 ns for VCI 1.65–2.1 V (≈ 4.5 MHz) and ≥ 160 ns for VCI 2.1–3.5 V (≈ 6.25 MHz); drivers default to 4 MHz
- **Bit order:** MSB first
- **CS active:** low (CS# may be hard-wired low on a dedicated bus)
- **Framing:** a plain byte stream — no opcode or address bytes. The **D/C# pin** is sampled on every eighth clock: `D/C# = 0` → the byte is a command **or a command parameter** (the command table shows D/C# = 0 for parameter bytes), `D/C# = 1` → display RAM data. SPI goes through a `DisplayConnection` (`specs/transport_display.md`) with `busy = None`, which owns D/C, RES and CS. **Every command and parameter byte is sent with D/C# low**: the driver sends them with `send_command(byte)` (one byte per call, or one call per command with no `data`), and display RAM data with `send_data()`. The transport's `send_command(cmd, data)` sends its `data` with D/C# *high* and must **not** be used for command parameters (same note as `specs/display/ssd1331.md`)
- **CS# across a command and its parameters:** the datasheet's write figure (7-5) shows CS# low across DB1…DBn, and does not say whether CS# may be released between a command byte and its parameter; the per-call CS# framing of `DisplayConnection` is the working assumption (as for the SSD1305/SSD1306 SPI drivers). **Confirm on hardware**; if a module needs one CS# window per command, use the `hold_cs` extension of the SSD168x specs (`specs/display/ssd1680.md`, "DisplayConnection fit and required extension") once it exists
- **Read:** not possible over SPI ("no data read is provided in serial mode operation")
- **Interface select pins:** BS[2:0] = `000` (4-wire SPI); D2 left open, D3–D7, E and R/W# tied to ground
- **3-wire SPI (9-bit frames, BS[2:0] = `001`) and the parallel interfaces are not supported** (the byte-oriented SPI connection cannot send 9-bit frames)

## Command Set

Commands are single bytes sent with D/C# = 0; multi-byte commands are the command byte followed by its parameter bytes, **also with D/C# = 0**. Reset values are in parentheses.

| Command | Code | Description |
|---------|------|-------------|
| Set column address | `0x15`, then start, end | Column window in units of **two pixels (one byte)**: start 0–63 (reset 0), end 0–63 (reset 63); also sets the column pointer to start |
| Set row address | `0x75`, then start, end | Row window: start 0–127 (reset 0), end 0–127 (reset 127); also sets the row pointer to start |
| Set contrast | `0x81`, then `00`–`FF` | Segment current steps (reset `0x7F`; `0xFF` ≈ 300 µA at IREF = 10 µA, VCC = 18 V) |
| Set re-map | `0xA0`, then A | `A[0]` column address remap, `A[1]` nibble remap, `A[2]` address increment (0 horizontal = reset, 1 vertical), `A[4]` COM remap, `A[6]` COM split odd/even; bits 3, 5, 7 reserved 0. Reset `0x00` |
| Set display start line | `0xA1`, then `00`–`7F` | RAM row shown at COM0 (reset 0) |
| Set display offset | `0xA2`, then `00`–`7F` | Vertical shift by COM (reset 0) |
| Set display mode | `0xA4` / `0xA5` / `0xA6` / `0xA7` | Normal (reset) / all pixels GS15 / all pixels GS0 / inverse (GS0↔GS15, GS1↔GS14, …) |
| Set multiplex ratio | `0xA8`, then `0F`–`7F` | Ratio = data + 1: 16…128 MUX (reset `0x7F`); data 0–14 not allowed |
| Function selection A | `0xAB`, then A | `A[0] = 1` enable the internal VDD regulator (reset; needs VCI > 2.6 V), `0` external VDD |
| Display off / on | `0xAE` / `0xAF` | `0xAE` = off, sleep mode (reset); `0xAF` = on, SEG/COM on after tAF ≈ 200 ms |
| Set phase length | `0xB1`, then A | `A[3:0]` phase 1 (reset 4 DCLK), `A[7:4]` phase 2 (reset 7 DCLK), 1–15, 0 invalid. Reset `0x74` |
| Set front clock divider / oscillator | `0xB3`, then A | `A[3:0]` divide ratio − 1 (reset 0), `A[7:4]` oscillator frequency (reset 0; higher = faster) |
| Set GPIO | `0xB5`, then `A[1:0]` | `00` HiZ input disabled, `01` HiZ input enabled, `10` output low (reset), `11` output high |
| Set second pre-charge period | `0xB6`, then `A[3:0]` | 1–15 DCLK (reset 4); active only if enabled in `0xD5` A[1] |
| Set gray scale table | `0xB8`, then 15 bytes | Pulse widths (6 bits, in DCLKs) of GS1…GS15, strictly increasing (0 < GS1 < … < GS15) and GS15 > phase 1 + phase 2 |
| Select default linear gray scale table | `0xB9` | GS0 = GS1 = 0, GS2 = 2, GS3 = 4, … GS14 = 26, GS15 = 28 |
| Set pre-charge voltage | `0xBC`, then `A[3:0]` | `00h` = 0.20 × VCC … `05h` = 0.5 × VCC (reset) … `07h` = 0.613 × VCC, `08h`+ = VCOMH |
| Set VCOMH voltage | `0xBE`, then `A[2:0]` | `0` = 0.72 × VCC … `05h` = 0.82 × VCC (reset) … `07h` = 0.86 × VCC |
| Function selection B | `0xD5`, then A | `A[1] = 1` enable second pre-charge (reset 0), `A[0] = 1` external VSL (reset 0 internal). The datasheet prints the data bits as `01100010` pattern `0 1 1 0 0 0 A1 A0` |
| Set command lock | `0xFD`, then A | `0x12` unlock (reset), `0x16` lock: ignore all commands except `0xFD` 0x12 and ignore memory access |
| NOP | `0x84`–`0x86`, `0xB2`, `0xBB` | No operation |

### Scrolling commands

| Command | Code | Description |
|---------|------|-------------|
| Continuous horizontal scroll setup | `0x26` (right) / `0x27` (left), then A…G | A dummy `0x00`; B start row (0–127, reset 0); C step interval (`000` 6 frames, `001` 32, `010` 64, `011` 256, `100` 3, `101` 4, `110` 5, `111` 2); D end row (0–127, ≥ B); E start column (0–63, reset 0); F end column (0–63, ≥ E, reset 63); G dummy `0x00`. Scrolls by one column per step |
| Deactivate scroll | `0x2E` | Stops scrolling; **the RAM data must be rewritten afterwards** |
| Activate scroll | `0x2F` | Starts the scroll configured by the last `0x26`/`0x27` (valid sequences: `0x26` + params, `0x2F`; `0x27` + params, `0x2F`) |

Send `0x2E` before changing the scroll setup (the datasheet: otherwise the RAM content may be corrupted). The datasheet's feature list mentions vertical scrolling; the only vertical effect is the display start line (`0xA1`), which `set_start_line` exposes.

### Power-on / reset defaults

Display off (sleep), 128 × 128 mode, normal remap (`0xA0` = `0x00`: SEG0 ↔ address 0, COM0 ↔ address 0, horizontal increment, no nibble remap), display start line 0, column pointer 0, normal COM scan direction, contrast `0x7F`, normal display mode (`0xA4`), column window 0–63, row window 0–127, multiplex 128, internal VDD regulator enabled, phase length `0x74`, clock divide 1 / oscillator 0, pre-charge voltage `0x05`, VCOMH `0x05`, second pre-charge off, internal VSL, GPIO output low, unlocked. The display RAM contents are **undefined** at power-up; clear it before the display is switched on. (The datasheet does not state the power-on contents of the gray-scale table; the driver sends `0xB9` explicitly.)

## Display RAM

128 columns × 128 rows × 4 bits = 8 192 bytes: **one byte holds two horizontally adjacent pixels**, column address `c` (0–63) = pixels `2c` and `2c+1`, row address `r` (0–127). With the **default remap (`0xA0` = `0x00`) the low nibble (`D[3:0]`) is the left pixel (SEG `2c`) and the high nibble (`D[7:4]`) the right pixel (SEG `2c+1`)** (datasheet table 7-6: `D0[3:0]` at SEG0, `D0[7:4]` at SEG1; the first data byte goes to COM0). A pixel value 0–15 is the gray-scale table index (0 = off … 15 = brightest at the default linear table).

- **Horizontal address increment (reset, `A[2] = 0`):** after each data byte the column pointer increments; at the end of the column window it returns to the start column and the row pointer increments; after the last row it wraps to the start row. So a window of `w/2 × h` bytes written as one stream fills the window. **Used by the driver.**
- **Vertical address increment (`A[2] = 1`):** the row pointer increments first, then the column. Not used by the driver.
- **Column address remap (`A[0]`)** mirrors the *byte* order (column `c` ↔ `63 − c`); **nibble remap (`A[1]`)** swaps the nibbles inside each byte. **A horizontal mirror of the whole picture needs both bits (`A[1:0] = 11`)**; remap with one bit alone swaps pixel pairs and garbles the image (datasheet table 7-8 shows both set: `D0[3:0]` lands at SEG127).
- **COM remap (`A[4]`)** reverses the COM scan (vertical flip). **COM split odd/even (`A[6]`)** matches panels whose COM pins are wired alternately (figures 9-4/9-5); which setting a panel needs depends on its wiring — **not in the chip datasheet** (see Implementation Notes).
- The display start line (`0xA1`) and offset (`0xA2`) rotate which RAM row appears at which COM; with a MUX ratio below 128 only the first `MUX` rows are displayed.

A 128 × 96 module (the 1.32inch) uses multiplex 96 (`0xA8 0x5F`) and, depending on its wiring, an offset and/or start line — **not in the datasheet** (see Implementation Notes).

## Initialization Sequence

Per the datasheet's power-on sequence (internal VDD, external VCC):

1. Apply VCI (and VDDIO). After VCI is stable wait ≥ 1 ms (t0, for the internal VDD), then pulse RES# low for ≥ 100 µs (t1) and release it (`connection.reset()` with `reset_pulse_us ≥ 100`; for I²C wire RES# to a GPIO). All registers are reset after the pulse.
2. After RES# goes low wait ≥ 100 µs (t2), then power on VCC (board-level; the driver cannot switch it). The datasheet also states: **after VCI is stable wait at least 300 ms before sending commands** — the driver waits 300 ms after the reset.
3. Send the setup commands in one command stream with the display off (every byte with D/C# low): `0xFD 0x12` (unlock), `0xAE`, `0xA8 height−1` (multiplex), `0xA1 0x00` (start line), `0xA2 0x00` (offset), `0xA0 remap` (default `0x00`), `0xAB 0x01` (internal VDD regulator, reset value), `0x81 0x7F` (contrast), `0xB1 0x74` (phase length, reset value), `0xB3 0x00` (clock, reset value), `0xB9` (linear gray table), `0xBC 0x05`, `0xBE 0x05` (reset values), `0xA4` (normal display).
4. Clear the display RAM: `0x15 0x00 0x3F`, `0x75 0x00 0x7F`, then 8 192 bytes of `0x00`, before turning the display on.
5. `0xAF` (display on); SEG/COM are on after tAF ≈ 200 ms — wait 200 ms before relying on the picture.

Sleep: `0xAE`; the datasheet recommends then sending `0xAB 0x00` (internal VDD regulator off, "deep sleep", RAM kept but **not accessible**) to save power. Wake: `0xAB 0x01`, then `0xAF` (and wait tAF ≈ 200 ms). Power-off: `0xAE`, switch VCC off, wait tOFF (typ. 100 ms, min 0), then VCI off. VCI must never be removed before VCC, and VCC/VCI must never be pulled to ground.

## Implementation Stages

### Minimal

Goal: a 128 × 128 gray-scale OLED you can draw pixels on out of the box.

## Data Conversion

```
bytes_per_row = width // 2
index         = y * bytes_per_row + (x // 2)
set pixel     : if x is even : fb[index] = (fb[index] & 0xF0) | gray          # low nibble = left pixel
                else         : fb[index] = (fb[index] & 0x0F) | (gray << 4)   # high nibble = right pixel
get pixel     : (fb[index] >> (4 * (x % 2))) & 0x0F

show()        : cmd stream: 0x15, 0x00, bytes_per_row - 1, 0x75, 0x00, height - 1      (all with D/C# low)
                data stream: fb[0 .. bytes_per_row * height - 1]
show_region() : cmd stream: 0x15, x // 2, (x + w) // 2 - 1, 0x75, y, y + h - 1   (x, w even)
                data stream: for each row r in y .. y+h-1 : fb[r * bytes_per_row + x // 2 .. + w // 2 - 1]

I²C control bytes:  0x00  = last control byte, following bytes are commands (and parameters)
                    0x80  = one command byte follows, then another control byte
                    0x40  = last control byte, following bytes are display data
SPI:  D/C# low for command and parameter bytes, D/C# high for display data bytes

Frame rate     = fOSC / (D * K * MUX)      D = divide ratio, K = phase 1 + phase 2 + X DCLKs per row (default K = 4 + 7 + 30 = 41),
                                           MUX = multiplex ratio; fOSC 535 .. 655 kHz (595 typ) at the reset oscillator setting -> about 113 Hz at 128 MUX
Segment current = contrast / 256 * IREF * 32      (IREF = 10 uA -> ISEG about 300 uA at contrast 255)
Gray scale     : pixel value g (0..15) -> pulse width of GS(g); default linear table: GS0 = GS1 = 0, GSn = 2 * (n - 1) for n >= 2 (GS15 = 28)
```

The 4-bit RAM nibble is the pixel's gray-scale table index; the visible brightness is the table's pulse width times the contrast current, so `set_gray_table` doubles as gamma correction (the datasheet's figure 9-15).

| `{ line: { x0, y0, x1, y1, gray } }` / `{ rect: { x, y, w, h, gray, fill } }` | — | Draw primitives |
| `{ bitmap: { x, y, w, h, data: [..], gray } }` | — | Blit a 1-bpp row-major bitmap |
| `{ contrast: N }` / `{ invert: bool }` / `{ display: bool }` | — | Settings |
| `{ scroll: { direction: "left"\|"right", startRow, endRow, interval } }` / `{ scroll: false }` | — | Start / stop hardware horizontal scrolling |
| `{ startLine: N }` | — | Set display start line |
| `{ show: true }` | — | Flush the framebuffer |

Config panel fields: transport (I²C / SPI), I²C bus and address (`0x3C`/`0x3D`) or SPI bus/chip-select with D/C and RES GPIO numbers, width, height, remap, auto-show.

### Demo flow

An inject node every 100 ms drives a function node that draws a moving gray gradient bar on the 128 × 128 display and sends `{ clear: 0 }`, `{ rect … }` messages with increasing `gray`, then `{ show: true }`; a second inject toggles `{ invert: true }` / `{ invert: false }`, a third sets `{ contrast: N }` from a slider, a fourth starts/stops `{ scroll: … }`.

## Timing Constraints

- **Reset:** RES# low ≥ 2 µs (AC table) and ≥ 100 µs (power-on figure); registers are reset after the pulse.
- **Power sequence:** VCI first, wait ≥ 1 ms (t0), RES# low ≥ 100 µs (t1), wait ≥ 100 µs (t2) after RES# low, then VCC; after VCI is stable wait ≥ 300 ms before sending commands; after `0xAF` SEG/COM turn on after tAF = 200 ms. Power-off: `0xAE`, VCC off, tOFF typ. 100 ms (min 0), then VCI off. VCI must not be removed before VCC. These are recommended waits, not hard limits.
- **I²C:** tcycle ≥ 2.5 µs (≤ 400 kHz), start hold/setup ≥ 0.6 µs, stop setup ≥ 0.6 µs, data setup ≥ 100 ns, data hold ≥ 300 ns (SDAIN), bus idle time tIDLE ≥ 1.3 µs between transmissions.
- **SPI:** SCLK cycle ≥ 220 ns (VCI 1.65–2.1 V) / ≥ 160 ns (2.1–3.5 V), clock high ≥ 20 ns, clock low ≥ 25/20 ns, D/C# set-up/hold 15 ns, CS# set-up 20 ns / hold 10 ns, data set-up 15 ns / hold 30/15 ns — hence the 4 MHz default.
- **Scrolling:** after `0x2E` (scroll off) the RAM must be rewritten; scroll setup commands must not be issued while scrolling is active.
- **Conformance:** none of these has a bus-decodable start/end annotation pair that the host controls (the delays are recommended waits after commands, not measured events), so `specs/display/ssd1327_timing.conf` defines no checks.

## Implementation Notes

- **One base class, two transports:** implement an abstract base (`_Ssd1327Base`) with the framebuffer, drawing, and command logic and two hooks `write_commands(bytes)` / `write_data(bytes)`. The I²C classes prepend the control byte (`0x00`/`0x40`) to every transaction (one `connection.write` per stream, chunked to the platform's maximum write size; every chunk of data repeats the `0x40` control byte); the SPI classes call `DisplayConnection.send_command()` for every command **and parameter** byte and `send_data()` for RAM data. SPI RAM data can be sent as a single transaction per frame or window.
- **Plain `Connection`, not `RegisterConnection`:** the control byte is not a register address; same style as the SSD1305/SH1106 drivers. The SPI connection must not fold read/burst bits into the first byte.
- **I²C transaction sizes:** some platform I²C layers limit a write to 32 bytes (Arduino `Wire`); an 8 192-byte frame is then 256+ chunks (each chunk a fresh `0x40` control byte; the pointer keeps advancing between chunks) — **a full frame over I²C at 400 kHz takes roughly 0.2–0.3 s**, so animations should use `show_region`, or SPI.
- **Panel-specific remap (not in the datasheet):** many 128 × 128 modules need `A[6]` (COM split) and/or the column/nibble/COM remap bits set — vendor example code for such modules is reported (unverified) to use `0xA0 0x51` (column remap, COM remap, COM split) together with a start line / offset of 0 — otherwise the picture is mirrored or shows interleaved rows. The driver's default is the datasheet reset value `0x00`; `init(remap=…)` and `set_flip` / `set_remap` adjust it for the panel. If the picture looks like two interleaved halves, try `A[6] = 1`; if it is mirrored, `set_flip`.
- **128 × 96 module (1.32inch):** use `height = 96` (multiplex `0x5F`). Which COM rows the panel is wired to is not in the datasheet: if the picture is shifted vertically or wrapped, adjust `set_display_offset` / `set_start_line` (a 96-row panel on the 128-row chip often sits at an offset of 16 or 32 rows).
- **Nibble order:** the default RAM order puts the *left* pixel in the *low* nibble (the opposite of the usual "high nibble first" convention); drivers must not assume otherwise. With the column + nibble remap (`set_flip(horizontal=True)`) the whole picture mirrors; the framebuffer layout is unchanged.
- **Command parameters use D/C# = 0:** on SPI every parameter byte of a command is sent as a command byte (D/C# low); only display RAM data is sent with D/C# high. Sending a parameter as data corrupts the RAM and leaves the command incomplete.
- **VCC and VDD:** VCC (8–18 V) is external; VCI must be ≥ VDD at all times; the internal VDD regulator needs VCI > 2.6 V (`0xAB 0x01`, the reset value). With a 1.8 V-supplied module (VCI < 2.6 V) the regulator must be disabled and VDD tied to VCI (`0xAB 0x00`) — then there is **no deep-sleep saving** and the RAM stays accessible.
- **Deep sleep:** `sleep()` followed by `0xAB 0x00` keeps the RAM, but "no RAM access through the MCU interface when there is no VDD": the driver must send `0xAB 0x01` (and wait) before touching the RAM or turning the display on again; `wake()` does.
- **Gray table rules:** GS1 < GS2 < … < GS15 must hold strictly (and GS15 > phase 1 + phase 2), or the chip behaviour is undefined; `set_gray_table` rejects invalid tables. The frame rate depends on GS15 (the current-drive length enters `K`).
- **Scrolling:** the scroll engine runs in hardware and moves one column per step; after `0x2E` the datasheet requires the RAM to be rewritten, so `scroll_stop` re-sends the framebuffer. The step-interval codes are not monotonic (`000` = 6 frames, `100` = 3, `101` = 4, `110` = 5, `111` = 2, `001` = 32, `010` = 64, `011` = 256) — the driver takes a table index 0–7 mapped to the register codes `{0: 6 frames, 1: 32, 2: 64, 3: 256, 4: 3, 5: 4, 6: 5, 7: 2}`.
- **Command lock:** `0xFD 0x16` locks the interface until `0xFD 0x12`; the driver sends the unlock in the initialization sequence so a locked panel recovers after a reset-less restart.
- **Read access:** none on either transport (the driver keeps a framebuffer). The parallel interfaces have a read path; they are not covered.
- **Advance Information datasheet:** Rev 1.8 is marked "Advance Information"; the SPI mode and the module wiring (remap, offset) are not stated and are marked above as derived. The `0xD5` row's data-bit pattern is printed inconsistently (`A[2:0]` with `0 1 1 0 0 0 A1 A0`): only `A[1:0]` are defined.
- **Not covered:** parallel (6800/8080) and 3-wire SPI interfaces, the external-clock mode (CLS low), the GPIO pins as inputs, and the external VSL option beyond the raw `set_external_vsl`.
- **Datasheet:** SSD1327 Rev 1.8 (`https://github.com/CursedHardware/epd-driver-ic/blob/master/SSD1327.pdf`, 66 pages).

## Sigrok Decoder

Two decoders sharing one command table: `ssd1327` (input `['i2c']`, addresses `0x3C`/`0x3D`) and `ssd1327_spi` (input `['spi']`; the D/C# line is read from an optional logic channel, otherwise every transfer is shown as raw bytes). The I²C decoder splits each write into control bytes (`Co`, `D/C#`) and payload; command payloads are decoded into named commands with arguments (column and row windows, contrast, remap bit fields, start line, offset, display mode, multiplex, VDD regulator, display on/off, phase length, clock divide / oscillator, GPIO, second pre-charge, gray-scale table (15 widths), linear table, pre-charge voltage, VCOMH, function selection B, command lock, scroll setup/activate/deactivate); multi-byte commands consume their parameter bytes, and data payloads are shown with the current window and the byte count; each data byte can be rendered as two 4-bit gray values. There are no reads to decode. Warnings: a command byte not in the table, a parameter byte arriving as display data (SPI, D/C# high after a multi-byte command), an out-of-range window (column > 63, row > 127), a gray table that is not strictly increasing, a scroll setup command issued while scrolling is active, and a data write larger than the active window. No timing annotation pair is emitted (the datasheet delays are recommendations, not measured events).
