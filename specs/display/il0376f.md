# Chip Spec: IL0376F

**Manufacturer:** Good Display (Ilitek lineage; the datasheet is an UltraChip-lineage text: "Registers … reserved by UltraChip", "All-in-one driver IC with TCON for Color application")  
**Datasheet:** `datasheets/display/il0376f.pdf` (Good Display "E paper IC Specifications" IL0376F, issue date 2016-04-07, 43 pages, preliminary: package and loading values are TBD). No panel or module datasheet is committed: the module mapping below comes from the issue's Waveshare survey and is **unverified**  
**Category:** `display`  
**Transports:** SPI (4-wire; write-only or half-duplex, via `DisplayConnection`)

## Overview

The IL0376F is an all-in-one driver with timing controller for **black/white/red** electrophoretic (EPD) panels of up to **200 source × 300 gate** outputs. It is **not** a member of the single-bit-plane UC8151/UC8176 sub-family used by the other 400 × 300 e-paper specs: its source driver has **2 bits per pixel for black/white (four levels: white, two grays, black) plus 1 bit for red**, the frame memory is 200 × 300 × 3 bit, and the waveform is built from **eight host-written LUTs** (`0x20`–`0x27`): VCOM1, White, Black, Gray1, Gray2, VCOM2, Red0, Red1. It has an on-chip DC-DC converter (gate ±17…±20 V, source ±2.4…±8 V and ±15 V), a built-in temperature sensor with an I²C master for an external LM75, a low-power detector and a cascade mode (not covered). **The datasheet lists no OTP and no `REG_EN` bit: there is no on-chip waveform, so a driver cannot refresh the panel without LUTs, and the datasheet contains no example LUT.** The issue names the Waveshare **1.54inch e-Paper (B/C) V1** as the module (**unverified**; believed to be a 200 × 200 black/white/red panel). Legacy hardware, lowest priority of the e-paper list.

Differences from the other e-paper specs that shape the driver:
- **2-bit black/white pixels (4 pixels per byte) and 1-bit red pixels (8 per byte)**, so a frame is `ceil(width/4) × height` bytes for `DTM1` and `ceil(width/8) × height` for `DTM2`.
- **No OTP waveform, no `DSLP`, no `PTL`/partial window, no `AUTO`.** The only low-power state is `POF`.
- **`PSR`:** `RES` 94×230 (POR) / 94×252 / 128×296 / 200×300, `KWR` bit (0 = K/W/Red running both LUT1 and LUT2, 1 = K/W with LUT1 only); no `REG_EN` and no `BWR` naming.
- **`PWR` is a four-byte command** with the source-supply selection `RVSHLS` and programmable red-LUT source levels (`VDPS_LV`/`VDNS_LV`).
- **`TRES` is three bytes** (`HRES[7:1]`, `VRES[8]`, `VRES[7:0]`, 2-pixel horizontal granularity, up to 254), **no `TSGS`**, `VDCS`/`VV` count 0.1 V per code from 0 V.
- Frame rate comes from `PLL` (M/N table, POR `0x2A` = 50 Hz).
- The temperature sensor is only needed to pick OTP waveforms, which this chip has none of; the datasheet's sequences send `TSE` ("TSE off", `0x41`) before the LUTs.

The chip differs from an OLED/LCD in ways that shape the driver: a refresh is a long full-panel waveform (**no duration is stated**), the picture is **bistable**, and the display is powered on (`PON`), refreshed (`DRF`) and powered off (`POF`) around every update, with BUSY_N waited on after each step. The driver keeps a framebuffer and sends it on `show()`.

This spec covers **4-wire SPI**, full-panel updates with a **host-supplied waveform set**, black/white/red and four-level gray, and, with a half-duplex wire mode, the read commands. **Nothing in this spec has been verified on a panel, and the waveform is the open problem** (see Implementation Notes).

## Transport Configuration

### SPI (4-wire)
- **Mode:** CPOL=0 CPHA=0 (Mode 0), MSB first
- **Max clock:** write cycle ≥ 100 ns (SCL high/low ≥ 35 ns each) → **10 MHz**. The feature list's "operating frequency 20 MHz (max)" contradicts the AC table; the AC table is used. Driver default 4 MHz. **Read** cycle ≥ **150 ns** (high/low ≥ 60 ns) → ≤ 6.6 MHz; reads are short and the driver uses its write clock capped at 4 MHz
- **CS active:** low (CSB). Commands are processed on the stop condition (CSB rising edge: note 3 of the command table). The datasheet states (4-wire figure): **"CSB can be H between parameter-command and command-parameter"**, with SCL and SDA invalid while CSB is high — so the per-call CS framing of `DisplayConnection` is acceptable (**no `hold_cs` extension is needed**; compare the SSD168x specs)
- **Framing:** a byte stream; the **DC pin** is sampled per 8-bit group and "keeps the same value during the whole 8-bit cycle": low → command, high → parameter/data/read. Bytes are sent verbatim — no register address, no read/write bit
- **Bus selection:** pin **BS** low = 4-wire, high = 3-wire (9-bit frames; **power-on default per the pin table**, so the module's strap decides). The driver requires **4-wire**; the BS strap is board-specific. 3-wire framing is **not supported**
- **Bidirectional SDA:** the chip's SDA pin is an I/O. Read commands (listed under Command Set) clock data out on SDA after the command byte, with DC high and CSB low. Whether the board exposes DOUT depends on the wiring → `DisplayConnection` wire mode (`SIMPLEX` / `HALF_DUPLEX_HW` / `HALF_DUPLEX_PIN`, see `specs/transport_display.md`). `SIMPLEX` is sufficient for everything in Minimal
- **Register addressing:** none — takes a `DisplayConnection`, not a `RegisterConnection`

## Command Set

All commands are one byte sent with DC low; parameters follow with DC high. POR values in brackets. All registers are accessible **only when BUSY_N is high**, except `PWR`, `PFS`, `PON`, `PMES`, `BTST`, `LPD` and `FLG` (note 5 of the command table). Only commands the driver uses or exposes are listed.

**Not covered:** cascade (`MS`, `CL`, `VSYNC`), PMES, the external-sensor pass-through (`0x42`, `0x43`), AMV, 3-wire SPI. The datasheet lists **no** `DSLP`, `AUTO`, partial-window, OTP-programming or `0x30`-based `OSC` commands.

### BUSY_N flag

BUSY_N goes low after `POF`, `PON` (and, per the description, after `DTM1` + `DSP`), `DRF`, and while the temperature sensor is read. Commands are accepted only while BUSY_N is high (see above for the exceptions). Data and LUT commands raise no BUSY_N.

### Power-on / reset defaults

PSR `0x0F` (94 × 230, **K/W/Red**, scan up, shift right, DC-DC on), PWR `0x03 0x00 0x08 0x08`, PFS 1 frame, BTST `0x0F 0x0E 0x0D`, PLL `0x2A` (50 Hz), CDI `0x17`, TCON `0x22`, TSE internal, TRES 0, VDCS 0 V. The display RAM and the **LUT registers** are undefined after power-up.

## Display RAM

Three bit-planes in the controller: 2 bits per pixel for black/white (`DTM1`) and 1 bit per pixel for red (`DTM2`), each written as a plain stream from the first pixel to the last (no address counter or window commands). Pixel order within a row is source order (`S0` first with `SHL = 1`), rows in gate-scan order (`G0` first with `UD = 1`).

| `DTM1` (DDX = 1) | Level |
|------------------|-------|
| `00` | black |
| `01` | Gray1 |
| `10` | Gray2 |
| `11` | white |

The drive is **per pixel value and waveform, not NEW/OLD**: the LUT of the pixel's value (`LUTB`, `LUTG1`, `LUTG2`, `LUTW`; `LUTR0`/`LUTR1` for the red plane) is applied; there is no previous-image plane, so every refresh is a full drive.

**The combination of K/W and red data is not specified.** In `KWR = 0` the chip runs "both LU1 and LU2". The driver writes **white (`11`) in the K/W plane under every red pixel** and the red value in the red plane (assumed: white drive first, then the red waveform), and `0` ("not red", assumed `Red0`) elsewhere. Confirm on hardware; if the roles of `Red0`/`Red1` are the other way round, set `DDX = 0` for the red plane's sake — which also inverts the K/W plane mapping, so the driver would then invert its K/W stream.

## Initialization Sequence

Derived from the datasheet's command descriptions and its data-transmission / display-refresh waveform figures (`TSE`, LUTs, data, `DSP` or `DRF`). **Not verified on an IL0376F panel**, and the LUT contents come from the caller (see Implementation Notes).

1. Apply VDD/VDDIO; BS strapped low (4-wire).
2. **Hardware reset:** `RST_N` low ≥ 10 ms, then high; wait ≥ 10 ms, then BUSY_N high (the datasheet states no timing; conservative values).
3. `PSR` `0xDF` for K/W (`RES = 11` 200 × 300, `KWR = 1`, scan up, shift right, DC-DC on) or `0xCF` for K/W/Red.
4. `PWR` `0x0F 0x00 0x08 0x08` (**assumed**: both internal supplies on and `RVSHLS = 11` so the K/W levels "15 V (VSH)" / "−15 V (VSL)" of the LUT table exist; gate ±20/−19.3 V; red-LUT source ±4.0 V at their POR). The datasheet does not say which `RVSHLS` a given panel needs — `set_power` overrides it.
5. `TRES` with `(width, height)`: `HRES` as one byte (`width & 0xFE`), then `VRES` high/low (`0xC8 0x01 0x2C` for 200 × 300, `0xC8 0x00 0xC8` for 200 × 200).
6. `CDI` `0x17` (DDX = 1, 10 hsync, border normal): written explicitly.
7. `TSE` `0x80` (internal sensor off, as in the datasheet's figures: "TSE off (41h)" before the LUTs).
8. The eight LUTs `0x20`–`0x27` from the caller's waveform set (KW mode may skip the red LUTs `0x25`–`0x27`, but writing them is harmless).

An update (`show()`):

1. `DTM1` + `ceil(width/4) × height` bytes (2 bpp, pixel 1 in D7:D6); `DTM2` + `ceil(width/8) × height` bytes (red; zeros when no red was drawn).
2. `PON`; wait BUSY_N high.
3. `DRF`; wait BUSY_N high (refresh, no stated duration).
4. `POF`; wait BUSY_N high.

(The datasheet's figures show two ways to start a refresh: "Data Start Transmission + Data Stop" and "Display Refresh (12h)". The driver uses `DRF` and does not send `DSP`; the `PON`/`POF` wrap follows the sibling chips and is **unverified** for this one.)

Low power: `POF`. **There is no deep sleep:** `sleep()` powers off, `wake()` re-runs the Initialization Sequence (after a hardware reset the LUT registers are lost).

## Implementation Stages

### Minimal

Goal: a 200 × 300 (or smaller) black/white e-paper panel you can draw pixels on, given the module's waveform.

| Operation | Parameters | Returns | Notes |
|-----------|------------|---------|-------|
| `init` | `connection` (`DisplayConnection`), `waveform: bytes \| tuple` (the eight 15-byte LUTs in command order `0x20`…`0x27`, 120 bytes), `width: int = 200`, `height: int = 300`, `busy_timeout_ms: int \| None = 30000` | — | Allocates the framebuffer, runs the Initialization Sequence in K/W mode (including the BUSY_N wait), leaves the panel unchanged until `show()`. `width` even and ≤ 200 (`TRES` resolves 2 pixels), `height` ≤ 300 |

| `show` | — | — | Write both planes, `PON` → `DRF` → `POF`; blocks until BUSY_N is high again |
| `sleep` | — | — | `POF` (if on); `wake()` re-initialises |

**Constants:** `BLACK = 0`, `GRAY1 = 1`, `GRAY2 = 2`, `WHITE = 3` (the `DTM1` codes at `DDX = 1`), `RED = 4` (Full / KWR only).

**Sensible defaults:** 200 × 300 K/W, internal DC-DC, PWR `0x0F 0x00 0x08 0x08`, soft start, PLL, TCON at power-on values, CDI `0x17`, SPI Mode 0 at 4 MHz, BUSY timeout 30 s (not derived from the datasheet; measure the real refresh and adjust). **There is no default waveform**: `waveform` is a required argument until a vendor waveform has been verified on hardware and added as a constant. The K/W framebuffer is `ceil(width / 4) × height` bytes at 2 bits per pixel, MSB-first (**15 000** at 200 × 300; 10 000 at the believed 200 × 200 panel), initialised to white; the `DTM1` stream is the framebuffer verbatim. In C++ the buffer is caller-supplied (`valid()` instead of exceptions). Works with `SIMPLEX` wiring.

## Data Conversion

```
bytes_per_row_kw  = ceil(width / 4)                  # 2 bits per pixel
bytes_per_row_red = ceil(width / 8)                  # 1 bit per pixel
index_kw   = y * bytes_per_row_kw + (x // 4)
shift      = 6 - 2 * (x % 4)                          # pixel 1 in D7:D6
set pixel  : fb_kw[index_kw] = (fb_kw[index_kw] & ~(3 << shift)) | (level << shift)
             level: BLACK=0, GRAY1=1, GRAY2=2, WHITE=3                (DDX = 1)
RED pixel  : fb_kw level = WHITE (3) ; fb_red[y * bytes_per_row_red + (x // 8)] |= (1 << (7 - (x % 8)))      (assumed, see Display RAM)
non-red    : fb_red bit = 0

TRES:       b0 = width & 0xFE ; b1 = (height >> 8) & 1 ; b2 = height & 0xFF        200 x 300 -> C8 01 2C ; 200 x 200 -> C8 00 C8
```

## Timing Constraints

- **Reset:** the datasheet gives no reset pulse width or recovery time; the driver holds RST_N low ≥ 10 ms and waits ≥ 10 ms (`DisplayConnection.reset()`), then BUSY_N high.
- **Power on / off:** BUSY_N goes low for the power-on and power-off sequences (the datasheet's power sequence figures are empty in the text extraction; no durations are stated); the driver waits for BUSY_N each time.
- **Refresh:** after `DRF`, BUSY_N goes low and the panel refreshes. **No duration or maximum is stated**; the refresh length follows from the caller's LUTs (frames × the PLL frame rate, 50 Hz at POR). The driver default timeout is 30 s (a driver choice). The update must not be interrupted.
- **Commands that drive BUSY_N low:** `POF`, `PON`, `DRF`, and `DTM1` + `DSP` (the driver does not use `DSP`); the temperature sensor read. The driver waits BUSY_N high after each of PON, DRF, POF.
- **SPI (write):** tSCYCW ≥ 100 ns, SCL high/low ≥ 35 ns, CSB setup (tCSS) ≥ 60 ns, CSB hold (tCSH) ≥ 65 ns, CSB-to-clock (tSCC) ≥ 20 ns, CSB high between transfers (tCHW) ≥ 40 ns.
- **SPI (read):** tSCYCR ≥ 150 ns, SCL high/low ≥ 60 ns, output access and disable times per the AC table.
- **Operating range:** −30 … +85 °C (chip), 0 … 70 °C (rating note); sleep current ≤ 1 mA, operating current 2 mA typ (DC/DC on, no waveform transitions).
- **Conformance:** no bound exists to compare against (see `specs/display/il0376f_timing.conf`).

## Implementation Notes

- **The waveform is the blocker.** The chip has no OTP: all eight LUTs must be written after every reset, and the datasheet gives the LUT *format* (5 phases of two level/frame bytes and a repeat byte) but **no waveform**. A driver that sends no LUTs refreshes nothing useful. The values must come from the module vendor (the Waveshare 1.54inch (B/C) V1 demo code is expected to carry a set; none is transcribed here because it cannot be verified from the committed documents). Minimal therefore takes the waveform as a required argument, and a vendor waveform constant can be added once it has been verified on hardware.
- **DisplayConnection owns D/C, RES, BUSY and CS.** The driver never touches them; it calls `send_command(cmd, data)`, `send_data`, `read_data`, `reset`, `wait_busy` from `specs/transport_display.md`, exactly as the UC8276C, IL0373 and IL0398 drivers do. `read_data(n)` is `n` one-byte CS windows with DC high. **The transport needs no extension for this chip** (the datasheet says CSB can be high between a command and its parameters).
- **BUSY_N low = busy** (pin table).
- **Streamed data:** a full frame is up to 15 000 + 7 500 bytes; the driver streams `send_data` blocks under one CS assertion (this worked for whole planes on the UC8276C). **Confirm on hardware**; the fallback is per-byte `send_data` calls.
- **Power setting is a guess:** the default `PWR` bytes (`0x0F 0x00 0x08 0x08`) follow the LUT table's "15 V (VSH)" levels and the `RVSHLS` description; the power-on `PWR` (`RVSHLS = 00`, 2.4–8 V sources) would not provide ±15 V. Which `RVSHLS` (and `VDPS_LV`/`VDNS_LV`) a panel needs depends on its waveform — **verify on hardware**; `set_power` is the override.
- **Red roles:** `Red0` / `Red1` (and the K/W data under a red pixel) are not defined as "not red" / "red" in the datasheet. The driver assumes red-plane `1` = apply red, K/W under red = white; if the panel shows the red inverted, `set_interval(ddx=0)` flips the plane meanings (and the K/W code mapping).
- **Gray levels:** `GRAY1`/`GRAY2` are the chip's two intermediate levels (LUT 3/4); whether they are visibly distinct depends entirely on the supplied waveform.
- **DSP vs. DRF:** the datasheet says that after `DTM1` + `DSP` "BUSY_N becomes 0" (the refresh starts) and describes `DRF` separately; the driver sends `DRF` explicitly and does not send `DSP`; whether `DSP` alone starts a refresh is unconfirmed — verify on hardware to avoid a double refresh if `DSP` is ever added.
- **`TSE` before the LUTs:** the datasheet's figures show `TSE` ("TSE off") first. The chip has no OTP waveform to select by temperature, so the sensor is not needed for updates; `TSE = 1` disables the internal one (assumed to avoid interference). `read_temperature` needs `PON` (or `PMES`).
- **Resolution:** `TRES` takes even widths only (`HRES[7:1]`), so modules with odd widths are not representable. Smaller panels use a subset of the outputs; which source line is column 0 is panel-dependent (no `TSGS` here; `set_flip` mirrors).
- **Orientation:** with `UD = 1`, `SHL = 1` row 0 is `G0` and column 0 is `S0`; whether that is the physical top-left depends on the panel's FPC; `set_flip` corrects either case. Confirm on hardware.
- **Memory:** 15 000 + 7 500 bytes at 200 × 300 (K/W 2 bpp + red 1 bpp); 10 000 + 5 000 at 200 × 200. In C++ the buffers are the caller's (no heap): an undersized or null buffer, an odd width or a size over 200 × 300 makes `valid()` false instead of corrupting memory; the AVR build uses a small window.
- **SKU mapping:** the issue lists the Waveshare 1.54inch e-Paper (B/C) V1 as an IL0376F module (unverified); no panel specification is committed. Check the module's controller marking and panel specification before claiming support (the 1.54inch (B/C) V2 is believed to use an SSD1681, `specs/display/ssd1681.md`). Whether the module's source-driver supply matches the assumed `PWR` is unknown.
- **Blocking update:** `show()` blocks for the whole refresh; on MicroPython/CircuitPython this stalls the interpreter and the examples must say so.
- **Datasheet status:** issue date 2016-04-07, no revision number; the feature list's "operating frequency 20 MHz (max)" conflicts with the 100 ns write cycle (the AC table is used); the temperature-sensor commands carry garbled bit descriptions (`TSC` `TS[3:0]`, `LPD` and `TSE` titles copied from the wrong command: "Internal temperature sensor switch" appears as the description of `DDX` and `LPD`); the power sequence and BUSY_N flow-chart figures are empty in the document text; `PFS` shows two different command codes; the VDNS table has a −2.6 V typo; there is no reset timing, refresh duration or example waveform.

## Sigrok Decoder

Decoder id `il0376f`, input **`display_spi`**: it stacks on the connection decoder `Display-SPI` (`sigrok/display_spi/`, see `specs/transport_display.md`), which frames the SPI (4-wire or 3-wire) and reports CS#, RES# and the raw BUSY level as `BYTE` / `CS` / `BUSY` / `RESET` / `IDLE` packets. The BUSY polarity is chip-level: this decoder treats BUSY_N **low** as busy and emits the `busy_start` / `busy_done` timing markers. It has no channels or options of its own. After a read command the response bytes are taken from the connection decoder's DOUT value when that channel is wired, otherwise from the shared DIN line. A CS# release between a command and its parameters is legal (the datasheet: "CSB can be H between parameter-command and command-parameter") and not warned. Typical stack: `-P display_spi:clk=0:mosi=1:cs=2:dc=3:busy=4:res=5,il0376f`.

Annotation rows: **Data** — one annotation per command with decoded parameters (resolution, power settings in volts, PSR bit fields, CDI fields, PLL frame rate, LUT phases as level/frames/repeat, …); **Status** — `Busy for <duration>` spans (BUSY_N low) and RES# low spans; **Warnings** — a command from the BUSY list above for which BUSY_N was not already low at the CS# rising edge that completes it (`NOBUSY`; skipped when BUSY is not probed), unknown command, wrong parameter count (LUTs expect 15 bytes, `PWR` 4, `TRES` 3), a command (other than `PWR`, `PFS`, `PON`, `PMES`, `BTST`, `LPD`, `FLG`) sent while BUSY_N is low, pixel write larger than the frame. Read commands (`FLG`, `TSC`, `TSR`, `REV`, `LPD`, `VV`, `DSP`) show the decoded response bytes; they are meaningful only when the probe sits on the shared DIN/DOUT line of a half-duplex wiring. A command with parameters, or an open-ended read, is reported when the next command arrives or on the connection decoder's `IDLE` packet.

`OUTPUT_PYTHON` packets: `('COMMAND', (command_byte, parameter_bytes))`.
