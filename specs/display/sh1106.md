# Chip Spec: SH1106

**Manufacturer:** Sino Wealth  
**Datasheet:** `datasheets/display/sh1106.pdf` (SH1106 V0.1 preliminary, from `http://www.hpinfotech.ro/SH1106.pdf`)  
**Category:** `display`  
**Transports:** I²C, SPI (4-wire)

## Overview

The SH1106 is a single-chip CMOS OLED/PLED driver with controller for monochrome dot-matrix graphic panels of up to **132 × 64** pixels: 132 segment (column) outputs, 64 common (row) outputs, 132 × 64 bits of display RAM, an on-chip oscillator, an internal charge pump (DC-DC) for the OLED supply, 256-step contrast control, row/column remapping, vertical scrolling via the display start line and programmable multiplexing. It supports 8-bit 6800/8080 parallel, 3-/4-wire SPI and 400 kHz I²C interfaces; this spec covers **I²C and 4-wire SPI**. It is the chip behind the common 1.3″ 128 × 64 OLED modules, which show 128 of the 132 RAM columns (see Display RAM). It differs from the SSD1306 in having **page addressing only** (no horizontal/vertical auto-wrap addressing modes) and a 132-column RAM.

The two transports share one command set. The driver family is therefore a base class holding the command logic and framebuffer with two transport hooks: `Sh1106Minimal` / `Sh1106Full` (I²C) and `Sh1106SpiMinimal` / `Sh1106SpiFull` (SPI) — see Implementation Notes.

## Transport Configuration

### I²C
- **Address:** `0x3C` (SA0 = VSS) — `0x3D` (SA0 = VDD1); 7-bit address `0111 10 SA0` (the same two addresses as the PCF8578/PCF8579)
- **Max clock:** 400 kHz (fast mode)
- **Identity register:** none; chip has no ID register (`registry/chips.json` entry has `"id_probe": null`; it shares `0x3C`/`0x3D` with the PCF8578/PCF8579, which cannot be told apart)
- **Probe safety:** `write_sensitive` — every byte after the address and a control byte is a command or display data
- **Interface select pins:** IM0 = 0, IM1 = 1, IM2 = 0; CS tied low, D2–D7 tied low
- **Protocol:** write = `[addr+W] [control byte] [data byte(s)] …`. The **control byte** is `Co D/C 0 0 0 0 0 0`: `Co = 1` means one data byte follows and then another control byte; `Co = 0` means all remaining bytes in the transaction are data. `D/C = 0` → the data is a command, `D/C = 1` → display RAM data. So a command stream is `0x00, cmd, cmd, …` (or `0x80, cmd` per command) and a RAM stream is `0x40, d0, d1, …`. Read = `[addr+R] [data…]`, returning status or RAM data according to the D/C bit of the last write (see Read access)
- **Register addressing:** none — plain `Connection` (`write`, `read`), not `RegisterConnection`

### SPI (4-wire)
- **Mode:** CPOL=0 CPHA=0 (Mode 0) — the datasheet shows data sampled on the rising SCL edge but does not name the idle level; Mode 0 is the usual choice (confirm on hardware)
- **Max clock:** 4 MHz at VDD1 ≥ 2.4 V (tSCYC ≥ 250 ns), **2 MHz** at VDD1 down to 1.65 V (tSCYC ≥ 500 ns); drivers default to 2 MHz
- **Bit order:** MSB first
- **CS active:** low (CS may be hard-wired low on a dedicated bus)
- **Framing:** a plain byte stream — no opcode or address bytes. The **D/C pin (A0)** is sampled on every eighth clock: `A0 = 0` → the byte is a command, `A0 = 1` → display RAM data. The driver needs an `OutputPin` for D/C (`dc_pin`) and drives it before each transfer: low for command bytes, high for data bytes
- **Read:** not possible over SPI
- **3-wire SPI (9-bit frames with an embedded D/C bit)** and the parallel interfaces are **not supported** (the byte-oriented SPI connection cannot send 9-bit frames)
- **Interface select pins:** IM0 = 0, IM1 = 0, IM2 = 0; D2–D7 tied low

## Command Set

All commands are single bytes sent with D/C = 0; "double-byte" commands are a mode byte followed by a data byte sent in the same command stream. POR values are in parentheses. Do not send commands not listed here ("Don't use any commands not mentioned").

| Command | Code | Description |
|---------|------|-------------|
| Set lower column address | `0x00 \| A[3:0]` | Low nibble of the column pointer (POR `0x00`) |
| Set higher column address | `0x10 \| A[7:4]` | High nibble of the column pointer (POR `0x10`); columns 0–131 (`0x00`–`0x83`) |
| Set pump voltage | `0x30 \| A[1:0]` | VPP: `00` 7.4 V (POR), `01` 8.0 V, `10` 8.4 V, `11` 9.0 V |
| Set display start line | `0x40 \| A[5:0]` | RAM line shown at COM0 (0–63; POR 0) — hardware vertical scroll |
| Set contrast | `0x81`, then `00`–`FF` | Segment current ISEG = α/256 × IREF × 32 (POR `0x80`) |
| Segment re-map (ADC) | `0xA0` / `0xA1` | `0xA0`: column 0 ↔ SEG0 (normal, POR); `0xA1`: column 131 ↔ SEG0 (reversed) |
| Entire display on | `0xA4` / `0xA5` | `0xA4` follows RAM (POR); `0xA5` forces all pixels on (RAM kept) |
| Normal / reverse | `0xA6` / `0xA7` | `0xA6` RAM 1 = pixel on (POR); `0xA7` inverted |
| Multiplex ratio | `0xA8`, then `00`–`3F` | Ratio = data + 1 (1–64, POR `0x3F` = 64) |
| DC-DC control | `0xAD`, then `0x8A` / `0x8B` | `0x8A` DC-DC off (external VPP), `0x8B` on when the display is on (POR). Issue while the display is off |
| Display off / on | `0xAE` / `0xAF` | `0xAE` sleep/power-save (POR), `0xAF` on |
| Set page address | `0xB0 \| A[2:0]` | Page 0–7 (POR 0) |
| COM scan direction | `0xC0` / `0xC8` | `0xC0` COM0→COM63 (POR); `0xC8` reversed — takes effect immediately (vertical flip) |
| Display offset | `0xD3`, then `00`–`3F` | Shifts the COM mapping (POR 0) |
| Clock divide / oscillator | `0xD5`, then `A7:A4 osc, A3:A0 div-1` | Divide ratio = A[3:0] + 1; oscillator −25 % … +50 % in 5 % steps, `0101` = nominal (POR `0x50`) |
| Pre-charge / discharge | `0xD9`, then `A7:A4 discharge, A3:A0 precharge` | DCLKs, 1–15, `0` invalid (POR `0x22`) |
| COM pins configuration | `0xDA`, then `0x02` / `0x12` | `0x02` sequential, `0x12` alternative (POR `0x12`) |
| VCOM deselect level | `0xDB`, then `00`–`FF` | β × VREF (POR `0x35` ≈ 0.77 × VCC) |
| Read-modify-write | `0xE0` | Column pointer increments only on writes until `End` |
| End | `0xEE` | Leaves read-modify-write; column pointer returns to its pre-`0xE0` value |
| NOP | `0xE3` | No operation |

### Power-on / reset defaults

Display off (segments/commons high-impedance), 132 × 64 mode, normal segment and scan mapping, start line 0, column pointer 0, contrast `0x80`, internal DC-DC selected, pump 7.4 V, multiplex 64, clock divide 1 at nominal oscillator, precharge/discharge 2/2, COM alternative, VCOM `0x35`, normal (non-inverted) display, entire display follows RAM. The display RAM contents are **undefined** at power-up (the datasheet's init flow ends with "clear internal RAM to 00H").

## Display RAM

132 columns × 8 pages × 8 bits = 132 × 64 bits. One data byte holds 8 vertical pixels of one column of one page: **bit 0 is the top row of the page** (D0 at the top, page 0 at the top at start line 0). Addressing is **page addressing only**: set the page (`0xB0|p`) and the column pointer (`0x00|low`, `0x10|high`), then write data bytes; the column pointer **auto-increments after every data read/write** (up to column 131) but the page does **not** change. Moving to the next page requires a new page + column command (even to continue at column 0 of the next page). The column pointer is independent of the page address.

Segment mapping: with ADC = 0 column `n` drives SEG`n`; with ADC = 1 column `131 − n` drives SEG`n`. **128-pixel-wide modules** are normally wired to SEG2…SEG129, i.e. the visible area starts at RAM column 2 (not stated in the datasheet — common module practice): the driver exposes `column_offset` (default 2, `0` for a true 132-column panel).

## Initialization Sequence

Per the datasheet's power-on flow (1.1, internal DC-DC):

1. Apply VDD1/VDD2 with RES low ≥ 10 µs (if `res_pin` is wired, pulse it low ≥ 10 µs and release, then wait ≥ 2 µs).
2. Send the setup commands in one command stream (display still off): `0xAE` (off), `0xD5 0x50` (clock), `0xA8 0x3F` (multiplex 64), `0xD3 0x00` (offset 0), `0x40` (start line 0), `0xA0|ADC`, `0xC0|(scan<<3)`, `0xDA 0x12` (COM alternative), `0x81 0x80` (contrast), `0xD9 0x22`, `0xDB 0x35`, `0x30` (pump 7.4 V), `0xA4` (follow RAM), `0xA6` (normal).
3. `0xAD 0x8B` (DC-DC on), then wait for VPP to stabilise (datasheet: "typically 100 ms").
4. Clear the display RAM (8 pages × 132 bytes of `0x00`, one page + column set per page) before `0xAF`.
5. `0xAF` (display on); wait ~150 ms (datasheet-typical) before relying on the picture.

With an **external VPP** (`internal_dcdc=False`): use `0xAD 0x8A` instead, apply VPP before `0xAF`, and wait ~50 ms after display-on (datasheet flow 1.2). Power-off: `0xAE`, remove VPP and wait ~100 ms before removing VDD.

## Implementation Stages

### Minimal

Goal: a 128 × 64 monochrome OLED you can draw pixels on out of the box.

| Operation | Parameters | Returns | Notes |
|-----------|------------|---------|-------|
| `init` | connection (I²C: `addr=0x3C`; SPI: + `dc_pin`, optional `res_pin`), `width: int = 128`, `height: int = 64`, `column_offset: int = 2`, `internal_dcdc: bool = True` | — | Runs the Initialization Sequence (with the waits), clears the RAM and framebuffer, switches the display on; `width` ≤ 132, `height` ≤ 64 and a multiple of 8 |
| `clear` | — | — | Zero the framebuffer (call `show` to update the panel) |
| `set_pixel` | `x: int`, `y: int`, `on: bool = True` | — | Framebuffer only (0 ≤ x < width, 0 ≤ y < height); out-of-range ignored |
| `show` | — | — | Write the whole framebuffer: for every page one page + column command stream followed by `width` data bytes starting at `column_offset` |

**Sensible defaults:** 128 × 64 panel at RAM column offset 2, internal 7.4 V charge pump, contrast `0x80`, segment/scan mapping normal (ADC 0, scan `0xC0`), clock divide 1, multiplex 64, normal (non-inverted) display. The framebuffer is `width × height / 8` bytes with the RAM layout above (page-major).

## Data Conversion

```
page, bit      = y // 8 , y % 8
fb[page][x]    = framebuffer byte for column x of that page            (x = 0..width-1)
set pixel      : fb[page][x] |=  (1 << bit)     clear: &= ~(1 << bit)
RAM column     = column_offset + x

show():  for p in 0..height/8-1:
            cmd stream: 0xB0|p, 0x00|(col & 0x0F), 0x10|(col >> 4)     with col = column_offset
            data stream: fb[p][0..width-1]

I²C control bytes:  0x00  = last control byte, following bytes are commands
                    0x80  = command byte follows, then another control byte
                    0x40  = last control byte, following bytes are display data
SPI:  D/C low for command bytes, D/C high for data bytes
```

## Timing Constraints

- **Reset:** RES low ≥ 10 µs (≥ 5 µs at VDD1 ≥ 2.4 V); the chip is ready within 2 µs (1 µs) after RES goes high.
- **DC-DC / display-on sequence:** after `0xAD 0x8B` wait for VPP to stabilise — datasheet "typically 100 ms"; after `0xAF` wait "typically 150 ms" (internal DC-DC) or 50 ms (external VPP); after `0xAE` before removing power wait ~100 ms. These are recommended delays, not hard limits.
- **I²C:** fSCL ≤ 400 kHz, tBUF ≥ 1.3 µs (datasheet I²C characteristics).
- **SPI:** SCL cycle ≥ 250 ns (≥ 500 ns at VDD1 down to 1.65 V), CS setup/hold 120/240 ns, address (D/C) setup/hold 150 ns (300 ns at low VDD1), pulse widths ≥ 100/200 ns — hence the 2 MHz default.
- **BUSY:** the status register's BUSY bit goes high during internal operation or reset; commands sent while busy are rejected. Over SPI there is no status read, so the driver relies on the datasheet timing and does not stream commands faster than the clock limits.
- **Conformance:** none of these has a bus-decodable start/end annotation pair that the host controls (the delays are recommended waits after commands, not measured events), so `specs/display/sh1106_timing.conf` defines no checks.

## Implementation Notes

- **One base class, two transports:** implement an abstract base (`_Sh1106Base`) with the framebuffer, drawing, and command logic and two hooks `write_commands(bytes)` / `write_data(bytes)`. The I²C classes prepend the control byte (`0x00`/`0x40`) to every transaction (one `connection.write` per stream, chunked to the platform's maximum write size; every chunk of data repeats the `0x40` control byte); the SPI classes drive `dc_pin` low/high and call `connection.write`. SPI RAM data can be sent as a single transaction per page.
- **Plain `Connection`, not `RegisterConnection`:** the control byte is not a register address; the same style as the PCF8576 driver. The SPI connection must not fold read/burst bits into the first byte (no register addressing).
- **I²C transaction sizes:** some platform I²C layers limit a write to 32 bytes (Arduino `Wire`); chunk RAM data accordingly (each chunk a fresh `0x40` control byte; the column pointer keeps advancing between chunks).
- **Page addressing only:** unlike the SSD1306 there is no horizontal addressing mode; `show()` must set page and column for each of the 8 pages. Writing more than `132 − column` bytes in one go wraps nowhere (the column pointer stops at 131), so never write past the last column.
- **132 vs 128 columns:** the visible columns of a 128-wide module start at RAM column 2. Using offset 0 on such a module shifts the picture left by two pixels and shows two garbage columns on the right; configure `column_offset` for the panel.
- **DC-DC ordering:** `0xAD 0x8B` (DC-DC on) should be sent while the display is off, with the 100 ms stabilisation wait before `0xAF`. The panel must not be driven with the display on before VPP is stable.
- **Read access (I²C only):** RAM reads need one **dummy read** after the column address is set; status is read with the D/C bit cleared in the last control byte. Reading over SPI is impossible. Reading is rarely needed because the driver keeps a framebuffer.
- **Read-modify-write:** `0xE0` … `0xEE` is not used by the driver (the framebuffer replaces it); `send_command` exposes it.
- **Do not use undocumented commands:** the datasheet warns that other commands may cause malfunction; many SSD1306-oriented code snippets (horizontal addressing `0x20`, column/page range `0x21`/`0x22`, charge pump `0x8D`, scroll commands) do **not** exist on the SH1106 — a shared SSD1306/SH1106 driver must not send them.
- **Preliminary datasheet:** version V0.1 marked "Preliminary"; values such as the SPI mode and the 128-column offset are not stated in it and are marked above as derived.
- **Not covered:** parallel (6800/8080) and 3-wire SPI interfaces, the external-clock mode (CLS low) and the scroll helpers of other controllers.
- **Datasheet:** SH1106 V0.1 preliminary (`http://www.hpinfotech.ro/SH1106.pdf`, 47 pages).

## Sigrok Decoder

Two decoders sharing one command table: `sh1106` (input `['i2c']`, addresses `0x3C`/`0x3D`) and `sh1106_spi` (input `['spi']`; the D/C line is read from an optional logic channel, otherwise every transfer is shown as raw bytes). The I²C decoder splits each write into control bytes (`Co`, `D/C`) and payload; command payloads are decoded into named commands with arguments (column nibbles combined into a column number, page, start line, contrast, ADC, invert, multiplex, DC-DC, display on/off, scan direction, offset, clock divide / oscillator, precharge/discharge, COM config, VCOM, pump voltage, read-modify-write / end), double-byte commands consume their data byte, and data payloads are shown with the current page and column (auto-incrementing, clamped at 131) and a count; each data byte can be rendered as an 8-pixel column. Reads are shown as status (BUSY / ON-OFF) or RAM data. Warnings: a command byte not in the table (including SSD1306-only commands such as `0x20`, `0x21`, `0x22`, `0x8D`), a data write that crosses column 131, and a write whose first control byte has `Co = 0`/`D/C = 0` but no command bytes. No timing annotation pair is emitted (the datasheet delays are recommendations, not measured events).
