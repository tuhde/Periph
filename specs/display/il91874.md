# Chip Spec: IL91874

**Manufacturer:** Good Display (Ilitek lineage; the datasheet is a UC8151-family text: "all-in-one driver with TCON for color application")  
**Datasheet:** `datasheets/display/il91874.pdf` (Good Display IL91874 specification, version 0.3, 90 pages, preliminary: several typ/max values are marked "to be confirmed by design" or TBD). No panel or module datasheet is committed: the module mapping below comes from the issue's Waveshare survey and is **unverified**  
**Category:** `display`  
**Transports:** SPI (4-wire; write-only or half-duplex, via `DisplayConnection`)

## Overview

The IL91874 is an all-in-one driver with timing controller for **black/white** (and, with a red-capable panel, black/white/red) electrophoretic (EPD) panels of up to **320 source × 300 gate** outputs: two bit-planes of display RAM (320 × 300 bits each = 12 000 bytes per plane), an on-chip RC oscillator, DC-DC booster and regulators for the gate, source and VCOM voltages (VGH/VGL ±13…±16 V, VSH/VSL ±2.4…±11 V, VSHR for red), an on-chip temperature sensor (−25…+50 °C, 8 bit) with an I²C master for an external LM75, a 4 KB OTP holding 15 temperature-dependent waveform sets (LUTs), a low-power detector, a **partial-window update** and a cascade mode (not covered). The issue names the Waveshare **2.7inch e-Paper V1** and **(B) V1** as modules (**unverified**; believed to be 264 × 176 black/white and black/white/red panels). Legacy hardware, lower priority.

It belongs to the same command family as the IL0373 (`specs/display/il0373.md`), the IL0398/UC8176 (`specs/display/il0398.md`) and the UC8276C (`specs/display/uc8276c.md`): one-byte commands, the `PON → DRF → POF` update cycle with an active-low BUSY_N, `DisplayConnection` wiring. **What differs from them (the register-level facts a shared implementation must not assume):**
- **Partial update commands exist:** `PDTM1` (`0x14`), `PDTM2` (`0x15`) and `PDRF` (`0x16`) with an (X, Y, W, L) window; there is **no** `PTL`/`PTIN`/`PTOUT` (`0x90`–`0x92`).
- **`0x30` is `OSC`, not `PLL`:** `SEL_DIV[1:0]` + `SEL_F[5:0]`, POR `0x3C` = 76.29 Hz (a different table from the M/N one).
- **`TRES` (`0x61`) has 4 bytes with 2-pixel horizontal granularity** (`HRES[8:1]`); **`0x62` is the source/gate start (`TSGS`)**, not `0x65`.
- **`PSR` power-on value is `0x07`** (scan *down*, `UD = 0`; RES bits select 320×300 / 300×200 / 296×160 / 296×128).
- **`PFS` sets three delays** (VSH/VSL/VSHR off times of 5/10/20/40 ms), `PWR` has a **sign bit for VSHR**, VDCS is 0.05 V/step to −3.0 V.
- **`BTST` default values are inconsistent** in the datasheet (see Implementation Notes); the driver leaves it alone.
- No `AUTO`, no `LVSEL` (the low-power threshold is fixed at 2.5 V), no `PWS`.
- Temperature commands (`TSC`, `TSE`, `TSW`, `TSR`) work **only after `PON` or `PMES`**.

The chip has **two pixel modes**: *KW* (black/white with NEW/OLD planes, `PSR.BWR = 1`) and *KWR* (black/white/red, **power-on default**, `BWR = 0`). Because the issue's primary module is a black/white panel, **this spec makes KW the primary mode** (as the IL0373 and IL0398 specs do) and exposes KWR (and the red colour) in Full only — see Implementation Notes.

An e-paper panel differs from an OLED/LCD in ways that shape the driver: a refresh is a multi-second full-panel waveform (**no duration is stated** in the datasheet, see Timing Constraints), the picture is **bistable**, and the display must be explicitly **powered on (PON) → refreshed (DRF) → powered off (POF)** around every update, with BUSY_N waited on after each step. The driver keeps a framebuffer and sends it on `show()`.

This spec covers **4-wire SPI**, full-panel updates with the **waveform loaded from OTP**, a user-supplied LUT, a partial-window update (`PDTM1`/`PDTM2`/`PDRF`) and, with a half-duplex wire mode, the read commands. A dedicated *partial refresh waveform* is not in the datasheet and is not specified.

## Transport Configuration

### SPI (4-wire)
- **Mode:** CPOL=0 CPHA=0 (Mode 0), MSB first; the write figures show SDA stable around the rising SCL edge
- **Max clock:** write cycle ≥ 100 ns (SCL high/low ≥ 35 ns each) → **10 MHz**. The feature list's "clock rate up to 20 MHz" contradicts the AC table; the AC table is used. Driver default 4 MHz. **Read** cycle ≥ **150 ns** (high/low ≥ 60 ns) → ≤ 6.6 MHz; reads are short and the driver uses its write clock capped at 4 MHz
- **CS active:** low (CSB). The datasheet states explicitly (4-wire figure): **"CSB can be H between parameter/command"**, and that SCL, SDA and D/C are invalid while CSB is high — so the per-call CS framing of `DisplayConnection` is acceptable (**no `hold_cs` extension is needed**; compare the SSD168x specs)
- **Framing:** a byte stream; the **D/C pin** is sampled per 8-bit group: low → command, high → parameter/data/read (D/C set-up/hold ≥ 20 ns). Bytes are sent verbatim — no register address, no read/write bit
- **Bus selection:** pin **BS** low = 4-wire, high = 3-wire (9-bit frames; **power-on default per the pin table**, so the module's strap decides). The driver requires **4-wire**; the BS strap is board-specific. 3-wire framing is **not supported**
- **Bidirectional SDA:** the chip's SDA pin is an I/O. Read commands (listed under Command Set) clock data out on SDA after the command byte, with D/C high and CSB low. Whether the board exposes DOUT depends on the wiring → `DisplayConnection` wire mode (`SIMPLEX` / `HALF_DUPLEX_HW` / `HALF_DUPLEX_PIN`, see `specs/transport_display.md`). `SIMPLEX` is sufficient for everything in Minimal
- **Register addressing:** none — takes a `DisplayConnection`, not a `RegisterConnection`

## Command Set

All commands are one byte sent with DC low; parameters follow with DC high. POR values in brackets. **Defaults can be changed by OTP** ("Default setting" OTP addresses `0x020`–`0x04D`: PSR, PWR, PFS, BTST, PDRF `DFV_EN`, OSC, TSE, CDI, TCON, TRES, AMV, VDCS, CCSET, TSSET, TSGS), so a panel may not power up with exactly these values; the driver writes every setting it depends on. Only commands the driver uses or exposes are listed.

### BUSY_N flag

All commands except `REV`, `FLG`, `VV` (and the read forms of `DSP`, `TSC`, `TSR`, `LPD`) are **ignored while a refresh (DRF/PDRF/DSP) is running** (datasheet register restriction table). Commands that drive BUSY_N low (flag column): `POF`, `PON`, `DSLP`, `DSP`, `DRF`, `PDRF`, `TSC`, `TSR`, `AMV`, `APG`. Data, LUT, `PSR`, `PWR`, `PMES` and the other setting commands raise no BUSY_N.

### Power-on / reset defaults

PSR `0x07` (320 × 300, **B/W/Red**, LUT from OTP, **scan down**, shift right, booster on), PWR `0x03 0x00 0x26 0x26 0x03`, PFS 5 ms, OSC `0x3C` (76.29 Hz), CDI `0xD7`, TCON `0x22`, TSE internal with offset 0, TRES / TSGS 0. The display RAM contents are **undefined** after power-up.

## Display RAM

Two planes, each **320 × 300 bits** (40 bytes × 300 rows); `DTM1` writes plane 1 and `DTM2` plane 2 (and `PDTM1`/`PDTM2` a window of each). A full-frame transfer is a plain stream written from the first pixel to the last: the chip has no address counter or window commands for it. Each byte carries 8 horizontal pixels with **bit 7 = first (leftmost) pixel** ("KPixel1" in D7); a frame is `ceil(width/8) × height` bytes per plane, rows in gate-scan order.

**B/W mode** (`PSR.BWR = 1`; `DTM1` = OLD, `DTM2` = NEW). With `CDI.DDX[0] = 1` (the default) the `{NEW, OLD}` bit pair selects the waveform:

| NEW | OLD | LUT |
|-----|-----|-----|
| 0 | 0 | LUTBB (stays black) |
| 0 | 1 | LUTWB (white → black) |
| 1 | 0 | LUTBW (black → white) |
| 1 | 1 | LUTWW (stays white) |

so **a NEW bit of 1 is white**. A pixel with equal NEW and OLD bits is not driven (or follows the VCOM LUT with `DFV_EN`), so the driver sends `OLD = NOT NEW` for every pixel: every pixel is driven to its final state, which makes a refresh independent of what the panel showed before (a full "flashing" update) and needs no second framebuffer. Border (`VBD`, `DDX[0] = 1`, B/W mode): `00`/`11` floating, `01` LUTWB, `10` LUTBW.

**B/W/Red mode** (`PSR.BWR = 0`, power-on default; `DTM1` = B/W plane, `DTM2` = red plane). With `DDX = 01`:

| Red bit | B/W bit | Colour (LUT) |
|---------|---------|--------------|
| 0 | 0 | black (LUTB) |
| 0 | 1 | white (LUTW) |
| 1 | 0 | red (LUTR) |
| 1 | 1 | red (LUTR) |

Red wins. Border (`DDX[0] = 1`): `00` LUTB, `01` LUTW, `10` LUTR, `11` floating.

**The polarity depends on CDI.DDX, and the OTP may change the power-on value** (default-setting OTP address `0x038`). The driver therefore writes CDI explicitly instead of relying on the OTP default.

## Initialization Sequence

Derived from the datasheet's power-management notes and command descriptions and from the UC8276C/IL0398/IL0373 flows (the UC8276C and IL0373 flows were verified on panels; the datasheet contains no reference code). **Not verified on an IL91874 panel.**

1. Apply VDD/VDDIO; BS strapped low (4-wire).
2. **Hardware reset:** `RST_N` low ≥ 10 ms, then high; wait ≥ 10 ms, then BUSY_N high (the power-on figure shows "> 1.5 ms" around RST_N, the UC8276C needs a 1 ms recovery; these values are conservative).
3. `PSR` `0x1F` in B/W mode (LUT from OTP, `BWR = 1`, scan **up**, shift right, booster on; written explicitly because the POR is scan down) — `0x0F` in B/W/Red mode.
4. `TRES` with `(width, height)` (`0x01 0x40 0x01 0x2C` for 320 × 300; for a 264 × 176 panel in portrait order — width 176, height 264 — `0x00 0xB0 0x01 0x08`); `TSGS` is left at 0.
5. `CDI` `0x97` in B/W mode (VBD = 10, DDX = 01, 10 hsync; the IL0373 value) or `0xD7` in B/W/Red mode: written explicitly so the framebuffer polarity does not depend on the OTP default. Leave `PWR`, `BTST`, `OSC`, `TCON` and `VDCS` at their power-on/OTP values (see Implementation Notes).
6. No RAM clear is required: `show()` always writes both planes completely.

An update (`show()`):

1. `DTM1` + `ceil(width/8) × height` bytes (B/W mode: OLD = `NOT fb`; B/W/Red mode: the B/W plane); `DTM2` + the same number of bytes (B/W mode: NEW = `fb`; B/W/Red mode: the red plane, zeros when no red pixel was drawn).
2. `PON`; wait BUSY_N high.
3. `DRF`; wait BUSY_N high (refresh, no stated duration).
4. `POF`; wait BUSY_N high.

A partial update (`show_region`): `PON`; `PDTM1` + window + OLD bytes; `PDTM2` + window + NEW bytes; `PDRF` + window; wait BUSY_N high; `POF`.

Deep sleep: `POF`, then `DSLP` `0xA5`. **Wake = hardware reset + the Initialization Sequence**; the driver's framebuffer is unaffected.

## Implementation Stages

### Minimal

Goal: a 320 × 300 (or smaller) black/white e-paper panel you can draw pixels on out of the box.

| Operation | Parameters | Returns | Notes |
|-----------|------------|---------|-------|
| `init` | `connection` (`DisplayConnection`), `width: int = 320`, `height: int = 300`, `busy_timeout_ms: int \| None = 30000` | — | Allocates the framebuffer, runs the Initialization Sequence in B/W mode (including the BUSY_N wait), leaves the panel unchanged until `show()`. `width` even and ≤ 320 (`TRES` resolves 2 pixels), `height` ≤ 300; the row stride is `ceil(width / 8)` |
| `clear` | `color: int = WHITE` | — | Fill the framebuffer (`WHITE` or `BLACK`) |
| `set_pixel` | `x: int`, `y: int`, `color: int = BLACK` | — | Framebuffer only; out-of-range ignored |
| `show` | — | — | Write OLD/NEW, `PON` → `DRF` → `POF`; blocks until BUSY_N is high again |
| `sleep` | — | — | `POF` (if on) then `DSLP`; only `wake()` / a hardware reset restores communication |

**Constants:** `BLACK = 0`, `WHITE = 1`.

**Sensible defaults:** 320 × 300 B/W (KW), waveform from OTP (`PSR.REG_EN = 0`), internal temperature sensor, power setting / soft start / OSC / TCON at power-on values, PSR `0x1F`, CDI `0x97`, SPI Mode 0 at 4 MHz, BUSY timeout 30 s (not derived from the datasheet, which states no refresh time; the UC8276C's tri-colour refresh took 16.8 s, a black/white one is expected to be shorter — measure the real refresh and adjust). The framebuffer is `ceil(width / 8) × height` bytes (**12 000** at 320 × 300; 5 808 at the believed 176 × 264 panel), initialised to white; the OLD/NEW planes are produced while streaming, no second buffer. In C++ the buffer is caller-supplied (`valid()` instead of exceptions). Works with `SIMPLEX` wiring.

## Data Conversion

```
bytes_per_row = ceil(width / 8)
index         = y * bytes_per_row + (x // 8)
bit           = 7 - (x % 8)                      # bit 7 = first (left) pixel
set pixel     : fb[index] |= (1 << bit) for WHITE;  &= ~(1 << bit) for BLACK        (RED: see below)

B/W mode      : DTM1 (OLD) = NOT fb      DTM2 (NEW) = fb          # every pixel driven
B/W/Red mode  : DTM1 = fb_bw             DTM2 = fb_red
                BLACK: bw=0 red=0   WHITE: bw=1 red=0   RED: bw=0 red=1    (DDX = 01)
                fb_red[index] |= (1 << bit) for RED;  &= ~(1 << bit) otherwise

TRES:       b0 = (width >> 8) & 1 ; b1 = width & 0xFE ; b2 = (height >> 8) & 1 ; b3 = height & 0xFF
            320 x 300 -> 01 40 01 2C        176 x 264 -> 00 B0 01 08
TSGS:       b0 = (s_start >> 8) & 1 ; b1 = s_start & 0xFF ; b2 = (gscan << 4) | ((g_start >> 8) & 1) ; b3 = g_start & 0xFF
PDTM/PDRF window (x multiple of 8, w multiple of 8):
            b0 = (x >> 8) & 1  (PDRF: | DFV_EN << 7) ; b1 = x & 0xF8 ; b2 = (y >> 8) & 1 ; b3 = y & 0xFF
            b4 = (w >> 8) & 1 ; b5 = w & 0xF8 ; b6 = (l >> 8) & 1 ; b7 = l & 0xFF        (w = width, l = rows)
            then PDTM data: (w / 8) * l bytes, rows top to bottom within the window

VSH / VSL / |VSHR| (PWR):   code = round((volts_abs - 2.4) / 0.2)    2.4 .. 11.0 V (0x00..0x2B; VSL negative)
VSHR byte (PWR byte 4):     code | (0x40 if volts < 0)
VGHL_LV (PWR byte 1):       code = 16 - volts_abs                    16 V (00) .. 13 V (11), VGL = -VGH ; byte = VCOM_HV << 2 | VGHL_LV
VCOM_DC (VDCS, VV):         code = round((-0.10 - volts) / 0.05)     -0.10 .. -3.00 V (0x00..0x3A)
                            read: volts = -0.10 - 0.05 * VV
OSC (0x30):                 byte = (SEL_DIV << 6) | SEL_F ; POR 0x3C (DIV 0, F 60) = 76.29 Hz
                            the datasheet gives a 64 x 3 table (SEL_DIV 0..2, with F 16..31 undefined for DIV 0 and F >= 27/59 for DIV 2/3 partly undefined)
                            DIV 0: F 0..15 = 156.25 .. 197.61 Hz, F 32..63 = 153.49 .. 68.01 Hz ; DIV 1: roughly half, DIV 2: roughly a quarter (20 .. 54 Hz)
temperature (TSC):          celsius = int8(ts)                       -25 .. +50 degC range, two's complement
temperature offset (TSE):   TO[3] sign, TO[2:0] magnitude 0..7 degC  (1100 = -4)
```

All mappings are regular fits of the datasheet tables (0.2 V per code from 2.4 V; VGH/VGL 1 V per level; VCOM 0.05 V per code with code 0 = −0.10 V). The OSC frequencies depend on the datasheet's table (p. 42), which a driver must not approximate: `set_osc` takes the raw fields and no frequency conversion is specified.

## Timing Constraints

- **Reset:** the datasheet's power-on and DSLP figures show "> 1.5 ms" at RST_N but no pulse-width table; the driver holds RST_N low ≥ 10 ms and waits ≥ 10 ms (`DisplayConnection.reset()`), then BUSY_N high.
- **Power on / off:** `PON` takes ~80 ms and `POF` ~50 ms of BUSY_N low in the datasheet's sequence figures (indicative); the driver waits for BUSY_N each time.
- **Refresh:** after `DRF`/`PDRF`, BUSY_N goes low and the panel refreshes. **No duration or maximum is stated.** The reference value for the sibling UC8276C (400 × 300 B/W/R, measured) is 16.8 s, for the IL0373 B/W 3.3 s; the IL91874 has not been measured, so the driver default timeout is 30 s (a driver choice, not a datasheet value). The update must not be interrupted.
- **Commands that drive BUSY_N low** (datasheet register restriction table): `POF`, `PON`, `DSLP`, `DSP`, `DRF`, `PDRF`, `TSC`, `TSR`, `AMV`, `APG`. Everything else raises no BUSY_N. The driver waits BUSY_N high after each of PON, DRF/PDRF, POF.
- **SPI (write):** tSCYCW ≥ 100 ns, SCL high/low ≥ 35 ns, CSB setup (tCSS) ≥ 60 ns, CSB hold (tCSH) ≥ 65 ns, CSB-to-clock (tSCC) ≥ 20 ns, CSB high between transfers (tCHW) ≥ 150 ns, D/C setup and hold ≥ 20 ns, data setup/hold ≥ 30 ns.
- **SPI (read):** tSCYCR ≥ 150 ns, SCL high/low ≥ 60 ns, SDA access time ≤ 10 ns, output disable ≥ 15 ns.
- **Deep sleep exit:** hardware reset, then the full Initialization Sequence.
- **Operating range:** −30 … +85 °C (chip). The OTP picks the waveform by the sensed temperature from 14 boundaries (`TB0`–`TB13`: "TEMP < Boundary n" in order) and 15 waveform sets.
- **Conformance:** no bound exists to compare against (see `specs/display/il91874_timing.conf`).

## Implementation Notes

- **DisplayConnection owns D/C, RES, BUSY and CS.** The driver never touches them; it calls `send_command(cmd, data)`, `send_data`, `read_data`, `reset`, `wait_busy` from `specs/transport_display.md`, exactly as the UC8276C, IL0373 and IL0398 drivers do. `read_data(n)` is `n` one-byte CS windows with DC high. **The transport needs no extension for this chip** (the datasheet says CSB can be high between a command and its parameters).
- **BUSY_N low = busy** (pin table, BUSY_N behaviour in the command descriptions, FLG bit 0).
- **Streamed data:** a full frame is 12 000 bytes per plane; the driver streams `send_data` blocks under one CS assertion (this worked for whole planes on the UC8276C). **Confirm on hardware**; the fallback is per-byte `send_data` calls.
- **Pixel mode default:** KW (B/W) is the primary mode because the issue's first module is a black/white panel and the IL0373 B/W design (OLD = NOT NEW, full drive) was verified on a panel; the chip's power-on mode is KWR. Whether the module's OTP carries waveforms for the selected mode is **not in the datasheet** — if a refresh does not run or looks wrong, try `set_mode`. The `OLD = NOT NEW` choice and the border value (`VBD = 10`) are driver decisions; if the panel ghosts, the alternative is to keep the previous frame as OLD.
- **Defaults and OTP:** OTP can override PSR, PWR, PFS, BTST, OSC, TSE, CDI, TCON, TRES, AMV, VDCS, CCSET, TSSET, TSGS and the `PDRF` `DFV_EN` default. The driver writes PSR, TRES and CDI explicitly and leaves `PWR`, `BTST`, `OSC`, `TCON` and `VDCS` alone: a wrong `PWR` can drive the panel outside its rating, and the VCOM value is normally set at the factory. `set_power` / `set_vcom_dc` are for users who know their panel's values.
- **`BTST` POR is inconsistent:** the register table prints `0x03 0x00 0x26` (apparently copied from another command), the command description gives period 10 ms, strength 3 and off time 6.58 µs for every phase (`0x17 0x17 0x17`, the UC8276C value). The driver does not write `BTST`; `set_soft_start` takes explicit bytes.
- **Partial update (`show_region`):** `PDTM1`/`PDTM2` write only the window's bytes and `PDRF` refreshes only that window ("the other pixels' output would follow the VCOM LUT"). The waveform is the OTP waveform; the datasheet defines no partial LUT, so whether the update is flicker-free is **unknown — confirm on hardware**. `X` and `W` are multiples of 8; the window bytes are row-major within the window. In B/W mode the window's OLD data is `NOT NEW` as for a full update; `DFV_EN` (data follow VCOM) is exposed as `data_follow_vcom` and only valid in B/W mode. After a partial update the planes outside the window keep their previous OLD/NEW content.
- **DSP vs. DRF:** the datasheet says that after DTM1/DSP "when data_flag = 1, BUSY_N signal will become 0 and the refreshing of panel starts", and `DRF` also refreshes. The driver sends `DRF` explicitly and does not send `DSP`; whether `DSP` alone starts a refresh is unconfirmed — verify on hardware to avoid a double refresh if `DSP` is ever added.
- **Refresh requires power on:** `DRF` must be preceded by `PON`; the driver always wraps `DRF`/`PDRF` in `PON`/`POF`. The temperature commands also need `PON` (or `PMES`), which `read_temperature` and `set_temperature_sensor` account for.
- **LUTs:** the datasheet documents `0x20`–`0x24` (44-byte VCOM LUT, 42-byte data LUTs, level codes and frame/repeat counts) and the OTP layout, but gives no example waveform; `write_lut` is an untested escape hatch and the driver uses the OTP waveform only.
- **No `AUTO`:** the family's `AUTO` (`0x17`) does not exist here; there is no `refresh_auto`.
- **Temperature:** the internal sensor is the POR choice and is read once automatically at `PON`; the driver does not expose forced temperature (`TSSET`, cascade only).
- **Resolution:** `TRES` takes even widths only (`HRES[8:1]`); modules with odd widths are not representable. A panel smaller than 320 × 300 uses a subset of the outputs; which source line is column 0 is panel-dependent (`TSGS` can offset it; reachable through `send_command`).
- **Orientation:** with `UD = 1`, `SHL = 1` (the driver's PSR; the chip's POR is `UD = 0`) row 0 is `G0` and column 0 is `S0`; whether that is the physical top-left depends on the panel's FPC; `set_flip` corrects either case. Confirm on hardware.
- **SKU mapping:** the issue lists the Waveshare 2.7inch e-Paper V1 and (B) V1 as IL91874 modules (unverified); no panel specification is committed. Check each against its panel specification and controller marking before claiming support; the later 2.7inch V2 uses a different controller. The (B) version is a three-colour panel: use `MODE_KWR`.
- **Memory:** 12 000 bytes at 320 × 300 (one framebuffer in B/W mode; plus 12 000 for the red plane in KWR). In C++ the buffer is the caller's (no heap): an undersized or null buffer, an odd width or a size over 320 × 300 makes `valid()` false instead of corrupting memory; the AVR build uses a small window.
- **Blocking update:** `show()` blocks for the whole refresh; on MicroPython/CircuitPython this stalls the interpreter and the examples must say so.
- **Datasheet status:** version 0.3, preliminary: the feature list's "clock rate up to 20 MHz" conflicts with the 100 ns write cycle (the AC table is used); typical and maximum currents are "to be confirmed by design"; `BTST` and `VDCS`/`VV` bit widths are inconsistent between the register table and the descriptions; the `OSC` section prints "SEL_F[4:0]" in the register table and `[5:0]` in the description; the cascade, pin and OTP-programming sections are not covered here.

## Sigrok Decoder

Decoder id `il91874`, input **`display_spi`**: it stacks on the connection decoder `Display-SPI` (`sigrok/display_spi/`, see `specs/transport_display.md`), which frames the SPI (4-wire or 3-wire) and reports CS#, RES# and the raw BUSY level as `BYTE` / `CS` / `BUSY` / `RESET` / `IDLE` packets. The BUSY polarity is chip-level: this decoder treats BUSY_N **low** as busy and emits the `busy_start` / `busy_done` timing markers. It has no channels or options of its own. After a read command the response bytes are taken from the connection decoder's DOUT value when that channel is wired, otherwise from the shared DIN line. A CS# release between a command and its parameters is legal (the datasheet: "CSB can be H between parameter/command") and not warned. Typical stack: `-P display_spi:clk=0:mosi=1:cs=2:dc=3:busy=4:res=5,il91874`.

Annotation rows: **Data** — one annotation per command with decoded parameters (resolution, power settings in volts, partial window, PSR bit fields, deep-sleep check code, CDI fields, OSC fields, …); **Status** — `Busy for <duration>` spans (BUSY_N low) and RES# low spans; **Warnings** — a command from the BUSY list above for which BUSY_N was not already low at the CS# rising edge that completes it (`NOBUSY`; skipped when BUSY is not probed), unknown command, wrong parameter count (LUTs expect 44/42 bytes, `PDRF` 8, `PDTM1`/`PDTM2` 8 plus data), command while BUSY_N is low (other than `FLG`, `REV`, `VV`), pixel write larger than the frame, bad deep-sleep check code. Read commands (`FLG`, `TSC`, `TSR`, `REV`, `LPD`, `VV`, `DSP`, `ROTP`) show the decoded response bytes; they are meaningful only when the probe sits on the shared DIN/DOUT line of a half-duplex wiring. A command with parameters, or an open-ended read, is reported when the next command arrives or on the connection decoder's `IDLE` packet.

`OUTPUT_PYTHON` packets: `('COMMAND', (command_byte, parameter_bytes))`.
