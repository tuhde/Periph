# Chip Spec: DRV8830

**Manufacturer:** Texas Instruments
**Datasheet:** `datasheets/motor/drv8830.pdf`
**Category:** motor
**Transports:** I²C

## Overview

The DRV8830 is a low-voltage H-bridge motor driver for a single brushed DC motor (or one
winding of a stepper), controlled entirely over I²C — there are no PWM/direction input
pins. Instead of a fixed duty cycle, the host commands a target *output voltage*; the chip
PWM-regulates its H-bridge to hold that average voltage across the motor winding
regardless of supply (`VCC`) sag, which keeps motor speed constant as a battery
discharges. It integrates current-limiting (with an external sense resistor) and reports
overcurrent, overtemperature, and undervoltage faults on both an open-drain `FAULTn` pin
and a readable/clearable fault register. Up to nine devices can share one I²C bus via two
address-strap pins (`A0`, `A1`), each of which is tri-state (GND / `VCC` / open).

## Transport Configuration

### I²C
- **Address:** `0x60`–`0x68`, selected by strapping `A0`/`A1` to GND, `VCC`, or leaving
  them open (9 combinations — see Table 5 of the datasheet); strapping is sampled once at
  power-up and cannot be changed dynamically
- **Max clock:** 400 kHz (Fast mode); also supports 100 kHz (Standard mode)

## Pin Configuration

| Pin | Active | Notes |
|-----|--------|-------|
| FAULTn | low, open-drain | requires external pull-up; asserted whenever `FAULT` is set in the `FAULT` register (undervoltage, overcurrent, or overtemperature) |

`OUT1`/`OUT2` (H-bridge motor outputs) and `ISENSE` (current-limit sense resistor
connection) are power-stage pins, not signals wired to the `Connection` or the API. `A0`/
`A1` are board-level address straps, not runtime-controllable pins.

## Register Map

| Address | Name | R/W | Reset | Description |
|---------|------|-----|-------|-------------|
| `0x00` | CONTROL | R/W | `0x00` | `VSET[5:0]`, `IN2`, `IN1` |
| `0x01` | FAULT | R/W | `0x00` | `CLEAR` (write-only), unused, `ILIMIT`, `OTS`, `UVLO`, `OCP`, `FAULT` |

Both registers are accessed by writing the sub-address (`0x00`/`0x01`) followed by a data
byte (write) or a repeated `START` and a read (see Figures 9/10 of the datasheet) — there
is no auto-increment; each transaction addresses exactly one register.

### Bit Fields

#### `CONTROL` (`0x00`)

| Bits | Name | Description |
|------|------|-------------|
| 7:2 | VSET[5:0] | Commanded output voltage DAC code — see Data Conversion. Codes `0x00`–`0x05` are reserved (do not write) |
| 1 | IN2 | H-bridge input 2 — see H-Bridge Logic table below |
| 0 | IN1 | H-bridge input 1 |

##### H-Bridge Logic (`IN1`, `IN2`)

| IN1 | IN2 | OUT1 | OUT2 | Function |
|-----|-----|------|------|----------|
| 0 | 0 | Z | Z | Standby / coast (POR default) |
| 0 | 1 | L | H | Reverse |
| 1 | 0 | H | L | Forward |
| 1 | 1 | H | H | Brake |

While `IN1`/`IN2` command Forward or Reverse, the H-bridge PWM-regulates its *on*-time
duty cycle to hold the `VSET`-commanded average voltage across the winding (see Data
Conversion); `VSET` has no effect in Standby or Brake.

#### `FAULT` (`0x01`)

| Bits | Name | Description |
|------|------|-------------|
| 7 | CLEAR | Write-only — writing `1` clears all fault status bits (`ILIMIT`/`OTS`/`UVLO`/`OCP`/`FAULT`) and re-enables the H-bridge if it was disabled by a latched `OCP` fault |
| 6:5 | — | Unused |
| 4 | ILIMIT | Set if the fault was caused by an extended current-limit event (current limit engaged for ≥275 ms, see Timing Constraints) |
| 3 | OTS | Set if the fault was caused by an overtemperature condition |
| 2 | UVLO | Set if the fault was caused by an undervoltage lockout event |
| 1 | OCP | Set if the fault was caused by an overcurrent (short-circuit) event |
| 0 | FAULT | Set if any fault condition exists (logical OR of `ILIMIT`/`OTS`/`UVLO`/`OCP`) |

`OCP` and `ILIMIT` latch the H-bridge disabled until `CLEAR` is written or `VCC` is
power-cycled; `UVLO` and `OTS` clear themselves once the underlying condition resolves
(`VCC` rises above the lockout threshold, or die temperature drops), but the status bits
in this register stay latched until `CLEAR` is written regardless.

## Initialization Sequence

1. Construct the driver with the `Connection` at whichever address (`0x60`–`0x68`) matches
   the board's `A0`/`A1` strapping.
2. Read the `CONTROL` register once to confirm the device answers on the bus — the DRV8830
   has no WHO_AM_I/identity register, so this doubles as the presence check.
3. No register writes are required at `init` time: the POR default (`CONTROL`=`0x00`,
   `IN1`=`IN2`=0) already leaves the motor in standby/coast.

## Interrupt

| Property | Value |
|----------|-------|
| INT pin | `FAULTn`, active-low, open-drain — requires an external pull-up |
| Level | 1 (single fixed condition) |
| Condition(s) | Any fault — undervoltage, overcurrent, or overtemperature |
| Clear mechanism | write `CLEAR`=1 to the `FAULT` register (see Implementation Notes for why this is not done automatically) |

### Full driver interrupt API

| Method | Signature | Description |
|--------|-----------|--------------|
| `on_interrupt` | `on_interrupt(callback)` | Subscribe; callback receives the same `(fault, ocp, uvlo, ots, ilimit)` tuple as `read_fault()` |
| `off_interrupt` | `off_interrupt()` | Unsubscribe |
| `poll_interrupt` | `poll_interrupt() -> (fault, ocp, uvlo, ots, ilimit)` | Equivalent to `read_fault()` — does **not** clear the fault (see Implementation Notes) |

## Implementation Stages

Each chip is implemented in two stages. The Full class extends Minimal — it inherits
everything and adds the rest.

### Minimal

Goal: drive the motor at a regulated voltage in either direction, with no configuration
beyond the connection.

| Operation | Parameters | Returns | Notes |
|-----------|------------|---------|-------|
| `init` | connection | — | Confirms the device answers; makes no register writes |
| `drive` | voltage (float, volts, signed) | — | Positive = forward, negative = reverse, `0.0` = standby/coast. `abs(voltage)` is mapped to the nearest valid `VSET` code (clamped to the chip's 0.48 V–5.06 V usable range, see Data Conversion) and written together with `IN1`/`IN2` in one `CONTROL` write |
| `brake` | — | — | Sets `IN1`=`IN2`=1 (short-brake) |
| `stop` | — | — | Sets `IN1`=`IN2`=0 (standby/coast) — equivalent to `drive(0.0)`, provided as an explicit, self-documenting call |

**Sensible defaults:** no register writes at `init` — the chip's own POR default already
leaves the motor in coast; `drive()` always writes a full `CONTROL` byte (`VSET` and
`IN1`/`IN2` together) so a stale `VSET` from a previous call never lingers into a new
direction command.

### Full

Goal: expose complete chip functionality. Extends Minimal.

| Operation | Parameters | Returns | Notes |
|-----------|------------|---------|-------|
| *(inherits Minimal)* | | | |
| `set_output` | vset (int, 6–63), in1 (bool), in2 (bool) | — | Raw register-level control, for callers that already have a `VSET` code (e.g. from `read_output`) rather than a voltage |
| `read_output` | — | `(voltage, direction)` — voltage float, direction "forward" \| "reverse" \| "coast" \| "brake" | Reads back `CONTROL` and decodes it |
| `read_fault` | — | `(fault, ocp, uvlo, ots, ilimit)` (all bool) | Reads `FAULT`; does not clear it |
| `clear_fault` | — | — | Writes `CLEAR`=1 to `FAULT`; re-enables the H-bridge if `OCP`/`ILIMIT` had latched it disabled |
| *(interrupt API)* | | | See Interrupt section above |

**Additional configuration options:** raw `VSET`/`IN1`/`IN2` register access, output
read-back, and fault reporting/clearing.

## Data Conversion

```
# Per the datasheet's Table 1 "Commanded Output Voltage" (Section 7.3.2):
voltage = VREF * vset / 16                # VREF = 1.285 V typical (1.235-1.335 V range)
vset    = round(abs(voltage) * 16 / VREF) # inverse (round half up), then clamp to 6-63

# vset codes 0-5 are reserved (datasheet Table 1) and must never be written; a
# requested |voltage| that rounds below the vset=6 floor (~0.48 V) is treated
# as 0 V (coast) rather than clamped up to the floor, since it is closer to
# "off" than to the minimum drivable voltage.
```

The datasheet is internally inconsistent here: the sentence below Table 1 gives
`4 * VREF * (VSET + 1) / 64`, which yields 0.56 V at `0x06` and 5.14 V at `0x3F`, while
every row of Table 1 itself (`0x06` = 0.48 V, `0x10` = 1.29 V, `0x3F` = 5.06 V) matches
`4 * VREF * VSET / 64` = `VREF * VSET / 16`. Drivers follow Table 1, which is also what the
0.48 V–5.06 V usable range quoted throughout this spec is based on. The one-LSB difference
(~80 mV) is within the ±4% `VREF` tolerance either way.

`read_output()` reports `0.0` V for a reserved `VSET` code (`0x00`–`0x05`, e.g. the POR
default), and always reports the commanded magnitude — the sign/direction is returned
separately. `stop()`/`drive(0.0)` write `CONTROL` = `0x00` (the POR value) and `brake()`
writes `CONTROL` = `0x03`: `VSET` has no effect in Standby or Brake, so a reserved code there
is harmless; only Forward/Reverse writes are guaranteed a valid `VSET` code.

Config panel fields:
- **I²C bus** — bus number (e.g., `1` for `/dev/i2c-1`)
- **I²C address** — dropdown of the 9 valid addresses (`0x60`–`0x68`), since the address is
  fixed by board strapping and cannot be probed

### Demo flow

An Inject node ramps `msg.payload.voltage` from `0` to `3.0` in `0.5` V steps every second,
holds for 5 s, then reverses to `-3.0` V, demonstrating the PWM voltage-regulation feature
holding motor speed constant. A second, independent Inject node polls every 2 s (any
message, no payload) to read fault status; a Function node checks `msg.payload.fault` and,
if set, sends `{ stop: true }` followed by `{ clear_fault: true }` to recover.

## Examples

### Demo

A battery-powered toy motor controller demonstrating the chip's headline feature: constant
speed across a discharging battery. The demo calls `drive(3.0)` (forward at a regulated
3.0 V) and holds it, printing `read_output()` every second — the reported `voltage` stays
at 3.0 V even though the example's simulated/observed `VCC` may vary, because the DRV8830
performs the regulation internally. After 5 readings, it calls `drive(-2.0)` (reverse at
2.0 V) for the same duration, then `brake()` briefly, then `stop()`. Throughout, it checks
`read_fault()` after every `drive()` call; if a fault is reported (for example, a stalled
motor tripping `ILIMIT`), it calls `stop()` and `clear_fault()` before continuing, printing
which fault fired.

## Timing Constraints

- **Register write cycle (`register_write`):** a single `CONTROL` or `FAULT` register
  write (`START`, address, sub-address, data, `STOP`) takes approximately 70–90 µs at
  400 kHz Fast-mode clock — the only host-observable, conformance-checkable timing this
  chip has; everything else below is autonomous hardware behavior with no I²C signature.
- Master must wait at least 60 µs after `VCC` is applied before generating the first
  `START` condition — a power-on sequencing requirement, not something a bus capture can
  reference (there is no prior transaction to time from).
- Current-limit engagement: the PWM duty cycle is reduced once `ISENSE` exceeds 200 mV
  (typ.) for more than ~3 µs — autonomous, not driver-actionable.
- Current-limit fault registration (`ILIMIT`): an overcurrent condition must persist for
  approximately 275 ms before `FAULT`/`ILIMIT` are set and the H-bridge is latched off —
  autonomous, not driver-actionable.
- Soft-start ramp: when transitioning out of Standby or Brake into a commanded duty cycle,
  the duty cycle ramps up over up to 12 ms rather than stepping immediately — autonomous,
  informational (explains why `drive()` does not reach full commanded speed instantaneously).
- I²C bus AC timing: up to 400 kHz (Fast mode) — covered by `specs/transport_i2c.md`.

## Implementation Notes

- **This is the first `motor`-category chip.** `nodejs/packages/node-red-contrib-periph-motor/`
  does not yet exist and must be created (with its own `package.json`, mirroring another
  category's Node-RED package) before the Node-RED Implementation Checklist items below can
  be completed; see the repo's "New category" guidance for what else that entails (e.g. a
  lockfile regen at the npm workspace root).
- `poll_interrupt`/`read_fault` deliberately do **not** clear the fault register the way
  many other chips' interrupt-polling methods do (compare the DS3231 driver's
  `poll_interrupt`, which clears on every read). A latched `OCP`/`ILIMIT` fault here also
  disables the H-bridge; auto-clearing on every status read would silently re-enable a
  genuinely faulted motor driver. Clearing is always an explicit, separate `clear_fault()`
  call.
- `VSET` and `IN1`/`IN2` share one register (`CONTROL`). `drive()` always writes all three
  fields together in a single transaction so that changing direction never transiently
  drives the previous voltage code with new direction bits (or vice versa).
- Both `VSET` (0.48 V–5.06 V) and the chip's absolute voltage accuracy depend on the
  internal 1.285 V reference's tolerance (1.235 V–1.335 V per Electrical Characteristics,
  roughly ±4%) — `drive()`/`read_output()` compute against the typical 1.285 V value; do
  not expect better than ~4% absolute voltage accuracy without per-unit calibration.
- If the programmed voltage exceeds the actual `VCC`, the H-bridge runs at 100% duty cycle
  (no headroom left to regulate) and behaves like a plain, non-regulated H-bridge driver —
  this is expected, not a fault.
- An undervoltage event can cause the `A0`/`A1` address latches to be re-evaluated; if this
  happens, the I²C interface may stop responding at the previously-used address until
  power is cycled. This is a board-level hardware caveat, not something the driver can
  detect or recover from over the bus.
- The chip has no WHO_AM_I/identity register; `init()` presence detection is a plain
  register read, matching this repository's other identity-register-less chips.
- Both registers support repeated-`START` reads (see Figures 9/10 of the datasheet) —
  unlike some chips in this repository (e.g. PCF8523), a repeated `START` is fully
  supported here.

## Sigrok Decoder

Decoder `drv8830` (`sigrok/drv8830/`) stacks on the `i2c` decoder and recognizes any
address in the `0x60`–`0x68` range (the 9 valid `A0`/`A1` strap combinations).

| Row | Annotation | Meaning |
|-----|------------|---------|
| Data | `data` | `CONTROL` register read/write decoded to `VSET` (converted to volts per Data Conversion), `IN1`, `IN2`, and the resulting H-bridge function (Forward/Reverse/Brake/Standby) |
| Status | `status` | `FAULT` register reads/writes decoded to `FAULT`/`OCP`/`UVLO`/`OTS`/`ILIMIT`, and `CLEAR` writes |
| Timing | `timing` | `register_write_start`/`register_write_done` marker pair bounding any `CONTROL` or `FAULT` write transaction |
| Warnings | `warning` | A `CONTROL` write commanding Forward or Reverse with a reserved `VSET` code (`0x00`–`0x05`) — Standby/Brake writes with `VSET`=0 are the normal `stop()`/`brake()` encoding and are not flagged; a write to an address outside `0x60`–`0x68` (not this device) |
