# Contributing

This project is AI-implemented: chip drivers and infrastructure are generated by Claude Code and OpenCode. Human contributors are welcome to add chips, fix bugs, or improve documentation using the same workflow.

## Quick orientation

| File | Purpose |
|------|---------|
| `CLAUDE.md` | Repo layout, category list, Minimal/Full pattern, AI workflow |
| `AGENTS.md` | Code conventions and patterns (written for AI, useful for humans too) |
| `TOOLCHAINS.md` | Installing the toolchains needed to compile every platform, on Debian 13 |
| `TESTING.md` | How to run hardware tests on all platforms |
| `specs/<category>/<chip>.md` | Single source of truth for each chip driver |
| `specs/_template_chip.md` | Template for new chip specs |

## Adding a chip

### 1. Get the datasheet

Download the datasheet PDF and commit it:

```
datasheets/<category>/<chip>.pdf
```

Categories are listed in `CLAUDE.md`. Use the closest fit; `other` is a valid fallback.

### 2. Write the spec

Copy `specs/_template_chip.md` to `specs/<category>/<chip>.md` and fill it in completely:

- Register map with bit fields
- Initialization sequence and timing
- Data conversion formulas
- Minimal and Full API tables (with all defaults for Minimal explicit)
- Demo scenario description

The spec is the reference documentation. Code is derived from it.

### 3. Implement

Create a feature branch (`feature/<chip>`) and implement against the spec:

| Language | Paths |
|----------|-------|
| Python driver | `python/periph/chips/<category>/<chip>.py` |
| Python examples | `python/examples/<category>/<chip>/minimal.py`, `complete.py`, `demo.py` |
| C++ driver | `cpp/src/chips/<category>/<Chip>.h`, `<Chip>.cpp` |
| C++ examples | `cpp/examples/<Chip>_Minimal/`, `<Chip>_Complete/`, `<Chip>_Demo/` (dir name = .ino name) |
| Node.js driver | `nodejs/packages/periph/src/chips/<category>/<chip>.js` |
| Node.js examples | `nodejs/packages/periph/examples/<category>/<chip>/minimal.js`, `complete.js`, `demo.js` |
| Node-RED node | `nodejs/packages/node-red-contrib-periph-<category>/nodes/<chip>/<chip>.js`, `<chip>.html` |
| Node-RED flow | `nodejs/packages/node-red-contrib-periph-<category>/examples/<chip>/demo.json` |
| Rust driver | `rust/periph/src/chips/<category>/<chip>.rs` (add `pub mod` to `mod.rs`) |
| Rust examples | `rust/examples/<chip>_minimal/`, `<chip>_complete/`, `<chip>_demo/` |

When adding the first file to a directory that contains only `.gitkeep`, remove the `.gitkeep`.

See `AGENTS.md` for detailed code conventions — class structure, connection interface, language-specific rules.

### 4. Write tests

Add one test file per platform following the naming convention in `TESTING.md`. Use `INA226` as the reference.

### 5. Open a PR

- One commit per implementation stage (Minimal, then Full)
- Link the datasheet in the PR description
- CI must pass. PR CI is *reduced*: jobs the diff cannot affect are skipped and the C++ jobs build only the touched chips plus a smoke set (see "CI scope" below)

## Code conventions (summary)

Full detail is in `AGENTS.md`. The key rules:

**All platforms**
- Drivers depend only on the connection interface — never on a concrete connection class
- Two classes per chip: `<Chip>Minimal` (base) and `<Chip>Full` (extends Minimal, never duplicates)

**Python**
- No f-strings, walrus operator, or `match` — MicroPython lags CPython
- No type annotations
- Constants as `_REG_NAME = 0x00` class-level variables

**C++ (Arduino)**
- No STL, no exceptions, no heap allocation in drivers
- Register constants as `static constexpr uint8_t`
- CommonJS only (`require` / `module.exports`) — required for Node-RED

**Node.js**
- CommonJS only (`require` / `module.exports`)
- camelCase methods, UPPER_SNAKE constants

**Rust**
- Library crate is `no_std` — no `std`, no heap allocation in drivers
- Generic over `embedded-hal::i2c::I2c` trait; all methods return `Result<T, I2C::Error>`
- `Ina226Minimal<I2C>` stores the `I2C` instance (owns the bus); `Ina226Full<I2C>` wraps it via composition
- Alert constants (`SOL`, `SUL`, etc.) are `pub const u16` at module level
- Add new workspace members to `rust/Cargo.toml`

## Running tests

See [TESTING.md](TESTING.md).

```
cpp/test_arduino.sh  --compile-only power/ina226
cpp/test_linux.sh    --compile-only power/ina226
cpp/test_zephyr.sh   --compile-only power/ina226
rust/test_linux.sh   --compile-only power/ina226
```

## Reporting issues

Open a GitHub issue. Include the chip name, platform, and a minimal reproduction if it's a driver bug.

## CI scope and releases

Compiling every example and test on every platform takes too long for each PR,
so CI has two scopes (logic: `scripts/ci/changed.sh`, called from
`scripts/ci/run.sh`, shared by GitHub Actions and GitLab):

| Trigger | Scope |
|---|---|
| Pull request / push to `main` | **Reduced.** Jobs whose inputs did not change are skipped (docs, `specs/`, `datasheets/`, wiki: nothing runs). C++ jobs build only the chips named in the diff plus one chip per transport from `scripts/ci/smoke.txt`. Changes to shared C++ code (`connection/`, `storage/`, build scripts), the CI definition, or any unrecognised path run everything. |
| Manual run (`gh workflow run ci.yml --ref main`; GitLab: Run pipeline) | **Full.** Everything, not narrowed to the diff. |

Locally, `scripts/ci/run.sh <job>` runs everything unless `PERIPH_CI_BASE=<sha>` is set;
preview a scope with `PERIPH_CI_BASE=$(git merge-base HEAD main) scripts/ci/changed.sh <job>`
and list the apps a filter selects with `cpp/scripts/build-all.sh <platform> --list <filter>`.

**Releasing:** pushing the tag starts `release.yml`, which calls `ci.yml` itself and waits for
it to pass before publishing. That CI run is diffed against the newest ancestor of the tagged
commit on which CI passed on `main`, so a commit CI has already verified has nothing left to build.
There is no manual step before tagging; run `gh workflow run ci.yml --ref main` only if you want the
full matrix.

## Self-hosted CI runner

CI runs on your own hardware instead of GitHub-/GitLab-hosted containers. Both
pipelines (`.github/workflows/ci.yml`, `.gitlab-ci.yml`) call
`scripts/ci/run.sh <job>`; edit job logic there.

Runner host (Debian 13, bare, no Docker): install everything in
`TOOLCHAINS.md` as the runner's user, plus `arduino-lint`
(<https://arduino.github.io/arduino-lint/>) and `python3-smbus2`. Expected
locations (override via env in the runner's `.env`): `~/pico-sdk`,
`~/esp-idf`, `~/STM32CubeF4` (with FatFs), `~/zephyrproject` +
`~/.venvs/zephyr`. The cargo target dir persists in
`~/.cache/periph-ci`; ccache lives in `/var/cache/ccache/<platform>`
(override with `PERIPH_CCACHE_ROOT`) — create it once with
`sudo install -d -o <runner-user> /var/cache/ccache`.

- **GitHub Actions:** register the runner with labels `self-hosted,linux,periph`
  (Settings → Actions → Runners). Only `ci.yml` uses it; release and Claude
  workflows stay on GitHub-hosted runners. Because this repo is public, set
  Settings → Actions → General → "Require approval for all outside
  collaborators" so fork PRs can't run code on your machine unreviewed.
- **GitLab:** `gitlab-runner register` with the **shell** executor and tag
  `periph`; disable shared runners for the project if you want only yours.
- Run one runner instance per host: jobs share `~/.arduino15` and the SDK dirs.
- Check a single job locally: `scripts/ci/run.sh go-linux`.
